## T2 — Config layering, validation, and the one credential rule

## Why this exists

`init` writes config, so the rules it must obey come first.

And **one of those rules is a refusal**, which is unusual for a configuration system and is the right call for one specific
reason.

## Scope

### Five layers (C2, D2)

```
built-in defaults → user file → project file → environment → flags
```

C2's reasoning is the shape: *"a user configures once; a project overrides what is project-specific; a flag wins for one
run."*

**Answer Q1**: what does the framework's config machinery provide, and does it layer this way? **If it provides more than
needed, S1's B8 allow-list discipline applies** — a service configured down is a service someone configures back up.

### Validation names the key **and** the file (C3, D3)

*"Invalid configuration" is a support ticket. Naming the key and the file is a fix.*

```
error: invalid configuration

  what:  'max_iterations' in ./aeon/config.yaml is "twelve"; expected an integer
  why:   iteration bounds are numeric and enforced per step
  do:    set it to a number, e.g. max_iterations: 12
```

**With five layers, the file matters more than usual** — the same key can appear in three of them, and "invalid
configuration" leaves someone editing the wrong one.

### The one credential rule (C4, C17, D4, D5, D6, I1, I2)

**Credentials come from the environment, or from a dedicated file path. Never a config file. Never `argv`. Never a log.**

C4's reason is one sentence: **a config file gets committed.** So a key there is a **load-time error, not a warning** —
a warning is something people learn to scroll past, and this failure is permanent and public.

S19's O1 added the other half: a value in `argv` is in the process list and in shell history, and **that failure is silent.**

So one rule, one reader (I1):

```go
// The only place credentials are read.
func Credential(name string) (value string, source Source, ok bool)
```

**Answer Q6**: how many places read credentials today? **I1 requires one**, and every other path takes them from it — which
is also what makes D6 checkable, because there is one function whose output must never be printed.

`Source` exists so `doctor` can report **where** a credential came from without reporting **what** it is.

### Not in scope

`init` (T4), `doctor`'s rendering (T8). This task is the rules; those obey them.

## Tests

| Test | Asserts |
| --- | --- |
| `TestKeyInConfigFileIsALoadTimeError` | A credential-shaped key in any config layer **fails at load**. Not a warning (D4, C4) |
| `TestNoFlagAcceptsACredentialValue` | Every command's flags; only paths (D5, C17) |

| `TestValidationNamesKeyAndFile` | **Both**, in the `What`. With the same key set in three layers, the named file is the offending one (D3, C3) |

`TestValidationNamesKeyAndFile` **with the key set in three layers** is the case that matters. Naming a file is easy when
there is one; the layering is exactly what makes "invalid configuration" useless.
