# T8 — `doctor` — every state in its own states

## Why this exists

**Last among the code tasks** (R5), because it reports what every other task configures. A `doctor` written early reports a
system that does not exist yet.

**And it is where the whole product's honesty converges.** Six independent slices refused to collapse an uncertain answer into
a certain one ([P31](../../ARCHITECTURE.md#8-product-decisions)) — cost, the `bash` receipt, blueprint validation, connection
liveness, verification, provider capabilities — and retrieval adds four availability reasons on top.

**`doctor` is the one screen reporting all of them, which makes it the single place the whole pattern can be undone.**

## Scope

### It renders; it decides nothing (I4)

Every state it shows was **computed by the slice that owns it.** `doctor` reads and formats.

That is why C15 is a rendering rule rather than a logic one — and why flattening would be so easy to do by accident, since a
formatter's instinct is to summarise.

### It flattens nothing (C15, D10)

**Answer Q3 first**: enumerate every three-state and multi-state value `doctor` must report. **A missing list blocks the
task**, because D10 is checked against it.

The list includes, at minimum: cost state per route, capability state × 3 per capability per route, retrieval availability × 4,
per-corpus staleness, narrow-surface mountings, credential presence per credential, forge configuration, bash policy
presence.

**Every one in its own states.** And the check is literal:

| Must not appear | Over |
| --- | --- |
| `ok`, `all good`, `healthy` | Any uncertain value |
| A green mark | A `declared`-but-unprobed capability |
| `$0.00` | An unmetered route |
| `available` | A corpus that is stale |
| Absence from the screen | A mounting that is not listening |

**A `doctor` that says "everything looks good" over an unverified capability and an unmetered route has thrown away six
slices of design work at the last possible moment — and it would look helpful doing it.**

### It also says what is fine (O3)

Briefly. **A screen showing only problems gives no way to tell a healthy system from an unchecked one**, and someone reading
it needs to know `doctor` looked.

### No credential is printed (D6, C17)

**Presence and source, never value.** T2's `Source` exists for exactly this line:

```
  credentials   ANTHROPIC_API_KEY present   (environment)
                forge token       present   (~/.config/aeon/forge.key)
                                            no credential is printed here
```

**That last line is on the screen deliberately.** Someone about to paste `doctor` output into an issue needs to know it is
safe, and the absence of a key is not visible evidence that keys are never shown.

### It works with retrieval absent (S22's D1)

In the no-retrieval build, the retrieval section reads **not built** — not missing, not an error. S22 made the slice
deletable, and `doctor` is the one place that would break the claim by erroring on an absent package.

### It reports the HTTP bind (S19's O8)

Address, and that a key is set. **Never the key.** *A listening port nobody remembers opening is what N15 exists to
prevent, and a default only helps the first time.*

### `doctor.check` is a daemon method, not only a CLI render (D16, I10, P34 — added 2026-10-26)

**`doctor.check {}` is a registered socket method returning the same structured report** the CLI's `doctor`
renders from — gathered by the identical collection step (I4's "every value comes from its owning package"
applies to the socket path exactly as it does to the CLI's), not a second readout of cost, capability,
retrieval, or credential state. The CLI becomes the first renderer of this report, not its only one — the
app's own health screen is the second, and D10's flattening rule binds the **report's shape**, not just the
CLI's text: a `State` field that collapses `declared`/`verified`/`contradicted` into a boolean would flatten
the socket response even with the CLI's text rendering left untouched.

**D6 and C17 bind the report itself, not only its text rendering.** The struct carries presence and source
per credential — never a value field — so there is no way for a socket caller, now or in some future
renderer, to receive what the CLI's text format merely declines to print. A credential's value reaching the
wire through `doctor.check` would be worse than reaching a terminal: it would be the first credential this
product's socket surface ever exposed.

### Not in scope

Fixing anything. `doctor` diagnoses; its `Do` lines point at the commands that fix (T1). A second collection
implementation for the socket path — `doctor.check` calls the CLI's own collector (see above).
