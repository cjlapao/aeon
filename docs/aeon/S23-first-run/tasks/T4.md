# T4 — Presets and `aeon init`

## Why this exists

**One task** (R6): a preset with no `init` is data nobody reads, and an `init` with no presets asks a stranger about base
URLs.

And this is where most of the five minutes is spent, so it is where the budget is either kept or lost.

## Scope

### Three presets (C6, D9)

**Answer Q8**: each preset's contents — model, capability declarations, price, base URL.

| Preset | Covers |
| --- | --- |
| Anthropic | — |
| OpenAI | — |
| **OpenAI-compatible** | **Ollama, vLLM, LiteLLM, OpenRouter** |

C6's reason is the question `init` asks: **a stranger picks a provider, not a wire format.** Not *"what is your base URL, and
does the server support `stream_options.include_usage`?"*

**A preset produces a route** (S18's M12), not a second configuration path. So the capability declarations, the price, and
the three capability states are all S18's.

### Each named server is actually tried (O7, D9)

**Answer Q9**: which servers, at which versions.

`testdata/servers.json` records them, and the preset's notes say which were tried and at what version — **the same
requirement S18's O7 put on `CAPABILITIES.md`**, for the same reason: *"works with OpenAI-compatible servers"* is
unfalsifiable, and a list with versions is a claim someone can check.

### `init` is fully scriptable (C5, D7)

**Every prompt has a flag**, and the whole flow runs **with no TTY** — over SSH, in a container, in CI.

```
aeon init --provider anthropic --model claude-… --key-file ~/.config/aeon/a.key --non-interactive
```

*A wizard with no scripted path is a wizard nobody automates* — and this one has to work where there is no terminal at all.

### It probes what it configured (C18, D8)

```
  probing route 'anthropic'…
    tools             verified
    streaming-usage   verified
```

**A preset is a claim** about a server's capabilities (S18's M28), and **the first run is when verifying it costs nothing.**
A contradiction found three steps into a loop costs a confused user instead.

**A probe failure does not fail `init`** (O6). An unreachable server at setup time leaves capabilities `declared` and **says
so** — S18's own rule that *"could not check" and "checked and wrong" are different facts*, arriving here. Someone setting up
on a train should not be blocked from finishing.

### It does not overwrite (O5)

**Answer Q11.** An existing config is **reported, not replaced**: what exists, what would change, and `--force` required.

*A first-run command that silently replaces a working configuration is one people run once and never trust again* — and the
person most likely to re-run `init` is someone whose setup is already half working.

### It obeys T2's credential rule

The key goes to the environment or a dedicated file. **`init` never writes a credential into config** (D4) — which means
`init` is also the place a stranger learns the rule, so its prompt says where it is putting the key.

### Presets are readable from the daemon surface (D16, I10, P34 — added 2026-10-26)

**`presets.list` is a registered socket method** returning the same three templates (provider, model,
capability declarations, price, base URL) `init`'s prompt reads from `presets.go` — the identical data, not
a parallel description of it. **It is the only new write-adjacent surface this task adds.** Applying a
preset is not a fourth method: the app composes it from methods that already exist — `routes.set` (S3) to
create the route, then S18's `routes.probe` to verify it — the same two calls `init` itself makes
internally once a preset is chosen. This is what lets the app's own first-run wizard show "Anthropic /
OpenAI / OpenAI-compatible" as options and wire one up, without a terminal, while staying a thin client of
the exact route-creation and probing logic `init` uses — no second "apply preset" implementation to drift
from the CLI's.

### Not in scope

`doctor` (T8). The README (T7). A write method for applying a preset — composing `presets.list` with
S3's `routes.set` and S18's `routes.probe` covers it without inventing one (see above).

| `TestInitUsesThreePartErrors` | Every failure path (T1) |
| `TestPresetsListSocketReturnsTheSameTemplates` | `presets.list`'s response matches the templates `init`'s prompt reads — a call-site check, not a second copy of the data (D16, P34) |

`TestProbeFailureDoesNotFailInit` is the one that protects the five minutes. The strict version — refuse to finish until the
probe succeeds — is defensible and would block someone whose network is briefly down from ever completing setup.
