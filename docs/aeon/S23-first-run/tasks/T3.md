# T3 — Exit codes

## Why this exists

C10: *"a loop in CI needs to distinguish 'failed' from 'blocked' from 'waiting for a human'."*

Those are three different things and **only one of them is a problem with the run.** A CI job that treats all non-zero exits
as failures will fail a build because a loop politely asked a question.

## Scope

### The table (C10, D12)

```go
const (
    OK       = 0   // did what was asked
    Failed   = 1   // the work failed
    Blocked  = 2   // the loop cannot proceed — a code action unavailable, a bad plan
    Waiting  = 3   // a human is needed: a gate, a permission ask, an escalation
    Usage    = 4   // the caller's mistake — bad flag, bad argument
    Config   = 5   // configuration or credentials (T2)
)
```

**`Waiting` is the one that earns the table.** A CI job seeing `3` knows the loop is fine and a person is needed — and can
notify rather than fail. Seeing `1` it would page whoever broke the build.

And it composes with S19: a CI-triggered loop is **unattended**, so a gate does not produce `Waiting` — it produces `Blocked`
with the ask denied (G7, L22). **Both codes exist because both situations do**, and which one a CI job sees tells it whether
running attended would have helped.

### Every command uses the table (D12)

Not `os.Exit(1)` scattered across commands. **One table, one mapping**, so a code means the same thing everywhere — which is
the only way a CI job can branch on it.

**Answer Q5**: what exit codes exist today, and does anything distinguish `waiting`?

### Documented (C10, D12)

`aeon/docs/EXITCODES.md`, and in `--help`. **A code nobody documented is a code nobody branches on**, which makes the table
pointless — the whole value is a CI job written against it.

### Not in scope

The error *shape* (T1). A code is what a process returns; a shape is what a message contains. Both, for the same event.
