# T5 — Blueprints shipped and overridable

## Why this exists

C12 and P18: *"we ship a standard one but we do not impose"*, literally.

That is the whole reason the graph is data (L1): there are **five** protocol shapes in this repository, and freezing one into
code would have made the other four second-class.

## Scope

### Shipped (C12)

`aeon/blueprints/standard/` holds `dev-loop.yaml` and `two-step.yaml` — S8 authored the format and S17 filled the ladder;
this task is where they ship.

### Overridable per project (C12, D14)

```
./aeon/blueprints/dev-loop.yaml     ← wins
<install>/blueprints/standard/dev-loop.yaml
```

A project's own takes precedence, by name.

### `list` says which is which (D14)

```
  dev-loop     (this project)   ← overrides the shipped one
  two-step     (shipped)
```

**The provenance is on the screen**, because *"why is this loop not doing what the documentation says"* is answered by that
line and by nothing else. Someone who copied a blueprint six months ago and edited it will not remember.

### Shipped blueprints are validated in CI (S8's D13)

S8 required it: *"so the standard ones cannot rot as the registries change."* This is the task where they are shipped, so it
is the task that owns the check.

`dev-loop.yaml` must pass `--strict` — which S16 made possible by implementing the code actions, and which S8's committed
fixture exists to make visible.

### It composes with the pin (S8's L6)

A running loop keeps its **pinned content**, so overriding a blueprint does not change a loop in flight. Worth a test,
because a stranger who edits a blueprint and sees no change in a running loop will think the override did not work.

### `blueprint.list`'s provenance, not a new method (D14, P34 — added 2026-10-26)

**No new socket method.** `blueprint.list` already exists (S8/S9); this task's only obligation to it is that
its response carries the same **shipped vs. project-override** provenance the CLI's `list` prints — the
same fact D14 already requires on screen, now also in the structured response, so the app's own blueprint
picker can show "dev-loop (this project) — overrides the shipped one" without shelling out to the CLI. One
field, read from the same override-resolution this task already builds for the CLI — not a second
resolution.

### Not in scope

Authoring a blueprint (S8, S17). Validation itself (S8). A new socket method for provenance —
`blueprint.list`'s existing response carries it (see above).
