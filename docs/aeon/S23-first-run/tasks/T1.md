## Notes (2026-10-29, S23 T1)

The shape is structural, not a convention. `internal/errs.Error` has three
unexported fields (`what`/`why`/`do`) and one constructor `New`; `NewKinded`
joins a kind to the three parts. A struct literal that names two fields
cannot compile — pinned by `TestErrorMissingDoDoesNotCompile`, which runs
`go build` on `testdata/missingdo` (the file sits in `testdata` so
`go build ./…` skips it, but naming it explicitly builds it and it fails —
S11's forged-token shape, D11/C6).

Adopted, not just declared. `narrow.Error` and `forge.ForgeError` each carry
their kind **and** the three parts (an embedded `errs.Error`, `New`/`NewMsg`,
`What/Why/Do` accessors). S16's five forge kinds and S19's four narrow kinds
survive and stay branchable (`TestKindsSurvive`). The `Do` is a kind-derived
action — `aeon init --key-file`, `aeon list`, `retry`/`aeon doctor` — never
"check your configuration" (`TestDoIsAnActionNotAdvice`, O4). No credential
value in any field (`TestNoCredentialInAnyField`, C17/D6); the
domain/infrastructure division survives (`TestErrorsAreStillDomainVersusInfrastructure`,
DB19).

**Q2 finding (recorded, not forced).** S11's policy **verdicts**
(`internal/policy`) and S22's retrieval **availability** (`internal/retrieval`)
are discriminated *results*, not errors: they answer a question, they do not
fail a call (AGENTS §5, DB19), so they carry a kind but not the three-part
error shape. They are the "cannot" the task names, and the finding is the
answer — the closed set of *error* types is the two boundary types adopted
above, not the result types.

## T1 — The three-part error shape, structurally required

## Why this exists

**First** (R4), because every other task in the slice produces errors, and retrofitting a third **required** field across
five packages is worse than starting with it.

C9's reason is one sentence and it is the whole argument: **the audience cannot ask the author.** And a convention saying
errors should have three parts reliably produces errors with two — **the one that gets dropped is always the third.**

## Scope

### The type (C16, D11)

```go
// Error is the product's error shape. All three fields are required.
type Error struct {
    What string   // what happened
    Why  string   // what it means
    Do   string   // what to do
}

// New is the only constructor. There is no zero-value path.
func New(what, why, do string) Error
```

**No exported struct literal.** If `Error{What: …, Why: …}` compiles, the third field is optional in practice and C16 is a
convention again.

**Answer Q2 first**: how many distinct error types exist across the slices, and can they all carry three parts? S16's forge
errors (five kinds), S19's narrow errors (four), S11's policy verdicts, S18's capability contradictions, S22's availability
reasons.

**If any cannot, that is a finding** — C16 is structural or it is nothing, and a type that opts out is the one whose errors
will be two parts.

### `Do` is an action, not advice (O4, D-checks)

*"Check your configuration"* satisfies a struct and **fails C9.**

**Where a command exists, `Do` contains the command:**

```
what:  'anthropic_api_key' is set in ~/.config/aeon/config.yaml
why:   a config file gets committed. Aeon reads credentials only from the
       environment or a dedicated key file
do:    remove that line, then:  export ANTHROPIC_API_KEY=...
```

Asserted by a test over every constructed error in the codebase: `Do` contains a command, a path, or a named next step —
**not a verb phrase about checking things.**

### The existing kinds keep their discrimination

S16's five forge kinds, S19's four narrow kinds, S22's four availability reasons — **they all survive.** The shape is about
what an error *says*; the kind is about what a caller *branches on*. Both, not one instead of the other.

So an error carries its kind **and** the three parts, and a caller can switch on the kind while a human reads the text.

### Not in scope

Exit codes (T3) — a code is what a process returns, and a shape is what a message contains.
