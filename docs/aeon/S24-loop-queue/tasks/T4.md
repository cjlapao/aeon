# T4 — `queueAdvance: ask`

## Why this exists

T3 marks an item `done` or `blocked` and, for `'auto'`, materializes the next one directly. This task is
the other half: `'ask'` mode, and the `blocked` case from T3 that always asks regardless of mode.

**Read first:** `internal/store/chat.go`'s `Question`/`NewQuestion` shape and `design.md` §2's measurement
that `question.loop_slug` is `NOT NULL` with an FK to `loop`. This is why the question in this task attaches
to the **just-finished loop's slug** — that row still exists — and not to anything project-level. There is
no project-level question mechanism in this slice, and this task does not add one.

## Scope

**1. Raise a `gate`-kind `Question`** (`QuestionKind` = `"gate"`, matching the existing closed set in
`chat.go`) scoped to the just-finished loop's slug, body naming the next queue item's goal plainly enough
for a person to decide without reading the row (e.g. `"next queued item: <goal> — advance?"`).

**2. On answer:** an affirmative answer calls `NextReady` and materializes it exactly as T3's `'auto'`
branch does — **one materialization code path, called from two places (T3's auto branch and this task's
answered branch), not two.** A negative or declining answer leaves the queue halted; nothing auto-retries
asking again.

**3. The `blocked` case from T3 always raises this same question**, independent of `queueAdvance` — T3
calls into this task's question-raising function directly rather than duplicating it.

## Validation

- [ ] `TestAskRaisesGateQuestionOnFinishedLoopSlug` — the question row's `loop_slug` is the loop that just
      finished, not the next (not-yet-existent) one
- [ ] `TestAnsweredApproveMaterializesNextReady` — answering affirmatively starts exactly the item
      `NextReady` would have returned
- [ ] `TestUnansweredNeverMaterializes` — an unanswered gate question leaves the queue halted indefinitely,
      asserted by advancing time in the test, not by a short sleep
- [ ] the materialization call in this task and in T3's `'auto'` branch are the same function, asserted by
      a single call-site check
