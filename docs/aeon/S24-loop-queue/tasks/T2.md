# T2 — `internal/queue`: the core package

## Why this exists

Every other task in this slice (the reactor, sizing, the CLI, the socket methods) calls into this package
rather than touching `queue_item` rows directly. One package owns position, status transitions and the
read/write shape, the same discipline `internal/policy` owns the policy vocabulary — a second place that
also knows "is `pending → running` legal" is a second truth the day someone edits one and not the other.

**Read first:** `internal/store/machine.go`'s `AllowedTransitions()` — the existing precedent for a closed
transition table over a status type, including how its own exhaustiveness test is shaped. Follow that
pattern, do not invent a new one.

## Scope

**1. `QueueItem` and `Status`** (`types.go`): the Go mirror of T1's row shape, `Status` as a named string
type with the seven constants, and a package-level `AllowedTransitions() map[Status][]Status` enumerating
exactly the edges `design.md`'s CG1 diagram lists — including `sizing → pending` (a failed sizing run,
CG5's neighbor) and the four `{pending, ready} → cancelled` edges. `running` has no outgoing edge to
`cancelled` — attempting it is refused, not silently ignored.

**2. Store CRUD** (`store.go`): `Append` (assigns the next `position` in the project, defaulting
`sizingMode`-dependent initial status — `pending` either way, CG1's diagram starts there regardless of
mode), `List` (ordered by `position`), `Reorder` (pending items only — `design.md` §7's open item: an item
mid-`sizing` is still `pending`'s cousin for this purpose since its position is independent of its sizing
run; make that call here and record it in this task's Notes, not as a silent assumption), `Remove`
(transitions to `cancelled`, never deletes the row — D12, and the project's standing "never silently lose a
record" pattern that `loop_archive`/`policy_event` both already follow), `NextReady` (the single `ready`
item with the lowest `position` in a project that currently has nothing `running`).

**3. `Transition(item, to Status) error`**: the one function every other task calls to move a status. It
consults `AllowedTransitions()` and refuses (a discriminated result, DB19 — not a bare `error`) anything not
listed.

## Notes

- **The transition table is 11 edges** (7×7 minus the rest, asserted as a floor + full cross-product
  refusal): pending→{sizing,ready,cancelled}, sizing→{ready,pending,cancelled}, ready→{running,
  cancelled}, running→{done,blocked}, blocked→{cancelled}, cancelled→{} — `done` and `cancelled`
  terminal, refusals name "terminal".
- **The four cancellable statuses were a three-way doc disagreement, resolved to the union**:
  CG1's prose named `{pending, ready}`, CG1's diagram shows `sizing │` (cancellable), T2.md counts
  "four", and CG2's escape hatch demands `blocked→cancelled` (without it a blocked item is a
  permanent halt with no person's way out). `{pending,sizing,ready,blocked}` honours all four
  sources; recorded here and at the table in `types.go`.
- **`reorderable = {pending, sizing, ready}`** — the recorded call T2.md demanded. The slice text
  says "pending items only"; in `sizingMode: manual` every appended item is `ready` on landing, so
  a pending-only reorder is a no-op in the default configuration. Ready is movable (its claim is
  claimed-FROM at `ready→running`, so a reorder mid-claim loses honestly); `running` refuses
  naming "history and is fixed".
- **Self-transitions are idempotent** (machine.go's carried rule): re-`Remove` of a cancelled item
  is success, not refusal — the test asserts it and the table test still drives every non-self
  pair through refusal.
- **Claimed-FROM everywhere**: `TransitionQueueItem`/`ReorderQueueItems` update `WHERE status =
  from` (or an `IN` set) and a row touched under the caller yields `Moved=true` refusals naming
  "moved under" — no lost-update window between read and write.
- **Corrupt `with_json` refuses the read** naming corrupt — never silently empty; the corruption
  gate plants the bad row through the store's own `AppendQueueItem` (raw `WithJSON`) because the
  sibling package cannot reach `s.w`.
- **`CreateLoop` seeds no tier rows** (T1's finding, carried): queue fixtures seed via
  `CreateComponent` + `CreatePinnedLoop` (the pin creates the loop row the FK needs).
