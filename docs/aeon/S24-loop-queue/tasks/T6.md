# T6 — `aeon queue` CLI

## Why this exists

The first concrete surface over `internal/queue`. `cmd/aeon/policy.go`'s `cmdPolicy`/usage-string shape is
the template to follow for argument parsing and help text — this task adds a sibling, not a new style.

## Scope

**Verbs**: `aeon queue append --blueprint … --goal … [--tech …] [--with k=v]… [--attended]` ·
`aeon queue list [--project-root …]` · `aeon queue reorder <id> <position>` · `aeon queue remove <id>` ·
`aeon queue set-size <id> --min N --max N --basis "…"` (only meaningful in `sizingMode: manual` — refused
with a named reason in `skill` mode, where `report_size` is the only writer of size) · `aeon queue settings
[--queue-advance auto|ask] [--sizing-mode manual|skill]` (bare form reads current settings; with flags,
writes them).

**`append` validates the blueprint the same way `loop.start` already does** — no second blueprint-existence
check invented here; call into whatever `loop.start`'s handler already uses so the two surfaces cannot drift
on what counts as a valid blueprint name.

**`--attended` is the per-item override (D5).** Omitted, it falls back to the project's declared default;
neither path ever falls back to "whoever happens to be present when the daemon starts it" (G14).

- [ ] `TestQueueSettingsRoundTrip` — writing then reading `queue-advance`/`sizing-mode` returns exactly what
