# T3 — the reactor

## Why this exists

This is the one piece of the slice that is genuinely new behaviour rather than a CRUD surface over T2's
store: something has to notice a loop finished and decide what happens next.

**Read first:** `design.md` CG2 and CG4 before writing a line. CG2: a `blocked` terminal status halts
advancement **unconditionally** — `queueAdvance` is never consulted for that branch, only for the
`done` branch. CG4: nothing here polls or watches for an idle, non-empty queue — the reactor only ever runs
in response to an event it actually received. **Before writing this task's code, check whether the daemon
already has a generic event-subscription seam** (`internal/loop`'s `emit` function and its callers are the
place to look) or whether every existing consumer reads `loop.finished`/`loop.blocked` inline at the point
of emission. If no generic seam exists, add the minimal one this task needs — not a general pub/sub layer.
Record which one you found in this task's Notes.

## Scope

**1. On `loop.finished` (status always `done`, per `design.md` §2's measurement — but assert this, don't
assume it holds forever):** mark the matching `queue_item` (found by `loop_slug`) `done`. If
`project.queue_advance == 'auto'`, call `NextReady` and, if non-empty, materialize it (T3 calls into T2's
store and the *existing* `loop.start` path — never a new one, §4 of the brief). If `'ask'`, hand off to T4's
question-raising path instead of materializing anything itself.

**2. On `loop.blocked` (any `BlockedReason.Kind`, CG2 — no sub-classification):** mark the matching
`queue_item` `blocked`. **Advancement halts regardless of `queueAdvance`.** Raise the same question T4 uses
for the `ask` case — a blocked loop is never a silent, "the project configured itself past this" outcome.

**3. No `queue_item` lookup for a `loop_slug` that is not a known queue item is an error.** A loop started
by a person directly (not through the queue) finishing is not this reactor's business — it does nothing,
quietly, for any loop whose slug does not match a `queue_item.loop_slug`.

## Notes

- **The seam found: inline at the daemon's emission point.** `internal/loop`'s `emit(dep, …)` feeds
  `loop.Deps.Event`, which the daemon wires (blueprint.go:179) to `d.publishLoop` — every terminal
  kind (`loop.finished` from rest.go:94, `loop.blocked` from advance.go:159/257/324/416) passes
  through it, and publishLoop ALREADY resolves the loop identity (ReadPinnedLoop → pin.Loop). The
  reactor joins there (one call line, two kinds) rather than inventing a pub/sub layer — the
  existing consumers (memory view, events) all read inline at emission; this is the pattern found.
  The daemon-side `d.publish("loop.blocked", …)` calls in OnStepContinued are park-failure noise
  WITHOUT a resolved loop identity — the reactor deliberately does not subscribe to those.
- **Never blocks the emit path (V18):** `onQueueTerminal` dispatches a goroutine and returns;
  `TestQueueNeverDelaysTheEmitPath` holds the start door shut and asserts publishLoop returns in
  wall time (<50 ms), then releases and waits for the work to land.
- **A failed start blocks, it does not un-claim:** CG1's closed machine has no `running → ready`
  edge, and inventing one would let two actors "return" a claimed item concurrently. `blocked` is
  the honest word for a claim that started nothing — the halt, the question, and the
  cancel-escape-hatch all exist for it (decision recorded in `advanceNext`'s comment).
