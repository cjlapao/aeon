# T2 — `RerunClass` on every tool, against a committed list

> **2026-10-17 implementation note:** The current registry has five tools, including S5's `list` and
> `write_file`. The committed fixture therefore has eleven names: those five plus the six names this spec
> marked pending. `write_file` is `detectable`; `list` is `safe`; `bash` is the sole `unsafe` tool. The
> full tool suite passes with localhost listener access.

## Why this exists

Case C dispatches on whether a tool can be re-run. That is a property of what the tool **does**, so it belongs on
the tool, not in a table recovery keeps beside itself and forgets to update.

And it must be **mandatory**. A tool arriving at S11 without a class would get whatever the zero value is, and a
zero value that means "safe" turns a forgotten line into silent re-execution.

## Scope

```go
type RerunClass string

const (
    // Re-running produces the same observable state. Read-only, or idempotent by nature.
    RerunSafe RerunClass = "safe"

    // Re-running may fail, and the failure is visible rather than damaging.
    RerunDetectable RerunClass = "detectable"

    // Re-running may cause an effect that already happened, and nothing can detect it.
    RerunUnsafe RerunClass = "unsafe"
)
```

Add `RerunClass() RerunClass` to the `Tool` interface. It has no default and no zero value that means anything:
`RerunClass("")` fails the committed-list test.

### The classes

| Tool | Class | Because |
| --- | --- | --- |
| `read` | `safe` | Read-only |
| `glob`, `grep` | `safe` | Read-only |
| `webfetch` | `safe` | Read-only, and its no-credential rule means a repeat leaks nothing new |
| `todo` | `detectable` | State the daemon owns; a re-apply converges |
| `write` | `detectable` | Same path, same content, same result |
| `edit` | `detectable` | Exact-match, so a second application **fails loudly** rather than patching twice (W17) |
| `question` | `safe` | Suspends rather than acting. And a suspended step is never recovered anyway (K29) |
| `bash` | **`unsafe`** | Arbitrary effects, none detectable by inspection |

**`bash` is the only `unsafe` one**, and that is worth knowing rather than discovering: the receipt machinery
guards exactly one thing.

### The committed list (O6, I6)

`testdata/rerun_classes.json` holds the complete tool-name → class mapping, including the six tools that do not
exist yet. The test walks the registry and asserts each registered tool's class matches, **and** that every name in
the file is either registered or explicitly recorded as not-yet-implemented.

This is S1's service-fixture pattern: a tool arriving at S11 without a class fails a test written now, rather than
defaulting into `safe`.

## Tests

| Test | Asserts |
| --- | --- |
| `TestEveryToolDeclaresARerunClass` | Every registered tool returns one of the three constants. **The empty string fails** |
| `TestBashIsTheOnlyUnsafeTool` | Exactly one registered tool is `unsafe`, and it is `bash`. Asserted as a count plus a name, so a second unsafe tool fails rather than passing a "bash is unsafe" check |
| `TestRerunClassesMatchCommittedList` | Registry and fixture agree; a name in the fixture that is neither registered nor marked pending fails |
| `TestFixtureCoversAllNineTools` | The fixture names all nine tools of the final set, so the six absent ones cannot arrive classless |
