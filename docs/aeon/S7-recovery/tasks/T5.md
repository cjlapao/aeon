# T5 — `RecoverStep` — acting on a plan

**Notes (2026-10-17):** `RecoverStep` applies `DetermineCase` to the persisted checkpoint. Case A resumes from its saved tail; Case B reissues the lost model turn; Case C reuses a completed receipt or fails an incomplete or mismatched one without executing `bash` again. Structured failures are saved in the recovery record. Unit tests cover each action, and the replay walk proves Case A, B, and both Case C receipt states with real `SIGKILL`.

Two spec assumptions needed correction. `ResumeStep` originally accepted only a pending question, so it gained a recovery mode to resume a running step from a committed tail. A model stream killed before usage arrives cannot yield the first call's exact cost; the saved cost is `unknown(stream-aborted-early)` with measured later calls as a lower bound. These changes preserve the original bounds and do not claim a known total.


## Why this exists

T4 decided. This executes, and its two hardest cases are **the same transcript state with opposite correct
answers** (C2): a `bash` whose receipt has a completion is recovered, and one whose receipt does not is failed.

## Scope

```go
func RecoverStep(ctx context.Context, dep Deps, st store.Step, msgs []model.Message,
                 receipts []store.Receipt) (StepResult, error)
```

It calls `DetermineCase`, then acts:

**Case A** → `ResumeStep`, unchanged (N7, I1, D16). Recovery reaches S6's resume path rather than the loop, so a
resumed step and a recovered step cannot drift apart.

**Case B** → re-issue. The transcript is already correct — the lost turn left no trace — so this is the loop
continuing from where the record says it is. And it **records that recovery re-issued** (O1), on the step, so the
doubled cost has a stated cause. A step whose cost exceeds its visible turns with no explanation reads as a
billing bug, and the tokens were really spent (D3).

**Case C** → apply each `CallPlan`:

- `ReRun` — execute the tool now, exactly as the loop would
- `RecoverResult` — append the captured result as the `tool_result` block, then continue. **The tool is not
  executed** (D6)
- `FailStep` — fail the step, with the plan's reason, and do not execute or recover anything else

**`CaseUnclassifiable`** → fail with the reason (O5). The caller (T6) continues to the next step.

### Bounds and context (D12)

Recovery reads iterations and the **absolute deadline** from the manifest, exactly as `ResumeStep` does. It does
not re-resolve context and does not reset the count.

That is not a tidiness point: without it, a step that crashes repeatedly gets a fresh budget each time, and the
absolute deadline S5 chose over a duration is what makes "crash, restart, crash" terminate.

### The failure reason (K33, D7)

A structured reason, not a sentence assembled at the call site:

```go
type RecoveryFailure struct {
    Kind      string  // "unknown-tool-outcome" | "digest-mismatch" | "unclassifiable"
    Tool      string  // the tool named, when there is one
    ToolUseID string
    Detail    string  // a human sentence
}
```

It is stored on the step and surfaced by T7. S8's redo edges consume it, and "failed" without a cause is a loop
that retries the same thing forever.

| `TestRecoverFailsOnUnknownOutcome` | The **same transcript**, receipt without completion: the step fails, the reason names `bash` and the state, and the spy is at zero (D7, C2) |
| `TestRecoverFailsOnDigestMismatch` | A completed receipt whose digest does not match: fail, reason `digest-mismatch`, result not used (D8) |
| `TestRecoverFailStepSkipsOtherCalls` | One safe and one unsafe-incomplete call: the step fails and the **safe tool is not executed** |
| `TestRecoverReadsBoundsFromManifest` | Iterations continue from the manifest's count; the deadline is the original absolute one, not a fresh window (D12) |
| `TestRecoverUnclassifiableFailsWithReason` | Each of T4's four triggers produces a failed step with a `RecoveryFailure` naming it |

`TestRecoverRecoversCapturedResult` and `TestRecoverFailsOnUnknownOutcome` must **share their transcript fixture**.
That is the point: identical records, opposite answers, and only the receipt between them.

## Definition of done

- [ ] Case A reaches `ResumeStep`, and a recovered step is deep-equal to an uninterrupted one
- [ ] Case B records that it re-issued, and both calls' cost is reported
- [ ] `RecoverResult` appends without executing
- [ ] `FailStep` names the tool and the receipt state, and skips remaining calls
- [ ] A digest mismatch fails rather than using the result
- [ ] Bounds and context come from the manifest
- [ ] `RecoveryFailure` is structured, not a formatted string
- [ ] D6's and D7's tests share one transcript fixture
- [ ] `ResumeStep` is unmodified (N7)
- [ ] No test kills a process (D17)
