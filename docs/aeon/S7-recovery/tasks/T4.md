# T4 — `DetermineCase`, a pure function

**Notes (2026-10-17):** Implemented as a pure runtime function over a storage-neutral receipt view. The
constructed-input table covers complete and missing model turns, all receipt states, digest mismatch,
unclassifiable records and the pending-question shape. Runtime tests pass. Manifest validation remains the
daemon caller's responsibility, since the function's promised inputs do not include a manifest.

## Why this exists

**This is the task that matters.** Every action in T5 dispatches on its answer, and the answer is wrong in a way
nobody notices until a crash — at which point the loop either loses work or repeats a `git commit`.

It is pure for exactly that reason (K30, I3). Staging a crash at a precise instant is unreliable; staging every
instant is impossible. A pure function over constructed inputs can be tested **exhaustively**, and that is the only
place in this slice where "exhaustively" is available.

## Scope

```go
type Case int

const (
    CaseA Case = iota + 1  // the tail is complete; resume
    CaseB                  // no committed assistant turn; re-issue
    CaseC                  // unanswered tool_use blocks; consult classes and receipts
    CaseUnclassifiable     // the record does not make sense
)

type Plan struct {
    Case   Case
    Reason string        // always set for CaseB and CaseUnclassifiable; a human sentence
    Calls  []CallPlan    // CaseC only
}

type CallPlan struct {
    ToolUseID string
    Tool      string
    Action    CallAction  // ReRun | RecoverResult | FailStep
    Result    string      // RecoverResult only: the captured result
    IsError   bool
    Reason    string      // FailStep only: names the tool and the receipt state
}

// DetermineCase is pure: no store, no clock, no I/O.
func DetermineCase(msgs []model.Message, receipts []store.Receipt, classes map[string]tools.RerunClass) Plan
```

`classes` is passed in rather than looked up, because a registry lookup is a dependency and this function has none.

### The rules

**Case A** — the last assistant turn's `tool_use` blocks all have matching `tool_result` blocks. Resume.

**Case B** — the transcript's tail has no assistant turn: it ends on a user or tool message, or it is empty. The
model call never committed and nothing executed. Re-issue.

An **empty** transcript is Case B (Q1): `internal/protocol/step.go` creates the step row before calling `RunStep`,
so a crash in that window leaves a `running` step with nothing in it, and re-issuing is exactly right.

**Case C** — the last assistant turn has `tool_use` blocks lacking results. Per unanswered block, by class:

| Class | Receipt | Action |
| --- | --- | --- |
| `safe`, `detectable` | (not consulted) | `ReRun` |
| `unsafe` | absent | `ReRun` — nothing happened |
| `unsafe` | present, `completed_at` set, digest matches | `RecoverResult` with the captured result |
| `unsafe` | present, `completed_at` set, digest **mismatches** | `FailStep` — the result belongs to a different call (D8) |
| `unsafe` | present, `completed_at` **nil** | `FailStep` — started, outcome unknown (D7) |

**`CaseUnclassifiable`** (O5) — the record does not make sense:

- a receipt references a `tool_use_id` present in no message
- a `tool_result` references a `tool_use_id` present in no assistant turn
- a tool named in an unanswered block has no entry in `classes`
- the manifest is absent or unparseable (Q10)

Each returns a `Reason` saying which. One bad step must fail with an explanation and let recovery continue to the
next; a panic or a silent guess would take the rest of the machine's loops with it.

**A tool with a completed receipt but no `result` recorded** is `FailStep`, not `RecoverResult`. `completed_at` set
with `result` NULL should not happen — T1's `CompleteReceipt` writes both — and treating it as a successful empty
result would fabricate an outcome from a bookkeeping bug.

## Tests

`TestDetermineCaseTable` is a table test, and it must be **complete** (D1, A6). Enumerate:

- Empty transcript → B
- Tail is a user message → B
- Tail is a tool message with no assistant after → B
- Assistant turn, text only, no tool_use → A
- Assistant turn, one tool_use, one matching result → A
- Assistant turn, two tool_use, two matching results → A
- Assistant turn, two tool_use, one result → C with one call planned
- C × `safe` → ReRun
- C × `detectable` → ReRun
- C × `unsafe`, no receipt → ReRun
- C × `unsafe`, receipt completed, digest matches → RecoverResult, result carried
- C × `unsafe`, receipt completed, digest mismatches → FailStep, reason names the mismatch
- C × `unsafe`, receipt incomplete → FailStep, reason names the tool and the state
- C × `unsafe`, receipt completed with NULL result → FailStep
- C × two unanswered calls, one safe one unsafe-incomplete → **FailStep wins**: the step fails, and the safe one is
  not re-run, because a step that fails has nothing to re-run for
- Receipt referencing an unknown `tool_use_id` → Unclassifiable
- `tool_result` referencing an unknown `tool_use_id` → Unclassifiable
- Unanswered block whose tool is absent from `classes` → Unclassifiable

| Test | Asserts |
| --- | --- |
| `TestDetermineCaseTable` | The full enumeration above |
| `TestDetermineCaseIsPure` | Called twice with the same inputs, deep-equal results; and the inputs are **unmodified** afterwards |
| `TestDetermineCaseNeverPanics` | A fuzz seed of malformed transcripts — empty blocks, duplicate ids, a `tool_result` before any assistant turn — every one returns a `Plan`, never a panic |
| `TestSuspendedShapeIsNotSpecialCased` | A transcript whose unanswered `tool_use` is a `question` classifies as C. **This is correct**: `DetermineCase` does not know about `status`, and the scan (T6) is what never passes it a suspended step (K29). The test documents that the separation is deliberate rather than an oversight |

`TestSuspendedShapeIsNotSpecialCased` is the one to write carefully. It looks like it asserts the wrong behaviour.
It asserts that the `status` filter is the single point where suspension is respected — and a second, redundant
check inside the pure function would be a place for the two to disagree.
