# T7 — Recovery on the wire and in the CLI

**Notes (2026-10-17):** The daemon emits all four recovery events. `step.show` exposes the saved recovery case, structured failure and receipts; `step.answer` and `step.show` report a recovering error while a row is being handled. The CLI prints failed tool details and provides `aeon debug receipts <id>`. Protocol conformance fixtures cover the event and error shapes. The Recovery test bench replays retained events from sequence zero and inspects durable records by step ID.


## Why this exists

S2 built subscriptions and gave the daemon lifecycle events so they would be testable before any domain events
existed. Recovery is the first thing a **client** needs to see that is neither a step's progress nor a plain
lifecycle transition — the daemon doing work on behalf of steps nobody asked about yet.

And T5's structured failure is useless if it never leaves the database.

## Scope

### Events

```
recovery.started    { total }
recovery.step       { stepId, case, index, total }
recovery.resolved   { stepId, outcome, failure? }
recovery.finished   { recovered, failed, total }
```

`recovery.step` carries `index` and `total` (O3) for the same reason the log does: during a slow recovery the
useful question is how much is left.

`recovery.resolved`'s `failure` is T5's `RecoveryFailure`, serialised whole — `kind`, `tool`, `toolUseId`, `detail`.
A client that only shows `detail` still works; one that wants to offer "retry" can branch on `kind`.

These follow S2's additive rule: a client that does not know them ignores them, so this is not a protocol version
bump.

### Conformance fixtures

`testdata/conformance/recovery.json`, in the shape S2's other fixtures use — the cross-language contract, so a
future editor plugin sees the same events without reading Go.

Include a fixture for **each** failure `kind`, because a client's handling of `unknown-tool-outcome` and
`digest-mismatch` may reasonably differ.

### Requests during recovery (T6's Q9 consequence)

A `step.get` or `step.answer` for a step recovery has not reached yet returns a **`recovering`** error with the
step's id — not `not_found`, and not a stale snapshot. Saying "I am working on it" is the truth; the alternatives
are both lies, and one of them invites a client to create a duplicate.

### CLI

**`aeon step show <id>`** — when a step failed in recovery, print the failure: the kind, the tool, and the detail.
The demo's §3 depends on this being legible without `--json`.

**`aeon debug receipts <step-id>`** — list a step's receipts: tool, `tool_use_id`, `arg_digest`, `started_at`,
`completed_at` or `—`. The demo's §4 uses it to show that the digest is recorded, and it is the only way to see the
unknown state directly.

Under `debug` because it is a diagnostic, not a product surface, and R6 says operational controls do not become
tools an agent can reach.

**`aeon serve --no-recover`** — T6's flag, wired and documented in `--help` with what it does and does not do.
