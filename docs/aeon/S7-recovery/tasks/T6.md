# T6 — The start-up scan — automatic, observable, idempotent

**Notes (2026-10-17):** Startup opens the socket before scanning `running` steps. The scan records cases, emits progress, persists each outcome with its transcript and recovery record in one transaction, and continues after a failed or panicking step. `--no-recover` reports without changing rows. The debug crash hook is compiled only with `aeondebug`; `make dev` enables that tag and release builds omit it. The replay walk killed recovery after two committed outcomes and confirmed the second start resolved only the third. It also confirmed a suspended question stayed untouched across `SIGKILL`.


## Why this exists

Recovery is the thing that runs when something has already gone wrong. So it must survive going wrong itself: a
crash **during** recovery is ordinary, and the next start has to pick up where it stopped without re-recovering
what it already did (K34).

And it must be **visible**. A silent multi-minute recovery on start is indistinguishable from a hang, and the person
watching has no way to tell (D13).

## Scope

```go
// Recover scans for steps whose process is gone and acts on each.
// Returns a summary; never returns an error for a single step's failure.
func Recover(ctx context.Context, dep Deps) (Summary, error)
```

### The scan (K29, D9)

```sql
SELECT id FROM step WHERE status = 'running' ORDER BY id
```

**`status='running'` and nothing else.** A suspended step also has an unanswered `tool_use` — the `question` — and
without this filter recovery would "recover" every loop correctly waiting for a human, re-issuing a call the model
never needed to make. This one `WHERE` clause is the whole of K29, and D9 asserts it by attempt.

`orphaned` and `done` steps are not scanned either. `orphaned` is S4's terminal marker for a step nothing will
finish; recovering it would resurrect something already accounted for.

### Per-step, atomically (K34, D11)

Each step's outcome commits in **one transaction**: its new status, its result or failure, and its transcript
additions together. A crash between two steps leaves the first fully recovered and the second still `running` —
which is exactly the state the next scan handles.

Idempotence follows from the filter rather than from a marker: a recovered step is no longer `running`, so a second
scan does not see it. There is no "already recovered" flag to get out of step with reality.

### One bad step does not stop the rest (O5)

A step that fails to recover — unclassifiable, or an error from `RecoverStep` itself — is marked failed with its
reason, logged, and the scan **continues**. A panic is caught per step for the same reason. One corrupt transcript
must not take the rest of the machine's loops with it.

### Ordering against the socket (Q5, Q9)

**The socket opens first, then recovery runs.** A daemon that will not accept connections until recovery finishes
is one nobody can inspect during a slow recovery — and "slow" here means a Case B re-issue against a model, which
is seconds to minutes per step.

Requests that arrive for a step still being recovered get a clear "recovering" response rather than a lie about its
state. That is a small protocol addition and it belongs to T7.

### Observability (D13, O3)

Before acting on each step, report it: its id, its case, and a **running count against a total** — "recovering 3 of
7". During a slow recovery the useful question is how much is left, not what the current one is.

Reported through the daemon's existing logger **and** as protocol events (T7), so both a terminal and a subscribed
client can see it.

### `--no-recover` (K35, D14, O4)

Reports what it found — every step, with its case — and **leaves them `running`**. It does not mark them anything: a
flag that quietly relabels state loses the information the next start needed.

Seeing what recovery *would* do without letting it act is the difference between debugging a recovery loop and
guessing at one.

### The debug hooks (Q6, Q8, F2)

`AEON_DEBUG_CRASH_DURING_RECOVERY=<n>` exits the process after recovering *n* steps. The demo needs it to stage §6,
which cannot be hit by hand.

It lives behind a **build tag** (`//go:build aeondebug`), with a no-op implementation in the default build, so a
release binary cannot be made to exit by an environment variable. `make dev` sets the tag; `make build` does not.
A test asserts the release build ignores the variable.

## Tests

| Test | Asserts |
| --- | --- |
| `TestScanSkipsSuspended` | A `status='suspended'` step with an unanswered `question` is put through a full recovery pass and comes out **untouched** — same status, same transcript, and `RecoverStep` never called (D9, C3) |
| `TestScanSkipsOrphanedAndDone` | Neither is scanned |
| `TestScanIsIdempotent` | Two consecutive passes over the same store produce identical final state, and the second calls `RecoverStep` **zero** times |
| `TestScanResumesAfterInterruption` | Three running steps; a fake writer that stops after two; a second pass recovers only the third and does not touch the first two (D11) |
| `TestScanContinuesAfterOneFailure` | Three steps, the middle one with a corrupt transcript: it is marked failed with a reason, and the third is still recovered (O5) |
| `TestScanRecoversPanicPerStep` | A `RecoverStep` stub that panics on one step: that step fails, the scan finishes |
| `TestScanCommitsAtomically` | A store spy proving status, result and transcript land in one transaction |
| `TestScanReportsEveryStepWithCase` | The log carries one line per step, with its case, a running count and a total (D13, O3) |
| `TestNoRecoverLeavesStatusRunning` | With `--no-recover`: cases are reported, `RecoverStep` is at zero, and every step is still `running` (D14, O4) |
| `TestSocketOpensBeforeRecovery` | A client connects while recovery is still working (Q9) |
| `TestReleaseBuildIgnoresCrashHook` | With the debug tag absent, `AEON_DEBUG_CRASH_DURING_RECOVERY=1` changes nothing (F2) |

`TestScanResumesAfterInterruption` stages a mid-recovery crash **without killing anything** (C5): the injected
recoverer simply stops. That is a truer test than a `kill -9` anyway, because it lands at a controlled point.

## Definition of done

- [ ] The scan filters on `status='running'` alone
- [ ] A suspended step survives a pass untouched, asserted by attempt
- [ ] Each outcome commits atomically; idempotence follows from the filter, not a flag
- [ ] One bad step, including a panic, does not stop the scan
- [ ] The socket opens before recovery runs
- [ ] Every step is reported with its case, a running count and a total
- [ ] `--no-recover` reports and leaves steps `running`
- [ ] The crash hook is behind a build tag and absent from release builds
- [ ] All eleven tests exist and pass; none kills a process (D17)
- [ ] `make test`, `make lint` green
