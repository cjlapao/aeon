# T3 — Writing a receipt before an unsafe tool runs

**Notes (2026-10-17):** Implemented with a narrow `ReceiptWriter` and a companion checkpoint writer. The
assistant turn is saved before tools execute; `bash` begins its receipt before `Call`, captures completion
before the tool result checkpoint, and refuses to execute if beginning the receipt fails. Runtime, daemon,
protocol and store tests pass with an isolated HOME.

## Why this exists

The receipt's whole value is **when** it is written. A receipt written after the process spawns records nothing
about the window it exists for — which is precisely the window between "about to run" and "ran".

So this task's gate is an **ordering** assertion, not a presence one (D10). A test that checks a receipt exists
after the tool finished passes against code that writes it at the wrong moment.

## Scope

### The narrow writer (K32, I4)

K6 says the runtime persists nothing and opens no store. A one-method-pair interface preserves that:

```go
// ReceiptWriter records that an unsafe tool is about to act, and what came of it.
type ReceiptWriter interface {
    Begin(ctx context.Context, toolUseID, tool, argDigest string) error
    Complete(ctx context.Context, toolUseID, result string, isError bool) error
}
```

No `stepID` — the writer is constructed for one step, so the runtime cannot address another step's receipts even by
mistake. The `step` handler (`internal/protocol/step.go`) supplies one backed by T1's store methods; `RunStep` and
`ResumeStep` take it alongside their existing dependencies.

A **nil** writer is legal and means no unsafe tool may run: the loop refuses an `unsafe` tool with a clear error
rather than executing it unrecorded. That keeps every existing runtime test — which has no writer — honest, and
makes "run an unsafe tool with nothing recording it" impossible rather than merely unlikely.

### In the loop

```go
if tool.RerunClass() == tools.RerunUnsafe {
    if w == nil {
        return refuseUnrecorded(tool.Name())
    }
    if err := w.Begin(ctx, block.ID, tool.Name(), tools.ArgDigest(tool.Name(), block.Input)); err != nil {
        return ... // a failure to record is a failure to run
    }
}
result := tool.Execute(ctx, block.Input)
if tool.RerunClass() == tools.RerunUnsafe {
    _ = w.Complete(ctx, block.ID, result.Content, result.IsError)
}
```

Two properties in that shape:

- **A failure to record is a failure to run.** If `Begin` errors, the tool does not execute. The alternative —
  running it anyway — produces exactly the unknown state the receipt exists to prevent.
- **`Complete` runs before the transcript write.** That ordering is the whole of D6: a crash between them is the
  recoverable case, and a crash the other way round would leave a completed receipt for a tool result already
  persisted, which is harmless but proves nothing.

`Complete`'s error is deliberately dropped. The tool ran, the result is in hand, and failing the step because a
bookkeeping write failed would discard real work. A crash after this point falls back to the unknown state, which
is the honest answer.

### Not in scope

No policy on **which** bash commands may run (N2, S11). No change to how `bash` executes. No change to
`ResumeStep`'s behaviour beyond receiving the writer (N7).

## Tests

| Test | Asserts |
| --- | --- |
| `TestReceiptWrittenBeforeSpawn` | A spy writer and a `bash` stub that **records the order**: the `Begin` call is observed by the stub as already having happened. Asserted on ordering, not on presence afterwards (D10) |
| `TestBeginFailureBlocksExecution` | A writer whose `Begin` errors: the tool's `Execute` is **never called**, proven by a spy at zero |
| `TestSafeToolWritesNoReceipt` | A `read` produces no receipt. The machinery guards one tool, not every tool |
| `TestReceiptCompletedBeforeTranscriptWrite` | With a spy store recording call order, `Complete` precedes the `step_message` insert |
| `TestNilWriterRefusesUnsafeTool` | A nil writer refuses `bash` with a clear error and **does not execute it** |
| `TestCompleteErrorDoesNotFailTheStep` | A writer whose `Complete` errors: the step still succeeds with the tool's real result |
