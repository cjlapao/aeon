# T4 · Category tagging

**Prefix:** TL · **Rules:** TL6 (D4) · **Depends on:** T2, T3 (shares the capture plumbing T3 added).

## Goal

`SectionSpec` gains a required `Category` field; every construction site is updated; the frozen opening
context's sections are tagged `system_prompt`/`injected_context`, and `RunLoop`'s tool-result message
appends are tagged `tool_result` at the point they're already structurally distinct (no new classification
logic — recording what the code already knows). This closes D4 for three of its four surviving categories;
T3 already closed the fourth (`assistant_output`).

## Files to modify

- `internal/runtime/types.go` — add to `SectionSpec`:
  ```go
  type SectionCategory string
  const (
      CategorySystemPrompt    SectionCategory = "system_prompt"
      CategoryInjectedContext SectionCategory = "injected_context"
  )
  type SectionSpec struct {
      Title, Text, DeclaredFile string
      Category SectionCategory // required — no default
  }
  ```
- Every call site from `VERIFY: grep -rn 'SectionSpec{' internal/runtime cmd/aeon internal/daemon` — add
  the field, keyed. Decide per site whether it's building the system prompt proper or an injected-context
  section (the title/source usually makes this obvious — e.g. the declared-file sections are
  `injected_context`, the fixed instructional text is `system_prompt`; where it's genuinely ambiguous,
  record the call and the choice made in Notes rather than guessing silently).
- `internal/runtime/loop.go` — at the point a tool result is appended to the transcript (near the
  `d.Tools.Call` choke point, `VERIFY` current line, T6 of this slice also edits code near here — read
  T6's diff if it landed first, per plan.md's "independent but close together" note), add the
  `RecordTurn`-shaped call (or extend T3's, if one capture call can carry both — decide which reads
  cleaner and record it) tagging `tool_result`.
- `internal/runtime/types_test.go` or a new file — the tests below.

## Do NOT

- Do not add a `tool_schema` category — TL6's finding says it cannot be measured today; don't ship a column
  nothing will ever fill.
- Do not default `Category` to a guessed value at a call site you're unsure about — record the ambiguity in
  Notes and make the most defensible choice, don't silently pick one.

## Notes (2026-10-30, built in worktree branch `s33-telemetry`)

**`SectionCategory` lives in `internal/runtime/telemetry.go`, not types.go's
SectionSpec block** (the task snippet's placement): the type is shared by the
interface (T2) and the sections (T4), and defining it beside the interface
kept one definition while T4's field arrived beside it. types.go's
`SectionSpec` gained `Category SectionCategory` — required, no default,
documented why (P31: a guessed category is the confident wrong answer).

**`AssembleContext` is the one enforcement gate** (every section passes
through it, production and test): empty, off-vocabulary, or TRANSCRIPT-side
(`assistant_output`/`tool_result` are recorded by the loop, never declared)
values are refused by name with the section index and title, in the
project's refusal style. `tool_schema` refused as just another unknown —
`TestAssembleRefusesAnUncategorisedSection` walks all three cases.

**Composition persisted: `ContextManifest.Sections []SectionRecord`
{Title, Category, Chars} + `SystemChars`.** Chars counts the RESOLVED body —
a declared file's read bytes, a retrieval's returned text — the context the
model was SHOWN, not the declaration that asked for it. Filled by
AssembleContext, frozen with the manifest through the EXISTING checkpoint
(no new persistence: K14's discipline, and T8's `telemetry.loop` reads the
stored bytes back through `runtime`, the type's owner). `SystemChars` counts
the system prompt AS SENT including the handoff-schema suffix — obtained by
extracting `SystemPromptText(h)` out of `OpeningTranscript` so the count and
the transcript have ONE definition (a second builder would drift the day the
suffix changed). Pre-S33 manifests: Sections nil / SystemChars 0 → the
readout says "not recorded", never infers.

**tool_result tagged at the executed-call point of `runTool`** — after
`d.Tools.Call`, beside the wall bracket: gate refusals returned earlier
having run NOTHING and correctly record NOTHING (a policy decision is not
tool activity; a refused command counted as a run would inflate TL9's own
number). Usage EMPTY + cost `unknown` by construction (a tool result is not
a spend event — the store's T1 rule keeps its cost columns NULL and counts
only the wall); its own `RecordTurn` call rather than an extension of
stream()'s, per the task's "which reads cleaner": the model-call row and the
transcript-append row are different facts at different points and folding
them together makes each read like the other. Failure spoken
(`step.telemetry.error`), never fatal.

**The 49 call sites, decided not guessed:** `defaultSections`' three
(Task, Workspace, How to work) → `system_prompt` — the call recorded: the
TASK section is the handler side's own instructional prompt (frozen opening
text), not externally given material; protocol's DeclaredFile and Retrieval
sections → `injected_context`; test sites keyed by content (text
instructions → system_prompt, `DeclaredFile`/`Retrieval` literals →
injected_context), all swept mechanically then vet-cleaned (three external
files needed `runtime.`-qualified values — one sweep bug fixed, double
prefixes stripped).
