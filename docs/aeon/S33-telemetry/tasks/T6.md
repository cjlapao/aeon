## File half — reuses existing fields, zero new plumbing

`tools.Result` (`internal/tools/read.go:106-129`, confirmed this session) already carries `Path`,
`LinesAdded`, `LinesRemoved` — added for S31's D8, riding the event stream. At the loop's one tool-dispatch
choke point (`internal/runtime/loop.go:739`'s `res := d.Tools.Call(ctx, use.Name, use.Input)`, confirmed
this session), when `res.Path != ""`, call `d.Telemetry.RecordFileActivity(ctx, stepID, res.Path, action,
&res.LinesAdded, &res.LinesRemoved)` (nil-guarded). **`action` is `"write"` whenever `Path` is set** — the
`read` tool's result comment explicitly says `Path` is "write-shaped" only (`VERIFY` this is still true by
checking whether `read.go`'s own tool ever sets `Path` — if it does, this task's action-determination needs
a different signal, e.g. the tool name, and that finding goes in Notes before writing the call).

## Command half — one small, S31-shaped `Result` amendment

`internal/tools/bash.go`'s internal `RunResult` already carries `ExitCode`/`Duration` (confirmed this
session), but the generic `tools.Result` the loop sees does not. Add two fields, same pattern as S31's own
`LinesAdded`/`LinesRemoved` addition (new fields, old fields and the ten tools' model-facing behavior
frozen, N5):
```go
type Result struct {
    // ... existing fields unchanged ...
    ExitCode *int          // nil for non-command results; bash sets it always, success or failure
    WallMs   int64         // 0 for non-command results
}
```
`bash.go`'s result-construction path sets both from its `RunResult`. At the same choke point, when
`use.Name == "bash"` (gate on the tool name — a legitimate `exit 0` must still be recorded, so a
"non-zero field" test would wrongly skip successful runs), call `d.Telemetry.RecordCommandActivity(ctx,
stepID, command, res.ExitCode, res.WallMs)`.

## Notes (2026-10-30, built in worktree branch `s33-telemetry`)

**The task's `res` type at the choke is not `tools.Result` — it is
`runtime.ToolOutcome`.** `loop.go` cannot import `tools` (both are leaves);
the daemon's `toolCaller.Call` (internal/daemon/step.go) is the ONE
conversion point between them. So the `ExitCode *int` / `WallMs int64` pair
lands on **both** structs — `tools.Result` (populated by bash) AND
`runtime.ToolOutcome` (read by the loop) — and is copied at the one
conversion site, which is exactly how S31's `Path`/line-counts already
cross. The conversion comment updated; no new conversion point introduced.

**VERIFY finding on the file half — `edit` emits NO write-shaped result.**
The task asked to check whether `read` ever sets `Path`: it does not
(`Path:` is set by exactly one site, write.go's success return) — so
`res.Path != ""` remains the write signal. But the sweep found more:
**`edit.go`'s success return sets neither `Path` nor the line counts** (it
builds `Result{Content, Summary}` only). Consequences, recorded:
1. Edits produce NO `step_file_activity` rows and contribute nothing to
   `files_written_total`/line totals today — the capture reuses what tools
   REPORT (this task's zero-new-plumbing rule), and edit reports nothing.
2. Adjacent pre-existing gap (NOT S33, recorded here as discovered):
   `daemon/step.go`'s V8/Q7 `onWrite` trigger fires only when
   `writingTools[name] && res.Path != ""`, and `writingTools` includes
   `edit` — so **the write trigger has never fired for an `edit`**. Fixing
   it is a tools-side change (populate edit's Path + `countLineDiff`, the
   same 3 lines write.go already has) and belongs to S31's home, not this
   capture task's file list.
3. `TestEditDoesNotYetEmitWriteShape` pins the current behaviour with
   instructions: whoever populates edit should FLIP it, deliberately.
`TestFileActivityCapturedFromExistingFields` therefore drives `write` (the
one tool that carries the fields), and
`TestReadToolNeverProducesFileActivity` pins the read side.

**Command gating: `use.Name == "bash" && res.ExitCode != nil`.** Name-gated
per the Do-NOT (never a "non-zero fields" test — an exit 0 is the most
load-bearing row D6 has); the `!= nil` companion is NOT that forbidden test:
bash sets `ExitCode` to a NON-NIL pointer to zero on every command that
STARTED, so nil means "the command never started" (no shell, no token — the
Spawn-error path, which also never reaches the ExitCode assignment). A
command that never ran is not a run (T4's refusal principle), and
`TestNeverStartedCommandIsNotARow` pins it. The command string rides from
the runtime's OWN parse (`commandArgument`, the same one definition the
permission ask uses), never a tool echo (SEC-051's trust side).

**`Errorf` keeps absence**: the refusal constructor leaves both new fields
zero — asserted, so a future constructor cannot smuggle command facts into
a non-command result.
