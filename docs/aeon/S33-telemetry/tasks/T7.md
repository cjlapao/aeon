# T7 · The rollup chain and the component-move transfer

**Prefix:** TL · **Rules:** TL2, TL3, TL9 (D7, D9) · **Depends on:** T1, T3, T5, T6.

## Goal

Prove T1's "every `RecordX` bumps all three tiers in one transaction" claim with real, varied capture
calls behind it (not just T1's own synthetic test), and implement **TL3's component-move transfer** — the
one genuinely new finding this slice adds beyond the brief: `UpdateComponent` must carry a component's
rollup totals when it moves between projects.

## Files to modify

- `internal/store/components.go` — in `UpdateComponent`, inside the **same transaction** as the existing
  `project_id` column change (`VERIFY` current line, confirmed this session around line 140-155), when
  `in.ProjectID != ""` and differs from the component's current `project_id`:
  1. Read the component's current `component_telemetry` row (it may not exist yet if the component has
     never produced telemetry — handle the zero-row case as "nothing to transfer," not an error).
  2. `UPDATE project_telemetry SET <every total column> = <every total column> - <the component's value>
     WHERE project_id = <old project_id>` (only if the old project's row exists — it must, if the
     component had any telemetry, since T1's bump-on-write creates it).
  3. `UPDATE project_telemetry SET <every total column> = <every total column> + <the component's value>
     WHERE project_id = <new project_id>` (upsert if the new project has never had telemetry before).
  4. `cost_state`/`wall_ms_state` (if T1's Q1 added it) at the destination project **recompute from its
     members after the transfer**, not a simple floor-merge — a project gaining a `partial`-contributing
     component must floor to `partial` even if it was `known` before; a project losing its only
     `partial` contributor may be able to return to `known`. This is the one place in the slice where a
     state is recomputed rather than incrementally carried, and it is justified because a move is rare and
     the member set it depends on just changed.
- `internal/store/components_test.go` — the tests below.

## Tests

| Test | Asserts | Fails when |
| --- | --- | --- |
| `TestMoveTransfersRollupExactly` | moving a component with existing telemetry: old project's totals decrease by exactly the component's contribution, new project's increase by exactly the same, workspace totals unchanged | TL3's arithmetic wrong |
| `TestMoveWithNoTelemetryIsANoOp` | moving a component that has never produced telemetry succeeds with no row changes anywhere | the zero-row case wasn't handled and errors instead |
| `TestMoveRecomputesCostStateAtDestination` | moving a `partial`-contributing component into a `known` project floors the destination to `partial`; removing it from the source lets the source return to `known` if nothing else there is `partial` | the state wasn't recomputed, only incrementally floored (which can never improve) |
| `TestMultiTierBumpIsTransactional` | a crash/rollback simulated mid-`RecordX` leaves **zero** of the three tiers updated, never one or two of three | the three updates aren't actually one transaction |
| `TestRealLoopProducesConsistentRollups` | a full scripted multi-turn, multi-tool-call step produces `step_turn`/`step_compaction`/`step_file_activity`/`step_command_activity` rows whose sums **equal** the component tier's totals exactly | drift between detail and rollup anywhere in the chain |

## Definition of done

- [ ] Component move transfers rollup totals exactly, in the same transaction as the existing `project_id`
      change.
- [ ] `cost_state` is recomputed (not incrementally floored) at both projects on a move.
- [ ] A full real-loop test proves detail-sum equals rollup-total, end to end.
- [ ] Every multi-tier bump is proven atomic.

## Do NOT

- Do not recompute a project's sums from scratch by re-summing every member component on every write — only
  on a move, and only for the one affected project pair.
- Do not touch loop-tier or archived data to implement the transfer — the component tier's own current
  totals are sufficient and are the whole point of TL3.

## Notes (2026-10-30, built in worktree branch `s33-telemetry`)

**The recompute runs AFTER the `project_id` flip, not inside the transfer —
and that ordering is the correctness.** The first cut put
`recomputeProjectCostState` at the tail of `transferProjectRollups`;
`TestMoveRecomputesCostStateAtDestination` immediately proved it wrong: at
that instant the mover's `component.project_id` is still the SOURCE's, so
the fold read the OLD member sets and both projects kept their pre-move
states (P stayed `known` after gaining a partial member; Q stayed `partial`
after losing its only one). Split: `UpdateComponent` runs the transfer
(subtract/add) before the UPDATE and the two recomputes AFTER it — same
transaction throughout, so the states can never be read mid-move by anyone.

**One column list, three readers.** `rollupAdditiveColumns` is now THE list
of the eighteen carried numbers; the tier upsert's column list, its DO
UPDATE sets and the transfer's subtract are all GENERATED from it
(`telemetryTierUpsert` extracted from the old tier loop). A subtract that
missed a column would silently leak that total out of the source on every
move — the generation deletes that failure shape. The FK-on-
`project_telemetry.project_id` (T1) turned out to be the injection point
the atomicity test needed: bumping against a nonexistent project fails the
chain AFTER the component tier wrote — rollback then asserts **zero**
survivors (and if any tier had ever been written on `s.w` instead of the
passed tx, it would outlive the rollback and this test catches exactly
that). The test also pins T1's CreateLoop bump: after the rolled-back
chain, workspace still reads exactly `loops_run: 1` and zero tokens.

**The move transfers `loops_run` too** — loops ride the component's root,
so the count they contributed rides the move (the Do-NOT's "component
tier's own totals are sufficient" is read as: the component row is the
transfer's source of truth; it itself never changes). Workspace untouched,
asserted by identity against the pre-move snapshot.

**Missing source row is a defect, said as one**: a component carrying
telemetry whose project row is absent means T1's bump-on-write invariant
broke upstream — `transferProjectRollups` refuses with that sentence rather
than quietly subtracting into nothing.

**Q1 revisit:** `wall_ms_state` was never added (no `step.wall_ms` writer —
T1's Q1 answer), so only `cost_state` is recomputed at both endpoints. The
compaction row's usage/cost DOES bump (T1's recorded fact) and the
consistency test folds it into the expected sums — its wall contributes
nothing because the row shape has none.

**End-to-end consistency (`TestRealLoopProducesConsistentRollups`, daemon):**
a REAL `runtime.RunLoop` — real compaction selection (oversized history vs
a 1200-token window), two executed tools through a `runtime.ToolCaller`
stub carrying the T6 fields (write's Path/counts, bash's ExitCode/WallMs),
three billed turns through the production adapter onto the real store —
then every detail table is summed and must EQUAL the component tier
column-by-column (tokens 260/47 pattern, cost Σ, wall Σ incl. tool_result
walls, files 1 write 4/1, commands 1 run 0 failed wall 120), and project
and workspace carry the same sums. The fixture is deliberately sized so
ONE compaction fits the transcript under the budget — a second attempt
would need a second admissible range (a blocked-run fixture rotted once at
400 tokens; the block reason named it, so the fixture records why it is
sized the way it is).
