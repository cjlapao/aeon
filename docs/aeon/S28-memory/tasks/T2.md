# T2 — `internal/learnings`: the core package

## Why this exists

Every other task calls into this package rather than touching `learning`/`learning_tag` rows directly.
**The package name itself is the first thing this task gets right**: `learnings`, never `memory` — see
`design.md` §2 before writing a line, and confirm no file in this task's diff imports or shadows
`internal/store`'s existing `Memory`/`AppendMemory`/`ReadMemory`.

**Read first:** `internal/handler/registry.go`'s `Lookup(name) (Handler, bool)` and `internal/store/schema.go`'s
`plugin_agent` table (`state` CHECK, the `plugin_agent_live` partial unique index) — both inputs to this
task's scope-validation function.

## Scope

**1. `Append(scope, scopeKey, body, provenance, observedCount, tags []string, source ...) (Learning, error)`**:
validates `scope`/`provenance` against the closed sets (SQLite's own CHECK is the backstop; this function's
job is the *agent*-scope check SQLite cannot express). For `scope == "agent"`: refuse unless
`handler.Lookup(scopeKey)` returns true **or** a `plugin_agent` row exists for `scopeKey` with `state !=
'revoked'` — a `disabled` plugin agent still exists (it can be re-enabled), a `revoked` one does not.

**2. `Query(filter) ([]Learning, error)`**: tag filtering runs first and always (D5) — a query with zero
embedding route configured still returns correctly tag-filtered, provenance/strength-labeled results.
Nothing in this function's signature or behaviour changes based on whether an embedding route exists;
ranking is T3's concern, layered on top, never a precondition for this function to work.

**3. Every returned `Learning` carries its provenance and strength (`observed_count` when applicable)
unconditionally** — there is no "summary" mode that drops them (D3, M3's whole safeguard).
