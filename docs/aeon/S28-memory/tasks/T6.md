# T6 — the `answer` skill, declared and actually askable

## UPDATED 2026-10-26 — S14 is now built, and this task's scope grew to match

**The original scope (frontmatter only) is necessary but not sufficient.** Checked against S14's real code
(`internal/agentsvc/invoke.go`): `Invoker.Invoke` refuses **before** it even looks at what skills a body
declares — *"agent %q has no signed card, so no skill of it can be asked."* **None of S13's 25 bodies has a
real signed `AgentCard` today** — checked: the only card files in this repository are test fixtures
(`internal/agentsvc/testdata/cards/`), and nothing generates one from a handler body. Declaring `answer` in
a body's frontmatter alone would be inert twice over, not once — not just "no caller yet" (as this task
originally read, written before S14 existed), but "no card to be asked through at all."

**The good news, also checked**: card signing is a plain Ed25519 signature (`agentsvc.Sign(card,
ed25519.PrivateKey)`) — no external CA, no operator ceremony, no second system. A card can be generated and
self-signed by the daemon's own tooling at build/release time. This task does that, not a heavier thing.

## Scope

**1. Add one skill declaration, named `answer`, to all 25 bodies' frontmatter** — unchanged from the
original scope. Same verbatim description: *"Respond using what you already know. Take no other action —
no file writes, no commands, no tool calls beyond what answering the question requires to recall or reason,
nothing that changes project state."*

**2. Generate a real `AgentCard` for each of the 25 bodies**, derived from its frontmatter (`name`,
`description`, the `answer` skill as an `AgentSkill{ID: "answer", Name: "answer", Description: <the
verbatim text above>}`), written to whatever directory `agentCardsDir()` (`cmd/aeon/agent_services.go`)
resolves at build/release time — not hand-authored per body.

**3. Sign each generated card** with one keypair generated for this purpose (not per-body — one signer,
25 cards), the private half held the way `internal/secrets` already holds the cursor signing key (generated
once, loaded thereafter, never regenerated silently) — mirror that package's own discipline rather than
inventing a second key-at-rest convention.

**4. No change to any body's existing tools, temperature, policy-agent, or working skills**, and no change
to any skill beyond `answer` reaching a card — unchanged from the original scope.

**5. Name, do not solve, the `SkillAccess` authoring gap.** S14's own T7 filled in a real `SkillAccess`
evaluator (checked: `internal/policy/spec_skillaccess.go`, no longer a stub) — but **no rows exist yet**
granting any agent permission to ask another's `answer` skill, the same way `CommandAccess`'s corpus needed
S11's own `aeon policy seed-corpus` run explicitly after that slice shipped. This task does not author
those rows (that is an operational step, deliberately manual, matching the project's "authoring is
deliberate, never automatic" pattern) — it should say so plainly in its own Notes so whoever runs the demo
knows to grant before asking.
