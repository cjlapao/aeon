# T3 — embedding integration

## Why this exists

`design.md` M5/D6: where an embedding route is configured, it ranks within the tag-filtered set — it never
chooses which agent answers, and never substitutes for tag filtering. This is A13's dispatch-stays-closed
rule, restated for this slice's own embeddings (brief D6), not inherited by reference alone.

## Scope

**1. On `Append`, if a route is configured**, compute and store the embedding in `learning_vec`, keyed by
`learning.id`. If no route is configured, write nothing — `learning_vec` having no row for a given learning
is the normal state, not an error.

**2. On `Query`, if a route is configured and the caller asked for similarity ranking**, re-order the
tag-filtered result set by vector distance. **The tag filter runs first, unconditionally** — this function
never widens or bypasses it; a learning the tag filter excluded is never reachable through embedding
similarity.

**3. Nothing here is reachable from, or reaches into, `internal/policy` or any dispatch path.** A13's
guarantee, asserted structurally (the same AST/import-boundary discipline S30's T6 used for its own
dispatch-boundary test).

## Validation

- [x] `TestNoRouteReturnsUnrankedSet` — with no route configured the query returns the tag-filtered set in

## Notes (2026-10-30, corrected 2026-10-31)

**Correction (2026-10-31).** The 2026-10-30 Notes made two false claims, both now fixed:

1. **"On `Append`, a configured route writes a `learning_vec` row."** False. `Append` writes the
   `learning` row and never touches `learning_vec`. Embedding is a separate pass — `EmbedPending`
   (`embed.go`) — that fills `learning_vec` for the learnings it has not embedded yet, idempotently.
   It is surfaced as a door, not folded into `Append`: the socket method `learnings.embed` and the CLI
   verb `aeon learnings embed` both call the one `EmbedPending(scope, scopeKey)` (P34 — the analogue of
   `retrieval.reindex`). A learning with no route configured has no `learning_vec` row, and that is the
   normal state (D5), not an error.
2. **The 2026-10-30 Notes cited three gate tests that did not exist** (`TestEmbeddingRanksWithinTagFilterNeverWidensIt`,
   `TestNoEmbeddingRouteLeavesLearningVecEmpty`, and a `TestEmbeddingNeverChoosesDispatch` that was
   only ever a promise in this file). The frontmatter `gate_test` and the Validation list above are
   corrected to the tests that actually exist.

**What actually exists, and is green (2026-10-31).** `embed.go` ranks within the tag-filtered set and
never widens or bypasses it (A13's dispatch-stays-closed rule, restated for this slice's own
embeddings). `EmbedPending` is the pass that fills `learning_vec`; with no route configured it refuses
(a named answer, not a zero) and `Query` returns the tag-filtered set in store order, unranked (D5).
On `Query`, a configured route re-orders the tag-filtered set by vector distance when the caller asked
for similarity ranking — the tag filter runs first, unconditionally, so a learning the tag filter
excluded is never reachable through embedding similarity (D6).

**The route is now wired (2026-10-31).** `initLearnings` (`internal/daemon/learnings_dispatch.go`)
resolves the embedding route exactly the way `cmd/aeon/retrieval_link.go` does — `tools.EmbedRoute`
over the same `protocol.Routes` — and calls `SetRoute(route, ModelClientEmbedder{…})`. With a route the
set ranks; without one the store stays `route == nil` and the set stands unranked (D5). The one
production caller is pinned by `TestLearningsEmbeddingHasExactlyOneProductionCaller` (the graph's
`SetGraphService` precedent).

**A13 is now structural (2026-10-31).** `TestEmbeddingNeverChoosesDispatch` (`dispatch_boundary_test.go`)
walks the module and asserts `internal/policy` and `internal/learnings` never import each other — the
import-boundary proof that an embedding (a ranking) can never reach the dispatch gate, the A13
guarantee the 2026-10-30 Notes only promised.
