# T8 · Budget doors: `budget.*`, `spend.report`, `loop.raise`, epic adoption, guards

**Prefix:** LC · **Shape:** P4 · **Rules:** LC5, LC8, LC12–LC14, LC20 · P34 · **Depends on:** T5, T7.

## Goal

Budgets are managed and read through the daemon: list-with-details, set/remove, effective-for-a-loop, spend over time, and the raise door; the epic's budget is written through the budget table with no second truth; every authority-changing method is human-door and guarded.

## Methods (all `RequiresInitialize`, none `Debug`)

| Method | Class | Params → result |
| --- | --- | --- |
| `budget.list` | read | `{scope?, subjectId?, enabled?, status?}` → `{budgets: BudgetView[]}`; `BudgetView` = row + `status: ok\|warn\|hit` + per-dimension `{cap, spendFloor, exact, unknownCount}` + `lastChangedBy/At` (list-with-details, rule 3) |
| `budget.show` | read | `{id}` → view + spend breakdown + applicable open loops + history (`budget_event`) + **worst-case overshoot note** (priced route: `maxOutputTokens × outputPrice` + input; unpriced: "not bounded in USD — set a tokens cap") |
| `budget.effective` | read | `{loopId \| rootId \| componentId}` → every budget that applies, tightest first |
| `spend.report` | read | `{groupBy: day\|trigger\|component\|epic\|route, since?, until?, rootId?}` → buckets (floor, exact, partial/unknown counts, tokens, steps) |
| `budget.set` | human door | `{scope, subjectId, window, usdCap?, tokensCap?, wallMsCap?, stepsCap?, unknownPolicy?, warnPct?, enabled?}` → `BudgetView` (create or update by the unique key; `dryRun?` returns the effect) |
| `budget.remove` | human door | `{id, confirm: <the daemon's statement digest>}` → `{removed}` (the digest of the statement the UI shows — P7 `useConfirm` shape) |
| `loop.raise` | human door | `{id, budgetId?, usdCap?, tokensCap?, wallMsCap?, stepsCap?, reason}` → `{loopId, raised:{budgetId, dimension, from, to}, resumed:bool, status}` |
| `budget.vocabulary` | read | scopes, windows, dimensions, unknown policies, refusal kinds — the closed sets for forms and the CLI (rule 4) |

Refusals ride `ErrBudgetRefused` (T0's block) with `data.kind`.

### Deviations from the task spec

- **Epic adoption took the spec's safe default (LC13).** The records person door
  refuses `epic_create`/`epic_update` entirely (`daemon/records.go`,
  `personDoorRefusal` — the catalog cannot distinguish the two doors), and the
  `budget_usd` param is dropped from the agent-facing epic decodes: the strict
  decode now refuses it as an unknown field (`refused: json: unknown field
  "budget_usd" — …`), so a model-typed figure dies before the store. Epic budgets
  are set only through `budget.set`, and `store/epics.go`'s `Epic.BudgetUSD` is
  DERIVED (`epicBudgetUSD(epicID)` = the epic's lifetime budget row's USD) — the
  column is no longer read or written (the grep test holds it).
- **T1 goldens row is N/A.** T1 is Partial (no epic-byte golden exists); the view
  bytes are preserved by the unchanged JSON tags, which `TestEpicRoundTrip` covers.
- **`TestEpicRoundTrip` fixed** (pre-existing breakage surfaced by the T8 epic
  work): it assumed the budget id `bud-<epicID>`; the store mints its own ids, so
  the test now captures the id the create returns.
- **`TestSpendReportBuckets`'s route-grain step total is 4, not 3.** The spec's
  "totals equal" holds for the floor (17) and the unknown count (1) at every
  grain; the step count is grain-structural — `COUNT(DISTINCT s.id)` per bucket, so
  a step crossing two routes is counted in each (r1=2, r2=1, r3=1). Step-grain
  groupings sum to 3; the test now asserts the grain's own total and names the
  reason.
- **The raise's `reason` now rides `ControlEvent.Reason` (production bug, found
  and fixed this task).** The T7 seam stuffed the person's text into the closed-key
  detail map (`detail["reason"]`), which the store's LC10 closed set refuses — a
  raise with any non-empty reason failed with `control event detail key "reason"
  is not in the closed set` (latent: T7's tests never passed a non-empty reason
  end to end). The fix does NOT widen the closed set (person text never rides
  detail): `RaiseLoopToRunning`/`RaiseLoopToWaiting` gained a `reason string`
  param that lands in the event's own person-authored column, and the daemon passes
  it there. `TestRaiseEndToEnd/in-step` (reason `"room to finish"`) is the guard.
- **The param-shape refusals are `protocol.ErrBadParams` values, not `*protocol.Error`.**
  The -32602 rejections (smuggled `actor`, missing `reason`, two caps, missing
  budget id) arrive as JSON-RPC's own bad-params (`Error()` = `"invalid params:
  <msg>"`, no `Data`); the door tests assert them through the string
  (`badParamsOf`), and the Aeon-coded refusals (confirm-required/mismatch,
  wrong-budget/dimension) through `budgetErrorOf` as before.
- **Six budget-plane exports were missing from the store's surface table** (two from
  T7 — `FindBudget`, `OpenLoopsForBudget`, `ApplicableBudgets(For)Ordered` — two
  from T8 — `ListBudgetEvents`, `SpendReport`): `TestEveryExportedMethodIsNamedInTheSurfaceTable`
  caught them on the first full store-suite run (T7's validation had never run the
  unfiltered store suite). Named with their consumers in the S55 budget block of
  `store.go`'s table.

### Findings recorded, not fixed (pre-existing)

- **The loop arm's component tier matches no ID-subject budget.** T6's
  `loopSubjectTiers` exposes the component tier with subject = `loop.ComponentRoot`
  (a PATH) and the root tier via `RootOf(path)` → `ErrNotFound` → empty, so a
  component-scope budget (subject = component ID) is reachable from a loop only
  through `budget.effective`'s `{componentId}`/`{rootId}` arms, not through the
  loop's tier walk. T6.md lines 51 + 62 carry the evidence. Enforcement therefore
  cannot fire a component-scope cap for a loop until the tier walk learns
  path→ID resolution; named here because T8's effective door makes the
  asymmetry visible (the read arm finds it, the gate does not).
- **The latent `loop.answer` kick window.** A loop parked `waiting/cap-hit` that a
  person resumes through `loop.answer` (the question door) re-runs the parked step
  WITHOUT re-checking the budget at the step's boundary — the same shape T7
  admitted for `ResumeLoop`. Out of T8's scope; recorded so T9's watchdog (or a
  later task) can decide whether the answer door needs the same admission logic.
