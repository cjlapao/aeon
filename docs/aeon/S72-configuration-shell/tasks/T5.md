# T5 · The shell stays live while a page works (async + the six-second page)

**Rules:** the operator's request, 2026-11-06, quoted below. **Depends on:** T4 (whose walk opened F-3).
**Not in the original brief** — added to SLICES.md as its own task because it spans three planes
(the seed engine, the Rust shell, the web layer) and carries its own measurements.

## The request

> "we need to make all operations async for the UI, for example policy, the page does say loading but
> the app is locked and I cannot do anything, so we need to add the loading to the menu item, use the
> loader component from the UI kit and make it all async so the UI can work and people can move to
> other pages if they way. Also we need to check why some pages like the policy takes almost 20
> seconds to load, there is not that much data there"

Two asks, three real causes. The 20 s was never one thing: it was a slow daemon read **and** a frozen
window **and** a page asking for more than it renders. Fixing only one would have left the complaint
standing.

The follow-up ask, same day, recorded because it widened the task's scope on purpose:

> "lets make sure everything we do in rust is async. probably doing like same as an rest api calls? sop
> everything we add can always be async. is this possible?"

That turned "make the one slow command async" into "make the whole command surface async, and keep it
that way". Answered, done, and guarded under [Same-day follow-up](#same-day-follow-up-every-command-in-the-shell-is-async-asked-answered-enforced).

## What was actually wrong

**1 · The lock is Rust, not the page.** `#[tauri::command] fn rpc_call(...)` in `src-tauri/src/main.rs`
was synchronous, and a synchronous Tauri command runs on the **main thread** — the thread that paints
the window and dispatches clicks. `Session::call` then parks that thread on `rx.recv_timeout(CALL_TIMEOUT)`,
where `CALL_TIMEOUT` is 300 s. So the window did not "feel slow"; it stopped existing as an event sink for
the duration of one daemon call, and no spinner anywhere could be seen because nothing repaints. Proof the
daemon was never the locker: while a 6 s `seed.status` was in flight on one connection, a second
connection answered `policy.list` in **0 ms**.

**2 · The six seconds is the seed engine reading its own source once per record.** `Set.Records` is a
function, and `seed.go` says out loud that it is *not cached*. For `agents.firstParty` the source parses
every embedded body and canonicalises every record — measured on this host at **69.1 ms** per call for 33
records (`EmbeddedDefinition` alone is 1.86 ms, 33 of them), and **8.3 ms** per call for `tools.core`'s 137
records. The engine resolved keys per record by re-calling it: `statusOne` called `recordVersion(s, key)`
per decision, `applyDecision` called `recordFor(s, key)` per write, and `Plan`'s retire pass called
`recordByKey(set, key)` per ledger row. So one status read cost **N+3 full source rebuilds** — 35 × 69 ms
for the agents set, ~139 × 8.3 ms for the catalog. That is the whole 6 s; the sets whose source is a
static slice cost 20 ms for more records.

**3 · The Policy page asked for the whole registry.** `PolicySection.tsx` called `seed.status {set:""}`
(all fifteen sets) and then kept one set out of the answer — `policy.corpus`, which alone costs **0.02 s**.

## What landed

**Go — one read of a set's source, indexed (`internal/seed/`).**
- `snapshot.go` (new, 80 lines): `setSnapshot`, one read of the source indexed by key, with `version`,
  `record`, `lookup`, `id`. Its comment carries the measured costs, so the next reader inherits the fact.
- `engine.go` (618 lines): `statusOne`, `Plan`, `Apply`/`applyDecision`/`applySkip` and `Restore` all take
  one snapshot per operation; `readLive` walks the snapshot; the per-record `recordVersion`/`recordFor`
  scans are **deleted**, not left behind for someone to reach for again.
- `plan.go` (331 lines): `Plan` keeps its signature and now delegates to `planRecords(records, …)`; the
  retire loop tests an index built from the slice it was handed. `PlanRestore` keeps its signature and
  delegates to `planRestoreRecord` for the same reason.
- `snapshot_test.go` (178 lines): **the guard that keeps this from coming back.** A counting source proves
  `Status` (single set and all sets), `Plan`, `Apply`, a no-change re-`Apply` and `Restore` each read the
  source **exactly once** for a 12-record set — invisible to the correctness tests, because every read
  returns the same records.

**Rust — nothing on the window's thread (`ui/src-tauri/`).**
- `session.rs` (741 lines): `SessionHandle` — the calling half of a session, `Clone + Send + 'static`
  (`next_id` became an `Arc<AtomicU64>` so two handles cannot mint the same id). `Session::call` delegates
  to it; `connect`'s handshake still uses the private `call_raw`; the `initialize` refusal still stands on
  both public paths.
- `main.rs` (428 lines): `connect`, `rpc_call`, `disconnect`, `workspace_add`, `workspace_remove`,
  `workspace_select` and `component_files`' `component_list`/`component_read` are `async fn`, and **every**
  blocking step — the socket, the disk, *and* the `std::sync::Mutex` waits — sits inside
  `tauri::async_runtime::spawn_blocking`. `AppState.session`/`workspaces` became `Arc<Mutex<…>>` for that.
  `connect` holds the session slot across the whole connect: retiring-then-opening was two steps that the
  old command boundary made atomic for free, and now the lock is what makes it atomic.
  `endpoint_path`, `background_presence`, `workspace_list`, `workspace_active` stay synchronous on purpose
  — they read memory, and two of them run on every render.
- A call no longer holds the session mutex, so one slow method no longer queues every other caller behind
  it; `Session::drop` still retires the reader, and a handle that outlives its session finds `state` closed
  and says so (the reader resolves pending calls on exit).

**Web — the row the user clicked says what its page is waiting for (`ui/src/`).**
- `lib/pageWait.ts` (97 lines, new): a page declares an owner id; anything inside it that waits takes a
  ticket against that id and releases it when it settles. Release is a closure, not a counter the caller
  decrements, because the page that started a call is often not the page on screen when it lands.
- `useRpcQuery` takes a ticket per call (`context`, not a value set from an effect — a child's effects run
  before its parent's, so an effect would have missed the first fetch entirely).
- `lazyConfigRender.ts` (46 lines): the Suspense fallback is now the kit's `Spinner` ("Opening…") and takes
  a **chunk** ticket while it is up.
- `ConfigScreen.tsx`: `ConfigPageBody` declares the owner as `config:<page id>` — which *is* the menu row's
  slug, so the page reports into the row the user clicked without either side importing the other.
- `PageLayout.tsx`: the config row gets `loading: <that page has waits>`. That is the kit's own
  work-in-progress state — its loader takes the icon's place (in the rail too) and the link carries
  `aria-busy`. The kit's loader, not an invented one.
- `PolicySection.tsx`: `{ set: POLICY_CORPUS_SET }` instead of `{ set: "" }`.

## Same-day follow-up: every command in the shell is async (asked, answered, enforced)

The ask was "make sure everything we do in Rust is async — like a REST call — so everything we add can
always be async. Is this possible?" **Yes, and it is now the rule, enforced by a test rather than by
discipline.**

The asymmetry that makes the rule free: a synchronous `#[tauri::command]` runs on the **main thread**,
which is the thread that paints the window and dispatches every click — so its body *is* the window's
availability. An `async fn` command runs on `tauri::async_runtime`. Meanwhile the web layer **already
`await`s every command** (`ui/src/lib/bridge.ts` hands back a Promise for each), so sync and async are the
identical call to the caller: the conversion needed **zero JS change**, and what it changes is only *who*
waits — a tokio worker, or the window.

- Landed (all in [ui/src-tauri/src/main.rs](../../../../ui/src-tauri/src/main.rs)): the last four
  synchronous commands — `endpoint_path`, `background_presence`, `workspace_list`, `workspace_active` —
  are `async fn`. Tauri's macro requires an async command taking `State` to return `Result`, so they
  return `Result<_, String>` whose `Err` arm they never take; that is the required shape, not a failure
  claimed. Being memory-only reads, they answer **directly in the async body** — no `spawn_blocking`,
  because there is nothing there that can block, and putting a `Vec` clone on a worker thread would cost
  a thread handoff to save nothing.
- **Zero JS changes**, verified rather than assumed: the three callers (`endpointPath`, `workspaceList`,
  `workspaceActive`) already `await` through `invokeShell`, and `endpointPath`'s `catch` now has a real
  rejection path where before it only caught a missing command.
- The rule is written where it cannot be missed: the header of `main.rs`, which is also the file every
  new command has to be edited in anyway (`generate_handler![]`). It names the two mechanical
  consequences — async + `State` ⇒ must return `Result`; anything that truly blocks goes inside
  `tauri::async_runtime::spawn_blocking`, and only that.
- Enforced by `aeon/ui/src-tauri/tests/command_threading.rs` (237 lines, 4 tests). It **walks `src/`**
  instead of naming files, so a command added in a file that does not exist yet is judged the day it is
  written; the second test asserts the scan sees **exactly** the `generate_handler![]` set, so the check
  cannot quietly go blind. Both have teeth: a planted `fn a_canary_that_freezes_the_window` fails both,
  and the failure message says what to do about it (the canary file was removed; `src/` holds the nine
  files it held before).
- 13 commands, 13 async. The shell's two raw threads are **not** commands and stay as they are: the
  socket reader (`session.rs`) and the 60 s tray poller (`background_tray.rs`) each own a thread already,
  which is exactly what "off the main thread" meant before there was an async runtime to borrow.

**Two more freezes, found by following the rule past the command surface — and fixed here.** Making all
thirteen commands async did not, on its own, free the window: the main thread appears in places that are
not commands and have no async form to be moved to, and both of them were waiting on a lock a worker holds
for as long as the daemon takes.

- **The close handler froze the app.** `on_window_event` ran `state.session.lock()` to answer
  `close_policy`'s "is there a live session?" — and `connect` holds that very mutex across a whole connect,
  seconds of kernel waiting when the workspace points at a host that is not answering. So: every command
  async, and one click on the X still froze the window for the length of a connect. Fixed with a
  `session_live: Arc<AtomicBool>` mirror, written by the only two places the slot changes (`connect`,
  `disconnect`) and read by the handler. The answer is the same one the lock would have returned once it
  unblocked — the flag is false for exactly the seconds the slot was empty — minus the wait.
  `background::close_policy` itself is untouched and still pure, and its four tests still pass unchanged.
- **The tray poller held the session slot across a daemon call.** `refresh_tray` called `inbox_count()`
  — which waits up to `CALL_TIMEOUT` — *while holding* the slot's mutex, so a daemon that stopped draining
  turned that mutex into a barrier every `connect`, `disconnect` and `rpc_call` queued behind. Worse in
  combination with the bullet above: the main thread waiting on that mutex, plus an async command's
  `set_icon` waiting on the event loop, is a hang until the call times out. Fixed by cloning a
  `SessionHandle` out inside the lock and putting the guard down before the call — the handle is the type
  built to be held across a wait, a mutex guard is not — which meant moving `inbox_count` onto
  `SessionHandle` where its reason for living is stated.
- Both are guarded, and both guards were **canaried** (the old line put back, the test seen to fail, the
  file restored): `the_main_thread_event_handlers_wait_on_nothing_a_worker_holds` allows exactly one lock
  in that handler — the one-slot tray poke, which cannot block — and
  `no_lock_is_held_across_a_call_to_the_daemon` refuses a count asked for inside the lock's scope.
- Cost of the second fix, recorded honestly: `Session::call` became dead inside the binary (the shell now
  always goes through a handle), so it carries an `#[allow(dead_code)]` naming the three test files that
  still speak through a whole `Session`. The warning count is back to the three it was at base.

**What was considered and declined, with the reason:** moving the *transport* to real async I/O
(`tokio::net::UnixStream` in place of the blocking std socket plus reader thread). That is the half of
"like a REST call" the shell does not need: a REST client's blocking read costs you a thread from a pool
of many, while this is **one** long-lived duplex socket with its own reader thread and a push stream —
there is no per-call connection to make concurrent, and the JSON-RPC id/correlation layer would still sit
on top. It would add a direct `tokio` dependency to a `Cargo.toml` that does not have one, rewrite
`Drop`/shutdown semantics that three test files currently pin (`liveness.rs`, `live_stream.rs`,
`remote_transport.rs`), and change nothing a person can feel. The command boundary is where the window
lives, and that boundary is now fully async.

## Out of frame, said plainly

The **desktop window was never run here** (no webkit runtime, the S49/S58/S59 named gap). The Rust half is
therefore proven by construction and `cargo check --all-targets`, not by clicking a real window: the walk
harness stubs the shell with an async bridge, so it cannot even reproduce the freeze it is fixing. What the
browser can and did show — the row's loader, the 324 ms load, navigation landing mid-flight — is recorded
above; the freeze's removal is a code fact (sync command → `spawn_blocking`), pending a desktop run. The
same-day sweep adds one stronger fact and no less caveat: the shell's Rust suite has now been **run**
(rc=0, 55 passed), and a guard file now refuses any command that would put work back on the main thread
and any main-thread handler that waits on a lock a worker holds —
but neither is a window being clicked, which is still the missing evidence.

## Follow-ups opened / closed

- **F-3 closed** (T4's table): `seed.status` answers in 140 ms cold, not ~6 s.
- **New, F-6**: `handler.EmbeddedDefinition` parses an embedded body on every call (1.86 ms each, no
  cache). The engine no longer multiplies that cost, but every other caller still pays it — `Source()` is
  still ~69 ms for the agents set, and that is most of the remaining 140 ms of the whole-registry status.
  A memoised definition loader (with the copy-on-return discipline `Lookup` already uses) would take the
  whole-registry status toward ~20 ms. Deliberately not done here: it touches the handler guards, which is
  a different slice's argument to have.
- F-1, F-2, F-4, F-5 from T4 are untouched by this task and still open.
- **New, F-7 — `CALL_TIMEOUT` is 300 s, and it was chosen for the old failure mode.** A call now parks a
  thread from tokio's blocking pool (finite, default 512) for up to five minutes while a wedged daemon
  thinks, and the web layer has no timeout of its own, so a page can show a spinner for five minutes with
  nothing to say about why. That is strictly better than a frozen window, which is what the same number
  used to cost — but the number was set when "slow" meant "the app is a picture", and now that the window
  stays live the honest companion is a shorter bound plus a sentence the page can render. Out of frame
  here because changing it changes what a person sees on a wedged daemon, which is S58's supervision
  argument to have, not this one's.
- **New, F-8 — the one main-thread site that is not a command:** `setup` runs synchronously before the
  event loop serves anything, and it reads the workspace store off disk and probes the endpoint
  (`endpoint::probe` is a `UnixStream::connect`, normally an instant `ECONNREFUSED`, but a store directory
  on a network mount is a slower story). Tauri's `setup` signature is sync, so the fix is moving the
  daemon-probe half onto a thread rather than making the command async; nothing measured has shown a slow
  start, so it stays a known shape rather than a guess at a number.
