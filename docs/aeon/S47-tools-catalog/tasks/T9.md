### Deviations from the spec, and why

1. **The spec named one file; there are two.** `tools_guard_test.go` reached 1242
   lines with the predicates and the canary in it. SIZE1 says a change that pushes
   a file past 1000 splits in the same change, and the split is cohesive: the
   predicates and the canaries that prove them are one concern
   (`tools_guard_predicates_test.go`, 431), the claims about the tree another
   (836). Both are `package main`, and the canary still calls the same predicate
   the guard calls.
2. **`tools.grants` is exempted by NAME from the write-shape pattern.** The spec's
   own regex admits `grant`, and S34's `tools.grants` — a READ about grants —
   matches it. The exemption lives in `s47NeighbourMethods` as one entry with its
   reason, so it is visible and countable rather than a widened pattern; the canary
   proves a new `tools.grantSomething` still lands in the newcomer branch and is
   caught. The pattern also gained the words `commit · write · seed · repair ·
   sync · clear · prune · install · uninstall` beside the spec's eleven.
3. **The walk roots are `../../internal/…`, not `internal/…`.** A `cmd/aeon` test
   runs in `cmd/aeon`, so the repository's packages are two levels up — the S46
   precedent walks `../../cmd/aeon` for the same reason. Recorded because an empty
   walk here looks exactly like a clean tree.
4. **Every walk asserts non-emptiness, and the reader walk also asserts its named
   files are PRESENT.** The spec said "do not pass on an empty walk"; a walk whose
   root is wrong passes, so the guard checks the floor (50/20/20/10/60) and the
   both-directions presence of the named reader set.
5. **The tampered row is written through the product's doors** — `SeedWithTx` +
   `(*Store).ToolUpsertTx` — not a hand-written `INSERT`. The row this guard lies to
   is a row the product writes.
6. **Guard 4 drives the seams through their exported setters**
   (`tools.SetSearchResolver`, `tools.SetGraphService`, restored by `t.Cleanup`)
   with a promoted-nil `graph.Service` stub, because the registry is what varies and
   the assertion that matters is that the combination tested is the combination
   named.
7. **Guard 5 builds its own daemon instead of reusing `parityDaemonTable`** — it
   needs the seed engine mounted and `NarrowMethods` populated, or a narrow door
   reads `unknown` and the classification check is softer than production's.
8. **Guard 6 reaches the own view by an inline type assertion** to
   `ownViewReader` (`ToolsMine`/`ToolShow`), the same method set as `daemon`'s
   `toolsViewAPI`, because `protocol.ToolsCatalog` deliberately carries only the four
   person reads. A rename that moves the own view out of reach fails the assertion
   rather than skipping.
9. **`CreateAgent`/`UpdateAgent` never write `tools` or `origin`** — measured: the
   `UPDATE agent SET` in `store/agent.go` does not name either column, and the only
   writer in this build is S43-extra's agent seed set. So every agent that did not
   arrive through the seed is `origin:'user'` with `tools:"[]"`, and SD7 ("a name on
   a custom agent's row is not a capability the app can dispatch") makes its own
   view EMPTY. A guard that planted an agent with `CreateAgent` and then asserted
   "the own view shows the held set" would have been asserting that nothing is
   shown — a passing guard testing nothing, which is the failure this task exists to
   refuse. `seatDispatchableAgent` therefore stamps `origin='system'` and an
   allow-list with the seed applier's own statement.
10. **The planted world is S46's, not a copy.** `mineWorld`, `betaMarkers`,
    `assertNoBetaBytes`, `mineCtx` and `mineSeam` are called from
    `mcp_admin_mine_test.go` in the same package, so the two families are checked
    against the same rows and the same marker list MC2 was written for.
11. **The `mcp.mine.*` set is five, not two**: `servers · status · grants ·
    proposeRemove · proposeRevoke`. Guard 6 checks the three reads; the two propose
    twins are writes and are S46's claim.

### What the tests found

- **The SD7/origin finding above** is the task's real discovery: an own-view guard
  built on `CreateAgent` would have passed forever while showing nothing.
- `daemon.New` wires the **graph service into `internal/tools`** as a side effect, so
  `graph` joins the registry once any daemon has been built in-process. That is why
  guard 7 asserts registry ⇔ seam rather than a bare name list — the conditional
  tools must be registered exactly when their seam is wired, and the attribution
  table cannot say that on its own.
- The registry measured **70 honest names**: 12 hand-written (`ask_agent bash edit
  glob grep list question read report_size todo webfetch write`) + 58 projected from
  `records.Catalog()` across 16 families; `Registry()` is 71 with the hidden alias.
  The attribution rows and their counts are now in the test as data, which is what
  "attributed, not just detected" needed.
- All **271** methods a fully wired daemon registers carry a surface classification,
  and all eight S47 doors are `read`; nothing S47 added reaches `narrow`,
  `agentsvc`, `tools` or `records` by name.
- `TestToolsGuardsHaveTeeth` caught two of its own guards being too soft while being
  written: the canary that fed `tools.update` alone also tripped the eight
  missing-door checks (fixed by feeding a complete table, so an offense can only
  come from the one thing the subtest changed), and the write-shape check accused
  `tools.grants` until the named-neighbour exemption was drawn (deviation 2).
