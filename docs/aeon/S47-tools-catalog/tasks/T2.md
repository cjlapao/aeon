# T2 · The `tool` table and the store's SQL half

**Prefix:** TC · **Rules:** TC2, TC4 (system tools only), TC7 · **Depends on:** T0 (trigger/CHECK questions, error block). Parallel-safe with T1, T6.

## Goal

Persist the **catalog entries** of system tools (not executors, not MCP tools) with SQL only in `internal/store` (I2). The table is written **only** by the seed applier (T3); everything else reads.

## Files

- `aeon/internal/store/migrations/<14-digit>_tool.sql` — **new** (timestamp from `date +%Y%m%d%H%M%S`, after the newest file; no `schema.go` edit):
  ```sql
  -- S47 T2: the tool CATALOG ENTRY as a record (design TC2). Executors and input schemas stay code — schema is stored as a read-only display copy with its SHA-256 so drift is detectable. Written only by the tools.core seed applier (origin='system'); MCP tools are NOT rows here (S46's tables are their one truth, TC4).
  CREATE TABLE tool (
    name         TEXT PRIMARY KEY CHECK (length(name) BETWEEN 1 AND 64 AND name NOT GLOB '*[^a-z0-9_]*'),
    family       TEXT NOT NULL CHECK (length(family) BETWEEN 1 AND 32),
    description  TEXT NOT NULL CHECK (length(description) BETWEEN 1 AND 4096),
    schema       TEXT NOT NULL CHECK (json_valid(schema)),
    schema_hash  TEXT NOT NULL CHECK (length(schema_hash) = 64),
    rerun_class  TEXT NOT NULL CHECK (rerun_class IN ('safe','detectable','unsafe')),
    capabilities TEXT NOT NULL CHECK (json_valid(capabilities) AND json_array_length(capabilities) >= 1),
    governed     TEXT NOT NULL DEFAULT '[]' CHECK (json_valid(governed)),
    twin         TEXT NOT NULL DEFAULT '',          -- the records socket twin, '' for core tools
    aliases      TEXT NOT NULL DEFAULT '[]' CHECK (json_valid(aliases)),
    conditional  INTEGER NOT NULL DEFAULT 0 CHECK (conditional IN (0,1)),
    notes        TEXT NOT NULL DEFAULT '' CHECK (length(notes) <= 200),
    version      INTEGER NOT NULL CHECK (version >= 1),
    origin       TEXT NOT NULL DEFAULT 'system' CHECK (origin IN ('system')),
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL
  );
  CREATE INDEX idx_tool_family ON tool (family);
  ```
  `origin` admits only `'system'` in this slice (a `CHECK` widened later by a rebuild if a user-authored tool ever exists — none can: executors are code). Rerun class has **no default** (the existing "a new tool cannot default safe" rule).
- `aeon/internal/store/tool.go` — **new**, SQL only, parameterised: `ToolRow` struct; `ToolList(ctx) ([]ToolRow, error)` (ordered by family, name); `ToolGet(ctx, name)`; `ToolUpsertTx(tx *sql.Tx, row ToolRow) error` (used **only** by the seed applier; **updates content columns, never `created_at`**); `ToolDeleteNeverExists` — **there is no delete accessor** (retirement is a ledger flag, S43-extra SD6); `ToolCount(ctx)`.
- `aeon/internal/store/tool_test.go`.

## Notes

**Built 2026-11-02.** `internal/store/migrations/20261102021407_tool.sql` (the `-- ` first line is its
`aeon db info` description; `schema.go` untouched), `internal/store/tool.go`, `internal/store/tool_test.go`.
`git status` shows those three plus the two record files; no shipped migration and no `schema.go` edit.

**One deviation, and it is T0's deviation 2 arriving in the schema.** The task's DDL sketch carried
`json_array_length(capabilities) >= 1`. T1 built the metadata honestly, and two tools — `todo` and `report_size` —
have **empty** capability sets: neither touches a store, a file, a process or a socket. That CHECK would have
made the seed refuse its own two truest rows, so the column now reads
`json_valid(capabilities) AND json_type(capabilities) = 'array'`, and the same `json_type` guard was **added** to
`governed` and `aliases` (the sketch only had `json_valid`, which admits `"tool_access"` and `{"a":"write_file"}` —
a string where an array belongs is exactly the shape a later reader cannot tell from real data). The count guard
is not lost, it moved to where it can be true: `internal/tools`' `TestEmptyCapabilitySetsAreOnlyTheDeclaredTools`
fails any tool **other than those two** arriving with an empty set, which a schema count never could. Pinned in the
other direction too — `TestToolChecksRefuseBadRows` now carries `capabilities: []` as a shape that **must insert**
(next to the `"tool_access"`-string and object-shape refusals), so nobody re-tightens it by accident.
Two CHECKs the typed write path cannot produce (`conditional` outside 0/1, `origin='user'`) are refused by **raw**
inserts in `TestToolChecksRefuseRawShapelessRows`, each beside a canary insert that must succeed — so a refusal is
the CHECK and not a typo in the statement. The migration is unshipped and exists only on this branch, which is the
only reason editing its shape is lawful at all (§3's forward-only rule).

**What `tool.go` holds.** `ToolRow` (the JSON columns stay text — this layer is SQL, the catalog package owns the
meaning), `ToolList` (`ORDER BY family, name`, so a UI list does not shuffle between refreshes), `ToolGet` (an
absent tool is `sql.ErrNoRows` — the catalog's `missing_row`, never a zero row), `ToolCount`, and
`ToolUpsertTx(tx, row)` as the **only** write: it takes the caller's transaction (nil is refused — the row and its
ledger row commit together or not at all), updates content + `updated_at`, and never `created_at`; `origin` is not
even a parameter, it is the literal `'system'` in the INSERT and a CHECK nothing else can satisfy. One `toolSelect`
constant and one `scanToolRow` serve both reads, so a column cannot be added to one and forgotten in the other. No
delete accessor exists — and `TestToolHasNoDeletePath` proves it from the package's sources (no `delete from tool`
in any non-test file, no exported `Tool*Delete|Remove|Drop` method) rather than from this sentence.

**Cross-layer pins.** `TestToolTableIsNotReadByTheRuntimeSpecPath` reads `tools/toolset.go`,
`tools/records_tools.go`, `runtime/loop.go` and `daemon/step.go` for any `store.Tool*` reference, **and** parses
`tool.go`'s imports to prove the store reaches neither `internal/tools` (it must not know what a tool *is*) nor
`internal/seed` (the hashing belongs to the domain, T3). It reads imports, not prose — the comments legitimately
name both packages, and a guard that fires on a comment is a guard somebody disables.
