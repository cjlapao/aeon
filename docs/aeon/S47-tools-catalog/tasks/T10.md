# T10 · Settings → Tools and → Surface

**Prefix:** TC · **Rules:** TC9, TC10, TC12 · P34 · standing rule 3 · **Depends on:** T5, T6, T9 and **S45 T9** (shared components: `AgentPicker`, the policy section's row link targets). Parallel-safe with T11 prep.

## Goal

A person can see **what the app can do and who may do it**: every tool with its details and capabilities, "to whom" as a per-agent matrix and as one agent's whole view, whether the catalog is current, and
the daemon's own surface with its doors — with links into policy (S45) and MCP (S46) for the places a person *acts*. **Read-only**: there is no edit control anywhere in these panels (TC1). Descriptor-driven;
no capability, family, state sentence or method summary is hardcoded. The real Settings screen — not the bench.

## Behaviour

**Tools tab.** `tools.list` with filters sent as **params** (family, source, capability, available, q — daemon-side). Row: name (+ aliases), family, source badge (`System`/`MCP`), **capability pills** (text + colour, one per capability — the vocabulary comes from the entries, never a UI list), re-run class pill, `available` vs `UNWIRED`, MCP `UNCLASSIFIED` warning chip, "catalog entry stale" chip when drift says `differs`/`missing_row`. Empty filter ⇒ the daemon's statement. **`DriftBanner`** from `tools.status`: all `current` ⇒ a quiet "catalog current (version N)"; otherwise lists `missing_row`/`retired`/`differs` with field names — a `differs` reads as "a tool changed without a catalog version bump", the daemon's text.
**Drawer** (`tools.get`): description, **schema** (pretty JSON, read-only code block), capabilities with their one-line meanings **sent by the daemon in the vocabulary data** (not UI prose), governed-by policy types, socket twin, aliases, the **per-agent matrix** (agent · state badge · reason **verbatim** · granted-by chips `default/handler/mcp-declare`; `dispatchable:false` agents shown as such with no grant state), and the **policy rows touching this tool** (id, action, source, origin badge, target, `describe` sentence) each with a **link** to the Policy section filtered to that row (`linkFor` builds the navigation from the data `{kind:"policy", id}`); an MCP tool also links to its server in the MCP section. A note, daemon-sent: "to change who can call this, add a policy rule or change the agent's tools — this view is read-only".
**By agent tab.** `AgentPicker` ⇒ `tools.byAgent`: tools grouped by state (`granted_allowed`, `granted_ask`, `granted_no_rule`, `granted_denied`, `not_granted`) with reasons verbatim; counts; a non-dispatchable (custom) agent shows the daemon's sentence instead of a table.
**Surface tab.** `surface.list` (filters daemon-side: kind, door, human-door-only, q): method, kind pill, summary, **door chips** (person · narrow:<action> · agent service · tool:<name>), a `Human door only` badge, `Debug` badge; counts by kind and door at the top. A method's detail (`surface.get`) in a drawer. An `unknown` narrow flag (seam unwired) renders as "unknown", never as "not on narrow".
**Cross-cutting.** Offline/reconnecting ⇒ last data shown (these are reads; no write controls exist); loading ⇒ the kit idiom; errors ⇒ `ErrorPanel`; no `localStorage` for catalog data; no `fetch`; no client-side filtering/sorting beyond display order; i18n parity; no new dependency.

**Deviations, each forced by a fact:**
1. **Four contract members were fixture-lossy.** `tools.list` params lacked `capability` and `surface.list` params lacked `humanDoorOnly` — those stay a cast at the call edge, the S46 T11 `ServersParamsWire` precedent (what a client may *send* does not need a fixture to prove it). `aliases` and `twin` were invisible on the *result* types because no fixture's rows carried them; those were fixed in the fixture source (`list-alias.json`, `list-twin.json`, `get-twin.json`) rather than by a cast, because a result field no fixture shows is invisible to every generated client — the fixture is the contract's source.
2. **`ErrorPanel` was unusable here**: it takes an `RpcError` object while `useRpcQuery` hands back a message string. Failures render through the kit `Alert` (intent + title + description), which is the same three-part shape and does not invent a sentence.
3. **There is no deep-link mechanism anywhere under `src/features/settings/`** (the precedents are `LoopsScreen`'s and `ComponentsScreen`'s own `useSearchParams`). `linkFor` therefore emits real hrefs carrying the daemon's own ids — `/settings?policy=<id>`, `/settings?server=<name>` — and nothing consumes them yet. A link that lands on the right screen but does not open the row is named as the gap it is; making it open is the policy and MCP sections' work, not a route this panel may invent.
4. **`tools.status` sends drift states and field names, not sentences**, so the per-state caption lives in the two catalogs under `settings.tools.drift.states.<state>` with the daemon's name and fields interpolated. That is the one sentence this section authors, in both languages, checked by name in the guard (a state with a caption in one language only would be a lie in the other). `tools.byAgent` likewise sends `dispatchable:false` with no sentence, so the non-dispatchable statement is an i18n line naming the flag.
5. **An unfiltered empty list carries no `statement`** (T5's rule: a decoration on every answer would make the sentence mean nothing), so the screen states emptiness neutrally and quotes the daemon's statement only when it sent one.
6. **No vocabulary word appears in the section source.** The source badge's colour comes from whether the entry names a `server` (data), not from comparing to a source spelling; `stateBadge`/`driftTone`/`capabilityPill`/`kindTone` are rules over the *shape* of the string the daemon sent. `spawn_process`, `network_egress`, `granted_allowed` and "agent service" appear zero times in the nine production files, which the guard asserts — and the two doccomments that quoted them were reworded, because a comment that names a state is how a state becomes load-bearing.
7. **`applyDisplayOrder` does not sort.** It keeps the daemon's (source, family, name) reading order and drops a repeated name; TC10 put filtering daemon-side, and re-ordering the catalog in a browser would put the look of it under the same wrong authority.
