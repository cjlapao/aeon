**The CLI.** `aeon loop messages <id> [--thread N] [--json]` (`cmd/aeon/loop_messages.go`, dispatched
from `cmdLoop` beside `loop message`, usage line added) is the human's terminal window onto the agents'
exchange — a READ only (MB7); the refusal and the usage both say so and point at `loop message` as the
person's door. It renders the SAID absence as its own sentence ("the loop holds no thread N — the read
said so, it did not come back empty", P31) apart from the genuinely-empty mailbox ("holds no exchange
rows: its agents have not spoken to each other — or have not yet"), and the state fold (posted ·
delivered · answered, the answered set computed from the replies' `result_of` links — the same fold the
UI does from the same fields). `--thread` negative is refused BEFORE dialling (the daemon's refusal
names the ruling too; the CLI one just saves the round trip). Flag tests in `loop_messages_test.go`
(S69's shape: flag-level, no socket): missing id names the other door, negative thread refused,
non-numeric refused, the usage names both doors.

**MB3's deferred question — DECIDED: no separate per-step ask cap on the runtime side.** An ask is one
tool call inside a turn, and turns are already bounded by the frozen manifest's `MaxIterations`
(`internal/runtime/types.go` — carried WITH the manifest so a resumed step is bounded too, the property
AT8 re-proved at recovery). A second number capping asks-per-step would be a second truth bounding the
same thing — D4's one-definition argument applied to budgets: the loop's bound is the manifest's, and
the mailbox inherits it exactly like `bash` does. The runaway that would need the cap (a model asking a
peer every iteration) is already the runaway that needs `MaxIterations`, and it dies at that number.
Recorded here rather than silently skipped; the store-side caps (thread depth, body size) shipped in T1.

**AT8 — `TestCrashMidAskRecoversOneRowNotTwo` (`agent_mailbox_test.go`): the true SIGKILL-mid-ask
Recover walk.** The exact death shape: the door has written the ask row, the process dies BEFORE the
suspension is recorded — step row still RUNNING, no checkpoint. A NEW daemon over the same store (the
old process's memory gone) walks the real `d.Recover` door a `serve` start walks: the step classifies
Case B ("no assistant turn was committed"), the model call is RE-ISSUED through the runtime loop with

call reaches the loop's mailbox arm BEHIND THE GATE (the first daemon-side ask through the loop;
