# T4 — materialization

## Why this exists

`design.md`'s R4: the one decision this slice made that wasn't a direct answer to a brief question, found
while designing D10's "renders S24's ordering, builds none of its own."

## Scope

**1. If the project has an `internal/queue`** (S24) in use — detected the way any caller checks (a query,
not a project-level flag this task invents) — **`Append` the item's materialization payload** (the same
`LoopStartParams`-shaped fields T1's `roadmap_item` already carries: effectively a `blueprint`/`goal`
derived from the item's brief/plan) to the queue, letting S24's own ordering and `queueAdvance` gate decide
when it actually starts.

**2. If the project has no queue in use**, call `loop.start` directly — the same existing entry point, no
second mechanism.

**3. Either branch transitions the item `ready → running`** and records the resulting `loop_slug` once the
loop exists (immediately for the direct-start branch; once S24 actually materializes the queue item for the
queue branch — the item may sit `running`-queued-but-not-yet-started briefly, which is honest: D6 already
established the item's status is its own field, not derived from the loop).

## Validation

- [x] `TestMaterializePrefersExistingQueue` — a project with an active queue routes through
      `internal/queue.Append`, never a direct `loop.start`
- [x] `TestMaterializeFallsBackToDirectLoopStart` — a project with no queue calls `loop.start` directly
- [x] `TestOneMaterializationPathEitherBranch` — the resulting `LoopStartParams` are identical regardless of
      which branch ran, diffed in the test

## Notes (2026-10-29)

**What exists.** `roadmapMaterialize` in `aeon/internal/daemon/roadmap_dispatch.go`: the
claimed-FROM claim `ready → running` FIRST (the single serialization point), then the project's
own rows decide the branch — `ListQueueItems(componentRoot)` > 0 means S24 is in use and the
materialization is a `queue.Append` carrying the durable `with` link (CG4: appending starts
nothing; the item sits honestly `running`-queued, loop pointer absent, until S24 starts it — D6's
own words); zero rows means a plain `StartBlueprintLoop` (slug `roadmap-item-<id>`, same link),
and the pointer records on success. `handleRoadmapTerminal` records the queue branch's loop when
S24's loop finishes (the row's `with_json` link names the item) and lands `done` from any stamped
materialization's `loop.finished(done)`; `blocked` speaks and touches nothing.

**Deviations, each with its reason.**
1. **D4's re-check lives in the dispatch, not only the door:** the door's `IsReady` gate rides
   `→ ready` transitions, so materialization re-decides it explicitly from the row AS READ NOW —
   a priority pulled back to `unknown` after `ready` refuses at the attempt (test-proven), naming
   which condition. The check-then-claim window (priority pulled between Show and claim) is the
   same accepted residual S24 documents for its own claim.
2. The queue probe is exactly the spec's "a query, not a project-level flag":
   `CountRoadmapItems`-style read of the project's OWN queue rows.
3. A `running` item WITHOUT a loop is the retry path (the claim landed, the start died): re-enter
   the branch; the deterministic slug makes it single-winner, and on the queue branch the link row
   answers a second dispatch with `already queued`. `running` WITH a loop refuses — the loop is the
   truth now (D6).
4. The direct branch's pointer failure after a successful start is a LOUD log (D11, queue's own
   rule: the loop exists, the loop is the truth) — never a rollback.
5. `TestOneMaterializationPathEitherBranch` diffs `Blueprint · Goal · WorkspaceRoot · Tech · With ·
   Attended` between the direct call and the queue row's passage through `advanceNext` into the
   SAME door. `Slug` is excluded and documented: the queue branch deliberately lets loop.start
   generate, as S24 does everywhere.
