# T4 · The start path: `resolveAutonomy` and the pin

**Prefix:** AL · **Rules:** AL6, AL7, AL8, AL14 · **Depends on:** T2, T3. Parallel-safe with T5.

## Goal

Schedule, webhook, event and (when S27 lands) scheduler starts consult the root's grants **once, at pin time**, through **one function in one file**, and the result enters the start door
only through the internal `startExtras` — never through `protocol.LoopStartParams`. With no grants (or no applicable grant) the loop is pinned exactly as today and **no** pin row is written.

## Files

- `aeon/internal/daemon/autonomy_start.go` — **new**; the only file that calls `store` grant reads for a start:
  - `func (d *Daemon) resolveAutonomy(ctx, origin autonomy.Origin, componentRoot string, labels []string) (*store.AutonomyPin, error)`:
    1. component for the root path (`ComponentForRoot`), then the **root component** (`RootOf`, S44-extra); an archived component is not this function's refusal (`startLoopWith` already refuses work on archived roots);
    2. read active grants for the root and the component (allows and denies), `AutonomyRev(root)`;
    3. `autonomy.Plan` with the origin and labels; `PinFrom(plan)`;
    4. **no applicable allow ⇒ return `nil, nil`** (no row; byte-identical to today);
    5. any store error ⇒ **return the error** and the start **refuses** with a typed sentence ("the autonomy policy for X could not be read: …"). A start that silently proceeded without the pin would be *less* permissive than the policy intended, but it would also
       hide a broken store from the person running a scheduler; refusing is the honest answer and costs nothing (the next tick retries). T0 records which error types the store can return here.
  - `startExtras` gains `Autonomy *store.AutonomyPin` (internal struct; comment: *never on the wire*).
- `aeon/internal/daemon/start_loop.go` — `startLoopWith` passes `x.Autonomy` into `store.NewLoop{AutonomyPin: x.Autonomy}` (one added field; **no other edit**). `AllowOutward: p.AllowOutward` is untouched.
- `aeon/internal/daemon/trigger_fire.go` / `event_fire.go` — each calls `d.resolveAutonomy(...)` and passes the result in its `startExtras`. **The `attended := false` lines and the absence of `AllowOutward:` are not touched.** For the schedule/webhook path (which currently calls
  `d.Table.StartBlueprintLoop(ctx, params)` and has no `startExtras`): T0 item 4/5 records how that call reaches `startLoopWith`; the minimal change is to route it through `startLoopWith(ctx, p, startExtras{StartedBy:…, TriggerID:…, Autonomy: pin})` — **characterize first** (T1's pin goldens must stay byte-identical), then change.
- `aeon/internal/daemon/autonomy_origin.go` — **new**: the closed `origin` constants used by callers; `scheduler` is reserved for S27 and has **no caller** in this slice (a test asserts the constant exists and that S27's call site is the only expected user).
- **Not touched, by design:** `internal/narrow/*`, `daemon/queue_reactor.go`, `daemon/roadmap_dispatch.go`, `protocol/blueprint_loop.go` (`LoopStartParams` gains **no** field).

## Behaviour (each a test)

1. A schedule-fired loop on a root with `allow forge.openPR` gets a pin row: `origin=schedule`, `allowed=[{grant, subject: forge.openPR, conditions}]`, `rev` = the root's `AutonomyRev`; `loop.attended = 0`, **`loop.allow_outward = 0`** (the legacy flag never flips — AL8).
2. The same for webhook and event origins; `StartedBy`/`TriggerID` unchanged.
3. A grant on `outward` is **expanded at pin time to the current outward action names** in `allowed` (so the snapshot is self-describing).
4. A grant whose `labels` do not intersect the start's labels is absent from `allowed`; with no labels supplied (all three origins today) a labelled grant never applies.
5. A grant added **after** the pin is not in the snapshot (proved in T5's end-to-end; here: re-reading the pin after a new grant is byte-identical).
6. A root with only denies (vetoes) ⇒ **no pin row** (nothing to pin; vetoes are live, AL3).
7. A child component's loop resolves the **root's** allows and both levels' denies.
8. Person `loop.start`, the narrow trigger, queue and roadmap starts never call `resolveAutonomy` (assert by call-count spy) and pin exactly as T1's goldens.
9. `resolveAutonomy` is called from exactly the origin sites (grep test: the identifier appears in `autonomy_start.go`, `trigger_fire.go`, `event_fire.go` and tests only).

## Definition of done

- [ ] One resolution function, one file; result enters only via `startExtras`; legacy flag stays 0; no grants ⇒ byte-identical.
- [ ] Narrow/person/queue/roadmap starts untouched; `LoopStartParams` unchanged.

## Do NOT

- Do not set `AllowOutward` or `Attended` anywhere but where they are set today. Do not add a field to `LoopStartParams`. Do not call `resolveAutonomy` from the narrow package or a person-facing door.
- Do not fall back silently on a policy read error. Do not infer origin from the transport.

**What exists.** `daemon/autonomy_start.go` (new) holds the one resolution function
`resolveAutonomy` + the `grantsToAutonomy` bridge + `pinEntry`/`parseStoreTime`;
`daemon/autonomy_origin.go` (new) the closed `origin` constants (`scheduler`

origin sites `trigger_fire.go` / `event_fire.go` each call `d.resolveAutonomy`
and pass the result in `startExtras{Autonomy: pin}`; `start_loop.go` passes
`x.Autonomy` into `store.NewLoop{AutonomyPin: x.Autonomy}`. The schedule/webhook
path (which previously called `d.Table.StartBlueprintLoop`) is routed through
`startLoopWith(ctx, p, startExtras{…})`; `start_loop_test.go`'s
`TestStartFromTriggerIsUntouched` is superseded by
`TestStartFromTriggerCarriesTheAutonomyConsultation` — T4 legitimately edits
`trigger_fire.go` to route through `startLoopWith`, so the old grep-guard is the
right inverse now (it pins the new wiring).

**Deviation — `ErrNotFound` is a no-grant, not a refusal (AL8, T0 item 5).**
`resolveAutonomy` treats `ComponentForRoot`/`RootOf` returning `store.ErrNotFound`
as *no component → no root → no grants → no pin → byte-identical* (returns
`nil, nil`); only a genuine, non-`ErrNotFound` read failure refuses with the
typed sentence. A workspace that registers no component has nothing to pin, so
folding its `ErrNotFound` into the refusal path (the spec's literal "any store
error ⇒ refuse") would have refused every fire in a non-component / temp-dir
workspace — the root cause of the 12 fire-test regressions seen before this fix.
The spec's "no applicable allow ⇒ no pin row, byte-identical to today" (T4 line 17)
is what the `ErrNotFound` branch honours; the refusal is kept for a *broken* read.

**Deviation — `ReadAutonomyPin` added to the store.** The behaviour tests assert
the pin's `origin`, `labels` and full `allowed`; the existing `PinnedLoop`/
`AutonomyLive` reads do not return those, so a read-only
`(*store.Store).ReadAutonomyPin(loopID) (*AutonomyPin, bool, error)` was added
(returns `(nil, false, nil)` when no pin row exists — the no-grant case). It is
read-only and touches no pin mutation (AL6/AL8 unchanged).

**`TestUnreadablePolicyRefusesTheStart` (behaviour 5) induced without a closed
store.** A closed store nils the reader (`Store.Close` sets `s.r = nil`) and the
fire's `ComponentForRoot` panics (nil deref) rather than refusing. The failure is
instead induced the way the code itself frames it — a grant whose `conditions`
pass the `json_valid` CHECK but cannot unmarshal into the typed `Conditions`
(`labels` a string, not `[]string`): `grantsToAutonomy`'s own comment is "an
unparseable value is the store could not be read, never a no-value," so the start
refuses with the typed sentence **before the start door** and the store stays
open, so `ListLoops` confirms no loop row (no half-write).

**Pre-existing `-race` panic (not a T4 regression).** The P10 `-race` runner
occasionally panics on the runner-outlives-store nil `*sql.DB` in
`GetLoop`→`viewLoop`→`publishLoop` (in `TestSecondFireNowWhileTheLoopRunsIsSkippedAndRecorded`);
the baseline (T3, T4 changes stashed) panics identically under `-race`, and a
`-race` re-run passed (exit 0) — flaky. **The no-race run is the deterministic
gate and is green.**
