# T10 · Descriptors, the effective-view contract and the UI specification

**Prefix:** AL · **Shape:** P7 (the daemon-side half and the specification; **no `ui/` code**) · **Rules:** AL14, AL15 · standing rules 3 and 4 · **Depends on:** T7. Parallel-safe with T8, T9.

## Goal

Everything a Settings panel needs from the daemon is present, complete and tested **before** anyone builds the panel, and the panel is specified precisely enough that its builder makes no product decision. This slice builds **no UI**; the next piece of UI work (the component-tree UI is the first on the list) consumes this.

## Files

- `aeon/internal/autonomy/vocabulary.go` (T2) — completed here with the **descriptor completeness** the UI needs: per subject `{kind, name, class, label (a plain-English noun phrase, e.g. "open a pull request"), requiresExpiry, forcedConditions[], covers[] (for `outward`: the expanded names)}`; per condition `{name, type, evaluated, forced, help}` with `help` text written **in the daemon** (one sentence each); `limits`; `origins` with a sentence each ("a loop started by a schedule", …). The **panel may not contain a hard-coded subject, condition, origin or sentence.**
- `aeon/internal/protocol/autonomy.go` — `VocabularyResult` shape frozen by a conformance fixture; `GrantView.describe`, `EffectiveView.actions[].because` and `PinnedView.grants[].live.sentence` are the **only** human-readable strings the UI shows for these; a field-by-field fixture proves each is present.
- `aeon/internal/daemon/autonomy.go` — `autonomy.vocabulary`/`effective`/`pinned` filled out to the contract; a `confirmation` string on a **dry-run** of each write: `autonomy.grant {…, dryRun:true}` returns `{valid, refusal?, confirmation}` where `confirmation` is the daemon's own sentence of what the grant would allow ("This lets an unattended loop started on **X** open pull requests, up to 5 a day, until 2026-12-01, while the budget has room. It does not let it merge."), and writes nothing (no change row — dry-runs write nothing, P3). `dryRun` is a param on `grant`, `deny` and `revoke` only.
- `docs/aeon/S56-autonomy-policy/tasks/T10.md` (this file) — carries the **panel specification** below; no other doc.

## The Settings panel specification (what the later UI task builds — P7)

A tab **Autonomy** on the real Settings screen (not the bench). Everything is rendered from the descriptors above.

1. **Root picker + effective view first.** For the chosen root: the `autonomy.effective` list — one row per registry action: verdict chip (run / deny), the `because` sentence, the grant link, and each condition as a chip (met / unmet / cannot-say with its sentence). When nothing is granted the daemon's `statement` is the whole panel body: *"No autonomy is granted on this root…"*.
2. **Grants list with details:** state, subject label, `describe` sentence, root, expiry (relative + absolute), conditions, used N times (link to uses), created by (peer) and via which proposal (`proposedBy`), active/revoked, and *"N running loops are pinned under this grant"* from `autonomy.show`. Daemon-side filters (`rootId`, `state`, `includeInactive`).
3. **Forms from the vocabulary:** subject picker built from `subjects`; the merge subject shows its forced condition (disabled, on) and a required expiry field bounded by `limits.maxMergeGrantDays`; conditions rendered from `conditions[]`. **No closed set, grammar, sentence or authority text is typed in the UI**; a source grep test (in the UI task) forbids hard-coded subject/condition literals.
4. **Confirming authority:** every **grant** calls `autonomy.grant {dryRun:true}` first and shows the returned `confirmation` in `useConfirm`; declining sends nothing; accepting sends the real call. `revoke` shows the grant's `describe` and the `affectedLoops` count from a dry run. Refusals are shown **verbatim with the draft kept**; rows update **from the response**, never optimistically.
5. **Pinned loops:** from a loop's page, `autonomy.pinned` — what this loop was pinned with, which grants are still live, which actions would run now.
6. **Proposals:** agent proposals (`autonomy_revoke`/`autonomy_deny`) appear in S45's proposals desk with the daemon's `Describe`; commit/reject there. This panel only links to them.
7. **Offline:** writes disabled, reads show the last data with a stale marker; en/pt parity; no new dependency; no `localStorage` for domain data; no `fetch`; existing panels and bench pages untouched.
8. **Guard test for the later UI task:** `autonomyRpc.guard.test.ts` — every literal passed to the rpc helpers is a registered method in generated `contract.ts`, found ≥ 1 per tab (never vacuous), with a canary flagging a bogus method name (P7).

## Behaviour (each a daemon-side test now)

1. `autonomy.vocabulary` has a `label` and `help` for **every** subject/condition/origin (no empty string) — the completeness test.
2. Adding a registry action (test double) with class `outward` appears in the vocabulary, in `outward.covers`, and in `autonomy.effective` as `deny — no grant`, with **no edit** to any `autonomy` file.
3. `dryRun` for each write returns `confirmation`/`refusal` and writes **nothing**: row counts and `autonomy_change` unchanged (a spy on the store's write handle).
4. `confirmation` names: the root, each action it would cover, the expiry, each condition in words, and — for merge — the S57 rule; it states what is **not** allowed ("It does not let it merge" when merge is absent).
5. `describe`/`because`/`live.sentence` are produced by **one** formatter in `internal/autonomy/sentences.go` (grep: no other file builds these sentences; `ui/` and `cmd/` contain none).
6. The vocabulary result is **byte-identical** across calls and contains no timestamps (cacheable once per session).

## Notes

### What exists (built 2026-11-01)

- `internal/autonomy/vocabulary.go` — `SubjectLabel(name)` exported: the one accessor for a subject's plain-English phrase (AL15). The daemon's dry-run confirmations read every word through it, so a form and a sentence never disagree about what an action is called. Unknown names answer themselves (the Vocabulary fallback, unchanged). The descriptor set itself was already complete at T2; T10's work here is the completeness/stability proof (behaviours 1, 6) and the label export.
- `internal/action/grant.go` — three new exported builders, the shared source for the words the decision site and the core both speak: `VetoSentence(name, vetoID)`, `RevokedClause(grantID, at, by)`, `ExpiredClause(grantID)`. Rule 2 and `liveFailureSentence` now call them instead of inlining the templates.
- `internal/autonomy/sentences.go` — `vetoSentence`/`revokedSentence`/`expiredSentence` render through the action builders (this file calls; it never re-types a word the decision site already says); `activeSentence` moved here from `live.go` so the whole live.sentence family sits in the one-formatter file.
- `internal/daemon/autonomy.go` — the write confirmations are now two families: the WRITTEN forms are byte-identical to T6 (the conformance fixtures `grant.json`/`deny.json`/`revoke.json` pin them), and the DRY-RUN forms say what the write would do (behaviour 4): `grantDryRunConfirmation` names the root, each action it would cover in plain words (one label, or `every outward action: X and Y`), the conditions in one fixed order (maxPerDay → requireBudget → labels → requireGates → expiry, `until <RFC3339>` or `with no expiry`), and — when the covers set does not contain `forge.merge` — `It does not let it merge.` (merge is a separate decision, and the outward class never covers it, so it gets the clause too). `denyDryRunConfirmation` and `revokeDryRunConfirmation` (the latter names the pinned-loop count) round it out. Helpers `coversMerge`/`joinAnd`/`joinOr`.
- `internal/protocol/conformance/autonomy/{grant,deny,revoke}-dry-run.json` (ids 414/415/416) — the dry-run shape frozen on the wire for all three write methods: same params as their written twins with `dryRun: true`, result `{grant: null, confirmation: <the sentence>}` (revoke additionally carries `affectedLoops`). The three fixtures are what make `dryRun` and the nullable `grant` observable, and that forced the `contract.ts` regeneration (deviation 3).
- Tests: `internal/daemon/autonomy_t10_test.go` (behaviours 2–5), `internal/autonomy/vocabulary_test.go` (behaviours 1, 6), `internal/protocol/autonomy_t10_test.go` (the three field-presence proofs: `GrantView.describe`, `EffectiveView.actions[].because`, `PinnedView.grants[].live.sentence` present and non-empty on the wire).

### Deviations

1. **Behaviour 2 — no test-double action, a derivation test instead.** The registry is CLOSED (D14: no exported mutation door, asserted by `TestRegistryIsClosedAsserted`), so "add a registry action (test double)" is not literally possible. The test names no action at all: it derives every expected set from `action.Names()`/`action.Classes()` — vocabulary subjects = exactly the non-local registry names, `outward.covers` = exactly the registry's outward set (sorted equality), the effective view carries every registry action (locals run, the rest deny with the no-grant sentence), and a grep proves no production autonomy file carries a registry name as its own string literal. A hardcoded list that missed the new name is exactly what fails it.
2. **Behaviour 5 — the one formatter's home is not `sentences.go` for all families, and the test caught a real second formatter.** The spec says the one formatter is in `internal/autonomy/sentences.go`, but the T5 decision site sits in `internal/action`, which the core wraps — never the reverse (the import direction is pinned by the boundary guards). So the veto/revoked/expired words MUST be built in the lower package if they are to have one source at all. Before T10 those three templates existed as byte-identical copies in BOTH files (hand-copied at T2/T5 — the duplication `live.go`'s header acknowledged by saying "the SAME sentences"). Resolution: the shared builders live in `internal/action` (`VetoSentence`/`RevokedClause`/`ExpiredClause`), and every other file — including `sentences.go` — renders through them. The test pins each family to exactly ONE home file and asserts `ui/` and `cmd/` carry none. Recorded, not unified: the run and condition-fail deny wordings differ per view by design (`granted by %s (rev %d)` in the effective view vs `%s (rev %d) at the loop's pin` under a pin — the rev-awareness is the point).
3. **Dry-run-only wording change — but protogen DID regenerate `contract.ts`.** The written confirmations are byte-identical to T6 (three conformance fixtures pin them); only the dry-run sentences are new, per behaviour 4's "what the grant would allow". No wire-TYPE change at all (`AutonomyGrantResult` already carried `Grant *GrantView` + `Confirmation`), but T6's committed `contract.ts` has ZERO `dryRun` — the generator is fixture-observed (examples establish observed fields, they do not claim to describe fields absent from every fixture), and no T6 fixture ever sent `dryRun: true`, so the fields were unobserved. The three T10 dry-run fixtures make them observable: `make protogen` adds `"dryRun"?: boolean` to the grant/deny/revoke params and widens `grant` to `null | {…}` on all three results; that diff is committed with this task (2026-11-01 close-out amend).
4. **Fixture id.** The dry-run fixture is id 414, not 411 as planned: `revoke-already.json` already holds 411.
5. **`SubjectLabel` export + `activeSentence` move** — see "What exists"; the export is what lets the daemon speak the vocabulary's words without re-typing them (AL15), and the move keeps the live.sentence family in the one-formatter file.
6. **Test identifiers.** `TestNewActionAppearsInVocabularyAndEffectiveWithoutAnEdit` (the spec's `TestNewActionAppearsEverywhereWithoutAnEdit` does not match P10's `-run` glob; this name does). In `autonomy_t10_test.go`: `autonomyUserActor` (not `userActor` — that name exists in `triggers_write_test.go`), and the type `autonomyRowCounts` + function `countAutonomyRows` — Go refuses a type and a function sharing one name in the same block (verified empirically on go1.26.6).
7. **Field-presence tests run outside P10's glob.** `internal/protocol/autonomy_t10_test.go`'s three names (`…IsOnTheWire`) do not match `Vocabulary|DryRun|Confirmation|Formatter|Descriptor`; they run with the full protocol suite (green, below).
