# T1 — The index, the four availability reasons, and the no-retrieval build

## Why this exists

**The deletability test lands here, not last** (R4). D1 is the slice's claim, and a build configuration added at the end
would find imports accumulated across eight tasks. It is cheapest to keep true from the first commit.

And **the index and its availability model are one task** (R5): the four reasons are properties of the index's state, and a
model bolted on afterwards is one shaped by whatever the index happened to do.

## Scope

### The tables (V1, V12)

`sqlite-vec` virtual tables plus FTS5, in S4's own database, **per project root** — a worktree is a distinct root.

**Answer Q1 first**: does S4's migration ledger accommodate them, and does fresh-equals-migrated still hold with a
**virtual table**? A virtual table's `sqlite_master` entry may not survive S4's normalised comparison.

**If it does not, the answer is a stated exception in that test — not a weakened check.** S4's equivalence test exists
because *"a missing `UNIQUE` is exactly the drift this catches"*, and softening it to accommodate one table would remove the
guarantee for the other twelve.

### A corpus has a **kind**, and the kind is a column (Stage 5)

**One cheap decision now that avoids a migration later.** S22 ships two corpora, and Stage 5's memory work adds a third
**kind** — not a third corpus.

| Kind | A result is | Can it be wrong? |
| --- | --- | --- |
| `retrieved` | a `file:line` location (V4) | **No.** It exists or it does not |
| `concluded` | a belief the system wrote | **Yes, and it persists invisibly** |

So: **a `kind` column on the corpus, with a closed set of two, not two hardcoded tables.** Adding `concluded` later is then
a row and a validator entry rather than a schema change on live indexes.

**Reserve the concluded kind's columns now, nullable and unused:**

| Column | For |
| --- | --- |
| `provenance` | `told` / `observed` / `assumed` |
| `observation_count` | the N behind `observed` |

They are **NULL for every `retrieved` row**, and a `CHECK` requires them present when `kind = 'concluded'` — so a future
concluded corpus cannot be written without them, which is the thing that would otherwise be discovered after the first
wrong belief.

**Nothing in this slice writes a `concluded` corpus.** The validator rejects the kind as not-yet-implemented, naming Stage 5
— the same shape S11 used for the six tools that did not exist yet.

### The four availability reasons (V19, D3)

```go
type Reason string

const (
    ReasonNoProvider        Reason = "no-provider"
    ReasonIndexEmpty        Reason = "index-empty"
    ReasonModelMismatch     Reason = "model-mismatch"
    ReasonDimensionMismatch Reason = "dimension-mismatch"
)
```

**Four, and no `extension-missing`.** S4's DB18 vendors `sqlite-vec.c` and registers it through
`sqlite3_auto_extension()`, so it is **compiled into the binary and present on every connection.** The state cannot occur,
and a constant for it would be a state someone writes a handler for.

Asserted by grep: the string appears nowhere.

V1's original evidence — a Node API check — is superseded, and that correction is already landed in the superseded design
(R12). Do not re-edit it.

### The no-retrieval build (D1, O1, I1, I2)

**This is the task's most important deliverable.**

A build configuration — a build tag, or a `Makefile` target that excludes the package — in which:

- `internal/retrieval` is absent
- `search` is not registered
- **the whole product's test suite passes**

**And CI runs it** (O1). *A deletability claim nobody builds is a claim that stops being true the first time someone adds
an import*, and it will be found by a user rather than a test.

**No package may import `internal/retrieval` except through an interface with a no-op implementation** (I2). That interface
is this task's, and it is what the rest of the system talks to — so T7's context resolution has somewhere to plug in
without S5 depending on this slice.

## Notes (T1, 2026-10-28)

**Q1 answered by measurement, both halves.** The migration ledger accepts the
virtual tables: `schema_migrations`-equivalent (`_migrations`) records
`0040_retrieval_index` beside 0039, and S4's equivalence test
(`TestAFreshSchemaAndAnUpgradedSchemaAreIdentical`) passes with the FTS5 table,
its shadow tables and `vec0` present — the fingerprint comparison copes with
virtual tables because a single DDL source replays identically into both
paths. **No exception to the equivalence check was needed, so none was
granted** (brief A7: stated facts, never a loosened check). The probe that
settled it: a store built fresh vs one upgraded from an earlier vintage,
`fingerprint()` 709 lines including the FTS5 shadow tables, byte-equal.

**`vec0` is NOT in the migration, on purpose.** sqlite-vec fixes the
embedding dimension at `CREATE` time (`FLOAT[<dim>]`), and V6 makes model and
dimension DATA — the corpus row answers a query; a migration cannot know a
route that has not been chosen yet. So the table arrives on demand:
`EnsureVecTable(root, corpus, dim)` creates
`retrieval_vec_<corpus>_d<dim>_<sha256(root)[:16]>` idempotently. The name is
DERIVED, never interpolated from user text: corpus names are gated
`^[a-z]{1,32}$` (identifiers cannot be parameter-bound in SQLite, so gate +
derivation is the only safe path), and the root is hashed — two worktrees and
two dimensions can never share one table. T1 proves the mechanism exists; T3
gives it a route to come from.

**The slice's biggest measured fact: FTS5 is behind a build tag.** Probed
before writing anything: `vec_version()` answers `v0.1.6` with no special
flags (sqlite-vec is registered by the driver's `sqlite_vec.Auto()` — DB18
holds), but `CREATE VIRTUAL TABLE … USING fts5` fails **`no such module:
fts5`** in the same binary. The bundled driver compiles FTS5 only under its
documented **`-tags sqlite_fts5`**; tagged, the MATCH probe and the
fingerprint both pass. Consequences, all shipped in this commit: the Makefile
gained `GO_TAGS := sqlite_fts5` carried by EVERY go invocation (build, test,
vet, race, run, dev, vectors, bootstrap pin), CI spells the tag too so a step
that bypasses make cannot pass a build make would refuse, `.vscode/launch.json`
carries `buildFlags` for the same reason its comment already gives for
`CGO_ENABLED` (delve builds its own binary), and new `make build-noretrieval`
/ `make test-noretrieval` are the D1 doors. A binary built WITHOUT the tag
fails at store open, loudly, naming fts5 — which is the honest shape, because
D3's four availability reasons deliberately contain no `fts5-missing` state:
V3's keyword half is not optional, so its absence is a build error, not a
runtime condition. `openStore`'s failure message says exactly that, and fired
for real during this task's first untagged run.

**Availability semantics, pinned by `TestFourAvailabilityReasons` (8 rows).**
`Availability` separates three questions that a single enum would blur:
`Available` = will a query be ANSWERED; `KeywordOnly` = WHAT am I getting
(D4's saying-so); `Reasons` = WHY NOT (they answer a refusal). The 4-set
(V19) has no word for "a route exists but nothing is embedded yet" — inventing
a fifth word would violate V19, and `no-provider` would be a lie (there IS
one), so that state is `Available + KeywordOnly` with NO reason: the label is
the sentence, the reasons are for refusals. Both mismatch kinds are checked
INDEPENDENTLY and every failing one is named — the demo's §5 refusal prints
both numbers, and a test that only ever produced one reason would not catch
hiding the second behind the first. `index-empty` is the only unavailability
that is not a refusal: D2 keeps "the index is fine and holds nothing" apart
from "found nothing" (the query ran) and from "absent" (Noop refuses with
`ErrNotBuilt` — never an empty slice dressed as an answer, which is V13 at
the seam; `TestNoOpInterfaceSatisfiesCallers` consumes BOTH backends through
one `Backend`-only function).

**`TestNoExtensionMissingState` hunts itself into a corner, and the house
rule holds.** The gate's own mandated NAME contains the banned token, so the
scan strips the assembled gate name (`"TestNo" + "Extension" + "Missing" +
"State"`) before scanning, and the ban list assembles its own tokens — the
hunter cannot contain the hunted (S21 T2's rule, applied to the hunter's
identity). A floor (`scanned ≥ 5` files) stops an empty scan passing by
deleting the scan; `TestOnlyTheInterfaceIsImported` carries the same floor
(≥ 300 files) for the same reason (E1's "no direct imports" is currently ZERO
importers, and zero importers of nothing would also pass).
