# T2 — Chunking, and per-chunk staleness

## Why this exists

**Before the corpora** (R-ordering), because both chunk — and two chunkers is how V11's heuristic drifts into two
different notions of what a chunk is.

## Scope

### Symbol-aware where cheap, line-window otherwise (V11, Q9)

V11's reasoning is the whole design: *"a chunk spanning two functions retrieves for neither. But a language-aware parser
per language is a project; a brace/indent heuristic plus a line window is most of the benefit."*

**Answer Q9**: the heuristic, and its fallback.

- **Brace languages** — a chunk boundary at a top-level `}` followed by a blank line or a declaration.
- **Indent languages** — a boundary where indentation returns to column zero.
- **Everything else, and anything the heuristic cannot resolve** — a fixed line window with overlap.

**The fallback is not a failure path.** Prose, configuration, and any language the heuristic does not know all take it, and
they are a large fraction of a repository. A fallback treated as exceptional is one that is badly tuned.

### Overlap, and why

Line windows overlap. Without it, a symbol split across a boundary appears in neither chunk's semantic neighbourhood — the
same failure V11 named, arriving through the fallback instead of the heuristic.

### A hash per chunk, not per file (V8, D-checks)

```go
type Chunk struct {
    Path     string
    Start    int      // 1-indexed line
    End      int
    Hash     string   // content hash of THIS chunk
}
```

**Per chunk** is what makes an incremental reindex incremental. A per-file hash means one edited line reindexes the whole
file, which on a large source file is most of the cost of a full reindex for one changed function.

### Not in scope

The reindex trigger and its asynchrony (T8). Embedding (T3). This task decides what a chunk is and how to tell it changed.

## Notes (T2, 2026-10-28)

**Q9 answered as the file reads (stated verbatim in chunk.go's header).**
Brace families (go/c/cpp/java/js/ts/cs/rs/swift/kt/scala/php/dart/json/css,
closed list) close a chunk at a `}` whose closing brace sits at column 0 and
whose next line is blank or begins at column 0 with a letter/attribute marker
— V11's shape, seen from outside a parser: it does not know strings from
comments, and that is the point (a brace heuristic plus a line window is most
of the parser's benefit at none of the project cost). Indent families
(py/rb/ex/exs/yaml/yml) break where a non-blank, non-comment line returns to
column zero. **Everything else takes the window — 120 lines, overlap 20 —
and the window is the NORMAL path**: prose, configuration, markdown and
unknown extensions are a large fraction of any repository, so there is no
"degraded" flag anywhere in `ChunkFile`'s signature to set. The overlap is
V11's named failure closing through the fallback: windowOverlap = 1/6 of the
window means any 20-line run appears wholly in at least one chunk.

**Two measured findings during this task:**

1. **Trailing blank padding was a chunk.** `three.go` minus its last
   function grew a phantom `[10-10]` chunk — the blank line between beta and
   gamma, promoted when gamma's chunk vanished. It retrieves nothing, and
   worse, chunks that appear as whitespace shifts make every edit look
   costlier than it is (the plan would Write them and T8 would pay embedding
   for air). `bounded` now trims trailing blank lines before emitting, and
   an all-blank range emits nothing; interior blanks stay — they are the
   separation a neighbourhood is made of. `TestStalePlanDeletesVanishedChunks`
   is what caught it: the deletion planned a WRITE for a line nobody edited.
2. **A line is the atom a chunk cannot split.** V4's results are `file:line`
   ranges, so `TestVeryLongLineDoesNotBreakChunking`'s honest answer for a
   200 KB single line is NOT "one enormous chunk" and NOT "split the line"
   (a range cannot name a column): the line is skipped and **reported** —
   path, line number, byte count, and the reason says why (the 64 KiB bound,
   `maxLineBytes`) — while the file's other lines keep their chunks. A minified
   bundle therefore costs one loud skip, not a silent blob or a cancelled file.

**`Chunk` carries Body, where the task's illustrative struct stopped at
Hash.** Body is INPUT — the text the index holds; V4's "results are
locations, never text" binds `Hit`, and a chunker that refused to hand its
caller the bytes would force every consumer to re-slice the file by the
ranges it just produced.

**Binary/empty detection is git's rule, stated:** NUL in the first 8 KiB.
Skips are a returned `[]Skip`, never silent — the whole-file skips name the
path and say `empty` or `binary (NUL byte in the first 8 KiB)`; T8's reindex
record is where these sentences surface.

**Stale = comparison, not work.** `PlanFile` reads the stored chunk rows
(hash only — `RetrievalChunkRow` carries no Body: V4's rule starts at the
seams) and answers `Write / Delete / Present / Unchanged / Skips`; `Empty()`
is T8's cheap per-file question over thousands of files. `ApplyChunkPlan`
upserts Write (the store's ON CONFLICT keeps it idempotent) and prunes via
`DeleteRetrievalChunksForSourceExcept` — **except-based, never wipe-then-write**,
because a wiped file answers queries as empty between the wipe and the
writes; a reindex must never make the index briefly wrong. The new store
pair (`RetrievalChunkRowsForSource`, `DeleteRetrievalChunksForSourceExcept`)
follows the house pattern (SQL in `internal/store`, named in store.go's
surface table — the S22 row extended in the same commit, as the guard
demands).

**Recorded for T3:** deleting chunk rows can leave `vec0` rows behind until
the embedding half grows a delete path — `ApplyChunkPlan` says so at the
seam, and the keyword half keeps answering meanwhile (availability stays
honest).
