# T8 — Mismatch refusal, async reindex, and per-corpus staleness

## Why this exists

Three properties that only exist once there is something to reindex, and two of them resolve a tension between correctness
and cost.

## Scope

### A mismatch refuses **and** prices (V17, D9, O3)

V6 established the danger: comparing vectors from two embedding spaces returns *"plausible, wrong results — **the worst
failure a retrieval system has**."* So refusing is right.

But V6's remedy — *"a mismatch forces a reindex"* — spends real money without asking, and **indexing a large repository
costs real money** (V10).

So both: **refuse to query, price the reindex, and reindex nothing** (V17).

```
refused: index built with text-embedding-3-small (1536 dims);
         route 'other-embed' is text-embedding-3-large (3072 dims)
         availability: dimension-mismatch

  Nothing was reindexed. A reindex would cost approximately $0.71
  (estimate: 1,204 files, ~38,000 chunks, unmetered portions excluded).

  To proceed:  aeon index rebuild --embed-route other-embed
```

**The figure is labelled an estimate, with its basis** (O3). *A figure presented as exact for work not yet done is the same
class of error as a confident total over a `partial` cost.*

**Answer Q10**: how it is estimated, and on what.

### Reindex is asynchronous and never blocks a step (V18, D10)

**An indexing pass that delays a step is a tax on every step.**

So: triggered by the loop after it writes (V8 — *"the loop already knows it wrote files"*), run in the background, and a
step may run against a **slightly stale index**.

That is the price of not blocking, and V4 is what makes it acceptable: results are **locations**, so a stale index may point
at a line that moved and the `read` of the current file self-corrects. **A quoted chunk would have been silently wrong.**

**Answer Q7**: how the loop signals that it wrote — `write`, `edit`, and `git.commitAndPush` are the candidates.

### Staleness is per corpus (O4, D10)

```
  code corpus     1,204 files   stale: 38 files (reindex running, 61%)
  history corpus     71 docs    current
```

**Not one global number.** Code churns and history does not, and a single figure would report the history corpus as stale
because a source file changed — which is both wrong and the kind of wrong that trains people to ignore the number.

**And a stale index that claims currency is worse than one that says how stale it is.** Same rule as everything else here.

### The CLI

`aeon index build`, `rebuild`, `status` — and `status` reports availability, per-corpus staleness, and the embedding route.

### The daemon methods, not only the CLI (D15, I10, P34 — added 2026-10-26)

**`retrieval.status {projectRoot}` and `retrieval.reindex {projectRoot, corpus}` are registered socket
methods**, calling the identical functions `aeon index status`/`rebuild` call — not a second
reindex/availability implementation. Locked exactly like S34's `mcp.check` and S18's `routes.probe`:
**`retrieval.reindex` never fires on its own** — not from `retrieval.status`, not from a stale `search.query`
result, not on daemon start. Every lock this task already applies to the CLI path (async, never delays a
step, per-corpus staleness, estimate-before-spend on a mismatch) applies identically to the socket path,
because it is the same code. This is what lets the app show "code corpus: stale, 38 files" and offer a
"reindex" button the way S34's `mcp.check` gave the bench a "Check" button — without this, an app user has
no way to even know an index is stale, let alone fix it.

### Not in scope

Chunking (T2), embedding (T3), the corpora (T4, T5). This task is when reindexing happens and what it refuses.

## 2026-10-31 — the reindex becomes an async worker (the graph's "same approach it was added")

**What changed.** "Asynchronous reindex" (V18/D10) previously meant *a bare
goroutine behind a per-(root,corpus) `reindexTracker`* — the daemon's own
queue, its own figures, its own "running" state. That is a second
implementation of exactly the thing S64 built for the graph. This change
replaces it: `retrieval.reindex` is now the **second registered worker on
the same `asyncworkers.Manager`** `graph.build` uses — one ledger
(`async_worker`), one scheduler, one set of `asyncworker.*` events, one
single-flight by dedupe key. The `reindexTracker` is gutted (its file now
holds only `reindexTimeout`); the "same approach it was added" the request
named is the manager, not a parallel queue. This supersedes deviation (2)
above — the "running"/`Percent` state is no longer the daemon's tracker; it
is the **ledger row**, read by the manager and overlaid by the status
door.

**The four doors, one wiring.**
- **Socket `retrieval.reindex`** (`internal/protocol/retrieval.go`
  `handleRetrievalReindex`) — mirrors `handleGraphBuild` exactly: a
  nil-seam refusal (V13, names `aeon index rebuild` as absent too) →
  decode → validate `componentRoot` / `corpus ∈ {code,history}` →
  `t.AsyncWorkers == nil` refusal (names the manager) → `filepath.Abs` →
  `StartView("retrieval.reindex", abs, abs+"\x00"+corpus, metadata)` →
  answer `RetrievalReindexAccepted{workerId,state,started}` in
  milliseconds. The per-corpus money decision (`embedRoute`/`force`) and
  the corpus ride `Metadata`; the runner reads them and names no corpus of
  its own (O8). The dedupe key is per-(root,corpus) — a code pass and a
  history pass run concurrently, each blocking only its own corpus.
- **Write-hook trigger** (`daemon.go` `notifyReindex`) — resolves
  `filepath.Abs`, then `workers.Start("retrieval.reindex", …,
  {"corpus":"code","trigger":"write-hook"})`; the bare-goroutine fallback
  survives only when the manager is absent (a no-retrieval build). Chained
  with the graph hook by `chainHooks(notifyReindex, notifyGraph)` at both
  `StepRunner` literals (pinned by
  `TestGraphWriteHookWiredAtBothStepRunners`).
- **Status `retrieval.status`** (`daemon.go` `wrapRetrievalStatus`) — runs
  the seam, then overlays the ledger: for each corpus a `queued`/`running`
  view sets `Reindexing:true` and merges `Percent` from the view's
  progress (three-state honesty — an unreported pass reads `running` with
  **no** fabricated figure, not 0 %).
- **CLI `aeon index rebuild`** (`cmd/aeon/index.go`) — start +
  `followWorker` (the graph.go helper, poll the row) + print the
  `ReindexOutcome` and its cost line; a double-click that finds the flight
  already flying follows that worker instead of double-passing. Grep-locked
  to be a client (P34): no `retrieval.New(`, `store.Open(`, the retrieval
  import, or `go func`.

**What was NOT changed / still stands.** The mismatch refusal, the price
walk (Q10), the force-wipe's three store doors, the per-corpus staleness
and the query's cheap store-only staleness note — all the Notes above —
are the seam's job and are untouched; the manager only changes *who runs
the pass and how its state is read*, not what the pass does.

## 2026-10-31 — the staleness signal (S71 evolves this task)

S71 (`S71-retrieval-staleness`) is the evolution of this task: the
retrieval status already walked the tree and reported `StaleFiles` (it saw
a file that changed or a new file that appeared, outside the loop), but it
did not say the *cost* of a pass (G1) and the walk re-hashed the whole tree
on every read (G2/G3). S71 adds the two — not a new trigger, so V21/V10 are
held, not relaxed:

- **The mtime-gate (G2/G3).** `reconcileCode` (the walk status and the
  estimate share) now `stat`s each source and compares its mtime against a
  recorded one (`retrieval_source_mtime` side table, migration
  `20261031220644_retrieval_source_mtime.sql`) before it hashes: a source
  whose mtime matches the recorded mtime is assumed fresh and not re-read;
  only the sources whose mtime moved (or are new) get the full hash. The
  hash is still the truth (a `touch`/`git checkout` that moves mtime
  without changing content is re-hashed, found unchanged, and *not*
  flagged, and the recorded mtime is refreshed) — the gate is a cheap
  filter, the hash is the confirm, and the two never disagree in a way
  that over- or under-reports. The gate is on the comparison-only pass
  only; the apply pass never skips (a rebuild re-processes all; an
  incremental counts the unchanged) and write-throughs the confirmed-fresh
  record.
- **The cost, folded into the status (G1).** `StatusCorpus.Drift`
  (`DriftFigures{Changed, Added, Removed, Cost}`) is computed on the *same*
  mtime-gated walk (no second walker) and folded into the status answer;
  the entry point maps it to the leaf `search.CorpusStatus.Drift`. The
  cost is three-state (`known`/`partial`/`unknown`, never `$0.00`, O3) and
  rides `model.ComputeCost` — the same pricing the real pass and the
  estimate use — so it cannot disagree with the work it prices. A clean
  corpus carries no Drift (no fabricated $0.00); the history corpus's Drift
  is nil (no tree walk — O4).
- **One named exception to Q7.** A bounded, on-demand `stat` on an
  *asked-for* status read is not a watcher/poll/second observer; the
  trigger set is unchanged (explicit + write-hook) and
  `TestQ7ExceptionIsNamed` greps it.

The invariants this task held (V18 async reindex, O4 per-corpus, V10 money
only on purpose, O3 no confident lie, Q7 no watcher) all stand; S71 holds
them and adds the mtime-gate + cost on top. See the SLICES S71 row and the
DEMO §S71 note.
