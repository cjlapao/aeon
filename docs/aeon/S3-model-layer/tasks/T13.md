> says so in its own UI with a badge and a line naming S9. That label is what stops a bench becoming the
> product by accident. The standing rule is `AGENTS.md` §4b.
>
> **It overrides S2's and S3's N8** — both read *"No UI capability beyond the version line"*. They were
> right when the UI was deferred wholesale and are now superseded.
>
> ### What it took, daemon-side
>
> Routes were read from the environment at startup, so configuring one meant editing a shell and
> restarting. Three methods now exist — `routes.list`, `routes.set`, `routes.delete` — plus `-31103 invalid
> route`, and `MutableRoutes` replacing `StaticRoutes`. A route set through the protocol is **immediately
> callable**, which is the whole point.
>
> ### The one rule the design is built around
>
> **A credential goes IN and never comes OUT**, enforced by *two types rather than one redaction*:
> `SetRouteParams` has an `apiKey`; `RouteView` has `hasKey`, a four-character `keyHint`, and **nowhere to
> put a key**. A `redactKey()` on the way out would be one forgotten call site away from leaking; a type
> with no field cannot. Asserted structurally — a test enumerates `RouteView`'s fields and fails on any it
> does not expect — because a test checking `view.apiKey === ""` would pass against a type that has the
> field and happens to leave it empty today.
>
> Three consequences, each deliberate: an **empty key on an edit keeps** the existing one, so the UI never
> holds a credential in order to change a model name; `clearKey` is a **separate flag**, because "unset" and
> "do not change" cannot both be an empty string; and the hint is the **last** four characters, since a
> prefix identifies a key's type and sometimes its project.
>
> Verified before building any of it: the transport logs **method names and never params**, so a key in a
> params object is not written to a log.
>
> ### What it took, Rust-side
>
> A **persistent session** with request/response correlation, which the previous one-call-per-connection
> shell could not do — and had to be able to do, because **subscriptions are per-connection** (T5): a UI
> that opened a fresh socket per request would subscribe on one connection and `ask` on another, and the
> daemon would correctly refuse the subscription id as somebody else's.
>
> So: a reader thread demultiplexing by the presence of an `id` (JSON-RPC's own rule), notifications emitted
> to the webview as `aeon://event`, and a lost connection as `aeon://closed` so the UI goes honest rather
> than showing its last good state forever. **One generic `rpc_call` command**, which is S9's U11 arriving
> early for a concrete reason: a command per method is a second copy of the method table that a later slice
> will forget to update.
>
> ### Two defects found by building it
>
> **`Alert` discards its children.** The kit renders `title` and `description` and drops everything else, so
> **five alerts across the app were silently showing a heading and losing the sentence that explained it** —
> including the one telling a user that nothing is saved. Found by reading the DOM after a test could not
> find content that was plainly in the JSX. Prose moved to `description`; the structured error panel moved
> to `Panel`, which does render children. Recorded in `ui/README.md` as the kit's third gap — the same trap
> as reaching for the nearest existing type, one level up.
>
> **A lost connection reported `Broken pipe (os error 32)`**, which tells a reader nothing they can act on.
> There is now one `connection_lost` helper, shared by the session and its tests, saying the daemon has
> closed and to reconnect.
>
> ### A test that was asserting the wrong thing
>
> "Thinking is rendered separately" compared the answer with `toBe` and failed on `'the answer▌'` — the
> streaming cursor. The cursor is an **affordance**, not noise: it is how a reader tells a reply still
> arriving from one that stopped early. It now has a test of its own, asserting it appears while streaming
> and is gone at `ask.done`.
>
> ### The bug the user found, and why it was silent
>
> **Reported as: *"it stays at streaming, and does not get anything back."*** Every call worked; no stream
> ever produced a thing.
>
> **Root cause: Tauri v2 gates the core `event` plugin behind its ACL, and this app had no capability at
> all.** `tauri.conf.json` said `"capabilities": []` and there was no `capabilities/` directory, so the
> generated `capabilities.json` was literally `{}`. Commands the app defines with `generate_handler!` are
> **not** ACL-gated; `listen` belongs to a core plugin and **is**. Hence the exact asymmetry observed:
> `invoke` fine, events denied.
>
> Fixed with `capabilities/default.json` granting `core:event:default` to the `main` window — and nothing
> else, which `capabilities/README.md` argues for: the web layer's whole access to the outside world is
> `invoke` of four app commands plus `listen` on two channels.
>
> ### How it was found, and the two things that made it hard
>
> Not by reading the config. By **elimination**, which required building something that did not exist:
>
> 1. **The Go → socket → Rust reader path had no test**, because `Session` took an `AppHandle` and an
>    `AppHandle` cannot be constructed outside a running app. So the reader was replaced by an `EventSink`
>    trait, and `tests/live_stream.rs` now drives a **real daemon through the production reader into a
>    recording sink** — which proved the daemon sent, the socket carried and the reader read. That left one
>    hop.
> 2. **`let _ = app.emit(...)`** discarded the result, so a failed emit was indistinguishable from an event
>    that was never sent. It now reports to stderr.
>
> And the reason it presented as a *hang* rather than an error: **the UI swallowed the listener's
> rejection** — `void (async () => { await onEvent(...) })()`. A denied `listen` became silence. Now:
> `listenerUnavailable()` gives that failure the three parts, the Ask page **refuses to start a stream**
> when its listener is not installed (the daemon would otherwise do the work, bill for it, and send the
> reply into a void), and the shell shows the cause above everything else.
>
> ### A guard, because nothing else can see this break
>
> `ui/test/capability.test.ts`. Deleting that capability file breaks **no other test**: the Rust compiles,
> the Go passes, every UI test passes against a fake that always succeeds, and the app builds. The only
> symptom is a window where every call works and every stream is silent. The test also asserts the
> permission stays **narrow** and that the window label matches — a capability naming a window that does
> not exist grants nothing, silently, which is the same failure again.
>
> ### Verified
>
> `make ci` green: **483 Go assertions, 51 UI, 10 Rust.** The whole flow walked live against the real
> daemon with no credential in the environment — configure a provider from nothing, subscribe, ask, stream,
> account — and `routes.list` asserted clean of the key afterwards. The window itself handshakes on a
> virtual display: `client=aeon-app/0.0.0 protocol=1` in the daemon's log.
>
> **And the streaming fix was verified in the real window**, not inferred. A temporary diagnostic entry
> point ran the full flow inside the webview and reported its verdict through the one channel readable from
> outside — a route named after the outcome. It came back **`probe-EVENTS-ARRIVED-3`**: listen installed,
> handshake done, subscribe, ask, and three events including `ask.done`. The diagnostic was then reverted.

## Context

A capability reachable only from a terminal is a capability nobody checks the way they will use it. S3
configured providers through environment variables and a daemon restart — workable for a developer with a
shell open, useless for deciding whether the thing is any good.

**This is a test bench and not a product.** S9 builds the real app; this exercises each slice where it will
be consumed. The distinction is stated in the UI itself, because a bench that looks finished is one somebody
builds on.

## What to do

**1. Three route methods** — `routes.list`, `routes.set`, `routes.delete` — with a mutable store seeded from
the environment, and a route set through the protocol immediately callable.

**2. The credential rule, enforced by types.** A request type with `apiKey`; a response type with `hasKey`,
a last-four `keyHint` and no key field. An empty key on an edit keeps the existing one; `clearKey` removes
it explicitly.

**3. A persistent Rust session** with correlation, notifications forwarded to the webview, and one generic
`rpc(method, params)` command rather than one per method.

**4. Three tabs** — Status, Providers, Ask — each rendering the honest states: three connection states,
three cost states, errors in three parts.

**5. Say what it does not do.** The bench badge, the S9 pointer, "nothing is persisted", and "nothing runs
it yet" beside a tool call.
