# T11 · UI: the composer on an idle loop, message and run cards, *Run blueprint…*

**Prefix:** CR · **Rules:** CR3, CR8 · D3, D8 · **Depends on:** T9 (T6 and T5 for the events) · **Contract:** [`../brief.md`](../brief.md) · [`../design.md`](../design.md)

## Goal

On an `idle` loop the composer stays and sends `loop.message`; while a step runs it still steers (S31, unchanged). The thread shows typed/templated messages with their source and a run card per run. A *Run blueprint…* panel lists `loop.run.options` and calls `loop.run`. A `done` loop still has no composer.

## Steps

1. `LoopDetail` (LoopScreen.tsx line 14): add `runSeq?: number; attended?: boolean | null; runs?: { runSeq: number; blueprint: string; version: number; state: string; startedByKind: string; goalId?: string; goalVersion?: number; taskId?: string; startedAt: string; endedAt?: string; cost: { usdAtLeast: number; exact: boolean; partial: number; unknown: number; steps: number } }[]`.
2. `types.ts` — add to the `ChatItem` union:
   ```ts
   | (Base & { kind: "message"; author: "human" | "system"; text: string; source?: "user" | "template" | "automation" | "blueprint"; messageId?: number })
   | (Base & { kind: "run"; runSeq: number; blueprint: string; version?: number; state: "running" | "done" | "failed" | "cancelled"; cost?: { usdAtLeast: number; exact: boolean }; startedBy?: string })
   ```
3. `fromEvents.ts` — new cases beside `loop.finished`:
   - `loop.message.posted`: if `p.author === "agent"` **skip** (the agent's reply is already in the stream as step text; showing both would print it twice). Otherwise push a `message` item, id `msg:${messageId}`; ignore a repeated `messageId` (the ring can replay).
   - `loop.run.started`: push a `run` item id `run:${runSeq}` state `running`, `startedBy: str(p.startedByKind)`; remember its index in a `runIndex` map.
   - `loop.run.finished`: patch that item (or push one if its start aged out of the window): `state` from `p.outcome`, `cost` from `p.cost` (`usdAtLeast`, `exact`); then `closeStream()`.
   - Unknown kinds stay ignored (the file's rule).
4. `session.ts`: widen the union to `"unknown" | "running" | "waiting" | "finished" | "blocked" | "idle"`; add `else if (ev.kind === "loop.run.finished") loopStatus = "idle"; else if (ev.kind === "loop.run.started") loopStatus = "running";` in the chain at lines 66-69.
5. `cards.tsx`: `MessageBubble({item})` — right-aligned bubble with the text through `<Prose>`; when `item.source` is set and not `"user"` show a `<Chip>` reading `from template` / `from automation` / `from blueprint`; `data-testid="agent-chat-message"`. `RunCard({item})` — one row: `Run {runSeq} · {blueprint}`, a state chip, and the cost: `≥ $0.50` when `cost.exact === false`, `$0.50` when exact, `—` when absent (never `$0`); `data-testid="agent-chat-run"`, `data-state={item.state}`. In `ChatStream.tsx` `Item`'s switch add `case "message"` and `case "run"`; in `filterForAgent` they fall through to `return false` already (loop-level items). The steps of a run render between its start card and its finish card, so the card is the run's anchor; there is no separate link (record in Notes).
6. `ChatComposer.tsx`: add props `mode?: "steer" | "message"` (default `"steer"`) and `onMessage?: (text: string, route?: string) => void | Promise<void>`. When `mode === "message"`: no target picker, no Stop button, placeholder `"Message the loop…"`, the send button reads `Send`, `send()` calls `onMessage({trimmed text, ...route if changed})` and clears the text; `canSend` needs only text and `!disabled`. In steer mode nothing changes (byte-identical rendering; the existing composer tests must pass unmodified).
7. `useChatActions.ts`: extend `ChatWiring` with
   ```ts
   onMessage(text: string, route?: string): Promise<void>;       // loop.message {id: loopId, text, route?}
   loadRunOptions(): Promise<RunOption[]>;                         // loop.run.options {id: loopId} -> result.options
   onRunBlueprint(req: { blueprint: string; goalId?: string; taskId?: string; message?: string }): Promise<void>; // loop.run {id: loopId, ...}
   ```
   All three throw `Error(result.refused.detail)` when the result has `refused` (the daemon's own words, shown verbatim). Define `RunOption = { blueprint: string; version?: number; runnable: boolean; reason?: string; candidates?: { kind: "goal" | "task"; id: string; title: string; state: string }[] }` in this file.
8. `RunBlueprintPanel.tsx` (no dialog component exists in the kit; render an inline panel above the composer): props `{ load, onRun, onClose }`. On mount call `load()`. One row per option: the name, and — when `!runnable` — the `reason` text in muted style and, if `candidates` exist, a `<select aria-label="goal or task for {blueprint}">` of `{kind} {title}`; a `Run` button, **disabled** when `!runnable` and no candidate is selected. An optional text input `First message (optional)`. `Run` calls `onRun({blueprint, goalId|taskId from the chosen candidate by kind, message})`; on a thrown error show `role="alert"` with its message and stay open; on success call `onClose`. Entries are never hidden: unmet ones are disabled-with-reason (S9 start-form precedent).
9. `LoopWorkspaceView.tsx`:
   - Compute `const idle = session.loopStatus === 'idle' || (session.loopStatus === 'unknown' && loop?.status === 'idle');`
   - `ended` stays as is (idle is not in `ENDED`); change `useNow(connected && !ended)` to `useNow(connected && !ended && !idle)`.
   - The composer rule (D3), exactly: `const messageMode = idle && running.length === 0;`. Pass to `composer`: `mode: messageMode ? 'message' : 'steer'`, `onMessage: chat.onMessage`, `disabled: !connected || (!messageMode && running.length === 0)`, `disabledReason` unchanged for steer mode and `'Disconnected from the daemon — reconnecting…'` when disconnected.
   - Add a `Run blueprint…` button, rendered only when `idle`, left of the composer (inside `AgentChat`'s `header` prop is acceptable); clicking toggles `RunBlueprintPanel` with `chat.loadRunOptions` / `chat.onRunBlueprint`; closing it calls nothing else (the `loop.run.started` event moves the view).
   - `LoopWorkspaceScreen` needs no change beyond passing the extended `chat` object (it already does).
10. `make -C aeon/ui typecheck && make -C aeon/ui test`.
