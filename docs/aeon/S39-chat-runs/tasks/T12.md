# T12 · UI: the `run_start` ask card and the unattended notice

**Prefix:** CR · **Rules:** CR4, CR7, CR8 · D5, D8 · **Depends on:** T10, T11 · **Contract:** [`../brief.md`](../brief.md) · [`../design.md`](../design.md)

## Goal

A `run_start` permission question renders as a readable "Start blueprint X on goal Y?" card using the existing question card; a loop that is not attended says so next to the composer in three states (attended, unattended, never declared).

## Prerequisites

- T10, T11 merged. Check: `grep -n "attended" aeon/ui/src/features/loops/pages/LoopScreen.tsx` prints the `LoopDetail` field from T11.
- Read `components/agent-chat/cards.tsx` (`QuestionCard`, lines ~28-120), `fromEvents.ts` (`case "question.asked"` and the tool-start case for how a tool's input arrives: `grep -n "step.tool.start" fromEvents.ts`), `policyText.ts`.

## Files to create / modify

- `ui/src/components/agent-chat/fromEvents.ts` — pass the tool name and a parsed summary into a permission question for `run_start`.
- `ui/src/components/agent-chat/types.ts` — `ChatQuestion` gains optional `runStart?: { blueprint: string; goal?: string; task?: string }`.
- `ui/src/components/agent-chat/cards.tsx` — one branch in `QuestionCard`.
- `ui/src/features/loop-workspace/AttendednessNotice.tsx` — new.
- `ui/src/features/loop-workspace/LoopWorkspaceView.tsx` — render the notice.
- Tests: `ui/test/chat-runs.test.tsx` (add), `ui/test/agent-chat-adapters.test.ts` (add).

## Steps

1. Find how the permission question body reaches the UI: `question.asked` carries `body` (the daemon's sentence naming agent, tool and rule — `permission_ask_test.go` shows its content) and the question's `toolUseId`. The matching `step.tool.start` for that `toolUseId` carries `tool` and a `summary`. In `fromEvents.ts`, when a `question.asked` of kind `permission` has a `toolUseId` whose earlier tool item is `run_start`, set `question.runStart` by parsing that tool item's **input** if the event carries it. VERIFY: `grep -n "input" internal/runtime/*.go | grep -i "EventToolStart"` — if the tool-start event has no structured input, parse nothing and rely on the body text (the card then shows the daemon's body verbatim and the heading below); do not invent fields.
2. `cards.tsx` `QuestionCard`: when a pending question has `runStart`, render the heading `Start blueprint {blueprint}` plus `on goal {goal}` / `on task {task}` when present, above the existing body and the existing approve/deny buttons. When it has no `runStart` but its tool item is `run_start`, heading `Start a blueprint run`. Everything else (buttons, `onAnswer`, answered state, `data-testid`s) is the existing rendering — do not fork it.
3. `AttendednessNotice.tsx`: props `{ attended: boolean | null | undefined }`; renders nothing for `undefined` (older daemon, field absent). Text, exactly: `true` → `Attended — a person is here to confirm asks.`; `false` → `Unattended — asks are denied at once. run_start cannot be confirmed here.`; `null` → `Never declared — treated as unattended. run_start cannot be confirmed here.` with `data-testid="attendedness"` and `data-state="attended|unattended|undeclared"`.
4. `LoopWorkspaceView.tsx`: render `<AttendednessNotice attended={loop?.attended} />` directly above the composer (inside the `AgentChat` `header` only if T11 did not already use it; otherwise wrap both in one fragment). Show it for `idle` loops and for running loops alike (it is a property of the loop).
5. Tests below; run typecheck and the UI suite.

## Definition of done

- [ ] typecheck and the full UI suite pass; no existing test edited (record any that was).
- [ ] The three notice strings match the text in step 3 character for character (the tests quote them).
- [ ] `QuestionCard`'s non-`run_start` rendering is unchanged (existing question tests pass).
- [ ] Notes: whether step 1 found structured tool input; native desktop appearance named as unverified.

## Do NOT

- Do not add a second answer path for `run_start`: approval goes through the existing `answer` method via `onAnswer`.
- Do not show the notice as "unattended" when `attended` is `null`/absent — three states, three texts.
- Do not let the UI start a run when the loop is unattended through chat; the *Run blueprint…* button (human peer) is unaffected by attendedness.
- Do not infer attendedness from socket liveness.
