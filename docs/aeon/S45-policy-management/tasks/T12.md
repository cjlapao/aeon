# T12 · The `policy.corpus` seed set: system policies become seeded, origin-marked rows

**Prefix:** PM · **Rules:** PM15, PM16, PM2, PM8, PM11 · S43-extra SD1/SD4/SD5/SD6/SD12 · **Depends on:** T1, T3 **and
S43-extra T3 (the seed engine)**. Gates T4's `policy.seedCorpus` and T5's `seed_corpus` effect.

## Goal

Apply the operator's rule (2026-10-30: *every record is in the database; system ones defined in code are seeded*) to
policy. The shipped corpus (38 agents / 367 rules, `internal/policy/testdata/corpus.json`, embedded) is today applied by
the bespoke `aeon policy seed-corpus` runner and its rows are told apart only by an id prefix. This task makes it a
**declared seed set** against the S43-extra engine — class **`guard`** (it adds `allow` rows) — with a real `origin`
column, so system policy is listed, versioned, audited and never clobbered, and the D4 rule ("no automatic seeder")
stays true by construction.

## Behaviour

1. **Guard class (SD5).** `policy.corpus` is **never applied at daemon start** (`ApplyInert` skips it; S43-extra T3/T6
   prove it). It is applied only by `seed.apply {set:"policy.corpus"}` (human door), by `aeon seed apply --set
   policy.corpus --yes`, by `aeon policy seed-corpus` (a verb alias kept for parity, calling the same engine path), by
   `policy.seedCorpus` (T4), by a committed `seed_corpus` proposal (T5), or by `aeon init`'s confirmed guard plan.
2. **Per-agent selection** (`--agent`, `agents:[…]`) maps to `keys` filtering by the `corpus.<agent>.` prefix — resolved in
   `policyseed` (the engine knows only keys); an unknown agent refuses by name (S43 slug existence is checked against the
   `agent` table, so a seed for a non-existent agent is refused, naming it — no orphan target, T2's slug rule).
3. **Removal by an operator** (`policy.remove` of a `corpus.*` row, T4) is allowed and audited; the engine then reports that
   record `removed` and **`seed.apply` does not resurrect it** (SD6); `seed.restore {set,key}` brings it back (explicit,
   human door, audited in `seed_event` *and* `policy_change` `op='seed'`).
4. **A seeded rule an operator wants different** is not edited: they add a user rule (e.g. a `deny`) — PL4 resolves it —
   and may remove the system rule. The UI says so (T9).
5. **Existing databases:** rows already seeded by the old verb are **adopted** (same id, `origin` backfilled to `system`,
   ledger `adopt` at version 1 with the fingerprint of the live row — a row an operator already hand-edited is
   `diverged`, never overwritten). The old verb's behaviour and output are unchanged (goldens).
6. **PL1 holds for seeded rows:** every record is `source: operator`, so an `allow` passes `checkAuthorship` exactly once
   (inside `AddInTx`); a corpus record with any other source is refused at `go test` time by `mustRegister`'s validation
   (the set's records are run through `policy.ValidateForAdd` in a unit test).
7. **Audit:** the engine writes `seed_event`; the policy layer additionally writes **one** `policy_change` row
   (`op='seed'`) per apply run (T3's table) so the Policy audit tab tells the whole policy story.
