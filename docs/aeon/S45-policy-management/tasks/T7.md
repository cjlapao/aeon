# T7 · Agent tools: seven catalog specs — reads and restrictive-only proposals

**Prefix:** PM · **Rules:** PM9, PM10 · the operator's standing rule "every management operation gets a tool" ·
S38 OL2/OL3/OL10 · **Depends on:** T2, T6. Parallel-safe with T8, T9.

## Goal

Agents can **see** the policy that governs them and **propose** that it be tightened — and nothing more. The seven
actions are added to the S38 records catalog (one definition, two doors), so each has a socket twin and a tool, a
parity test walks both directions, and the new tool names are **granted to no one by default**. An agent can never add,
remove, seed, commit or reject, and can never author an `allow`.

## The seven specs (`internal/records/catalog.go`, additive, family `policy` / `proposal`)

| Tool name | Socket twin | Class | Mutates | What it does |
| --- | --- | --- | --- | --- |
| `policy_list` | `policy.list` (existing) | safe | no | List policies with type, target, action, source, **origin (system/user)**, expiry and the one-sentence description; optional `type`/`target`/`source`/`action`/`origin` filters |
| `policy_show` | `policy.get` (T2) | safe | no | One policy in full: row, description, raw spec |
| `policy_why` | `policy.why` (existing) | safe | no | Why a question is allowed/denied/asked — the verdict sentence verbatim |
| `policy_in_force` | `policy.inForce` (existing) | safe | no | What is in force for one target, all three states |
| `proposal_list` | `proposal.list` (existing) | safe | no | The open proposals (status filter), newest first |
| `policy_propose_add` | `policy.proposeAdd` (new, T7) | detectable | **yes** | Create an **inert** proposal to add a `deny` or `ask` policy; nothing is enforced until a person commits |
| `policy_propose_remove` | `policy.proposeRemove` (new, T7) | detectable | **yes** | Create an inert proposal to remove a policy by id |

`registerRecords` **skips** a twin whose dot-name already stands (`records.go` header) — so the five read specs reuse
the existing/T2 methods with no new registration; only `policy.proposeAdd`/`proposeRemove` are new socket methods.

## Schemas — what is deliberately absent (OL3's "strict schema" rule)

Every schema is `"additionalProperties": false`.

- **No `source`, `actor`, `createdBy`, `status`, `kind`** field in any propose schema. `policy_propose_add`'s input is
  `{id, type, target:{kind,id}, action:("deny"|"ask"), spec, notAfter?, reason}` — `action` is an **enum of two**
  (`deny`, `ask`); `allow` is not a schema value, so an attempt is a parse error before it reaches the validator.
- `reason` is required (1–512 bytes): why the agent proposes it. Stored in the proposal payload's `reason` member
  (S35 TD1's payload is JSON; the **closed per-kind payload shape** gains one optional `reason` string — **VERIFY**
  with T0 whether `proposal_validators.go` already tolerates it; if not, T7 adds it to the validator, in
  `internal/desk/validate.go`, additively and with the create/commit validator parity test re-run).
- `policy_propose_remove` input `{id, reason}`.

## Behaviour (each a test)

1. **Forced identity.** The service builds the proposal payload with **`source: "agent"`** — not from input — so the
   existing `ValidateForAdd` (PL1's `checkAuthorship`) refuses an `allow` even if the schema were bypassed; the
   refusal is PL1's own sentence, verbatim. The proposal's `created_by` is the **agent actor** the records service
   stamps (T0 item 3.4 says exactly what that is — slug/handler/loop); the tool never names it.
2. **Inert.** The tool calls the **same create path** as `proposal.create` (`ValidateProposal` first, then
   `ProposalStore.CreateProposal`). The policy table is untouched; `policy.why` is byte-identical before and after
   (the arbiter test, driven through a tool call).
3. **No decision tool exists.** The catalog contains no spec whose twin is `proposal.commit/reject/discard`,
   `policy.add/remove/seedCorpus`. (T6 asserts it; T7 adds the positive list.) `proposal.discard` is *also* not an
   agent tool: discarding another actor's proposal is a human act in this slice (an agent may not retract a human's
   proposal; its own is the follow-up if ever wanted).
4. **Rate and size.** A single agent may hold at most **20 open proposals** (a counted refusal naming the limit and how
   to see them) and each payload ≤ 8 KiB — a runaway loop must not bury the desk. The limit is a **named constant**
   in `internal/desk` and a boundary test, not a hidden number.
5. **Granted to no one by default.** `tools.DefaultGrant()` is unchanged (`read, list, write`); the seven are
   *registered, not granted* (S11). A handler that wants them lists them explicitly in its tools — and even then the
   **policy** `tool_access` rows decide per call (`ask`/`deny`/`allow`), as for any tool. The doc comment on each spec
   says so.
6. **Counted registry bump.** `TestRegistryExactNames`'s `want` list and its count comment gain the seven names
   **deliberately** (S38's bump pattern: "Count 40 → 47 DELIBERATE" — compute from the real current count T0
   recorded, never from this file). The test body's logic is unchanged; only the data and a dated comment line.
7. **Descriptions are ≥ 40 characters** and tell a model apart from siblings (the catalog test enforces).

## Definition of done

- [ ] Seven specs, each with a socket twin and a tool; parity test green in both directions.
- [ ] `allow` unrepresentable in the schema and refused by PL1 if bypassed; `source` forced to `agent`.
- [ ] Proposals inert (arbiter byte-identical), validator parity with `proposal.create`, per-agent limit.
- [ ] No tool commits/rejects/discards/adds/removes/seeds; T6's guards green with the new specs.
- [ ] Registry bump counted and dated; default grant unchanged.

## Do NOT

- Do not add a `source`, `actor`, `status` or `kind` field to any schema.
- Do not add `allow` to the `action` enum, ever, in this slice.
- Do not add a tool twinned to a decision or authoring method.
- Do not add the seven to `DefaultGrant()` or to any handler's default tool list.
- Do not give the records package an import.
- Do not implement the propose actions through the authoring service (they create proposals, not policies).
