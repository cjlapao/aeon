## Context

**This task's real content is negative: a subscriber must receive *nothing* it did not ask for.**

One daemon serves every project on the machine (§1a). A filter that silently matches everything looks like it
works — events arrive, the client renders them — while quietly shipping every repository's activity to every
client. On a busy machine that is most of the traffic, and the client discards it after paying to receive it.

That is why subscriptions rather than server push (T4): the client says what it wants, once, and the daemon
sends only that.

**Subscriptions are per-connection and die with it** (T5). A durable subscription is server-held state keyed to
a client that may never come back, which on a daemon meant to run for weeks is a slow leak with a
client-shaped cause. Reconnection is a cursor's job (T4's `after`), not a subscription's.

**D6 asserts on the registry, not on delivery stopping.** Delivery stopping is what you observe when the
connection closes regardless; the registry emptying is the thing that proves nothing was retained.

**One registry** (I6). A second store of subscriptions makes D6's assertion meaningless.

**Read first:** `handshake.go` (T2) for connection state; the design's §Subscriptions for the wire shapes;
Q5's answer on shutdown ordering — subscriptions must be torn down **before** the socket closes.

## What to do

**1. `filter.go`** — `{projectRoot?, kinds?}`.

`kinds` matches **exactly, or by a single trailing `*`**. Any other wildcard form — a leading `*`, an interior
one, `?`, a character class — is a **named error** (O1), not a literal match. A filter that silently matches
nothing is the hardest bug in this slice to diagnose from outside: the client appears connected and simply
never receives anything.

`projectRoot` matches exactly. No prefix matching on paths — `/repo` must not match `/repo-backup`.

**2. `subscribe.go`** — the registry, keyed by connection then subscription id.

- `subscribe` → `{subscriptionId, from}`
- `unsubscribe` → removes it; unsubscribing twice is not an error, since a client racing its own teardown is
  ordinary
- connection close → **every** subscription for it removed
- bounds per connection and in total (O4), with the refusal **reported** rather than silently dropping the
  subscription. State the numbers and that they are guesses (Q8).

**3. Tear down before the socket closes** (Q5). If the lifecycle hook fires after, a delivery attempt races a
closed connection — which surfaces as an intermittent error nobody can reproduce.

**4. Write the tests as refusals.** Two subscribers, two projects: assert the first receives **zero** events
from the second, over a run rather than a single event. Same for kinds.
