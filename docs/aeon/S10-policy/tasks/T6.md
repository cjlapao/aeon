## Why this exists

Acceptance answers a real question — *"which policies is this agent under, and since when?"* — and it is
**one `if` away from being a security hole.**

> **An unaccepted policy is still enforced** (PL10).

If acceptance gated enforcement, **a plugin could evade policy by declining to accept it.** That is the
whole reason this task's most important test asserts a negative.

What acceptance actually buys is two things worth having: the question above, and **proof an agent knew at
the time it acted** — which, paired with T9's disagreement record, is the difference between *"it was not
told"* and *"it was told and tried anyway."*

**Read first:** `store.go` (T5); S4's `policy_acceptance` table.

## Scope

**1. Record acceptance** per target, with its instant, in S4's `policy_acceptance`.

**2. Idempotent.** Accepting twice is not an error and does not move the first instant — *"since when"* has
to mean the first time, or the field answers nothing.

**3. Nothing in `Evaluate` reads this table.** That is the guard: if the evaluator cannot see acceptance, it
cannot be made to depend on it. The grep in T2 already forbids the store import, so this follows — assert
it anyway, because the next person to touch `record.go` will not have read T2.

**4. `record.go` is a serialization point.** This task creates it; T7 adds events; T9 adds the
disagreement. **In that order, and never concurrently.**

- **Idempotency mechanism: `ON CONFLICT (policy_id, target_kind, target_id) DO NOTHING`, not an upsert.**
  "Since when" only means anything as the FIRST time: a `DO UPDATE SET accepted_at` would let a repeated
  accept (retry, crash, confused loop) silently rewrite history, and T10's disagreement record — the
  difference between "it was not told" and "it was told and tried anyway" — would inherit the moved date
  and accuse the wrong instant. DO NOTHING keeps the first row **whole** (the first `accepted_at` and the
  first `accepted_by`, asserted by `TestPolicyAcceptanceRecordIsIdempotentAndKeepsTheFirstInstant`), and
  a re-record returns nil — idempotence that errors is just a flakier interface. The conflict target is
  **named** rather than bare, so only the documented acceptance identity makes a re-record a no-op; every
  other failure — the foreign key to `policy` above all (acceptance of a nonexistent policy is a record
  of nothing) — still arrives as an error (`…EnforcesTheKey` covers the FK fire).
- **Target-validation decision: the boundary re-runs `ParseTarget` on whatever `Target` struct it is
  handed, and gates the third-party strings with the same identifier policy `Add` runs.** Go structs carry
  no guarantees — a casted `Target{Kind: "global"}`, an id repeating its kind, a named kind naming nothing
  are all constructible and all refused by name before the repo seam is touched (`recordCalls == 0`
  asserted). `policyID`, `target.ID` (named kinds) and `acceptedBy` pass `checkIdentifier` (charset
  allow-list, 64-rune cap, control/zero-width refusals — SEC-013) because they reach an operator's console
  through every "who knew what since when" listing; `accepted_by` is validated as a **bare name** like
  `Target.ID` — the kind:id rendering belongs to `Target`, and a second field spelling identities with its
  own separators is a second identity language nobody audits. A zero `at` is refused at both layers
  ("since when" with no instant is the row that answers nothing; D5 — the clock is a parameter). **No
  existence check for the policy id is duplicated at the boundary** — the FK owns that truth and a second
  authority would only get to disagree.
- **The all-agents NULL asymmetry, stated where the seed left it unstated:** `policy_acceptance.target_id`
