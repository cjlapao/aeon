# T7 — `policy_event`, and the age cap

## Why this exists

Two jobs. One is the audit trail: *"every time a policy refused something, with its subject."* The other is
**keeping the table from being the reason somebody deletes the database.**

**Every refusal, forever, is unbounded.** A loop that retries a denied tool twenty times in a round writes
twenty rows. Decided now rather than discovered at 2 GB (PL11).

**And the cap has to be visible, not just present.** A silently-trimming log is one that loses the row
somebody came looking for and never says so. So both the cap and the current depth are reportable, and
`doctor` (S23) surfaces them.

**Read first:** `record.go` as T6 left it; S4's `policy_event` table and its `(policy_id, at)` index —
which exists for exactly this query and this trim.

## Scope

**1. Record every refusal** with its subject: what was attempted, by whom, against which policy.

**2. Answer Q2: pick the cap, as a number.** This is a judgement, not a principle — state the number and
one sentence of reasoning in this task's notes. **90 days is a reasonable default** and the point is that it
is written down and reportable, not that it is correct.

**3. Trim by age, not by row count.** A row-count cap trims a quiet week and a busy week differently, so
*"what happened in July"* depends on how busy August was. Age is the property somebody actually reasons
about.

**4. Report depth and cap together.** `aeon policy events --depth` prints rows, the cap, and the oldest
retained instant — so "nothing older than this exists" is a statement rather than an inference.

**5. Trimming is not on the write path.** Do not trim on every insert; that makes every refusal pay for
housekeeping. Trim on daemon start and on demand.

**Q2 answered: the cap is 90 days** — `PolicyEventAgeCap = 90 * 24 * time.Hour`, a named const. The
reasoning in one sentence: it mirrors the reference's quarter-of-operations retention because an auditor
asks "who was refused for what **this quarter**" (D15's line wants a stable, reportable number), and the
seed's row-count-vs-age argument assumes a window long enough to outlive every loop's retries yet short
enough that the whole-table scans below stay cheap without a second index.

**`policy_event` columns AS ACTUALLY FOUND** (0005, `schema.go` ~582–592, read before writing one line of
SQL — nothing was missing and no second migration was needed): `id INTEGER PRIMARY KEY AUTOINCREMENT`,
`policy_id TEXT REFERENCES policy (id) ON DELETE SET NULL` (NULL = "fits no rule", the honest answer for
PL5/D10 refusals), `subject_kind TEXT NOT NULL`, `subject_id TEXT NOT NULL`, `outcome TEXT NOT NULL`,
`detail TEXT`, `at TEXT NOT NULL`, plus `idx_policy_event_policy ON policy_event (policy_id, at)`. Three
findings the spec's prose did not state: **`outcome` has NO CHECK constraint** — the DB does not police
the vocabulary, so `validEventKind` at the boundary is the only lock and `decodeEvent` re-verifies on
read (T10 extends it additively); `detail` is nullable (the write boundary never produces NULL —
`recordEvent` refuses blank, the store fail-fasts too, and a NULL read back as "" refuses nobody but a
non-instant refuses the whole report); and the FK cascades **SET NULL** — deleting a policy erases the
blame but keeps the refusal, which is exactly what an audit should do.

**`at` is stored in a fixed-width layout** — `"2006-01-02T15:04:05.000000000Z07:00"` (RFC3339Nano shape
with the 9-digit fraction FORCED, always UTC) — because the trim compares `at < cutoff` as TEXT, and
RFC3339Nano's trailing-zero drop makes lexicographic order disagree with time order (`…:00Z` would sort
AFTER `…:00.5Z`). `time.Parse(time.RFC3339Nano, …)` reads the form back unchanged. Pinned at SQLite
level: the zero-nanosecond row must store the literal `.000000000`.

**The index claim, measured not hoped.** `EXPLAIN QUERY PLAN` (sqlite3 3.53, re-asserted in-commit against
the exact constants `trimEventsSQL`/`statsEventsSQL` that production executes — `TestTheTrimAndAuditQueriesUseThePolicyEventIndex`):
the audit stats (`COUNT(*), MIN(at)`) and the trim answer from **COVERING INDEX** `idx_policy_event_policy`
— but only in the **`rowid IN (SELECT rowid … WHERE at < ?)`** shape; the bare `DELETE … WHERE at < ?`
was measured as a plain table SCAN, so the shape is load-bearing and the test pins it against "simplifying"
rewrites. The per-subject listing (`WHERE subject_kind = ? AND subject_id = ?`) **provably cannot use the
index** — neither column is in it, and adding one would be a second migration (N4 refuses); what bounds
that scan instead is the cap itself (at most 90 days of refusals, an indexed delete keeps it that way).
The test's discriminating control asserts a subject-column plan does NOT name the index.

**Truncation (the carried HIGH from the T6 gate):** `truncateRunes` keeps the head at `n/4` and the TAIL
at `n − n/4` runes over `[]rune` (never splits a multi-byte rune, appends no ellipsis) — the reference's
head-cut is wrong for Aeon because `Sentence()`'s state-bearing clause is its LAST segment (`default deny

second, weaker formatter for the same verdict is what verdict.go exists to make impossible.
