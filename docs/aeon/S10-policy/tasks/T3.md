# T3 — `ToolAccess`, and six refusing stubs

> ## Notes — what the code actually does, 2026-10-19
>
> Recorded by `golang-engineer-loop` while landing `spec_toolaccess.go` + `spec_stubs.go` (loop
> `aeon-s10-policy`, task **T5** — the loop's numbering differs from this file's; the loop calls this task T5,
> this seed file calls it T3). Read this before touching a spec, before implementing one of the six, and
> before adding any list of tools anywhere in this package.
>
> ### The two pinned schemas that are now load-bearing
>
> `ToolAccess` is `{"toolName": string, "state": "allow"|"deny"}` — exactly two keys, both required, no
> wildcards (there is no `*`, no `bash*`, no regex, and `TestTheToolNameMatchesExactlyNotByPrefixOrCase`
> refuses `"ba"` matching `bash`, `"Bash"` matching `"bash"`, and `"bash "` matching `"bash"`). The six stubs:
>
> | Type | The pinned shape | Lands with |
> | --- | --- | --- |
> | `CommandAccess` | `{"command": string, "state": "allow"|"deny"}` | S11 |
> | `RouteAccess` | `{"route": string, "state": "allow"|"deny"}` | S18 |
> | `EffectClass` | `{"effect": string, "state": "allow"|"deny"}` | S16 |
> | `CostCap` | `{"token": string, "max": number}` | S17 |
> | `SkillAccess` | `{"skill": string, "state": "allow"|"deny"}` | S14 |
> | `TriggerAccess` | `{"trigger": string, "state": "allow"|"deny"}` | S20 |
>
> **Later slices replace the EVALUATOR, not the row format.** A stored row needs a shape or the write boundary
> has nothing to check and any JSON becomes a policy; the shape that ships is also the shape the app renders.
> So S11/S14/S16/S17/S18/S20 swap in their matcher in their own reviewed diff, extending the schema with their
> own migration if they need more — they do **not** silently reinterpret rows stored under these.
> `TestThePinnedSpecShapesMatchTheirGoStructs` locks each shape string against the Go struct that defines it
> (the accepted keys are read out of the struct by reflection in `newSpecSchema`), so adding a field to the
> struct without saying so in the shape is a failing test rather than a quiet drift.
>
> **`CostCap` is the one schema with no `state`,** and the reason is in the type's meaning: a cap is not
> something you deny, so an `Allow` *is* the grant and the presence of the row *is* the cap — a `state` there
> would be a second, contradictable copy of a fact the row already states, which is why `"state"` is an
> *unknown field* for `CostCap`. `max` is a `json.Number`: `1000`, `1000.50` and `1e3` are caps, `"1000"` is
> not (a quoted number is a string), `1e999` is refused as not finite, a negative is refused, and **zero is
> accepted** — "spend nothing" is a decision, and it is not the same policy as no row at all.
>
> ### The state/action consistency rule, and why it is enforced twice
>
> `spec.state` must agree with `p.Action`: an `Allow` row carries `{"state":"allow"}` and a `Deny` row carries
> `{"state":"deny"}`. A spec that says the opposite of its row is a policy that says two things, and there is
> no honest way to evaluate one.
>
> It is refused at the write boundary (`ValidateSpec`, named in `TestTheSpecStateMustAgreeWithTheAction`) **and**
> the evaluator refuses to act on a row whose state contradicts it
> (`TestAToolAccessEvaluatorIsTotalOnRowsTheValidatorWouldRefuse`). The second half is the load-bearing one:
> rows written before the rule existed are already in the database, and the only guarantee that matters is that
> such a row is **inert forever** — never permissive, not even by a refactor. It is pinned by a mutation
> (M5: delete the agreement check → the contradiction test fails), not by a comment.
>
> ### Q1, confirmed: the default blocklist is empty
>
> The reasoning in Scope §4 is the answer, and it travels with the test that enforces it
> (`TestTheDefaultBlocklistIsEmpty`, three subtests): **a default blocklist is a policy decision disguised as a
> safe default.** A deployment that wants `bash` refused writes that Deny and `doctor` reports what is in force;
> shipping a list would hand every deployment a choice nobody made for their situation. And "empty" is not
> "permissive" — PL5 already denies everything, so a built-in list would be a *second, unauthored* denial
> mechanism next to the one rules are written with, and a denial whose author nobody can find is exactly what
> the audit trail exists to prevent. `TestTheBlocklistGuardCanFail` proves the AST half of that guard fires on
> both shapes a reversal would take — a named list (`var defaultBlocklist = []string{"bash"}`) and an anonymous
> package-level `[]Policy` — and leaves legitimate code alone (`[]PolicyType{ToolAccess}`, the schema table).
>

>
> Three things about *how* they check, because they are not the obvious implementation:
>
> 1. **Distinguishability is measured against both denials, not one.** Each stub's refusal is compared against a
>    real policy deny *and* against the default deny. Comparing only against a policy deny is the trap: a stub
>    that quietly returned the default deny — roughly what a `(false, "not implemented")` shorthand produces —
>    would read as "the system has no opinion about this tool" when the truth is "this system cannot tell you".
>    All three answers differ from each other, which is what T11's three states need.
> 2. **"Every registered type" is derived, never typed out.** `TestTheRegistryCoversEveryType` walks
>    `policy.AllPolicyTypes()` (pinning the closed set at seven) and checks each has an evaluator, a validator
>    and a non-empty schema; then it checks what production code registers is exactly those seven **by constant
>    name** — a computed first argument arrives as `<not-a-constant>` and fails, because a type nobody can
>    enumerate is a type nobody can audit.
> 3. **The strict decode is two layers.** A pre-scan over `map[string]json.RawMessage` names every unknown key
>    (sorted, so a refusal is stable enough to pin in a UI) and suggests the key a typo meant
>    (`{"tool":"bash"}` → *did you mean `"toolName"`?*, threshold: shared prefix ≥3, and no guess at all for an
>    unrecognisable key — a wrong suggestion costs more than none). `DisallowUnknownFields()` plus a
>    trailing-content check is the enforcement that cannot drift:
>    `{"toolName":"git","state":"allow"}{"toolName":"rm","state":"deny"}` is refused as `trailing`, which a bare
>    `json.Unmarshal` accepts — and a spec whose first object allows while its second denies is the worst
>    possible thing to read as one decision.
>

## Why this exists

The first real spec, and the shape every later type copies.

**`ToolAccess` absorbs two things that used to be separate** — a tool *grant* and a *blocklist*. Under PL1
and PL4 they are the same object: an operator-authored `Allow` is a grant, a `Deny` from anyone is a
blocklist entry, and deny wins. **There is no second mechanism to keep in sync.**

**The six stubs are the point of this task as much as `ToolAccess` is.** `RouteAccess`, `EffectClass`,
`CostCap`, `SkillAccess`, `TriggerAccess` and `CommandAccess` have no evaluator until S18, S16, S17, S14,
S20 and S11. A `default:` branch returning allow would **silently grant everything they govern**, and the
grant would be invisible because nothing authored it.

**Read first:** `evaluate.go` (T2); the design's type table; S11's `W21` rescope, which is why
`ToolAccess` governs more than a fixed nine.

## Scope

**1. `spec_toolaccess.go`:** `{"toolName": string, "state": "allow"|"deny"}`, validated on write.

**An unknown field is refused, not ignored.** A typo like `{"tool": "bash"}` that parses into a zero value
is a policy that matches nothing — and **a policy that matches nothing is indistinguishable from a policy
that permits everything**, which is the worst failure this table can have. S4's T2 put `CHECK` constraints
on the columns for the same reason; this is the same argument one level in.

**2. Register the evaluator** for `ToolAccess` in whatever registry T2 established.

**3. `spec_stubs.go` — the six.** Each gets its schema (so a policy can be *stored* and validated) and an
evaluator that **refuses**, reporting *"no evaluator for this type yet"* — distinguishable from *"denied by
policy"*, because they are different facts and T11's three-state answer needs to tell them apart.

**4. Confirm Q1 in the notes: the default blocklist is empty.**

That is this design's answer, and the reasoning is worth restating because it looks like the unsafe choice:
**a default blocklist is a policy decision disguised as a safe default.** A deployment that wants `bash`
refused authors that, and `doctor` reports what is in force. Shipping an opinion here would mean every
deployment inherits a choice nobody made for their situation — and PL5 already denies everything by
default, so "empty" is not "permissive."
