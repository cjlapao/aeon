## Why this exists

A guard nobody can read is a guard nobody can fix. This is the whole surface for authoring and explaining
policy — and **it is deliberately the only one** (PL15).

**`why` is the verb that matters.** It answers *"what would happen if"* **without changing anything**, which
is what makes a counter-intuitive rule like PL4 learnable instead of mysterious. The demo's §3 is `why`
showing a specific allow losing to a broad deny *and naming the allow it lost to*.

**No authoring on HTTP or MCP, ever** (PL15, and R6's reasoning): exposing it would hand a caller the means
to widen the very guards written to constrain it. Reading a verdict is fine. Authoring is CLI and app only.

**Read first:** `store.go` (T5) — this surfaces its refusals and does not reimplement them; `verdict.go`
(T4) — this prints its sentence and does not format its own.

## Scope

**1. Four subcommands.**

| | |
| --- | --- |
| `list` | every policy, with target, action, source and expiry. **With none, says the default is deny** — not an empty line |
| `add` | authors one. Surfaces T5's refusal verbatim when the authorship rule bites |
| `remove` | by id |
| `why` | evaluates and explains, **changing nothing** |

**2. `why` takes `--at`** so expiry is explorable, and the demo's §6 depends on it. Default is now.

**3. `add` does not re-validate.** It passes the policy to T5 and prints what comes back. A second
validator is a second place for the rule to drift (T5's one-place assertion).

**4. Empty `list` is a statement.** `no policies. default is DENY (PL5) — nothing is granted until
something grants it.` A guard whose empty state reads as "fine" is this slice's one unacceptable failure.

**5. No credential anywhere near this** — it takes none, and nothing it prints is secret. Noted because
`--spec` is free-form JSON and somebody will eventually put something in it that should not be in shell
history (S15's O1, S23's C17).
