## Why this exists

Until this task, policy is a library nothing calls. **This is where it becomes a guard.**

**Structurally before, not textually before** (G12, generalised). Not *"check, then dispatch"* as source
ordering — **a dispatch that is unreachable unless the verdict allowed it.** The difference matters because
source ordering survives a refactor that moves the check into a branch nobody takes.

**And the test is a negative with a spy at zero.** *"A denied tool is never called"* cannot be demonstrated
by observing a failure; it is demonstrated by the tool's implementation having not run. S11's bash receipt
makes the same argument about spawning.

**Read first:** `internal/runtime/loop.go` as S5 left it — the tool-call loop; `verdict.go` (T4);
`spec_toolaccess.go` (T3).

## Scope

**1. `policy_gate.go`** — one function between the model's tool-call request and the dispatch table. It
takes the policies in force, the request, and `at`; it returns T4's verdict.

**2. Make the dispatch unreachable on a refusal.** Structure it so the call site cannot reach the tool
implementation without an allowing verdict — a type the dispatcher requires, or a single choke point with
no second path. **State in the notes which mechanism you used and why it cannot be bypassed.**

**3. The refusal reaches the model as T4's sentence.** The model needs to know *why*, not just *no* — a
refusal it cannot interpret becomes a retry loop, and the retry is what fills T7's table.

**4. `at` comes from the caller, once per step.** Not `time.Now()` per tool call: two calls in one step
evaluating against different instants could straddle an expiry, and the step's transcript would show one
tool allowed and an identical one refused with nothing to explain it.

**5. Do not touch attendedness** (PL14). G14 pins it at loop start; this gate reads it, never sets it.

**The unreachability mechanism, and why it cannot be bypassed.** The dispatcher call in `loop.go` is
reached if and only if an allowing verdict came back. `runTool` is the **sole route** from a model
`tool_use` block to the dispatcher — every entry point (`RunLoop`, `ResumeStep`'s loop, `RecoverStep`'s
CaseC re-run) funnels through it — and the gate sits inside `runTool` immediately after the
`unparseable`-arguments early-return and **before** the single `d.Tools.Call` expression. A refusal
`return`s before that statement, so there is no branch around the check: to "move the check into a branch
nobody takes" a refactor must delete the only dispatcher call in the file. `TestGateIsStructurallyBeforeDispatch`
backs the structure two ways — behaviourally (the spy `ToolCaller` records **zero** calls across three
denied attempts, and the gate was consulted exactly three times) and textually (a source grep pins that
`loop.go` contains **exactly one** dispatcher-call expression and that it sits after the
`d.Policy != nil` guard). **Every dispatcher call site found in `loop.go`: one** —
`res := d.Tools.Call(ctx, use.Name, use.Input)` in `runTool` (line 459 at this commit). Grep found no
inline/handoff second route; the handoff path returns before `runTool`.

`model.ToolResultBlock(use.ID, dec.Sentence, true)` and an `EventToolEnd{Result: dec.Sentence,

`time.Now` (grep; the adapter takes `at` as a parameter). **Attendedness is not touched anywhere in the
