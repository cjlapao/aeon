# T2 — drill-down

## Why this exists

D2/H2 (read the transcript, V15 does not apply) and Q3's resolution (archived content is a second, explicit
fetch, never pulled in in the time-ordered list).

**Read first:** `design.md`'s H2 and Q3 sections. The quote to anchor on: V15 is about what gets embedded,
not what gets read, and `ArchiveLoop`'s own "read content before the transaction, decode as little as
possible" discipline is what Q3's "header first" answer mirrors.

## Scope

**1. Live drill-down**: given a loop/step identity from T1's merge, read `step_message` directly — the same
query S9's per-loop view already issues, called from this package instead of duplicated.

**2. Archived drill-down**: given an archived-loop identity, a *separate* call (never bundled into the
list/merge result) that reads `loop_archive_file` on request. The merge's own entries for archived loops
carry only the `Archive` header fields — no file content anywhere in that path.

## Notes

**Decided — the live drill-down reads through the at-HEAD read S9's views already issue, not a second query
(D2/H2).** `LiveTranscript` walks the loop's steps (`ListSteps`) and concatenates each step's `ReadTranscript`
messages oldest-first — `ReadTranscript` is the read the S9 views (recover/question/memory) already issue at
HEAD, called from this package rather than duplicated. The per-loop window the task names — `ReadLoopTranscriptPage`
(S42) — is foreign WIP on another branch and is **not at HEAD**, so the package stays self-contained on HEAD and
reads the live transcript through the at-HEAD read instead; the two are the same read shape (one per step, the
loop's steps in seq order), not a second implementation. V15 does not apply (H2): it is about what gets *embedded*,
not what gets *read*, so a transcript is read only when a person asks for it, never pre-fetched. A non-live entry
is refused by name (`WrongDoor`, DB19) — an archived loop's `step_message` is gone from the live tables, so reading
it as empty would read as "no transcript," a lie for a loop whose content is simply in the other table.

**Archived drill-down is a second, explicit fetch, never bundled (Q3).** `ArchivedTranscript` reads
`loop_archive_file` on demand via `ReadArchive(id, true)`, a separate call. The merge's entries carry only the
`Archive` header — `ListArchives` reads no `loop_archive_file`, and the `Entry` type has no file-content field by
construction, so the merge *cannot* have pulled a file a person never opened (the zero-read half). A drill reads
exactly one (the one-read half). A live entry asked of the archived door is refused by name (`WrongDoor`), the
mirror of the live door's refusal.

**Deviation (files_expected, small and necessary).** The task's `files_expected` lists `drilldown.go` and
`drilldown_test.go`; T2 also made a one-field addition to T1's `query.go` — `Entry.ComponentRoot` — because the
live drill-down builds its `Scope` from the loop's slug **and** component root, and the merge entry carried only
the slug. It is an additive field (both live and archived entries populate it from `ListLoops`/`ListArchives`),
no behaviour change to T1's merge or lanes, and no new table/column (D5 still holds).
