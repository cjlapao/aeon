# T3 — `aeon history` CLI

## Why this exists

The first concrete surface over `internal/history`, and where H3's parity guarantee (export and the view
never drift) is proven for the first of two surfaces that need it (T4 is the second).

## Scope

**Verbs**: `aeon history list [--project-root …] [--group-by loop|phase|task|agent] [--since …]` ·
`aeon history show <loop-or-archive-id>` (drill-down, T2) · `aeon history export [--group-by …] [--since …]`
— NDJSON, one object per line, **the identical query `list` uses**, not a second query that happens to
produce similar-looking output.

**Every rollup number renders through T1's floored type** — "at least $X (K of N steps unknown)" whenever
`Floor` is true. A bare `$X` is only ever printed when `UnknownCount == 0`; this task adds no second code
path that could print a bare number by forgetting to check `Floor`.

## Validation

- [ ] `TestExportAndListShareOneQuery` — call-site assertion: both verbs call the same
      `internal/history` function, parameterized only by output format
- [ ] `TestExportIsNDJSONOneRowPerLine` — output parses as one JSON object per line, matching the shape
      `list`'s own rows have
- [ ] a `blocked` loop's reason prints verbatim (D4), asserted against a fixture with a known
      `BlockedReason.Detail`

## Notes

**Decided — `aeon history` is a pure read through `internal/history`, a secondary client (P34).** The verb
opens the store via the shared `openStoreDirectly` (the justified second access path, as `policy` does) and
reads through the read-only `internal/history` package. It adds no store method, no table and no column (D5).
The app reads the same facts through the socket's `history.*` methods (S25 T4); the CLI and the socket read
the same `internal/history`, so the two cannot drift. The verbs take an injectable `*store.Store` (the
`policy` test idiom); the command opens it, a test reaches the same query with a temp store, never the real
one.

**H3 — `list` and `export` share ONE query, proven here for the first of its two surfaces.** Both call
`historyQuery` (the one read, `Merge` by loop, `Lanes` for a non-default grouping, flattened back to the entry
sequence so a regroup never changes a loop's facts); the only difference is the output — a human table,
NDJSON one object per line. There is no second query, so a cost or a reason cannot come out differently under
`list` than under `export`. The two gates pin it: `TestExportAndListShareOneQuery` asserts both verbs yield
the same set of rows as the shared query's own output, and `TestExportIsNDJSONOneRowPerLine` asserts each
line is one JSON object with the shape `list`'s rows have (the one `rowOf`).

**H6/P32 — every cost renders through the one floored formatter.** A row's cost is `Rollup.Render`:
"at least $X (K of N steps unknown)" when floored, a bare "$X" only when `UnknownCount == 0`. This verb adds
no second cost path, so it cannot print a bare number by forgetting to check `Floor`.

**D4/H4 — a blocked loop's reason is the stored reason, verbatim.** A row's reason is `Entry.Reason`, read
from the `loop.blocked` event stream (T1), never a synthesized verdict. `TestHistoryShowsABlockedReasonVerbatim`
pins it against a fixture with a known reason, in both `export` (the JSON `reason` field) and `list`
(the `blocked: …` line).

**Q3 — `show` is the drill-down (T2), by an entry's id.** `show` finds the entry in the shared query (so it
reads the same facts `list` does, never a second query), then reads it through its own door: a live loop's
transcript, an archived loop's cold-stored content on demand. A wrong entry is refused by name (DB19), not
read as empty.
