## Notes (T6 — the walk)

**Real run, not predicted.** All six numbered steps of `S25-history/DEMO.md` were walked against a real
`aeon` binary built from this checkout (`sqlite_fts5`) on a throwaway `XDG_STATE_HOME=/tmp/aeon-demo-state`,
with a fixture of three loops: one `running` (a known-cost $8.00 step, has a transcript), one `done` (a
known-cost $10.00 step with a transcript + an `unknown`-cost step with no messages), and one **archived**
(its `notes.md` written directly through `Store.ArchiveLoop`, since no CLI verb exists — `design.md` Q4).
The setup seeded the store directly through `*store.Store` (bypassing the no-`ArchiveLoop`-verb
limitation); every quoted line below is from that real run. **Steps 1–2 and 4–6 ran green; step 3
errored** — the three findings below are the deviations from the prediction, all stated plainly, none
softened.

- **F-1 — the archived loop sorts FIRST, not by creation order.** Step 1's `list` placed the archived
  `ghost` at the top of the sequence, above both live loops. The prediction said it would be "placed
  correctly by its original timestamps — not pinned to the end just because it was archived last." The code
  instead orders by the loop's *own timeline* (`Merge` sorts `Entry.Timeline` descending: `updated_at` for
  a live loop, `ended_at` for an archived one) — the archive's `ended_at` was the newest of the three, so
  it lands first. The "not pinned to the end" half of the prediction is true; its "by its original
  timestamps" half is not: an archived loop is ordered by when it *ended*, not when it *started*.

- **F-2 — `--group-by agent` drops the archived loop.** Step 2's grouped view returned only the two live
  loops' steps (the `done` loop twice — one row per agent — and the `run` loop); the archived `ghost` is
  absent. `Query`/`Lanes` regroup only the live entries; an archive is not a lane. The prediction said
  "the same three loops' steps regrouped by agent"; only two of the three survive a regroup.

- **F-3 — drilling the `done` loop errors; it does not show the floored rollup.** Step 3's prediction was
  that drilling the loop reads "at least $X (1 of N steps unknown)". The floored rollup *is* shown — but
  by the `list` (step 1: `at least $10.00 (1 of 2 steps unknown)`), not by the drill. `history show` reads
  a **transcript**, not the rollup; the `done` loop's second step (the `unknown`-cost `verify` step with
  no messages) has no transcript, so the drill errors: `aeon: history: read the live transcript of step 3:
  step 3 has no transcript`. The rollup and the transcript are two different reads; the prediction
  conflated them.

**Step 5 (export) proved H3 for real.** `history export --group-by loop` into a file returned the same
three rows as step 1's `list` — identical `kind`/`id`/`cost` (NDJSON just adding `title`/`timeline`
columns) — so the CLI and the NDJSON emitter are one query (H3), proven by running both and comparing, not
merely arguing.

**Step 6 (force `blocked`) proved D4/H4 for real.** Forcing the `run` loop to `blocked` with a recorded
`loop.blocked` event, the re-list showed its status `blocked` and its reason **verbatim** —
`blocked: no shell in review — the PR is closed` — never a synthesized "failed." A blocked loop with no
recorded reason renders an honest empty, not a fabricated verdict.

**Not shown, stated plainly.** (a) **The UI half is unrun** — this checkout has no Tauri/webkit2gtk, so the
`HistoryPage.tsx` render (T5) is not exercised here; its 7 vitest gates (clean-tree-verified) are the
witness, not a live click-through. (b) **No large fixture** — the three-loop fixture is too small to
produce a meaningful query plan, so Q1's "measure before indexing" is not validated by this walk (the
DEMO's own "does not show" note, honored).
