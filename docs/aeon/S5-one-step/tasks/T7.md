## Context

**The only safety boundary in this slice**, which is why it is a task of its own rather than a bullet inside T8.

There is no command policy until S11. So the allow-list is what stands between a step and an unrestricted
shell — and D1's test has to prove refusal **by attempt**: the model asks for `bash` and cannot get one.
"The toolset map does not contain bash" is a much weaker claim, and it would pass against a loop that
constructed the tool anyway from a name it recognised.

**A model asking for a tool it lacks gets told what it does have** (O6). Not silence, which it cannot recover
from, and not a step failure, which it can: a `tool_result` with `IsError` naming the missing tool and listing
the available ones lets the model choose differently on the next turn.

**A panicking tool must not take down the daemon** (O5). One daemon serves every project on the machine, so a
panic in one step's tool killing the process stops every other loop. Caught, converted to `IsError`, step
continues.

**But the boundary must not swallow a programmer error** (K20). An invalid handler or a nil dependency should
crash loudly at the boundary rather than being reported to a model as a tool failure. Name where that line is
(Q8).

**Read first:** `bash.go` and `read.go` (T5, T6); `docs/_archive/aeon-v1-horizontal/05-tools/tasks/T8.md` for `createToolset`;
the plan's Q8.

## What to do

**1. `toolset.go`:**

```go
func BuildToolset(granted []string, ctx ToolContext) (Toolset, error)
```

`granted` is the **only** thing determining what a step can call. An unknown name in it is a **construction
error** — a typo in a grant list should fail at construction, not silently grant nothing.

**2. The missing-tool response** (O6). When the model emits a `tool_use` for a name the toolset lacks, return a
`tool_result` with `IsError: true` whose content names the tool and lists what is available. The loop (T8)
continues.

**3. The panic boundary** (O5). Wrap each tool's execution. A panic becomes `IsError` with the recovered value
summarised. **Do not wrap construction** — a nil dependency or a bad grant list must panic at build time, where
the stack names the caller, rather than being reported as a tool failure at turn three.

**4. Write D1 as an attempt.** Build a toolset granted `["read"]`, drive a scripted fake client that emits a
`tool_use` for `bash`, and assert: no bash tool exists, no process is spawned, and the model receives a
`tool_result` naming `read` as what it has. Assert the no-spawn part by **observing process creation**, not by
the absence of an error.

**5. Assert the grant list is the only determinant** by grep: no other code path constructs a tool.
