>
> `step:ad-hoc declares bash, which this step was not granted. Granted: read`. "Tool not granted" alone leaves a

> ### `MaxOutputTokens` is required, deliberately not defaulted
>
> One provider REQUIRES the field, and a silent default truncates a long report with nothing saying why (S3's
> M16). The reason string says `truncates`, and a test asserts it does — so the next person to "helpfully" add a
> default has to delete an explanation first.
>
> ### The default handler's section order: Task, Workspace, How to work
>
> Q9. A model reads top to bottom, and a prompt buried under path conventions is a prompt the model weighs less
> than the conventions. Asserted by comparing the three sections' byte offsets in the rendered message.
>
> ### The schema shown and the spec enforced are checked against each other
>
> `DefaultHandoffSpec()` validates; `DefaultHandler`'s `HandoffSchema` is what the model is SHOWN. They are
> separate on purpose — one explains, one enforces — so a test walks the spec's required fields and enums and
> fails if the schema does not mention each. A schema promising a field the validator does not require is a field
> models stop sending.

## Context

The boundary between "what the caller wants done" and "what the model is asked", and its job is to **fail
early**.

**A handler declaring a tool the toolset lacks must fail at construction**, with a reason naming both the
handler and the tool — not on first use, three model turns in, as a tool-call failure the model then tries to
work around. A model cannot diagnose a missing tool, and the transcript that results is a confusing record of
it improvising.

**`MaxOutputTokens` is required** (M16), because Anthropic rejects a call without it. A missing value is a
construction error, not something the adapter defaults — defaulting here would hide the requirement from
whoever writes the next handler.

**The handoff schema is derived once**, not per retry. Deriving it twice is a place two shapes could differ, and
the retry is exactly where a mismatch would be least visible.

## What to do

**1. `compile.go`:**

```go
func CompileRequest(h StepHandler, input any, granted []string, d ContextDeps) CompileResult
```

**2. Assemble the sections** through T2. A handoff from a previous step, when there is one, becomes **its own
named section** rather than being spliced into another — the model should be able to tell a prior report from
its own instructions.

**3. Validate the tool list at construction.** Every name in `h.Tools` must be in `granted`. A miss returns a
failure naming both. Assert the failure happens **before any model call**, with a `Client` spy at zero.

**4. Derive the handoff's JSON Schema once**, here. In Go that is a hand-authored schema on the handler or one
produced from a struct — either way, produced once and carried, not regenerated.

**5. `MaxOutputTokens`** from the handler or the limits file, always present, and a missing value is a
construction error.

**6. The test that matters is negative**: a handler declaring `bash` against a grant list of `["read"]` returns
a failure whose reason contains both names — and the `Client` spy shows zero calls.
