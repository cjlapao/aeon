> ### Two panic boundaries, and what each deliberately does not catch
>
> `runGuarded` turns a panic in the LOOP into a `failed` result whose reason says *"This is a defect in Aeon
> rather than a problem with the request"* and carries the stack. It does NOT wrap construction: a nil dependency
> there panics where the stack names the caller.
>
> `guardedSink` wraps the sink — the CALLER's code, which at S9 will be an app — and **counts** failures onto the
> result rather than swallowing them. A client seeing no events and a successful result would otherwise have no
> way to tell which half broke. The sink is wrapped BEFORE `step.started` is emitted, and a test panics on exactly
> that event: a guard added later would miss the one case that kills the step before it begins.
>
> ### The caller's request is copied, not mutated
>
> Two tests: the manifest's `IterationsUsed` and the message slice. A step that incremented the caller's manifest
> in place would make a retried request start part-spent.

## Context

The seam three later slices depend on, and its most important property is a **negative** one.

**`RunStep` persists nothing** (K6, D15). That is what makes S7 possible: recovery reads rows from a previous
process and hands them to the same function. If the runtime opened a store, recovery would have to either
duplicate the loop or persuade it to accept somebody else's rows — and the second is how two loops appear.

So the test is a **store spy asserting zero calls**, plus a grep proving no store import. Both, because the
grep catches an import and the spy catches a passed-in handle used anyway.

**The sink is synchronous and lossless** (K19). S9 streams these to the app over the protocol, so they must
arrive **as they happen** — a step running four minutes with no output is indistinguishable from a hung one.

**A throwing sink must not kill the step.** A sink is a consumer, and losing a step's work to a logging bug is a
bad trade. Count the failures and report them.

**Programmer errors panic; step failures return** (K20). An invalid handler is a bug in the caller and should
crash loudly. A model failing its handoff is a normal outcome. Conflating them either buries real bugs inside a
`failed` result or turns ordinary model behaviour into a crash.

**Read first:** `loop.go` (T8); the superseded slice's event list (plan Q2); `internal/protocol/ask.go` (S3) for
how the sink reaches subscriptions.

## What to do

**1. `runstep.go`:**

```go
func RunStep(ctx context.Context, req StepRequest, opts RunOpts) StepResult
```

`RunOpts` carries the `model.Client`, the toolset and the sink — all injected, which is what makes D18
achievable.

**2. Emit in order**: `step.started`, then per iteration `model.delta`, `step.tool.start`, `step.tool.end`, and
finally `step.done`. **Keep the superseded names unchanged.**

**3. Wrap each sink emit.** A panicking sink is caught, counted, and reported on the result. Do not let it
propagate.

**4. Return exactly once**, for all four outcomes.

**5. `RunStep` opens no store**, imports no store package, and performs no I/O beyond its injected dependencies
(I3).

**6. Tests.** The store spy at zero is the important one. Then: the sink called **during** the step rather than
after — asserted by having the sink record the iteration count at call time and observing it vary; a throwing
sink not killing the step; and one panic case versus one returned-failure case.
