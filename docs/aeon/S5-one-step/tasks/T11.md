# T11 — The CLI: `aeon step`, `aeon step show`

> ## Notes — done 2026-10-16
>
> ### Built: `cmd/aeon/step_run.go` (437 lines), `step_run_test.go`
>
> `aeon step "PROMPT"` runs a step; `run` is accepted as an explicit spelling; `show`, `verify` and `list` keep
> their S4 meanings. Anything that is not a known subcommand is a prompt — the thing a person types first is
> what they want done, and that is the difference between a demo that is one command and one that is two.
>
> ### `--allow-bash` warns on stderr EVERY time, and the warning is not suppressible
>
> Tested three times in a row, because a warning printed once and then remembered is a warning nobody sees on the
> run that mattered. The same warning fires for `--tools read,bash`: attaching it to one flag rather than to the
> grant would make it easy to route around. And a read-only step prints nothing — a warning on every run is a
> warning nobody reads.
>
> ### The streaming is concurrent, and it has to be
>
> The `step` method blocks for the whole step, so the call runs in a goroutine while this goroutine drains
> events. The client DROPS events rather than blocking its read loop (S2's `EventBuffer` is 256), so draining
> concurrently is not an optimisation: a step emitting a delta per token would overrun the buffer in seconds.
>
> ### Only `failed` is a non-zero exit
>
> `reject` and `blocked` exit zero. The step worked and the answer was no, or it ran out of room — and a script
> treating every non-`ok` as a crash would retry a considered refusal.
>
> ### `--manifest` and `--requests`
>
> `--requests` reconstructs the model-call boundaries from the stored transcript and **states what it cannot
> show**: which tools each call offered. The transcript stores the conversation, not the request envelope, so the
> tool-free retry appears there as a final text answer. The property itself is asserted on the request object in
> `internal/runtime`, which is the only place that object exists. The spec'd demo text claimed this view shows
> the empty tool list; it cannot, and the demo now says so.
>
> ### Findings from the walk, fixed here
>
> `aeon step --help` printed the flag list and then exited 1 with `flag: help requested` — `ErrHelp` is a
> question, not a failure. `--allow-bash`'s own description said only "grant the shell tool", with the
> consequence nowhere a person reads before using it; the description now carries it, and the flags are declared
> in one function the test reads, so a copy of the text cannot stay right while the real one changes.

## Context

The skateboard, made runnable. And it carries one piece of text more consequential than any code in the slice.

**`--allow-bash` must warn on stderr every time it is used** (O1), not only in `--help`. A flag whose danger is
documented only in help is a flag somebody copies out of a shell history six months later, in a repository they
care about, having never read the help. The warning is one line and it is the difference between an informed act
and an inherited one.

Its help text must say, in plain words, that **there is no command policy until S11** — not "grants shell
access", which reads as a capability rather than a hazard.

**Without the flag, the step has `read` only.** The demo's most important negative check is a step being asked to
run a command and being unable to, and that behaviour must be visible from the CLI.

**`blocked` must render differently from `failed`.** A user seeing "failed" investigates their prompt; one
seeing "blocked: exceeded MaxIterations (12)" raises a number. The whole reason they are separate outcomes is
lost if the CLI prints both in red as "error".

**Read first:** `internal/protocol/client.go` (S2 T6); `step.go` (T10); `cmd/aeon/ask.go` (S3 T11) for the
streaming and cost-line patterns to match.

## What to do

**1. `aeon step <prompt>`** — subscribe to `step.*`, call `step` with the subscription id, print events as they
arrive: text incrementally, and one line per tool call showing the tool, its argument summary, and its result
summary.

Flags: `--allow-bash`, `--max-iterations`, `--tools` (explicit list), `--workspace`.

**2. `--allow-bash`:**

- adds `bash` to the grant list
- **prints a one-line warning to stderr on every use** (O1)
- its `--help` text states there is no command policy until S11 and that the model can run anything the user can

**3. The outcome line** distinguishes all four, with `blocked` carrying the bound and its value.

**4. The cost line** matches S3's three renderings exactly — `known`, `at least … (partial — missing: …)`,
`not reported (reason)`. Never `$0.00` for unknown.

**5. `aeon step show <id>`** — the transcript. `--json` for canonical JSON, `--manifest` for the frozen manifest
with hashes, iterations and deadline, and `--requests` for the requests sent — which is how the demo shows the
retry carrying no tools.

**6. Tests against a real in-process daemon on a temp store**, not a mock. And assert the stderr warning by
capturing stderr, not by reading the source.
