>
> Both bounds, with the client's call count at zero. Checking after would spend a request to discover there was no

> `exceeded MaxIterations (1)`.

>
> The step did not run out of room; something stopped it. A caller that cancelled knows why, and one that did not

>
> S3's M9. Two absent counts add to absent, not to 0 — a step whose provider reported no usage must not report a

## Context

The runtime's substance. **One loop** (I4) — S6 adds suspension to it and S7 calls it with rows read from the
store, so a second copy would drift, and drift is what breaks resume.

Three properties are easy to get subtly wrong, and each has a specific test shape.

**Serial execution** (K9, D3) needs a spy that would **detect** concurrency. One recording call order passes
against an `errgroup` implementation; one recording **entry and exit timestamps and asserting no overlap** does
not. Serial execution is what makes a transcript reproducible and what stops two tools writing the same file in
an order nobody chose.

**The retry is tool-free**, and the assertion is on the **request object** (K4, D4). Not "a retry happened" —
that passes against a retry offered tools it happened not to use. A retry that *can* call tools can start new
work: a step that already did its job doing it again, differently, while ostensibly restating its report.

**Exceeding a bound yields `blocked`, not `failed`** (D5, O2), naming the bound **and its value**. A caller
seeing `failed` files a bug report; one seeing `blocked` raises the budget. Conflating them sends every
over-long step to the wrong response, and "blocked" without the bound's name tells a caller to raise something
without saying what.

**Read first:** `compile.go` (T3), `handoff.go` (T4), `toolset.go` (T7); the superseded slice's bounded-loop
task; the plan's Q6 for what an unparseable tool argument owes.

## What to do

**1. `loop.go`** with one exported function both entry points will call:

```go
func RunLoop(ctx context.Context, st *LoopState, d LoopDeps) StepResult
```

`LoopState` carries the transcript, the manifest (holding `IterationsUsed` and the absolute `DeadlineAt`), and
the compiled request. `LoopDeps` carries the injected `model.Client`, the toolset and the event sink.

**2. Each iteration:** stream from the client, forwarding deltas to the sink **as they happen** (K19); collect
`tool_use` blocks.

- **No tool calls** → extract and validate the handoff (T4). Valid → `complete` with `ok`/`reject` from the
  handoff. Invalid → re-ask **once**, building a `ModelRequest` with **no tools key at all**; a second failure →
  `complete` with `failed`, transcript and partial usage intact.
- **Tool calls present** → execute **serially, in emission order** (K9), appending each `tool_result`.
- **A tool the step lacks** → `IsError` naming what is available (T7's O6), and continue.
- **An unparseable tool argument** (Q6) → `IsError`, continue. A model emitting bad arguments is normal.
- **Check bounds** before the next iteration: `IterationsUsed` against `MaxIterations`, the clock against
  `DeadlineAt`. Either exceeded → `blocked`, reason naming the bound and its value.
- **Honour `ctx`** between iterations and pass it to the client and the tools.

**3. Increment `IterationsUsed` on the manifest**, not a local — so S6 can persist it across a suspension without
changing the loop.

**4. Never produce `suspended`** (K21). S6 adds the path.

**5. The spy.** Each fake tool records entry and exit times; the test asserts no two intervals overlap. Assert
emission order separately, so a failure tells you which property broke.
