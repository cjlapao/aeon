> Both of this task's hard assertions are proven against real processes rather than fixtures.
>
> ### `oomKilled` from a genuine SIGKILL
>
> `kill -9 $$` — the shell kills itself, the kernel reports `exit=-1, signal=killed`, and the heuristic catches
> it. A second test asserts `exit 137` is ALSO caught and reports **no signal**, which is the measured difference
> (Q4c) and exactly why the field is a heuristic:
>
> ```
> a real SIGKILL   exit=-1   signal=killed
> exit 137         exit=137  signal=""
> ```
>
> The rendered message says the two are indistinguishable rather than diagnosing an OOM, and a test asserts it
> does not claim "out of memory" without that caveat. `kill -9` from a person, a supervisor and the OOM killer
> are the same signal; a diagnosis is a claim this layer cannot make.
>
> ### Group termination proven by a FREED PORT, with a control that proves the control
>
> The positive test starts `bash`, which backgrounds a grandchild holding a real TCP port; the timeout fires; the
> test waits for the port to become bindable. The negative control does the same without `Setpgid`, kills only
> the parent, and asserts the port is **still held**.
>
> Without that control the first test passes against an implementation that kills one process — because `bash`
> dies either way and the return code is identical. **The port is the only observable that distinguishes "the
> group is gone" from "the parent is gone and its child still holds a resource."**
>
> The grandchild is the test binary re-invoked through `TestMain`, so the suite needs no `nc`, no `python3` and
> nothing outside the module.
>
> ### Two things the walk of this test taught
>
> A buffer for the child's stdout makes `cmd.Wait` block until **every** writer of the pipe closes — including
> the grandchild. The control therefore writes to `/dev/null`, or it hangs for the ten seconds the holder lives.
> And the holder writes its own pid to a file, because once the parent is dead `Kill(-pid)` on the shell's pid
> signals nothing: without `Setpgid` the shell was never its own group leader, and a negative kill there would
> have killed the test run.

## Context

Its own task because its four bounded-discipline properties fail differently, and one of them is the assertion
most likely to be faked in the whole slice.

**This tool has no policy** (W12). No pattern list, no denials, no `ask`, no prompt. The 50-pattern corpus, the
seven authored `ask` rules and the human prompt are **S11**. `bash` at S5 runs what it is given, which is why
T7's allow-list is the only boundary and why the demo says so.

What lands now is the **bounded-command discipline** (W13), and it is about a step not hanging rather than about
permission. Four properties, four failure modes:

- **A command that never exits** must return `timedOut: true` with its partial output. A step waiting forever is
  a loop nobody can diagnose.
- **A command reading stdin** must fail promptly. Leaving stdin open means `cat` blocks for the whole timeout,
  and the symptom looks like a slow command rather than a stuck one.
- **`oomKilled` must be distinguishable from an ordinary non-zero exit.** Without it an engineer chases a phantom
  compiler bug while the real problem is the machine. **The test must actually SIGKILL a process** — an
  `oomKilled` assertion built from a hand-written fixture that never killed anything is not evidence.
- **The whole process group must die**, children included, with `SIGTERM` escalating to `SIGKILL`. Proven by a
  **freed port**, not by a return code: a return code tells you the parent exited and says nothing about what it
  spawned.

**Read first:** `docs/_archive/aeon-v1-horizontal/05-tools/tasks/T5.md` and `T6.md` — the bounded discipline, **not** their policy
content, which is S11's; the plan's Q3 for the timeout's provenance and Q4 for group termination.

## What to do

**1. `spawn.go`** — the bounded process layer:

```go
type RunResult struct {
    ExitCode int
    Signal   string
    TimedOut bool
    OOMKilled bool
    Stdout, Stderr string
    StdoutTruncated, StderrTruncated bool
    StdoutBytes, StderrBytes int   // TRUE sizes, before truncation
}
```

Set the process group so children can be signalled together (Q4). **Close stdin.** Cap stdout and stderr per
`limits.go`, keeping the true sizes. On timeout or cancellation: `SIGTERM` the group, wait the grace period, then
`SIGKILL`.

Detect `oomKilled` from exit 137 / `SIGKILL` — and state in a comment that this is a heuristic, because a process
killed by something else also looks like this.

**2. `bash.go`** — the tool. One parameter, `command`. Returns a result string a model can read: exit code,
whether it timed out, whether it was OOM-killed, and the captured output with truncation **stated**.

**No policy check.** Assert its absence by grep — no pattern matching, no deny list, no `ask` (S11 owns them).

**3. Tests.** The four properties above, each actually exercised:

- `sleep 9999` with a short timeout → `TimedOut`, partial output present
- `cat` with no input → fails promptly, asserted with a test timeout well below the command timeout
- a process the test **SIGKILLs** → `OOMKilled: true`; an `exit 1` → `false`
- a command spawning a child that holds a port → after termination, the port is **free**
