## Why this exists

**The property worth proving is that this slice decides nothing.**

A CI-triggered loop is **unattended**, so S16's effect classes apply: `outward` and `irreversible` resolve to **deny** (L22
with G7). **CI cannot open or merge a pull request unless someone opted in at loop start.**

Combined with T5, the narrow surface is **read-mostly by construction** — not by policy. Nothing has to be configured
correctly for that to hold, which is a stronger property than a permission list somebody maintains.

So this task's job is mostly to make sure the composition is real, and to add the one deliberate opt-in.

## Scope

### A triggered loop is unattended (D9)

**Confirm Q4**: how does `loop.start` take its attendedness today, and can a caller set it?

A loop triggered through the narrow surface is unattended by default, for the reason G14 gave: attendedness is **declared
at start and pinned**, never inferred from whether a client is connected. A CI job is not present in the sense a gate
needs, and a poll every ten seconds does not make it so.

### `allowOutward` is per loop, not per key (D10, O2)

```
POST /v1/loops  {"blueprint":"dev-loop","prompt":"…","allowOutward":true}
```

**Per loop.** A key that permanently grants outward actions is **a key whose theft is unbounded**; a per-loop flag makes
each grant a decision someone made at a moment.

And it is **one field, at the one moment someone is deciding what this run is allowed to do** — which is the right place
for it, because that is when the question is in front of them rather than six weeks earlier in a config file.

`allowOutward` does **not** grant `irreversible`. Merging is a separate matter and there is no field for it here: a CI job
that should merge is a CI job someone should have thought harder about, and S16's ask exists for that.

### End to end, not by policy read (D9, C8)

The test drives a triggered loop **until it reaches an outward action** and asserts the denial arrives — rather than
asserting that a policy table says it would.

**That distinction is the point of the task.** A test that reads the effect class proves the class is set; a test that runs
the loop proves the composition holds, and the composition is what the claim rests on.

### Not in scope

Effect classes (S16's). Attendedness's mechanism (S11's). This task wires a trigger to them and proves the result.
