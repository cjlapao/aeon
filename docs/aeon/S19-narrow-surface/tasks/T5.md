## Why this exists

**The sharpest decision in the slice**, and it follows from what a key is not.

A key authenticates *a caller*. **It does not make the caller a human.** So:

> **Can the narrow surface answer a question? No** (N16).

A gate exists to reach a human. **If CI can answer a gate, the gate is decoration.** And S11 already took the consistent
position: an **unattended** loop *denies* an `ask` rather than having it auto-answered (G7, G14). Letting a credential
answer would be the same mistake with a bearer token attached.

It comes after both mountings (R6's ordering) so the assertion covers **both surfaces**.

## Scope

### Readable

A `read` action lists a loop's open questions: id, kind, prompt, and the declared answer set. CI polling a loop needs to
know *why* it stopped, and *"waiting on a gate"* without the prompt is not an answer someone can act on.

Kinds are visible — a step question, a gate, a permission ask — because a human deciding whether to go and answer it
benefits from knowing what is asking. **That is not S9's U14 being contradicted**: U14 forbids distinguishing the mechanism
*to the person answering inline*; a monitoring surface reporting what a loop is blocked on is a different audience.

### Never answerable (N16, D6, D8)

**Asserted over the whole table** (C6), not by checking that a specific answer action is absent — the same reasoning as
T1's forbidden enumeration. The risk is an action added later whose name nobody thought to forbid.

And the refusal, when someone tries the obvious URL:

```
404  no such action

  Answering a question requires a person. A gate exists to reach one, and a key
  authenticates a caller rather than a human.

  Instead: answer in the app, or `aeon answer <id> <value>` from a terminal.
```

**404 rather than 403**, because the action does not exist — the same absence-not-refusal reasoning as N14. And the body
carries the reason and the alternative (O3).

### Never creatable (N6)

Also asserted over the whole table.

N6's reasoning: *"a fabricated prompt, once answered, feeds a value into a transcript as though the model had asked for
it."* A question the model never asked, answered by a human who assumed it did, puts a value into a transcript with false
provenance — which is a worse failure than either half alone.

### Both are permanent (§8 N3)

Not deferred. There is no future key, flag, or trusted caller for which this changes. Worth a comment in the code saying
so, because the next person to want it will look for the flag first.
