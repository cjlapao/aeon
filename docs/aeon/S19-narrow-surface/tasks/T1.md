## Why this exists

**First** (R4), because both mountings project this table — and building a mounting first means the table gets shaped by
whichever came first rather than by what belongs in it.

**The boundary document is in this task** (R5), not a later addition. N14 is absence **plus** legibility, and legibility
bolted on afterwards is legibility nobody wrote a test for.

## Scope

### The table (N12, N13)

```go
type Action struct {
    Name         string
    SocketMethod string     // N13 — the method this projects; asserted to exist
    Kind         Kind       // read | trigger
    Cannot       []string   // N12 — what this entry cannot do
}

// Actions is the ONLY registration point (O7).
func Actions() []Action
```

**Answer Q8 first** — the full table: name, socket method, kind, and `Cannot`. **A missing table blocks the plan**, because
D1, D3 and D5 all assert against it.

### Derived, not parallel (N13, D3)

Every entry's `SocketMethod` must **exist in S2's method table**, asserted against **that table** rather than a copied list
(C4). Two hand-maintained surfaces drift.

This is the third time this reasoning has applied: S9 generated its types from the protocol contract, S18 took policy from
one extractor, and this projects from one method table. At three it is a habit worth naming.

**Confirm Q1**: does S2 expose enough for every read action? **If any needs a method that does not exist, record the finding
about S2 — do not add one** (N8, R12). A narrow surface that grows the protocol is a narrow surface driving the wide one.

### `Cannot` is enforced, not decorative (N12, D5)

N12 requires *"every entry states what it cannot do"*. **An empty `Cannot` fails.**

Every narrow action is narrower than the socket method it projects, and **the difference is the point**. An entry that
cannot name its own narrowing has not been thought about.

### No operational control, by enumeration (N5, R6, D1, I1)

```go
// Asserted over the WHOLE table, not against named actions.
var forbidden = []string{"stop", "kill", "pause", "resume", "retry", "answer", "abort", "cancel"}
```

**An enumeration over the table, not a check for specific names** (C2). The risk is not the action someone would think to
forbid — it is **the one added in a year that nobody thought about.** A test that checks `kill` is absent passes the day
someone adds `terminate`.

R6's reasoning, unchanged since v1: *"handing an agent the means to start loops is handing it a way around every bound
placed on one."*

### The boundary document (N14, O3, D2)

Absence alone produces *"unknown tool"*, which reads like a **version mismatch** — so someone goes looking for the newer
Aeon that has it. A refusing tool would be **discoverable**, which is what R6 forbids.

So the surface itself carries the statement, and **it names what to use instead** (O3):

```
aeon has no operational control actions, by design.

  Available:  aeon_loop_start (trigger)
  ABSENT:     stop, kill, pause, resume, retry, answer — not restricted, absent.

  Reason: handing an agent the means to start and stop loops is handing it a way
  around every bound placed on one.

  Instead: `aeon loop stop <id>` from a terminal, or the app.
```

**A boundary that says only "no" leaves the caller stuck.** One that says "no, use this" is a redirection.

`aeon/docs/NARROW.md` carries the same content for a human reading documentation rather than a tool listing.

### Not in scope

Either mounting (T3, T4), auth (T2). This task is the table, its guarantees, and its boundary.
