# T8 · The app adapters: enriched hint consumer and `aeon://navigate`

**Prefix:** SV · **Rules:** SV9, SV18 (adapters only) · P7 (rules that apply) · **Depends on:** T4, T7; S45 T9 only if a shared component is reused. Parallel-safe with T6.

## Goal

The app consumes what T4 and T7 produce — without building the Inbox, Mission or Channels screens (specified in `design.md` SV18, built with the UI work after S44-extra). No new screen, no new dependency, no new capability.

## Files

- `aeon/ui/src/lib/protocol.ts` / `aeon/ui/src/proto/contract.ts` — the `AeonNotifyHint` type gains optional `attentionKey`, `deepLink` (via `make protogen`; never by hand).
- `aeon/ui/src/lib/notifications.ts` — `NotifyInput`/`AppNotification` gain optional `attentionKey`, `deepLink`; `push` **dedups by `attentionKey`** within a 10-minute window (so `loop.waiting` + `question.asked` for one question toast once); existing `MAX_HISTORY = 200` and `aeon-notifications-v1` unchanged (the entry shape is additive; `isAppNotification` stays valid for old entries). **VERIFY** the dedup window constant against the daemon's (`SV-D10`) and keep both named.
- `aeon/ui/src/app/NotificationListener.tsx` — pass `attentionKey`/`deepLink` from `event.notify`; a toast/OS notification with a `deepLink` carries an action that calls the navigate handler (below). Behaviour for a hint **without** the new fields is byte-identical (the T1 golden).
- `aeon/ui/src/lib/osNotify.ts` — **unchanged except** the notification passes `deepLink` as the Tauri notification `extra` where the plugin supports it; the `document.hasFocus()` rule is untouched (a hidden window is unfocused — SV10 relies on it). **VERIFY** the plugin's JS API for click handling; if a click action is unavailable on a platform, the OS notification stays informational and the in-app toast carries the link (recorded).
- `aeon/ui/src/app/NavigateListener.tsx` — **new**: `listen("aeon://navigate")` (already permitted by `core:event:default`) ⇒ `parseTarget` (**pure, mirrors the Rust `parse_link`**: the same three forms and the same id pattern) ⇒ `router.navigate` to the loop (`/loops/:id`), `/` (the Home GateBanners — **there is no Inbox route yet**; SV18 says the inbox screen comes later, so `aeon://inbox` maps to Home today with a recorded TODO in the route table) or the root's component page; `aeon://navigate-refused` ⇒ a visible "link not understood" toast with the fixed reason enum; an id that no longer exists ⇒ "that loop no longer exists" (a `loop.show` refusal, verbatim). Mounted once beside `NotificationListener` in `ProductShell`.
- `aeon/ui/test/notifications-dedup.test.tsx`, `aeon/ui/test/navigate-listener.test.tsx`, `aeon/ui/test/notifications-golden.test.tsx` (T1, re-run), `aeon/ui/test/supervisionRpc.guard.test.ts` — **new**: extracts every method literal passed to the rpc helpers in the touched files and asserts each is registered in the generated `contract.ts` (≥ 1 found; canary with a bogus method).
- i18n `lib/i18n/en.json` + `pt.json`: `notifications.link.refused`, `notifications.link.gone` (parity test).

## Behaviour

1. A hint with an `attentionKey` seen twice inside the window toasts once; two **different** keys toast twice; a hint with no key behaves as today.
2. `aeon://loop/<id>` from the tray, an OS notification or a deep link opens that loop's screen; nothing in the URL can answer, retry or stop anything (the handler only calls `navigate`).
3. A malformed link never navigates; the toast shows a **fixed** reason, never the raw URL (no reflected text).
