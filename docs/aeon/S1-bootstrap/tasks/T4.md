## Context

**The slice's real risk, and the only one that gets more expensive with delay.**

SQLite is settled on `mattn/go-sqlite3` with `sqlite-vec-go-bindings/cgo` (B3), and the decision is forced
rather than preferred: pure-Go `modernc.org/sqlite` exposes **no extension loading in its public API at
all**, so `sqlite-vec` cannot be loaded; and the pure-Go WASM route does not compile against the maintained
driver — `sqlite3.Binary` was removed from `ncruces/go-sqlite3` at v0.35 while the bindings still reference
it.

So `cgo` is on, the user's machine still needs nothing — `sqlite-vec-go-bindings/cgo` vendors
`sqlite-vec.c` and registers it via `sqlite3_auto_extension()`, compiling it into the binary — and the cost
lands on the build: **a C toolchain per target.**

Which is why this task exists now rather than at S22. The alternative is discovering the toolchain gaps with
fifteen slices of code sitting on top, and the alternative-alternative — starting pure-Go and switching —
converts a build problem into a driver swap.

**A Makefile that *would* build six targets does not satisfy this** (O2). All six must exist and run.

**Read first:** `internal/database/` as the framework exposes it; the plan's Q5 and Q6 findings; `sqlite-vec-go-bindings`'s
own `cgo` package for how `Auto()` registers.

## What to do

**1. Wire the driver** in `internal/database/driver.go`: `mattn/go-sqlite3`, with
`sqlite-vec-go-bindings/cgo`'s `Auto()` called once at init so the extension is registered on every
connection. Set the pragmas Aeon needs — WAL, `foreign_keys=ON`, `busy_timeout` — **on every connection**,
since `foreign_keys` is per-connection and defaults off.

**No schema in this task.** S4 owns the tables. This task proves the driver opens a file and that
`vec_version()` answers.

**2. Choose and record the cross-compilation approach** (Q8, D11) in `aeon/docs/BUILD.md`: native CI runners
per OS, or `zig cc` as a universal cross-compiler. Both work. **Record the reason**, so it is not re-decided
at S22 by someone who does not know it was decided here.

**3. Add `make build` targets for all six**: `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`,
`windows/amd64`, `windows/arm64`, emitting to `dist/aeon-{os}-{arch}`.

**4. Execute what you can, and name what you cannot.** Run `aeon version` on each binary natively or under
emulation where available. Any target that cannot be executed on the build machine is listed in `BUILD.md`
as **built but unverified**, with what would verify it. Silence about an unexecuted target is how a broken
binary ships.

**5. Smoke-test the extension**: open an in-memory store and assert `select vec_version()` returns a
version. That single query is the whole proof that the cgo path works, and it fails loudly if the bindings
are misregistered.
