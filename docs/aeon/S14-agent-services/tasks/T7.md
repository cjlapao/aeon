## Why this exists

**A2A has `securitySchemes`. We do not implement a second authorization system to hold them.**

A2A's per-skill security is **expressed through `SkillAccess`** (AS8) — S10's policy type, with S10's
authorship rule, S10's record and S10's refusal sentence.

**Because a second mechanism is a second place for the authorship rule to drift**, and the drift direction
is the dangerous one: an ACL that grants is an allow nobody authored as a policy. **MC4 refused exactly
this for tools**, and the reasoning does not change because the subject is a skill.

**Read first:** S10's `SkillAccess` spec and `verdict.go`; MC4 for the precedent; `invoke.go` (T4).

## Scope

**1. Every invocation evaluates `SkillAccess`** — caller, callee, skill. Through S10's evaluator; no local
check.

**2. No ACL in this package.** Assert by grep: `internal/agentsvc` holds no authorization state.

**3. The refusal is S10's sentence**, verbatim. One formatter, so the CLI, the app and a transcript all say
the same thing.

**4. If a card declares A2A `securitySchemes`, it is a *hint*, not an authority.** A third-party card
saying a skill is open does not open it — the policy does. **State this**, because the natural reading of
the A2A spec is the opposite.

**5. Default deny applies** (S10's PL5). A skill with no allowing policy is uninvokable, and that is the
empty-registry state rather than a bug.
