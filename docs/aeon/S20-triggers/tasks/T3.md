# T3 — Overlap: skip and record

> **Notes (golang-engineer-loop, 2026-10-27).**
>
> - **Q2, answered — and re-answered before the first commit, on the row:** the design's word
>   "suspended" is STEP vocabulary (S6 suspends the step, the reason rides `question`); the LOOP row's
>   owed-answer state is **`waiting`** (the engine's `SavePinnedRuntime` writes the set
>   `running / waiting / blocked / done / aborted` into a CHECK-less column). A predicate blocking on
>   the literal `suspended` would have blocked nothing — the task's warning ("a test that passes under

## Why this exists

**S5 is serial, so a loop overrunning its period is a signal** — not something to parallelise, and not
something to queue (N2). **Skip it, and record the skip** (TR5), because the gap in a history is only a
signal if something says why it is there.

**And there is a case with a real trap, which is Q2.**

> **A loop suspended on a question is neither running nor finished.**

If the next fire treats it as finished, **a second loop starts while a human still owes an answer to the
first.** Two loops on one blueprint, one of them invisible to the person who thought they were mid-task —
and the question they eventually answer belongs to a loop that is now stale.

**The design's answer is to treat suspended as still-going.** Whichever way it goes, **state it**, because
the implementation falls out differently and the behaviour is not guessable from the outside.

**Read first:** `clock.go` (T2); S6's suspended state; the design's TR5 and Q2; the brief's §9.

## Scope

**1. An overlapping fire is skipped**, with the previous loop named in the record.

**2. The skip is recorded** as a distinct outcome — not as `did not fire` without a reason, and not as an
absence.

**3. Answer Q2 and assert it either way.** The test must name the behaviour: *"a suspended previous run
blocks the next fire"* or *"a suspended previous run does not block it"*. **A test that passes under both
readings has not tested the decision.**

**4. Do not queue** (N2). Skipping is a decision; queueing is a different one that belongs with S27's caps,
because *"what to do when work piles up"* needs a notion of how much is too much.

**5. Overlap is per-schedule.** Two different schedules firing at once is normal; the same schedule
overlapping itself is the signal.
