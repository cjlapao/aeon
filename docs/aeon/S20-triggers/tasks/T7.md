# T7 — `TriggerAccess`: the governance switch

## Why this exists

S10's T3 shipped `TriggerAccess`'s schema and a **refusing stub**. This task gives it an evaluator — and
the sharpest test in the slice.

> **A verified webhook still evaluates `TriggerAccess`.**

That is TR9's second half made concrete: **authentication is not authorization.** The delivery is provably
from GitHub; whether GitHub may start a loop here is a separate question with a separate answer, authored
by an operator.

**And it is what lets a deployment say *"no webhooks here"* or *"no unattended schedules in production"***
without touching config — because putting that in config would reopen exactly what policy replaced.

**Read first:** S10's `spec_stubs.go` — **this replaces one**; S10's `verdict.go` for the sentence;
`webhook.go` (T6); the design's TR12.

## Scope

**1. The evaluator** for `{kind, state}`, where kind is `manual`, `schedule` or `webhook`. Replace S10's
refusing stub.

**2. Evaluated for both kinds.** A schedule fire and a webhook delivery both pass through it. **A check on
only one of them is the gap somebody finds later.**

**3. After verification, not instead of it.** Order the webhook path so the signature is checked first and
the policy second — then the refusal can honestly say *"signature verified"*, which is the parenthesis in
the demo's §6 and the thing that teaches the distinction.

**4. The refusal is S10's sentence**, verbatim. One formatter.

**5. Default deny applies** (PL5). With no `TriggerAccess` allow, nothing fires — and that is the
empty-policy state, not a bug. **Confirm what the shipped default is**: S10's Q1 answered *"the blocklist
is empty"*, so an allow must exist for triggers to work at all. **If that means a fresh install cannot
schedule anything, say so loudly in the notes** — it is a defensible choice but not an obvious one.

## Notes (what this task actually found, in its own words)

**The loud claim, stated where it bites (scope 5): a FRESH INSTALL FIRES NOTHING.**
S10's Q1 answered "the blocklist is empty", and PL5 denies what no allow matched —
so with no `trigger_access` rows every schedule tick and every signature-verified
webhook answers `refused`, recorded as refused, starting nothing. This is the
empty-policy state, defensible but NOT obvious, so it is asserted as behaviour:
`TestFreshInstallFiresNothing` proves it against the daemon a user actually starts
(the fire record carries the engine's own sentence byte-exact), and
`TestAuthoredAllowUnlocksTheFire` proves the other half — ONE operator row and the
identical fixture fires. The daemon test suite itself had to start seeding the
allow (webhook and overlap tests included): the governance became real *for the
suite too*, which is the strongest form of "wired, not decorative". Demo and
operator procedure: `aeon policy add --type trigger_access --id … --target all
--action allow --spec '{"trigger":"schedule","state":"allow"}'` (and the `webhook`
twin) BEFORE any fire can happen — carried to T9's DEMO legs.

**The subject of the verdict is the trigger itself.** `Request.Agent = trigger id`,
so refusals read "refused: agent:ship · …" — the trigger is the actor that asked,
and an operator may author a deny for ONE trigger (`--target agent:ship`) or the
whole deployment (`--target all`). The kind word stays the matching domain:
manual|schedule|webhook, exact comparison — `cron`, `SCHEDULE`, `*` all match
nothing (tested; inert toward deny, PL5 does the refusing).

**The order is measured by calls, not asserted in prose.**
`TestSignatureIsCheckedBeforePolicy`: a bad signature never touches governance
(hook call count stays 0 — the committee never meets for a stranger at the door);
a good one always does (exactly 1). And the refusal for the verified delivery is
byte-exact: S10's sentence + " (signature verified — authentication is not
authorization)" — asserted against `Verdict.Sentence()` itself, never a
re-assembled string. S10's own one-formatter guard (verdict_test.go:758) caught
two daemon tests assembling the sentence literally and made them call the
formatter instead; the guard earned its keep the day it was invoked.

**The decided set moved where the tests said it must.** `inforce_test`/
`inforce_internal_test` carry the decided-types set twice ("one fact, stated
twice, and they must move together") — TriggerAccess joined both, exactly as
CommandAccess at S11 and SkillAccess at S14 did before it.

**Measured and fixed the same day: the policy read PANICS on a closed store.**
T7's own fail-closed test found a nil deref travelling up through the policy
repo callbacks when the store is closed (shutdown race, real for a governance
hook the ticker calls). A governance read that crashes the tick goroutine kills
EVERY schedule with it, so the hook recovers and converts the panic into what
it is: a set that could not be read — `refused … (refusing, not guessing)`.
The store-side root cause is OPEN (every consumer of those callbacks shares the
exposure; named for the ledger, out of T7's width).

**Asked refuses, and that is a residual, not a bug.** A `TriggerAccess` row with
action `ask` routes the question to a gate that does not exist at fire time —
nobody is there to answer before the clock ticks. The fold's `!Allowed` covers
it (a question nobody can answer is not a permission) and the sentence still
says it was asked. If unattended ask ever wants to be real, it needs S11's
question-pending machinery beside the fire — a decision for a future slice,
not a silence here.
