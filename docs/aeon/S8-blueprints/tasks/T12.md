### Validating them is the format's real test (L16, D12)

**Those files carry eight marked gaps** (the design's table). Running the validator against them for the first time is what
decides whether the format works:

- A gap that turns out to be expressible after all → **remove the workaround from the YAML** and say so.
- A gap that produces an `invalid` diagnostic → **the format changes, not the blueprint.** D12 says *"if the real blueprint is
  invalid, the format is wrong"*, and these are the real blueprints.

Report each gap's outcome. **Eight resolutions is a deliverable of this task** — and **GAP-7 is expected to resolve as
"not a gap, a boundary"**: `conversational-map`'s Phases 2 and 3 are a chat with tools, not lanes. Resolving it by extending
the format would be the wrong answer, and recording that is the deliverable.

### `dev-loop.yaml` — the real one (L16, D12)

Author it from `opencode/skills/dev-loop-protocol/SKILL.md` and the shape in
`docs/_archive/aeon-v1-horizontal/07-loop-decide/design.md`. **Read the skill to author the blueprint, not to implement it.**

It must exercise the vocabulary: conditional lanes, a `gate`, an **iterating `build` lane** with a nested ladder,
capped `on_reject` edges with `then:`, `sets:` on ladder steps, `produces:` declarations, and a lane-level
`on_reject` with `with:` (the `qa` → `plan` re-entry in qa-fix mode).

**It must validate with zero `invalid` diagnostics.** If the real blueprint is invalid, the format is wrong — and the
correct response is to fix the format, not the blueprint. That is the point of shipping it.

Its `unverifiable` diagnostics will be the code actions (S16) and any resolver names (S13). Commit the **expected
diagnostic set** as fixture data, so a future slice implementing a registry flips those entries deliberately.

### `broken-fixture.yaml` (O7)

Trips **all seven** validation classes at once, shipped as test data and used by the demo's §5. A fixture living only

### CI (D13)

Both shipped blueprints validate under `--strict`… **except** that `dev-loop.yaml` cannot pass `--strict` until S16.
So:

- `two-step.yaml` — `--strict`, must pass
- `dev-loop.yaml` — default mode must pass with **zero `invalid`**, and its `unverifiable` set must match the
  committed fixture **exactly**

The second is the stronger check. "It has some unverifiable diagnostics" would pass while the format silently rotted;
an exact set means a new `invalid` fails and a *removed* `unverifiable` also fails, which is what catches S16
implementing an action without updating the expectation.

### Walk `DEMO.md`

End to end, on a throwaway repository, fixing whatever does not match — the demo or the code, whichever is wrong.

The three load-bearing sections:

- **§3, the pin from both sides.** A running loop ignoring an edit **and** a new loop honouring it. Either half alone
  reads as a bug.
- **§4, the real blueprint validating.** One `invalid` diagnostic means the slice is not done. And `--strict` must
  fail — a validator whose strict mode passes an unverifiable blueprint has no strict mode.
- **§7, the refused code action.** Confirm the loop **stops**. A skipped code action lets a loop reach `merge` having
  never pushed, and report success.
