# T4 — Validation part 1 — structure, internal references, unknown keys

**Notes (2026-10-18):** The validator reports structural, internal-reference, condition and unknown-key failures together with stable paths and order. Version 1 is a linear lane/ladder graph, so every declared step is on the success path; a statically false `when` is a valid conditional, not an unreachable declaration. The broken fixture exercises independent failures in one report.

## Why this exists

L9: validation is loud and **at load**. An unknown agent, an uncapped backward edge or an illegal `sets:` must fail
before a loop starts — **never mid-run with a half-built feature.** That is the rule, and it is worth restating
because every shortcut here trades a clear failure now for an obscure one later, at the worst possible moment.

This task owns the classes checkable from the blueprint **and the manifest alone**. T5 owns those needing the
registries, which is also where `unverifiable` arises — hence the split (R5).

## Scope

### The diagnostic (O1, O2, I7)

```go
type Diagnostic struct {
    State DiagState  // valid is not emitted; invalid | unverifiable
    Kind  DiagKind   // machine-readable: "unknown-key", "unreachable-step", …
    Path  string     // "lanes[build].ladder[verify].sets"
    Msg   string     // a human sentence
    Hint  string     // a suggestion, where there is one
    Slice string     // unverifiable only: "S16" — set by T5
}
```

`Kind` exists so `--strict` and the app can act without parsing prose (O1). A diagnostic whose only structure is its
sentence is one nobody can filter.

**Paths are the assertion surface.** Every test in this slice asserts on `Path` and `Kind`, never on `Msg` — message
wording will change and a test coupled to it becomes a tax on writing better errors.

### Ordering (O2)

Sorted by `Path`, then `Kind`. Deterministic output is what makes CI diffable and keeps a fixture test from being a
flake.

### The classes in this task

**Structural** — required fields present; a lane has `step` xor `ladder`; `iterate` implies `ladder`; a `gate` names
a question that exists in `questions`; a `model-step` has an `agent`; a `code-action` has an `action`; each has
**only** its own kind's fields (a `gate` with an `agent:` is an error, not a curiosity).

**Internal references** — step ids unique within their ladder; `goto` and `rework` name steps **in the same
ladder**; `iterate` names a `collection`-typed manifest field.

**Conditions** — via T2's `CheckCondition`, at every `when:` on every lane and step.

**Unknown keys** — T1's loader catches these; this task ensures they arrive as `Diagnostic`s with paths rather than
as a bare parse error, so `aeon blueprint validate` reports them alongside everything else.

**Reachability (D9)** — an unreachable step is an **error, not a warning**: the author believes something runs that
never will. A step is reachable if it is in a lane's linear order or is the target of a `goto`/`rework`. A lane whose
`when` is statically `false` is **not** unreachability — that is a legitimate conditional, and conflating them would
make every conditional lane an error.

### Every diagnostic, not the first (D7, L9)

Validation collects. An author fixing seven problems one run at a time will stop reading.

## Tests

| Test | Asserts |
| --- | --- |
| `TestEachFixtureTripsExactlyOneClass` | One fixture per class in `testdata/invalid/`, each producing **exactly one** `Kind`. A fixture tripping two proves nothing about either (D6) |
| `TestAllDiagnosticsReported` | A fixture tripping every class in this task yields all of them in one run (D7) |
| `TestDiagnosticsAreStablyOrdered` | The same fixture validated twice gives byte-identical output; a shuffled input map order does not change it (O2) |
| `TestUnreachableStepIsAnError` | `invalid`, not a warning — asserted on `State` (D9) |
| `TestFalseWhenIsNotUnreachability` | A lane whose `when` can never be true is **valid**. The distinction that keeps conditionals usable |
| `TestGotoOutsideLadderIsInvalid` | A `goto` naming a step in another lane fails with the source step's path |
| `TestGateWithAgentIsInvalid` | Kind-specific fields are enforced both ways |
| `TestIterateRequiresCollectionField` | `iterate: mode` fails; `iterate: tasks` passes |
| `TestAssertionsUsePathAndKindOnly` | A meta-test, or a review check: no test in this package asserts on `Msg` |
