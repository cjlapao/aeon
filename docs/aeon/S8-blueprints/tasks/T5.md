# T5 — Validation part 2 — the machine, termination, routing, and what cannot be checked

**Notes (2026-10-18):** Validation reuses S4 task statuses and mode transition tables, checks bounded back edges and distinguishes installed handlers from reserved S13 agents/resolvers and S16 actions. The task draft required every `produces` step to name a reject target; the derived real blueprints do not, while D12 requires zero invalid. Runtime now blocks an unhandled reject at the same position, which is a safe terminal outcome, and the real blueprint remains valid. Future names are explicit reserve lists, so typos still fail.

## Why this exists

These are the classes that need something **outside** the blueprint: S4's transition machine, and the registries.
And one of those registries does not exist yet, which is the problem this slice is built around.

## Scope

### Machine (`sets:`)

Every `sets:` must be a legal transition per S4's `ALLOWED_TRANSITIONS` **for the loop's mode, POC overlay
included** (Q3). This is pure reuse: existing, already-tested code validates the blueprint.

**If the POC overlay is not exposed by S4, say so in the task notes and treat mode-specific checking as
`unverifiable`** rather than checking against the default table. A `sets:` check that silently ignores mode is wrong
for every POC loop, and wrong in the reassuring direction.

Validating `sets:` needs a mode, so `Validate` takes one, and `aeon blueprint validate` defaults it while accepting
`--mode`. A blueprint valid for one mode and not another is a real thing, and hiding it behind a default is how a
POC loop fails at its third step.

### Termination (D10)

- A capped edge (`on_reject` with `counter`/`max`) **without `then:`** is `invalid`. That is an infinite loop
  waiting to happen, which is why the superseded design made `then:` required rather than defaulted.
- A **backward `goto` with no counter** is `invalid`, for the same reason.

Backwardness is positional: a `goto` to a step at or before the current one in its ladder's order.

### Routing completeness

A step that can `reject` must have a **resolvable target**:

- inside a ladder, the enclosing lane declares `rework`;
- at lane level there is no ladder, so the step's own `on_reject.goto` is **required**.

An unresolvable reject is an error, not a runtime surprise. And T10's `produces:` enforcement makes this sharper
than the superseded design assumed: **any step with `produces:` can reject**, because a missing artifact becomes one
(O3). So `produces:` without a resolvable reject target is `invalid` — a check the superseded design did not have,
and the one most likely to be tripped by a real blueprint.

### The registries, and `unverifiable` (L12, D5)

| Named | In S8 | Diagnostic |
| --- | --- | --- |
| `agent:` | the handler registry exists (T7) | a real check — unknown agent is `invalid` |
| `action:` | **the code-action registry arrives at S16** | `unverifiable`, with `Slice: "S16"` |
| a resolver name (`by-tech-tag`) | arrives at S13 | `unverifiable`, with `Slice: "S13"` |

An `unverifiable` diagnostic sets `Kind`, `Path`, `Slice`, and a message naming the registry. It is **not** an error
by default and **not** a pass: it is the third state (P31).

**Distinguishing an agent name from a resolver name** is the one subtlety. Both appear in `agent:`. The rule: a name
in the handler registry is an agent; a name in the **resolver-name reserve list** is a resolver and is
`unverifiable` until S13; anything else is `invalid`. The reserve list is committed test data, so S13 cannot add a
resolver whose name a blueprint already used as an agent.

## Tests

| Test | Asserts |
| --- | --- |
| `TestSetsValidatedAgainstTransitionMachine` | An illegal transition is `invalid` with the step's path; a legal one passes. Enumerated from S4's table, not hand-picked |
| `TestSetsIsModeSensitive` | A `sets:` legal in one mode and not another produces different results for `--mode` — or, if the overlay is unavailable, an `unverifiable` naming that. **Never a silent default-table pass** |
| `TestCappedEdgeWithoutThenIsInvalid` | Missing `then:` fails (D10) |
| `TestBackwardGotoWithoutCounterIsInvalid` | Fails; a **forward** `goto` without a counter passes |
| `TestProducesWithoutRejectTargetIsInvalid` | The new check (O3): `produces:` on a step in a lane with no `rework` and no `on_reject.goto` fails |
| `TestUnknownActionIsUnverifiable` | `State: unverifiable`, `Slice: "S16"` — **not** `invalid`, and **not** absent (D5, L12) |
| `TestUnknownAgentIsInvalid` | A name in neither registry nor reserve list is `invalid`. The registry that would confirm it **does** exist, so there is nothing to be unverifiable about |
| `TestResolverNameIsUnverifiable` | `by-tech-tag` yields `unverifiable` with `Slice: "S13"` |
| `TestReserveListIsCommitted` | The resolver reserve list is fixture data, so S13 cannot collide with an agent name already in use |
