# T6 — The three-state report, `--strict`, and `aeon blueprint validate`

**Notes (2026-10-18):** The CLI now provides `blueprint list`, `path`, `fields` and `validate` with JSON and strict modes. Default mode accepts named unverifiable diagnostics; strict mode exits nonzero with the same findings. The standard sources are embedded, materialized for editing on first use, and `blueprint.validate` exposes the report to the UI. Conformance fixtures cover the new methods.

## Why this exists

T4 and T5 produce diagnostics. This task decides **what they mean**, and that decision is the slice's product idea.

A validator that meets an `action:` it cannot check has two dishonest options: pass it silently, or fail a blueprint
that is correct. Both are wrong, and the first is worse because it is reassuring. So the report has three states
([P31](../../ARCHITECTURE.md#8-product-decisions), L12), and the reassuring option is the one explicitly rejected.

This is the third independent place in Aeon that needed this shape — cost (`known`/`partial`/`unknown`) and the
`bash` receipt were the first two — which is why it is now a product decision rather than a local choice.

## Scope

```go
type Report struct {
    Blueprint     string
    SchemaVersion int
    Version       int
    ValidCount    int           // checks that ran and passed
    Diagnostics   []Diagnostic  // invalid and unverifiable, stably ordered
}

func (r Report) OK(strict bool) bool  // strict: no diagnostics at all
                                      // default: no invalid ones
```

**`ValidCount` is a count of checks, not of fields.** "34 checks passed" tells you validation actually ran; "valid"
alone is indistinguishable from a validator that returned early.

### `--strict` (D5)

| Mode | Fails on |
| --- | --- |
| default | `invalid` only |
| `--strict` | `invalid` **or** `unverifiable` |

CI uses `--strict` so the shipped blueprints cannot rot (D13); a human does not, because a human running it today
would get nine failures for a blueprint that is correct.

### The output

```
dev-loop  schemaVersion 1  version 1

  valid          34 checks
  unverifiable    9 checks
    lanes[build].ladder[issue].action    forge.openIssue
      cannot verify — the code-action registry arrives at S16
  invalid         0

OK (9 unverifiable — use --strict to fail on these)
```

Three requirements on that output:

- **The counts come first.** A wall of diagnostics with the summary at the bottom gets scrolled past.
- **The final line states the mode's verdict and how to get the other one.** A user who does not know `--strict`
  exists will not think to ask for it.
- **`unverifiable` names the slice.** "Cannot verify" is an annoyance; "cannot verify — arrives at S16" is an answer.

`--json` emits the `Report` whole, for the app (S9) and CI.

### Conformance fixtures

`testdata/conformance/diagnostics.json`, in S2's established shape: one entry per `Kind`, so the app and CI read one
contract rather than each parsing the text.

### The CLI

- `aeon blueprint validate <name-or-path>` — `--strict`, `--mode`, `--json`
- `aeon blueprint path <name>` — where a shipped blueprint lives, so the demo can `cat` it
- `aeon blueprint fields` — T2's manifest table

Exit codes: `0` for OK in the chosen mode, non-zero otherwise. A CI check that has to grep stdout is a CI check that
breaks when the wording improves.

## Tests

| Test | Asserts |
| --- | --- |
| `TestReportIsThreeState` | A blueprint with one of each yields all three counts, and `unverifiable` is neither folded into `invalid` nor dropped |
| `TestStrictFailsOnUnverifiable` | Exit non-zero, and the diagnostics are unchanged — strict changes the **verdict**, not the findings |
| `TestDefaultDoesNotFailOnUnverifiable` | Exit zero, with the count and the `--strict` hint present in the output |
| `TestValidCountReflectsChecksRun` | A larger blueprint has a larger count; a blueprint that fails at parse has a count of **zero**, not a passing summary |
| `TestJSONReportMatchesConformance` | `--json` matches the fixtures byte-for-byte after canonical marshalling |
| `TestOutputPutsCountsFirst` | The summary precedes the diagnostics |
| `TestExitCodesDoNotRequireGrepping` | Both modes' exit codes asserted directly |

## Definition of done
