# T8 — `LoopState` — one snapshot read

**Notes (2026-10-18):** `LoopState` is reconstructed from a consistent pinned-loop read and contains the position, conditions, answers, counters, task identities, step states and pinned content. `Position.Item` stores a task ID, not an array offset. The state has no store handle; `Values()` supplies the manifest view. Current loop IDs remain S4 strings rather than the task sketch’s int64 example.

## Why this exists

`Decide` is pure (L1), which means everything it reads must arrive in one value. The inherited design states the
consequence sharply and it is worth keeping: **if `Decide` ever needs something outside the snapshot, the snapshot
is wrong** — that is the first thing to check when a case turns awkward, not a reason to pass the store in.

Building the reader before `Decide` (T9) is what keeps that honest. A snapshot designed after the fact grows a
field per awkward case.

## Scope

```go
type LoopState struct {
    ID        int64
    Slug      string
    Mode      string
    Status    string              // running | waiting | blocked | done
    Blueprint *blueprint.Blueprint // the pin (T3)
    Position  Position
    Lanes     map[string]LaneState
    Tasks     []TaskState
    Counters  map[string]int
    Flags     map[string]bool
    Question  *store.Question     // the open gate, if waiting
}

type Position struct {
    Lane string
    Item *string   // nil unless the lane iterates (L17)
    Step string    // "" for a single-step lane
}
```

### One read (I2, D1)

Assembled in **one** store call — a single transaction, one round trip to the API. Not a struct that lazily fetches:
a lazy field is a store dependency wearing a struct's clothes, and it makes `Decide` impure by the back door.

### `Item` is an identity, not an index (Q8, L17)

`Item` holds a **task identifier**, not a position in a list. A task added mid-loop must not shift what the loop is
currently working on, and a positional index does exactly that — silently, and in a way that looks like the loop
skipped an item.

State the answer to Q8 in the task notes, and if S4's task rows have no stable identifier, **that is a finding worth
raising before proceeding**, not something to work around with an index.

### `Values` for conditions

`LoopState` must produce T2's `Values` — the `mode`, `flags.*`, `counters.*`, `tasks.count` the manifest publishes:

```go
func (s LoopState) Values() blueprint.Values
```

Every field the manifest declares must be present. T2's evaluator **errors** rather than returning `false` on a
missing field, so a gap here surfaces immediately rather than as an invisible lane skip — which is the whole reason
that evaluator was written that way.

## Tests

| Test | Asserts |
| --- | --- |
| `TestStateIsOneRead` | A store spy counts **one** query round trip for a fully populated loop, and none afterwards while the struct is read (I2) |
| `TestStateCarriesEverythingDecideNeeds` | Every field the manifest declares is present in `Values()` — asserted by iterating `Fields()`, so adding a manifest field without a source fails here |
| `TestPositionRoundTrips` | Every `Position` shape — single-step lane, iterating lane with an item, an empty step — survives a store write and read |
| `TestItemIsAnIdentityNotAnIndex` | Add a task **before** the current item, re-read: the position still names the same task (Q8, L17) |
| `TestValuesErrorsSurfaceMissingFields` | A deliberately incomplete `Values` makes an evaluation **error**, not evaluate false |
| `TestStateIsNotLazy` | No store handle is reachable from `LoopState` — asserted on its field types |

`TestItemIsAnIdentityNotAnIndex` is the one worth writing first. It fails against the obvious implementation.
