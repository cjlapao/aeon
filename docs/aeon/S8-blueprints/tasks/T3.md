# T3 — Pinning the blueprint per loop, as content

**Notes (2026-10-18):** Migration 0014 adds `loop_blueprint` with raw YAML and runtime JSON. `CreatePinnedLoop` commits loop, content and initial position atomically. A reader transaction returns one consistent pin; it never reopens the source. Tests edit the file and show the old loop keeps its bytes while a new loop sees the edit. A corrupt pin raises `pin-unparseable` and the runner records a blocked state.

## Why this exists

L6: a blueprint is pinned **per loop, content and all**, at start. Two reasons, and the second is the one that
bites:

1. A resumed loop must run the blueprint it started with, or `Decide` is non-deterministic across a resume.
2. An edited blueprint can **strand a half-built feature at a step that no longer exists**.

Storing a reference instead of content makes a loop unreproducible the moment its file changes — and the file will
change, because being editable without a code change is the whole point (L1).

## Scope

**First, answer Q1**: does S4's `loop` table have somewhere to hold this, or is a column needed? If a migration is
needed it belongs here, following S4's discipline exactly — numbered, one transaction, ledger-recorded, and the
fresh-equals-migrated equivalence test must still hold.

Store the **raw YAML text**, not a marshalled struct. Two reasons: a round-trip through Go would silently normalise
away anything the loader tolerates, and `aeon loop show --blueprint` should print what the author wrote so a human
can diff it against the file.

```go
// Pin resolves and stores the blueprint content for a new loop. Called once, at start.
func Pin(ctx context.Context, s *store.Store, loopID int64, name string) (*blueprint.Blueprint, error)

// Pinned loads a loop's pinned blueprint. The only way a running loop reads its blueprint.
func Pinned(ctx context.Context, s *store.Store, loopID int64) (*blueprint.Blueprint, error)
```

Also record the blueprint's `id` and `version` alongside the content, so a loop's provenance is legible without
parsing the pin.

**`Pin` validates before storing.** A loop must never start on a blueprint that would not have passed
`aeon blueprint validate`. In this task that means a parse; T5 and T6 extend it to the full check.

### The refusal that matters (O5, D14)

**`Pinned` never falls back to the file.** If the pinned content will not parse, the loop is `blocked` with a reason
saying so — it is **not** re-pinned from disk. Silently re-pinning would change what a running loop is doing, which
is precisely what L6 exists to prevent, and it would do it at the moment the operator is least able to notice.

That refusal is the one place where the honest answer is worse for the user in the short term and right anyway.

## Tests

| Test | Asserts |
| --- | --- |
| `TestRunningLoopKeepsItsPin` | Start a loop; **change the source file**; `Pinned` returns the original content and the original lane set (D14, L19) |
| `TestNewLoopSeesTheEdit` | After the same edit, a **new** loop pins the new content. Both halves of L19 in adjacent tests, because either alone reads as a bug |
| `TestPinStoresRawText` | The stored text is byte-identical to the file, including comments and key order — a normalised pin is one nobody can diff |
| `TestPinRecordsIDAndVersion` | Provenance is readable without parsing the content |
| `TestUnparseablePinBlocksTheLoop` | Corrupt a pinned row directly; `Pinned` yields a **`blocked` domain refusal** naming the cause, and **does not read the file** — asserted with a filesystem spy at zero (O5) |
| `TestPinValidatesBeforeStoring` | A blueprint that will not parse is refused at `Pin`, and no loop row is left behind |
| `TestPinSchemaFreshEqualsMigrated` | If a migration was needed, S4's equivalence test still holds |

`TestUnparseablePinBlocksTheLoop`'s filesystem spy is the assertion that matters. "It returned an error" passes
against code that tried the file first and failed for a different reason.
