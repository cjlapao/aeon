# T7 — The handler registry

**Notes (2026-10-18):** Two handlers are registered: `default` can read, list, write files and ask a step question; `read-only` can only read and list. Blueprint structs contain no tool-grant field. `handler.Build` supplies the runtime grant; an unknown name is refused. Future S13 names are visible as unverifiable references, not pretend handlers.

## Why this exists

S5 has a **literal** handler. Its design said S13 would replace it with a registry lookup; S8 needs the lookup
first, because **a blueprint that can only ever name one handler demonstrates no routing at all** (L14). That
amendment is already recorded in S5's design — this task implements it.

The registry is deliberately thin. S13's job is the 25 bodies and the tech-tag resolver, not the map.

## Scope

```go
type Handler struct {
    Name         string
    SystemPrompt string
    Tools        []string   // names resolved against the tool registry at compile time
}

// Lookup returns a handler by name. Unknown is a domain refusal, not an error (S4's DB19).
func Lookup(name string) (Handler, bool)

// Names returns every registered handler, for validation (T5) and `aeon handlers`.
func Names() []string
```

Two entries: the `default` handler S5 already has, and one more so routing is demonstrable rather than notional —
the second differing in **both** prompt and toolset, since a second entry identical but for its name would prove
nothing.

### The registry cannot grant (I5, L8)

**This is the property to get right.** A blueprint names a handler; a handler names its tools; **a blueprint cannot
name a tool.** If a blueprint could widen a handler's toolset, every blueprint would be a privilege-escalation
vector.

So: the format has **no field** for tools — assert that by grepping the T1 types — and `Compile` takes the toolset
from the handler, never from the blueprint or the step. A step's `with:` arguments merge into its **input**, not into
its configuration.

The check is worth automating rather than trusting: a test that walks the `Step` struct's fields and fails if any
name matches `/tool|permission|allow|grant/i`. That catches the field being added later by someone who did not read
L8.

### The committed list

`testdata/handlers.json` names the registered handlers, following S1's fixture pattern. It is what T5's `agent:`
validation checks against, and it is how S13 adding 25 entries becomes a deliberate change to committed data rather
than a silent widening.

### Not in scope

No agent bodies (N2). No `by-tech-tag` or any resolver (N2, N8) — T5 already treats resolver names as
`unverifiable` until S13.
