# T3 · Verify records: migration M1, the store, the effective set, the change log

**Prefix:** VG · **Shape:** P3 · **Rules:** VG3, VG6, VG21 (the template table) · **Depends on:** T0; **needs S44-extra merged** (the component tree). Parallel-safe with T2, T4.

## Goal

`verify_command` (what a component declares), `verify_command_event` (who changed it), `verify_run` + `verify_run_result` (what happened) and
`verify_template` (the inert system templates) exist as tables with one store API, append-only where history matters, and `EffectiveGates` answers
"what runs here, and from where" for any node of the tree.

## Refusals (discriminated results, DB19 — `VerifyRefusal` values with sentences, as `ComponentRefusal`)

component unknown / archived; name not a slug or already taken among non-archived rows of that component; command empty, over 4096 bytes, containing NUL; timeout out of range;
requirement invalid; `memory_mb ≤ 0`; template unknown; apply-template name collision (reports each collision, writes nothing — all or nothing).

  node in `SourceID`; an archived node — child or root — supplies nothing and takes nothing; unknown
  component is `ErrNotFound`, an empty set is honest and not an error). Evidence is the
  Create→append→Finish pair: the draft is memory-only (a crash before finish leaves zero rows), the
  finish is ONE transaction (run + all results), the loop slot
  `(loop_slug, component_root, position, attempt)` is unique for `trigger='loop'`, the command text
  is SNAPSHOTted on each result (history survives edit and archive), tails ≤ 2 KiB at the table.
  `ApplyVerifyTemplates` resolves the whole set first, checks every name collision (against live
  gates of the node AND duplicates inside the set, each reported) before any write, and creates
  `origin='template'` gates with their `apply_template` events in one transaction.

**Deviations and rulings (recorded, not silently absorbed):**

1. **The spec's command line omits `-tags sqlite_fts5`.** Same T1/T2 finding: the store package
   opens the store, so the tag is mandatory (without it the 0040 FTS5 migration dies with
   `no such module: fts5`). All runs below carry it.
2. **The spec's `-run` filter matches only 3 of its own 10 named tests** (`Verify`, `MigrationM1`,
   `Effective` catch the migration drill, both effective-set tests and the two `Verify*` history
   tests; `TestEveryChangingWriteWritesOneEvent`, `TestNoEventForReadsRefusalsNoOps`,
   `TestRunIsNeverVisibleHalfWritten`, `TestCommandSnapshotSurvivesEditAndArchive`,
   `TestRefusalsAreDiscriminated`, `TestApplyTemplateIsAllOrNothing` and
   `TestSummariesContainNoUserText` do NOT match `Verify|MigrationM1|Effective|frozen|Migration`).
   Measured, not assumed (T2's filter-gap precedent). The full unfiltered package run is the
   authoritative one and is green; the spec command is run as written (plus the tag) on top.
3. **`ApplyVerifyTemplates` signature**: the spec's one-liner `(componentID, templateID, names,
   actor)` is realised as `ApplyVerifyTemplates(a Actor, componentID string, templateIDs []string)
   (VerifyApply, error)` — a list over template ids, one created row per template. All-or-nothing
   and the per-collision report become properties of ONE store call instead of a loop at the daemon.
4. **Count pins.** Per T0's ruling the `schema_test.go` count machinery is COMPUTED
   (`frozenMigrationCount()` = 45 frozen + the timestamped files) and absorbed the new file with no
   edit. The one hand-kept pin is S62's `TestMigrationCountAssertionsBumpedOnce`
   (`backup_run_test.go`), whose own protocol says "a later slice that adds a migration edits these
   two numbers with its own dated line" — bumped 29→30 / 74→75 with the S57 T3 dated line in this
   commit. The `schema_test.go` "newest is now 20261102085151" wording stayed true (S62's file is
   still the newest) and is wording, not a pin (T0).
5. **Name is immutable on update** (the spec is silent; the spec's own "rename = archive + add"
   history argument is the same one the audit makes): `VerifyCommandUpdate` has no name field;
   changing the name means archive the row and add a new one, which the audit records honestly.
6. **`memory_mb ≤ 0` on update is a refusal, not a clear**: the spec's refusal list says `memory_mb
   ≤ 0` and the add enforces it; the update treats non-nil `≤ 0` identically (nil = leave it), so
   there is no way to reach a zero row through the API.
7. **An archived root supplies nothing to its children** (VG3's "the root's" falls through to the
   empty set): archiving froze the node, so its gates keep governing nobody — including its
   children. Pinned in `TestEffectiveGatesOwnReplacesRoot`.
8. **The event snapshots (`before_json`/`after_json`) carry the record's fields, including the
   command text.** SEC-033 constrains the SUMMARY (a fixed template from ids and enums, never free
   text) — `TestSummariesContainNoUserText` pins the boundary both ways: every summary is the exact
   fixed sentence and carries no marker from the command, while the add event's after-snapshot does
   carry the command text (the columns exist so the audit is diffable; the record's own content is
   not "user text" in SEC-033's sense).
9. **I4 scope**: `ListVerifyRuns` composes its loop-slug filter through `Scope`/`ComponentScope` —
   a slug without its component root is an error (a bare slug is never a scope). `LatestPassingRun`
   keeps the pair in one statement (the I4 grep's inline exception).
