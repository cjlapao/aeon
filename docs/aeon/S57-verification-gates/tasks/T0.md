### 2. The 15 unchecked items

1. **`executeCodeAction` + `on_reject` on a code-action** — `loop/execute.go:56-180`: `Dispatch` error → `blockTo(…, "action-failed", err.Error(), name)`; deny → `action-denied` with the class sentence verbatim; success → `st.Evidence[stepKey(act.Position)] = ev`, `StepStates[…]={Status:"done"}`, emit `loop.action.executed`, `moveNext`. **The validator ACCEPTS `on_reject` on a code-action today** (`validate.go:422-437` has no kind restriction; `checkStepEdge` at `:590` validates the edge generically) **but the engine ignores it** — no code-action path routes a reject. So T6 both *consumes* the edge (VG7 mapping) and *narrows* the validator: a code-action with `on_reject` must name `verify.run` (other actions become invalid), which is a tightening of a currently-accepted-but-inert shape.
2. **`routeReject` / `DecideUnverified`** — `routeReject(ctx, dep Deps, id string, st *LoopState, step blueprint.Step, pos Position) error` (`advance.go:692`); needs the step (for `OnReject`) and the position. `DecideUnverified(sc store.Scope) (value int, atCeiling bool, err error)` is a `Counters` method (`counters.go:169`). T6's mapping can call `routeReject` honestly: for `fail` it passes the step (whose `on_reject` was validated for `verify.run`); for `unverified` it stores `Reason: "unverified: …"` in the StepState and then routes, which charges only the loop ceiling via `DecideUnverified`.
