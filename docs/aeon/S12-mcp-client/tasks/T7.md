# T7 — Grants are `ToolAccess` policies, and nothing else

## Why this exists

**MC4, and it is the reason this slice has no security model of its own.**

> A grant is an operator-authored `ToolAccess` policy. There is no second grant mechanism.

S10 collapsed *grant* and *blocklist* into one object with one authorship rule and one record. **A registry
ACL here would be a second place for that rule to drift** — and the drift direction is the dangerous one,
because an ACL that grants is an allow nobody authored as a policy.

**So the registry asks S10's evaluator.** This task replaces whatever grant source T1 stubbed.

**Read first:** S10's `evaluate.go` and `store.go`; `registry.go` as T6 left it; MC4 and MC10.

## Scope

**1. The registry consults S10's evaluator** for every core and public tool. Private visibility is
structural (T5) **and the call still evaluates** — invisible is not a substitute for allowed.

**2. Delete the stub.** No ACL, no allow-list file, no per-server permission map in this package. Assert by
grep: `internal/mcp` holds no grant state.

**3. Revocation is the policy's.** Removing the `ToolAccess` allow removes the tool. **There is exactly one
way to revoke**, and asserting that is this task's point — two ways means one of them gets forgotten and a
revoked tool stays live.

**4. MC10: the client grants nothing the policy did not.** A server offering a tool does not make it
available; the policy does. Assert with a configured server whose tool has no allow.

**5. `at` comes from the caller**, as S10's T8 established — once per step, not per tool call, so two calls
in one step cannot straddle an expiry.

## Notes (built 2026-10-24)

**Two views, deliberately not collapsed.** `ToolsFor` stays the **capability** view — config facts,
frozen with the step, because a policy event mid-step must not flicker the model's tool list (D12's
discipline). `GrantView` (new, `grants.go`) is the **authority** view — what the caller's set permits
at `at`, per tool, with the exact refusal text: `available · unavailable · refused · ask`, four states
because the three refusals plus owed consent render differently in the CLI (T9) and the transcript.
`TestCapabilityOutlivesGrant` pins the split so nobody "fixes" the capability view into tracking
policy: a revoked tool is still *capable* (declared, classified, reviewable) and is *not permitted* —
collapsing those two states is how revocation becomes invisible.

**Refusal texts have exactly one definition each** (`mc10Sentence`, `effectAskSentence` in
`grants.go`, used by the call path too): a refusal whose wording depends on which door you asked
through is two truths wearing one sentence.

**"Delete the stub" — the honest report: there was no stub to delete.** T1 was built with no grant
source at all rather than with one awaiting replacement, so scope item 2 lands as the grep pinning
the absence rather than a deletion diff. The validation still means what it was written to mean.

**Deviation from the task line "every core and public tool", stated:** the registry evaluates the
MCP tiers; **core verdicts belong to S11's step gate** (frozen set, per step — `internal/loop` +
`policy_gate.go`) and a second core evaluation here would be a second place for the verdict to
disagree with the gate that owns the step. `Registry.Call` answers `unknown tool:` for a core name
(core calls belong to the step toolset), and `GrantView` marks core tools
`available · "core: judged by the step's S11 policy gate (S12 does not re-decide core)"` — the truth
rendered, not invented into an MCP grant row.

**Where the consultation itself landed, and why not here:** the `policy.Evaluate` call is in
`Registry.Call` (T6 — its checklist demanded a deny that closes the door with no code change, which
a stub could not honour). This task is what its title promises: the greps that make MC4 structural,
the one-way-revocation pin, the `at` discipline, and the view that makes all of it visible.
