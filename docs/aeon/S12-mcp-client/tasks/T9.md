# T9 — The level-0 invariant: the layer is deletable

## Why this exists

**The adoption story, as a test** (MC11).

> An agent with no tools is valid, and the whole suite passes with this layer switched off.

A company with only MCP servers writes agents pointed at public tools. A company with none keeps markdown
agents. **Same system, two depths — and nobody has to buy the whole model to start.**

That is a claim, and it decays silently. The way it decays is ordinary: a test somewhere gains a configured
server because that was convenient, and six months later removing MCP breaks forty tests for reasons
unrelated to MCP. **S22 earned this discipline for retrieval; this is the same one.**

**Read first:** S22's deletability tests for the pattern; `internal/runtime/loop.go`; MC11.

## Scope

**1. Run the whole suite with no MCP configuration.** Not `internal/mcp`'s tests — **everything else**. It
must pass.

**2. An agent with no tools runs a step.** The 25 bodies S13 writes are markdown and a prompt; this asserts
the runtime does not require a registry entry to dispatch one.

**3. No package outside `internal/mcp` imports it unconditionally.** The seam is optional, so the import is
behind whatever construction makes it so — assert by grep, because an unconditional import is how
"optional" quietly stops being true.

**4. The absence is reported, not silent.** `aeon mcp list` with nothing configured says so (the demo's
§1), and a step whose agent declared a tool from an unconfigured server is told.

**5. Do not add a feature flag.** Deletability means *absent configuration works*, not *a switch exists*.
A flag is a second state to test and a thing that gets set wrong.

## How "no MCP configuration" was run, reproducibly

```bash
mkdir -p /tmp/mcp-absent-home/.config
cd aeon
export GOPRIVATE='github.com/cjlapao/*' CGO_ENABLED=1 \
  CGO_CFLAGS="-I$(git rev-parse --show-toplevel)/.tmp/cgo-shim" \
  GOCACHE=$(git rev-parse --show-toplevel)/.tmp/gocache \
  XDG_CONFIG_HOME=/tmp/mcp-absent-home/.config \
  AEON_MCP_CONFIG=/tmp/mcp-absent-home/nonexistent.json
go test ./... -count=1 -timeout 900s
```

`AEON_MCP_CONFIG` points at a file that does not exist and `XDG_CONFIG_HOME` at a directory with no
`aeon/mcp.json` inside it — both of `MCPConfigFile`'s resolution paths land on nothing. No feature
flag is involved because none exists (scope 5).

**My first attempt isolated `HOME` too, and ten packages failed with
`reading …/framework/go.mod …: could not read Username for 'https://github.com'`.** That is not the
suite needing MCP and not the suite needing the real home directory: `GOPRIVATE` makes the framework
resolve over git, and the credentials and the module cache live under the real `HOME`. Moving `HOME`
moved the module cache out from under the toolchain. **An isolation that breaks the build is not an
isolation, it is a different experiment** — the fix was to isolate exactly what the invariant is
about (`XDG_CONFIG_HOME`, plus the override variable) and leave the toolchain's own environment
alone. The command above is the corrected one.

## Notes (built 2026-10-24)

**The CLI exists because scope 4 demanded it and the DEMO names its verbs.** `cmd/aeon/mcp.go` adds
`aeon mcp list [--agent NAME] [--include-refused]` and
`aeon mcp call --agent NAME --tool SERVER.TOOL [--args JSON]`, wired with one `case "mcp"` in
`main.go` and two help lines. **This file and those three lines are the entire production wiring of
the layer**: `main.go` is the only other file in the product that names it, and deleting the file
plus that case leaves nothing that knows MCP exists. That is why the importer grep allows `cmd/aeon`
and forbids everything else — the seam is not "optional at runtime", it is **removable**, and a
runtime import would make deletion a surgery instead of a `git rm`.

**`list` reads three sources and invents none.** The config (absent ⇒ the §1 words), the policy
store through `openPolicyBoundaryDirectly()` — the same justified second access path `aeon policy`
already uses, WAL-serialised behind the daemon's writer — filtered to `tool_access` rows, and the
live servers (dialled once each, 30s budget) for the classes the operator never wrote. Classes render
from `ToolsFor` (the **raised** values — what the model is shown) and states from `GrantView` (the
authority's answer): two maps, each from its one accessor, no third derivation. A server that will
not answer prints *"its tools are reported absent, not silently dropped"* and the error behind it —
per-server, with the living server's tools intact.

**`call` refuses to be clever about its arguments.** `--args` must parse as one JSON object or the
input parser refuses it by name (input parsing, not policy validation — `aeon policy`'s drift rule,
restated); a missing `--agent`/`--tool` is refused rather than defaulted, because a call without a
caller is not a call. No config, or a server name nobody configured, prints the §1 words and
`unknown tool:` — **the same bytes a stranger gets** (T5's discipline reaching the CLI), no
suggestions, no server-name gossip. Credentials are never flags: the config names variables, the
client reads them from the environment at spawn (the standing rule — argv is the process list and
the shell history).

**One count I refused to remember.** `TestSuitePassesWithNoMCPConfig` originally asserted `len == 9`
for the core capability set — "the core nine", the DEMO's phrase — and **failed, because the registry
holds ten** (`bash edit glob grep list question read todo webfetch write`, pinned by
`TestRegistryExactNames` in `internal/tools`). The phrase and the code are both correct about
different things: W21's *nine* is the S5 set that became the core tier; the `question` tool arrived
with S11's D1. So the test asserts what it can verify — `tools.Registry()` minus the hidden
`write_file` alias, exactly — and the DEMO's §1 wording ("the core nine only (S11)") stays the
**walk's** finding in T10, where a phrase meets a screen, instead of being hard-coded here where it
would freeze a number nobody measured. AGENTS §4a: update counts by measuring.

**Two things this task did NOT do, stated:**
- **No runtime integration.** `internal/runtime/loop.go` is untouched — it is on the foreign-dirty
  list, and more to the point the task's own level-0 claim does not need it: the registry's tools are
  consumed by whoever builds the prompt, which is S13's registry work, and the runtime must stay
  MCP-free for the invariant to hold. `files_expected` named the file; the correct answer to a
  task file that expects a runtime import **is the grep that forbids it**.
- **No socket methods.** `mcp.list`/`mcp.call` over the endpoint are S19's projection question (and
  any write path over the socket would repeat the mistake PL15 exists to prevent). The CLI opens the
  store directly, same as `aeon policy`.

**Measured:** `go test ./internal/mcp/ -count=1` → `ok` (4.6s); `-race` → **92** top-level PASS (87
before this task, **5** new), 0 FAIL; `go vet ./internal/mcp/... ./cmd/aeon/` clean; `gofmt -l` empty
on both directories. The CLI's §1/§2/§3/§5/§7 surfaces were exercised for real against
