# T8 — Timeouts and degradation

## Why this exists

**A third-party server that hangs must not hang a loop** (MC9, N8). Bounded exactly as `bash` is — and for
the same reason: the failure is not hypothetical, it is what happens the first week somebody's docs server
is down.

**And the subtler half: a timeout is not an empty result.**

A hung call rendered as `[]` is a model concluding **the tool found nothing** — and then reporting that
absence as a finding. *"No results for that query"* and *"the server did not answer"* are different facts,
and only one of them is about the query.

**Read first:** W9's bounding of `bash` in S11 for the discipline; `client.go` (T2) and its hanging fake;
N8 and N10.

## Scope

**1. Every call carries a timeout** (N10), and **answer Q2**: the default, as a number, with reasoning in
the notes. The way S10's T7 picked its age cap — the point is that it is chosen and visible, not that it is
optimal.

**2. A timeout is a reported fact**, distinct in the transcript from an empty result and from an error.
Three outcomes, three renderings.

**3. A dead or unreachable server degrades the tool list, not the step.** Its tools are absent and **the
absence is reported** — a tool silently missing is a model wondering why it cannot do what its prompt says
it can.

**4. Degradation is per-server.** One failing server does not remove another's tools.

**5. The timeout is not retried automatically.** A retry doubles the wait and the model cannot tell one
hang from two. If a retry is wanted, it is the model's call, visibly.

## Q2 — the default per-call timeout: **30 seconds**

Chosen and visible, the way S10's T7 picked its age cap; the number is
`DefaultCallTimeout` in `degrade.go`, and the S12 DEMO prints it.

- **Healthy MCP calls are small network round-trips behind a small process**
  — a docs search, a ticket fetch: sub-second to a few seconds. Thirty
  seconds is an order of magnitude past "healthy" and still short enough
  that a human watching a step sees progress rather than a stall.
- **It is deliberately not bash's 600s** (`BashTimeout`, `limits.go`,
  W13's bound — the discipline W9 established). The failure modes differ: a
  local build genuinely runs for minutes, so bash's ceiling is honest; a
  third-party `tools/call` that has not answered in half a minute is not
  about to. The step loop is dominated by model latency, and a server
  occupying a step for ten minutes would read as a dead loop. **Same
  discipline, different number, because the two calls are different kinds
  of wait.**
- **The bound is caller-shortenable, never caller-lengthenable** —
  `bash.go`'s rule quoted verbatim in `degrade.go` (*"a tool that could
  raise its own ceiling has no ceiling"*). `boundCall` honours a shorter
  caller deadline and caps a longer one; `TestCallerBoundShortensNeverLengthens`
  proves a 1-hour caller deadline does not buy a 1-hour wait.

## Notes (built 2026-10-24)

**Three outcomes, three renderings, plus a fourth that is not a rendering.**
`CallOutcome` gained **`TimedOut`**, and the timeout's sentence says its own
thesis — *"the server not answering is a different fact from the tool finding
nothing"* — because the failure MC9 names is not the wait, it is the model
reporting an absence it never observed. The shapes pinned apart:
timeout `(TimedOut,IsError) = (true,true)` with a `timeout:` lead; empty
`(false,false)`, labelled, no refusal lead; server-side `isError`
`(false,true)` — **the server speaking is not the wire dying**; and the dead
transport returns a Go **error**, told from all three by being an error at
all. `isError` and `TimedOut` being separate booleans is what keeps the
server's own failure from being flattened into infrastructure failure, which
is T8's third outcome wearing the second outcome's clothes.

**No retry, structurally.** The client (T2) has no retry; the registry does
not loop; the timeout sentence *says* no retry was made and that another
attempt is the model's call to make, **visibly**. If a retry is wanted, the
model makes it and the transcript shows two calls — N10's reason for the ban
is not slowness, it is that a retry makes one hang indistinguishable from two.

**Degradation is per-server and is a fact about clients, not config.**
`DownServers()` answers only about configured names with no attached client
(`TestDownServersIsConfigDerivedNotClientGuessed`: a name nobody configured
must never be mourned). The capability view keeps its declarations when a
server dies — a dead server that deleted config facts would make the config
lie about what the operator wrote, and the recovery would have to be
re-reading files to find out what got lost.

**A test that caught itself, recorded honestly.** My first three-outcome test
failed on its *second* and *third* calls, not from a product bug: the fake is
single-threaded, so `empty` and `boom` queued behind the still-running 4s
`hang` and each hit their own bound — three timeouts where the test wanted
one. The fix was to wait **on the fake** (poll its counter query until it
answers, which is the moment the hang ended) rather than to sleep past a
guess: a test that sleeps past a guess can pass while a request leaks; a test
that waits on the server cannot. It also proved something worth knowing — a
queued call behind a hang is starved by design, and the bound measures
*client-side* patience.

**Not verified:** behaviour against a server that answers `tools/list` but
never `tools/call`, or one that answers late (after the bound) with a valid
result. Both are QAN cases for the real-server pass in T10; the late answer
at least lands on a waiter that is already gone (T2's `pending` cleanup),
which is the safe direction.

**Measured:** `go test ./internal/mcp/ -count=1` → `ok` (4.4s, dominated by
deliberate hangs); `-race` → **87** top-level PASS (80 before this task,
**7** new), 0 FAIL; `go vet ./internal/mcp/...` clean; `gofmt -l` empty.
