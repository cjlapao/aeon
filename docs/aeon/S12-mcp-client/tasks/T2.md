**The modules named are the argument, not the count.** JWT and OAuth2 are the
*server's* authorization machinery — this slice is a client only (N1). jsonschema
and uritemplate serve resources and schema validation this layer must not do (M22:
`internal/model` never inspects a parameters schema). testify is somebody else's
test framework imposed on ours. What S12 actually speaks is **four messages** —
`initialize`, `notifications/initialized`, `tools/list`, `tools/call` — plus the
JSON-RPC 2.0 envelope S2 already handles elsewhere in the product.

**The cost of the choice, stated:** we own `client.go`'s framing forever, and the
spec is the only contract either side has. That is why `testdata/fakeserver` is
built to the spec's letter (notifications get no reply; `isError` is a result
field, not a transport error) and the handshake is pinned by tests, and why the
QA suite still owes a real-server case (`docs/test_suites/aeon-mcp.md` QAN-10
stays open — **no test here has met a real MCP server**). The cost of the SDK:
eleven-plus modules, several serving surfaces this slice excludes, and an
upstream breaking change becomes our release blocker.

**Two bugs the first draft shipped, both found by tests written for other
reasons.** Recording them because they are the failure modes of this task:

1. **The HTTP transport sent requests without `id`.** The fake — correctly, to
   spec — treated them as notifications and answered nothing, so `initialize`
   failed with `unparseable JSON: EOF`. A request and a notification differ by
   one field, and the symptom names neither. `httpTransport` now mints ids from
   an `atomic.Int64` and the comment on that line says which field the bug was.
2. **The hang tool blocked the fake's whole loop.** The stdio fake is
   single-threaded, so a "calls" counter query behind a hung `tools/call`
   returned after 30s instead of answering the question. Fixed by bounding the
   fake's hang (`-hang 500ms`) rather than making the fake concurrent — the
   test's claim is *"the caller's budget expired"*, and a concurrent fake would
   have let the test pass even against a client that could not interleave.
   **A fake that is more capable than the client hides the client's bugs.**

**Parity is asserted, not assumed** (N7): `TestHandshakeAndListOverBothTransports`
and `TestCallOutcomesOverBothTransports` run the *same* body over both mountings —
including the injection description arriving **byte-identical** on both, which is
T4's precondition and can only fail on one transport.

**MC3 at the merge point.** `Registry.ApplyListings` is the only door server data
comes through, and it refuses twice: an **unconfigured server is refused outright**
(a server announcing itself is not a server configured), and a **reported tool the
config never declared is dropped, not added** (offered ≠ classified ≠ granted).
`TestUnconfiguredServerContributesNothing` and
`TestOfferedButUndeclaredToolIsNotAdded` assert both — the fake offers nine tools
and the capability list still shows the one the operator wrote.

**Grep guards, both with positive controls** (T1's near-miss is the reason):
`TestNothingIsDiscovered` scans every non-test `.go` in the package for walk /
listen / lookup / well-known machinery and *fails if its pattern set matched
nothing anywhere*, and `TestEveryTestTalksOnlyToTheFake` flags any test naming a
host that looks like a real FQDN (a dot), with loopback and `.invalid` allowed —
a placeholder name with no dot is a fixture, not someone's deployed API.

**Least privilege at the spawn:** a stdio server gets `PATH`, `HOME` and the
variables its config **named** — not the daemon's whole environment. A docs
server has no business reading unrelated credentials out of the process it was
spawned into.

**Measured:** `go test ./internal/mcp/ -count=1` → `ok` (1.1s); `-race` → **35**
top-level PASS, 0 FAIL; `go vet ./internal/mcp/...` clean. The fake is built by

# T2 — `client.go`: stdio and HTTP, configured never discovered

## Why this exists

The transport, and **the discipline that nothing appears without a config edit** (MC3).

**No scanning, no auto-registration, not even as a convenience flag.** A tool surface that changes without
a config edit is one nobody reviewed — and under MC4 it is also one nobody granted, which means the whole
of S10 was bypassed by a directory listing.

**MCP is JSON-RPC 2.0, and S2 already speaks it.** So Q1 is a dependency question, not a protocol one:
does an SDK earn its place in the tree, or is the client a few hundred lines over machinery that exists?
**Decide with `go mod graph` in front of you**, and record the reason — "it seemed easier" ages badly when
the SDK takes a breaking change.

**Read first:** `registry.go` (T1) — names go in it, this file does not own them; `internal/protocol/` for
S2's JSON-RPC; N7 and N11.

## Scope

**1. Two transports** (N7): stdio for local servers, HTTP for remote. **Same adapter, two mountings** — not
two clients.

**2. Answer Q1** in the notes: SDK or hand-rolled, with the dependency cost stated either way.

**3. A fake server in `testdata/`**, and it is the only thing the tests talk to. **Never point a test at a
real third-party service** — a suite that fails because somebody else deployed is a suite people learn to
ignore. The fake offers, at minimum: a read-only tool, an `outward` tool, an **unclassified** tool (T3's
subject), one with a **prompt-injection description** (T4's subject), and one that **hangs** (T8's).

**4. Namespacing** through T1's registry (MC8). Two servers offering `search` are `a.search` and `b.search`,
both reachable, neither shadowed.

**5. No discovery.** Assert it by grep: no filesystem walk, no port scan, no "well-known" lookup, no
registration endpoint.
