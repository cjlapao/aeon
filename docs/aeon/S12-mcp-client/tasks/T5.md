# T5 — Private namespaces: invisible, not unauthorized

## Why this exists

T1 built the registry so a peer's list never contains a private tool. **This task proves the call path
agrees**, and gets the error right.

> **`unknown tool`, never `denied`.**

**`denied` confirms the tool exists.** That is an information leak dressed as a refusal — a peer learns the
reddit agent has a reddit server, which is exactly the kind of thing a private namespace exists to not
tell it.

**And `unknown` is not a lie.** From this agent's point of view the tool does not exist: it is not in its
registry, not in its prompt, and not reachable. The honest answer and the safe answer are the same one,
which is unusual and worth noticing.

**Read first:** `registry.go` as T1 and T3/T4 left it; the design's MC2 and the brief's R2.

## Scope

**1. A call naming a tool outside `ToolsFor(agent)` answers `unknown tool`.** One path, so there is no
second place that might answer `denied`.

**2. The refusal reveals nothing.** Not the server name, not that a tool with that name exists elsewhere,
not a "did you mean". A suggestion engine over tool names is a disclosure channel.

**3. A private tool never reaches a peer's prompt.** Assert on the **assembled prompt**, not on the
registry — T1 asserted the registry, and the prompt is a second surface that could acquire its own list.

**4. Distinguish the three refusals**, because they are different facts and a transcript needs to tell them
apart:

| | |
| --- | --- |
| `unknown tool` | not in this agent's registry (this task) |
| `unavailable` | known but unclassified (T3) |
| `refused: … · ToolAccess "…"` | known, classified, denied by policy (S10) |

**5. Nothing here is a filter over a shared list.** If this task needs one, T1's shape was wrong — report
that rather than adding the filter.
