## Notes (built 2026-10-24)

**Q4, answered: classification comes from OUR configuration, never from the
server.** Asking the server means trusting a stranger's self-assessment of how
dangerous its own tool is — the same trust MC6 refuses when it rejects a
*default*, with extra steps. Our config is a reviewable diff; a server's prose
is not.

**The server's declaration is a hint that may RAISE a class and may never
LOWER one.** `raiseClasses` in `classify.go` is the merge, and it has exactly
one home: `Tool.withHint` is the only caller, and `TestClassifyFileIsTheOnlyRaiseSite`
fails if a second file calls `raiseClasses(` directly — because two merge sites
is two rules, and the two will disagree within a month. The direction is the
whole safety argument: **a hint can only move the system toward caution.** A
server that lies kind costs nothing (a raise that never lands looks exactly
like a config that was never raised — which is why
`TestHintDataArrivesOverBothTransports` asserts the annotations actually parse
over *both* transports: a hint silently lost in one transport fails closed and
*invisible*).

`ReadOnlyHint` is **read and deliberately unused** — it asserts *less* danger,
and a kind word from a stranger about its own tool is not evidence. It is
parsed rather than ignored at the wire so the shape matches the spec and the
refusal stays explicit for whoever greps `readOnlyHint` next year.
`DestructiveHint` outranks: it raises rerun `safe → detectable` (W16's failure
is recovery re-running a destructive call after a crash) and effect
`local → outward`. `IdempotentHint` / `OpenWorldHint` are accepted and ignored,
documented as such rather than absent from the struct.

**The dangerous default and the kind stranger are one failure in two sets of
clothes**, and both got their test: a server that claims `readOnlyHint` for a
tool *our* config never classified stays **refused**
(`TestServerHintNeverInventsAClass`). A hint modifies our decision; it is never
a source of one. The mirror pair asserts a `readOnlyHint` cannot walk our
`outward/unsafe` back to mild (`TestServerClaimCannotLowerOurClass`) — and
**both** start with a precondition assertion that the fake still makes the
claim, or the test passes vacuously, which is the specific way this kind of
test rots.

**`TestRaiseMergeIsTotal` is the property test** — 3 rerun × 3 effect × 4 hint
states, asserting the merge is total, never leaves the legal vocabulary, and
never moves an effect downward. No counts.

**Three refusals, three sentences, asserted not to collide**
(`TestUnavailableDistinguishableFromDeniedAndUnknown`): `unknown tool:` (T5),
`unavailable: … — no re-run class, no effect class (MC6)` (this task), and
S10's `refused: … · ToolAccess "…"` (T7 attaches it).
`UnavailableReason` names what is missing because *"unavailable" alone is not
actionable* — and the missing-only-one cases have their own tests so the
sentence never over-claims (a tool lacking only `rerun` must not mention the
effect class).

**The no-default grep caught three real things on first run, then needed
calibration — both directions recorded:**

1. It caught nothing wrong in `classify.go` initially: the first hit was the
   word `default:` **in my own comment** documenting the rule. Comments
   document, they must not trip the guard — the test now strips `//` lines
   before matching. (Keeping the comment and moving the goalposts is the right
   way round; deleting the comment to please the grep is the wrong one.)
2. It flagged `config.go`'s `EffectLocal = "local"` — **declaring the
   vocabulary is not assigning a default**, and the test now exempts constant
   declarations by their left-hand side (`Effect…`/`Rerun…`), with that
   distinction spelled out in the test rather than silently allowed.
3. It caught a genuine shape problem: `registry.go` was calling `raiseClasses`
   itself. That call moved into `classify.go` as `Tool.withHint`.

Also verified: `Availability` is deliberately **un-raised** — whether a tool
exists and is classified are configuration facts; the raised classes are what
the model is shown and what T6's use-time ask decides on.

# T3 — `classify.go`: both classes, and no default


## Why this exists

**W22, applied to a surface we do not author.**

Every tool declares a re-run class (W16) *and* an effect class (L22). For the nine, we wrote both. For a
third-party server, **somebody has to decide — and the decision cannot be a default** (MC6).

**Because the safe-looking default is the dangerous one.** `read-only` is the obvious fallback and it is
exactly wrong: the unclassified tool it silently permits might be the one that posts to the internet. A
default here is a guess about somebody else's tool, made once, applied forever, invisibly.

**So an unclassified tool is refused, and says so.** Not denied by policy — *unavailable*, which is a
different fact and reads differently in a transcript.

**Read first:** W16 and L22 in S11 for what the classes mean; `client.go` (T2) for the fake's unclassified
tool; the design's MC6.

## Scope

**1. Both classes required** before a tool is callable. No zero value that means anything.

**2. Answer Q4, and the security answer is our config.**

> **Asking the server means trusting a stranger's self-assessment of how dangerous its own tool is.**

MC6 refuses a *default* for that reason; accepting the server's claim is the same mistake with extra steps.
So classification is **declared in Aeon's configuration**, which is reviewable.

**If you do read the server's declaration, it is a hint that may RAISE a class and may never LOWER one.**
State that in the notes and assert it — a server claiming `read-only` for a tool we classified `outward`
must not win.

**3. The refusal names the tool and what is missing** — *"no effect class"* is actionable; *"unavailable"*
alone is not.

**4. No `default:` arm that classifies.** Assert by grep. A `default:` returning a class is this task's one
unacceptable failure, and it will look like tidy code.
