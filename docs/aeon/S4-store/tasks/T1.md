> ## Notes — done 2026-10-15
>
> ### The redirect was right, and the gap turned out to be exactly one thing
>
> The banner said: use the framework's contracts, expand only what is missing. Four probes, run before any
> code, found what was missing — and it is **the driver, and nothing else**:
>
> ```
> PROBE 1  the framework's OWN SQLite arm (service/sqlite.go, verbatim):
>            sql.Open("sqlite", "file:…?cache=shared&mode=rwc")   ← modernc.org/sqlite
>            select vec_version()  →  SQL logic error: no such function: vec_version
>            pragma journal_mode   →  delete        pragma foreign_keys → 0
>
> PROBE 3  mattn/go-sqlite3 with the mattn spelling:
>            ?_journal_mode=WAL&_foreign_keys=1&_busy_timeout=5000&_synchronous=NORMAL
>            →  journal=wal  fk=1  busy_timeout=5000  sync=1  CASCADE FIRES (0 children)
>          the other driver's spelling, on mattn:
>            ?_pragma=journal_mode(WAL)&_pragma=foreign_keys(1)
>            →  journal=delete  fk=0  CASCADE DOES NOT FIRE (1 child)
>
> PROBE 4  gorm over an already-open mattn *sql.DB (sqlite.Dialector{Conn:…}):
>            dialector=sqlite · vec_version=v0.1.6 · AutoMigrate ok · vec0 created
>            (*gorm.DB).DB() returns the SAME handle
>
> PROBE 5  SetMaxOpenConns(1): the second writer BLOCKS (still waiting at 300ms),
>          and the wait is interruptible — a 50ms context returned
>          "context deadline exceeded"
>
> PROBE 6  vec_version on both pools, and on four concurrent reader connections: v0.1.6 each
> ```
>
> **The brief's measured table was measured against the wrong driver pair.** It compared the two DSN
> spellings and concluded "use the mattn form", which is right — but it attributed the result to
> `gorm.io/driver/sqlite` + mattn, and the framework does not open that way. It calls
> `sql.Open("sqlite", …)` (modernc, pure Go) and hands the handle to `sqlite.Dialector{Conn:…}`. modernc
> accepts **both** spellings, so the silent-failure table only applies to mattn — and mattn is the driver
> Aeon needs, because modernc cannot host a C extension at all.
>
> ### So: injected mode, which is a published construction mode
>
> `database.New(database.WithDB(handle))`. Injected mode skips connect and config and still runs the schema
> lock, the migration runner and the store lifecycle on the handle it is given. What stays the framework's:
> `SQLiteConfig`/`PoolConfig` (read in `resolveConfig`), the `_migrations` ledger, the schema lock, the
> `Store` contract. What Aeon owns: the two `*sql.DB` handles, and the DDL.
>
> This is not "Aeon owns the store after all". It is one seam, taken because the framework's driver cannot
> do the one thing B3 requires.
>
> ### Deviations
>
> **The path chain is the framework's config plane, not a second resolver.** `opts.Dir` →
> `DATABASE_SQLITE_DSN` → `DATABASE_SQLITE_STORAGE_PATH`/`_FILE_NAME` → `paths.StoreDirFor(env)`. The last
> row exists because most CLI verbs never call `appenv.Apply()`, and without it `db info` would resolve the
> framework's own default of `"."` — the process's working directory — and report a different store
> depending on which shell it ran from.
>
> **`AEON_STATE_DIR` was added to `internal/paths`, not to the store.** The task's chain names it and the QA
> suite depends on it (D19), but it existed nowhere in the code. It is read in the ONE resolver, above the
> XDG chain, so there is still exactly one place that answers "where does state live".
>
> **`internal/paths` gained `StoreDirFor(getenv)`.** I7 requires the chain to be testable without mutating
> the process environment, and a test that calls `os.Setenv` has changed what every other test in the
> package reads.
>
> **`_txlock=immediate` on the writer DSN — not in the task, and load-bearing.** `busy_timeout` does NOT
> cover a lock upgrade: a deferred transaction that becomes a write gets `SQLITE_BUSY` immediately. Within
> one process the pool hides this (one connection), but the demo's concurrency step is two PROCESSES, and
> D11 forbids `SQLITE_BUSY`. Taking the write lock at BEGIN puts the wait where `busy_timeout` applies.
>
> ### Q6's answer, and what it settles
>
> `SetMaxOpenConns(1)` **blocks**, and the wait honours the caller's context. DB15's whole argument —
> predictable serialisation at the pool rather than a `busy_timeout` retry loop — depends on that, and it
> holds. If it had errored, the design would have needed changing rather than documenting.
>
> ### The numbers, stated as guesses (O7)
>
> `DefaultBusyTimeout` 5s, `DefaultReadPoolSize` 4, and a read-latency bound of 2s in the concurrency test.
> All guesses, all said so in the source. `writerPoolSize` is **not** a guess and not configurable: WAL
> allows one writer, and that is a code-level decision outranking configuration, like a service pin. The
> framework's `PoolConfig` is one pool, so it is read for the half it can describe — the reader.
>
> ### Not verified
>
> The Windows arm of `paths.StoreDirFor` is skipped on POSIX with a named reason (`runtime.GOOS` cannot be
> changed by a test). It is reachable only on the Windows CI target.

## Context

Every test in this slice needs a database, so this comes first. Two of its checks look pedantic and are not.

**`foreign_keys` is proven by a cascade, not a pragma read-back** (D10). Reading the pragma back proves the
statement ran; a cascade proves it took effect. And `foreign_keys` is **per connection** and defaults off, so
with `database/sql` creating connections lazily, a connect hook registered once can be missed by a connection
the pool opens later. The symptom is a cascade that silently does not happen, diagnosed as a data-modelling bug.
That is why the pragmas go in the **DSN** (DB16), where they are part of what opening means.

**`vec_version()` must answer on both pools** (Q2, D18). `sqlite-vec-go-bindings/cgo` registers the extension
through `sqlite3_auto_extension()`, which should apply to every connection — but "should" is why this is a
probe. An extension registered for one pool is a retrieval slice that works in tests and fails under load.

**Two pools, and the writer is single-connection** (DB15). WAL permits one writer and many readers. With one
pool, two goroutines writing both get connections and the second gets `SQLITE_BUSY`, which `busy_timeout` then
papers over — turning a design property into a retry loop whose latency nobody can predict. `MaxOpenConns(1)`
makes the second writer queue **at the pool**, predictably.

**Read first:** `docs/_archive/aeon-v1-horizontal/02-store/tasks/T1.md` for the path chain; `mattn/go-sqlite3`'s DSN
documentation; the plan's Q1, Q2 and Q6 answers.


assert the child is gone. Do that **on a connection the pool created after the first**, so a missed-hook bug
would show.
