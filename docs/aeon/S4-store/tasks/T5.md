>

## Context

The `step` table is where cost honesty either survives or quietly dies.

**`cost_state` is a stored column, never derived** (DB11). The temptation is one nullable `cost_usd` with the
state inferred from nullity — and that **collapses `partial` into `known`**, because a partial cost has a
number. The lower-bound semantics that S3's whole cost design preserved are gone at that point, and no later
slice can recover them: cost rollups and the app's "at least $X" both read this column.

**`context_manifest` is what makes resume and recovery consistent** (P5). It holds the declared context frozen
at first assembly with a content hash per file, plus `iterationsUsed` and an **absolute** `deadlineAt`.

Absolute, not remaining: a relative deadline cannot survive a suspension that lasts overnight — it would grant
the resumed step its whole budget again, and a step could escape its bounds by suspending repeatedly.

**`step.status` must distinguish `suspended` from `orphaned`** (§3a). A suspended loop has **no process, by
design** (P2). A reconciler treating "no process" as "orphaned" would mark every waiting loop as crashed and try
to recover it — and S7's recovery reads `status='running'` specifically because that is the only state that
means the daemon died mid-step.

**Read first:** `packages/loop-state-mcp/src/store.ts` for v1's `step` table; `internal/model/types.go` (S3)
for `Cost`; `../ARCHITECTURE.md` §3a for the recovery states.

## What to do

**1. `steps.go`** — step create, read, list by loop, update. Columns beyond v1's:

- `cost_usd` REAL NULL
- `cost_state` TEXT NOT NULL with a `CHECK`
- `cost_detail` TEXT NULL — JSON: `{"missing":[…]}` for partial, `{"reason":"…"}` for unknown
- `context_manifest` TEXT NULL — JSON: `{"files":[{"path","hash"}],"iterationsUsed":n,"deadlineAt":"…"}`
- `status` TEXT NOT NULL with a `CHECK` including `running`, `suspended`, `orphaned`, `done`

**2. Write cost through one function** taking S3's `Cost` and decomposing it into three columns, and read it
through one that reassembles. **No caller assembles the columns by hand** — one that writes `cost_state`
directly will eventually write one inconsistent with `cost_usd`.

**3. `context_manifest`** round-trips as JSON. The store holds it; it does not validate the hashes.

**4. The test that matters is negative.** Store a `partial` whose `cost_usd` is non-null **and** a `known` whose
`cost_usd` is non-null, read both back, and assert they are still distinguishable. An implementation inferring
state from nullity cannot pass that, and every positive test would pass against it.
