# T10 — `store.go`: the surface, and the two proofs no table can make

> ## Notes — done 2026-10-15
>
> ### The cold read is a real process, and it is this test binary re-executed
>
> `TestMain` dispatches on `AEON_STORE_COLD_READ_CHILD` before the test framework starts, so the child runs
> one program and prints one JSON report. It is a real process with its own address space, its own pools and
> its own `sqlite3_auto_extension` registration — which is the whole point. `go run` on a generated program
> would add a cgo compile to every test run and prove nothing more.
>
> The parent implements ARCHITECTURE §3's suspend sequence literally: a loop, a task, a document, a step, a
> transcript ending in an UNANSWERED `tool_use` (which is what a suspended transcript looks like, and which
> S3's validator accepts deliberately), a permission question carrying that `tool_use_id`, a partial cost, a
> context manifest, and `status='suspended'`. Then it CLOSES the store before the child runs, so nothing in
> the parent's memory can be what the child reads.
>
> The child compares: the transcript digest, the thinking signature **as an exact string**, the thinking
> text, the message count, the step status, the cost state and floor, the pending question's `tool_use_id`,
> `IsAwaiting`, the plan document's content, and that `vec_version()` answers in a fresh process.
>
> `TestTheColdReadChildFailsWhenTheTranscriptIsMissing` is the negative control on the harness: a child
> that printed a plausible digest for a step that does not exist would make the main test prove nothing.
>
> ### A test of mine that was wrong, not the store
>
> The concurrency test's "a reader never goes backwards" check compared a SHARED high-water mark across
> three readers, and reported `194 after 196`. Two readers legitimately see different prefixes at the same
> moment — one may be two writes behind. The check is now per-reader, and the comment records the false
> positive so nobody re-introduces it.
>
> ### Measured, on a real store, two processes
>
> ```
> 3000 writes from one process        87ms (34,309/s) · worst single write 1.168ms
> a SECOND hammer process, concurrent  completed; the two interleaved (seq 3037 then 3087)

> The read-latency bound in the test is 2s and is stated as a guess (O7). What matters is that a read answers
> in a time a UI can render, not that it answers in this particular time.

## Context

The seam, plus the two claims this slice makes that no per-table test can substantiate.

**"Resumes cold" means a different process.** Every test so far has written and read in the same process,
holding the same pools, with the same objects in memory. That proves serialisation, not resumption. The honest
test **spawns a real child process** that opens the file fresh, reads back a transcript and a question, and
reports a digest — because the failure being ruled out is precisely something surviving in memory that does not
survive on disk.

**"One writer, many readers" means concurrent processes.** DB15 arranges it with a single-connection writer pool
(T1), and the only way to know it is right is sustained writes with reads happening throughout, checking that
reads answer promptly and nothing reports `SQLITE_BUSY`.

The surface is fixed here. S5, S6, S7 and S11 all read and write through `store.go`, and **none of them writes
SQL** (I2). Keeping every statement inside `internal/store` is what makes a schema change a local change.

**Read first:** every module from T1–T9; the brief's §5 seams; `../ARCHITECTURE.md` §3's suspend/resume sequence,
which the resume test implements literally.

## What to do

**1. `store.go`** — the public surface. Export `OpenStore`, `ResolveStatePath`, the per-table functions, the
machine's tables and `ValidateTransition`, and the types. **Nothing without a named consumer** — an export with
no caller is surface to maintain for nobody, and this task's notes list each one's consumer.

**2. The cold-resume integration test.** In the parent: open a store in a temp dir; create a loop, a task, a
step; append a transcript including a **signed `thinking` block** and a `tool_use` with no `tool_result`;
`Ask()` a permission question carrying that `tool_use_id`; `Answer()` it; close the store.

Then **spawn a child process** running a small program that opens the same file, reads the transcript and the
question, and prints a digest. Assert in the parent that the digest matches — **including the `thinking`
signature as an exact string** across the process boundary.

**3. The concurrency integration test.** One goroutine appending events continuously; several others reading
concurrently. Assert no `SQLITE_BUSY`, that reads complete within a stated bound, and that a reader sees a
**monotonically growing prefix** — never a gap, which would indicate a torn read.

**4. The surface tests.** Assert the exact export set; assert the store imports from `internal/model` only the
four names (I1); and grep all of `internal/` and `cmd/` for SQL keywords, asserting hits only under
`internal/store` (I2).
