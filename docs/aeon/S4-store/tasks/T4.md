>
> `TestReadsUseTheReaderPoolAndWritesTheWriter` greps both ways: no `s.r.Exec`/`s.r.Begin` anywhere, and no

> ### Deviation: two `Where` methods rather than one with a column argument
>
> `Scope.Where` for tables whose column is `loop_slug`, `Scope.WhereLoop` for `loop`, whose own name is
> `slug`. The asymmetry is real — one is a reference, the other is the name — and collapsing them into one
> call with a column parameter invites passing the wrong one, which would still run.
>
> ### `ProjectScope.Where` returns `1 = 1` when unscoped
>
> So a caller can always write `WHERE ` + predicate. A caller assembling the WHERE conditionally is one who
> will eventually get the condition and the arguments out of step.
>
> ### Two things the tests caught
>
> `mustAffectOne`: without it, an UPDATE against a scope that does not exist succeeds silently and the
> caller believes it wrote something. Now `ErrNotFound`.
>
> `SetTaskStatus` touches the loop's `updated_at` too. "Every loop by recency" (2a) is the one list a
> person looks at, and a loop whose tasks are moving while its timestamp is stale sorts to the bottom of it.

> ### The mode is read from the loop, never taken from the caller

> A caller passing the mode could pass a different one from the loop's and get a transition the ladder does

## Context

The ported tables, with one sharp edge: **scoping**.

Every scoped row is keyed by `(loop_slug, project_root)` **together** (DB4). A query filtering on the slug alone
returns another project's rows — and slugs are chosen by humans and repeat constantly (`refactor` in two
checkouts). It is also invisible in testing unless a test deliberately creates the **same slug in two roots**,
which is why one does.

`project_root` is what makes a git worktree work for free: a worktree has a different path, so it is a different
project, gets its own loops, and its own concurrency guard. That behaviour is inherited, not designed here, and
must not be simplified away.

**Discipline is not a mechanism** (I4). Rather than trusting every query to remember the scope, it goes in a
helper that produces the predicate and its arguments, and a grep asserts no scoped SQL is written without it.

**Reads use the reader pool** (O6, I6). A read on the single-connection writer serialises behind every write,
and the symptom is a UI that stalls whenever a loop is busy — diagnosed as a UI problem.

**Read first:** `packages/loop-state-mcp/src/store.ts` for v1's loop and task methods and its composite-key
convention; `machine.go` (T3); the plan's Q3 for which tables are scoped.

## What to do

**1. `scope.go`** — a small type producing the predicate and bound arguments from `{LoopSlug, ProjectRoot}`.
Every scoped statement composes it. This is I4's mechanism.

**2. `loops.go`** — project upsert, loop create and read, phase read and set. Port v1's behaviour **without**
`awaiting_user` (DB6); the waiting question is T7's `IsAwaiting`.

**3. `tasks.go`** — task create, read, list, status change. **Every status change goes through
`ValidateTransition`** (T3), and a refusal is **returned as a result, not an error** (DB19). The store is where
the machine is enforced; a caller that could bypass it makes the machine advisory.

**4. Timestamps are ISO 8601 UTC** (I9), from an injectable clock so tests are deterministic.

**5. The scoping test is the important one.** Create two loops with the **same slug** in two project roots, then
assert every read, list and update touches exactly one. A test using distinct slugs cannot detect a missing
scope predicate — it would pass against a store with no scoping at all.
