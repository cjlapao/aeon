> ## Notes — done 2026-10-15
>
> ### Q1 answered: the framework's machinery SUBSUMES the ledger
>
> Run, not reasoned. `migrations.MigrationService` was driven standalone — no `system.Initialize`, no
> config service — on a mattn handle wrapped for GORM:
>
> ```
> three opens of one file   →  _migrations holds exactly one row per migration, all "applied"
> an ALTER migration        →  applied; `p` went from 2 columns to 3
> a FAILING migration       →  its transaction rolled back (the table it created is ABSENT),
>                              the run STOPPED (the migration after it never ran),
>                              the ledger recorded `failed`, and RunAll reported errors
> ```
>
> That is DB8 and DB9 exactly: numbered, ordered, one transaction each, recorded, run on every open — and
> D5's loud failure for free. So Aeon registers `SQLMigrationWorker`s and owns **no runner**. Running two
> migration systems over one file is the thing that works until it does not.
>
> One adjustment: `SetMaxRetries(1)`. The framework defaults to three, which is right when a replica might
> be contending on PostgreSQL; a SQLite DDL statement that failed is a statement with a mistake in it, and
> two more attempts only add misleading error lines before the real one.
>
> ### The deviation that matters: ONE DDL source, and what D4 therefore compares
>
> The design wanted two paths to the current shape — `schema.go` creating it directly, `migrate.go` walking
> an old one forward — with a test proving them identical (I3).
>
> **I did not build the second copy, because it cannot catch the bug it is for.** Two hand-maintained
> copies, edited in the same commit, agree with each other and still break an upgraded install: the drift
> that matters is between a database built by TODAY's `CREATE TABLE` and one built by an older `CREATE`
> plus every `ALTER` since.
>
> So there is one source (the ordered migration set) and D4's test compares **fresh against UPGRADED**: a
> frozen prior-version DDL held in `schema_test.go`, its ledger seeded for 0001–0005, walked forward by the
> runner. That fails exactly when somebody adds a column to an existing migration's `CREATE TABLE` instead
> of adding a new migration — the real version of this mistake, and the one two copies cannot see.
>
> `TestTheEquivalenceTestCanFail` is the negative control: it adds a column behind the comparison's back
> and asserts the diff names it.
>
> ### Q10 answered: how the frozen DDL stays alive
>
> It is a literal in the test, paired with `_migrations` rows for 0001–0005 — exactly what a database of
> that vintage carries. When 0007 is added, the runner walks the snapshot through 0006 **and** 0007 and the
> test keeps proving what it was written to prove. Nobody has to touch it. A snapshot without its ledger
> rows would have made 0006 re-run and fail on `duplicate column name`.
>
> ### Comparing schemas: not `sqlite_master.sql`
>
> `ALTER TABLE … ADD COLUMN` **rewrites the stored CREATE text by appending to it**, so an upgraded database
> and a fresh one hold different text for identical tables. A text comparison fails on every database that
> was ever migrated — which is every real one — so it would be switched off within a week.
>
> `fingerprint.go` describes the shape instead: columns with ordinal, type, nullability, default and pk;
> indexes with their columns, direction and uniqueness; foreign keys with their actions; and the CHECK
> expressions, which live nowhere but the text and are pulled out by paren-counting. 220 lines on a fresh
> store. A missing `UNIQUE`, a dropped `CASCADE` and a lost `CHECK` are each visible.
>
> ### Six migrations, matching the demo's prediction

> `0001_core_tables` · `0002_steps_and_events` · `0003_chat` · `0004_documents_and_archive` ·
> `0005_policy` · `0006_step_context_manifest`. The demo predicted "6 migrations applied, latest
> 0006_step_context_manifest" and that is what `aeon db info` prints.

> 2a's history indexes and 2b's three policy tables are in, with their CHECKs. `policy.not_after` is

> `question` and `chat_message` had **no foreign key to `loop`** — the archived design's DDL has none

## Context

The largest task in the slice and deliberately not split, because it binds an invariant whose breach is
**invisible until it is somebody else's problem**.

**I3 — a fresh schema and a fully migrated schema must be identical.** There are two paths to the current shape:
`schema.go` creates it directly for a new database, and `migrate.go` walks an old one forward. When they drift,
the bug appears **only on upgraded installs**, months later, on a machine you cannot reach — and it is invisible
in review because both files look correct on their own. A task boundary anywhere inside this leaves the
invariant unenforced across it, which is why the size guidance is waived here rather than the task split.

**The runner must be tested against a database it did not create** (O2). A runner exercised only on fresh
databases has **never run its `ALTER` path**. So the test builds a database from a **prior-version DDL held in
the test file** — not a committed binary, which goes stale the first time somebody adds a column and then
quietly stops testing anything.

**A failing migration must leave the prior version intact** (D5). A partially migrated database is worse than
one that refuses to open, because the caller proceeds against a shape nothing expects.

**Read first:** `packages/loop-state-mcp/src/store.ts` — all twelve `CREATE TABLE` statements, the `MIGRATIONS`
array, the ledger runner at the bottom; `packages/loop-state-mcp/test/unit/legacy-schema.test.ts` for how v1
tests old shapes; `docs/_archive/aeon-v1-horizontal/02-store/design.md` for the three new tables' DDL; the plan's Q3 and Q4.

## What to do

**1. `schema.go`** — DDL for every table. Port v1's twelve with the columns Q3 and Q4 established, **omitting
`awaiting_user`** (DB6). Add `step_message`, `question`, `chat_message`, the three cost columns and
`context_manifest` on `step`.

`CHECK` constraints on `question.kind`, `step.cost_state` and `step.status` (O5) — a typo must fail at write
time, where the stack names the caller.

**2. `migrate.go`** — the ledger: numbered ids, applied in id order, one transaction each, recorded in
`schema_migrations`, run on every open (DB8). Port v1's mechanism; it works.

Seed the array so both paths in I3 exist and can be compared, and **include at least one `ALTER TABLE`** so
DB9's capability is exercised by the suite rather than asserted.

A failing migration rolls back its own transaction and makes the **open** fail loudly.

**2a. The history-query indexes** (Stage 5's S25). Three indexes land **with this schema, not as a later migration**:

| Index | For |
| --- | --- |
| `loop` by last-touched, descending | "every loop by recency" |
| `event` by `seq` range | the time-ordered walk |
| `step` by `loop_id` | drill-down |

S25 is a **read-only projection** over data this schema already holds — no new table, no new column. But it is the first
query in the plan that reads a lot, and S4's own choices (two pools, a single writer) were made for one loop at a time.
**An index is free now and a migration on a live store later**, which is the whole reason it is here rather than there.

**2b. The policy tables** (Stage 3's S10). Three tables and their indexes land **with this schema, for the same
reason as 2a**:

| Table | Holds |
| --- | --- |
| `policy` | `id`, `type`, `target_kind`, `target_id`, `action`, `spec` (JSON), `source`, `not_after` (nullable) |
| `policy_acceptance` | which target accepted which policy, and when |
| `policy_event` | every refusal and every runtime disagreement, with its subject |

`CHECK` constraints on `policy.action` (`allow` / `deny`), `policy.type` and `policy.target_kind` (O5) — the type set
is **closed**, so a typo is a write-time failure rather than a policy that silently matches nothing. **A policy that
matches nothing is indistinguishable from a policy that permits everything**, which is the worst failure this table
can have.

`not_after` is **nullable, and null means no expiry** — not a sentinel date. A far-future sentinel is a policy that
silently lapses on a day nobody chose.

Indexes: `policy` by `(target_kind, target_id)` — the lookup every evaluation makes; `policy_event` by `(policy_id,
at)` — the audit query and the age-based cap.

**Why here and not at S10:** S4 is Stage 1 and S10 is Stage 3, so by then this store holds **real loops**. The same
sentence as 2a applies — *a table is free now and a migration on a live store later* — and it is more true here,
because these three carry the record that says what the system was allowed to do. **Nothing in this slice reads or
writes them**; S10 brings the evaluator. This task creates the shape.

**3. The equivalence test.** Create one database via `schema.go` and one by running every migration from empty,
then compare **normalised `sqlite_master`**: sort rows, strip whitespace and `IF NOT EXISTS`, compare `sql` per
object. **Include indexes and constraints** — a missing `UNIQUE` is exactly the drift this catches, and the one
most likely to be missed.

**4. The upgrade test.** Hold a prior-version DDL in the test file, create a database from it, seed rows across
several tables, run the runner, and assert: the schema now matches current, **every seeded row survived**, and
the `ALTER`ed column has the expected value for pre-existing rows.

**5. Idempotence and ordering.** Open the same file three times; assert one ledger row per migration. Assert
application order is by **id**, not array position, with a deliberately misordered array.
