# T8 — `events.go`: `seq` on the table, replacing S2's counter

> ## Notes — done 2026-10-15
>
> ### The promise, kept — and demonstrated on a real store
>
> ```
> seq before the restart   29
> daemon restarted
> seq after                30  daemon.started
>                          31  client.connected
>                          32  client.disconnected
>
> aeon watch --after 29     →  "from seq 30", and it replayed 30, 31 and 32 —
>                              events that happened while nothing was watching
> ```
>
> In S2 that cursor would have been handed `from seq 1`. The store's `event` rowid is the allocator, and
> `AUTOINCREMENT` never reuses an id — measured: after a close, a reopen AND a delete of every row, the next
> id was 4 where three had been used.
>
> ### Q8's sequencing: at construction, so there is no live swap
>
> `protocol.NewEventLog().WithBacking(...)` happens inside `daemon.New`, before the method table exists and
> therefore before any client can connect. There is no moment at which a subscription exists against the
> in-memory counter and then sees the table's numbering. **A live migration is not supported and is not
> needed** — a running daemon is not upgraded in place, it is restarted, which is the thing the cursor is
> being made robust against.
>
> ### The seam: an interface in `protocol`, the adapter in `daemon`
>
> `internal/protocol` imports nothing storage-shaped (T11/I1) and `internal/store` imports nothing but
> `internal/model` (S4's I1). So neither can know the other: `protocol.Backing` is declared in protocol
> terms, and `daemon.EventBacking` converts. `EventFilter` on the store side takes primitives — `[]string`
> and a project root — rather than a `protocol.Filter`, for the same reason.
>
> `EventLog.Head()` asks the TABLE when a backing is attached, because another process can append (a CLI
> verb writing an event is not refused) and a head from memory would hand a client a cursor that skips what
> it missed. A failed read falls back to the cache rather than to zero — zero would read as "nothing has
> happened", which is the one answer that is certainly wrong.
>
> `Resume` now serves a cursor older than the in-memory ring FROM THE TABLE, and reports no gap because
> there is none. That is a strict improvement on S2's honest-gap behaviour, which remains the fallback if
> the read fails.
>
> ### S2's doc comment and S2's demo
>
> Both deliverables of this task, both done. The doc comment is rewritten to describe the two modes (durable
> with a backing, which is every `aeon serve`; in-memory without one, which is a test mode and not a
> shipped configuration). S2's DEMO step 8 is rewritten rather than deleted, because the fact that it once
> was not durable is useful history for anyone reading the two slices in order.
>
> **S2's own guard flipped rather than being deleted.** `TestSeqIsDocumentedAsInMemoryAndResettingOnRestart`
> asserted the source contained the words "IN-MEMORY" and "resets on restart". It is now
> `TestSeqIsDocumentedAsDurableNowThatS4BacksIt`: the source must say DURABLE and must NOT still say
> "resets on restart". Deleting the test would have been the easy move and the wrong one — what is worth
> guarding is that the code and the comment agree, in whichever direction that happens to be.
>
> ### Gaps are correct, and the test proves the gaps are really there
>
> `TestAFilteredReadReturnsMatchingEventsWithGapsAndTheCursorStillWorks` interleaves two projects' events so
> the matching ids CANNOT be contiguous, asserts a gap was actually observed (otherwise the test would be
> exercising the easy case), and then resumes from the last matching seq and gets exactly the next matching
> event — not the next id.
>
> ### Kind filtering, and the injection-shaped mistake it avoids
>
> `loop.*` becomes a `LIKE` with the prefix escaped; an exact kind stays an equality. So a kind containing
> `%` cannot become a wildcard by accident, which `TestAKindContainingAWildcardCharacterCannotBecomeAWildcard`
> pins.

## Context

**This task closes a promise made in another slice.**

S2 emitted events with an in-memory counter that reset on every daemon restart. That was correct for a slice
with no store, and S2 did the right thing: it said so in a doc comment on the counter and said so in its demo,
**naming this slice as the one that would fix it.** So this task has an obligation beyond writing code — it must
**delete that doc comment and update S2's demo.** A limitation fixed in one place and still documented in
another is worse than either, because a reader trusts whichever they find first.

**`seq` becomes the `event` table's rowid** (DB17): one global monotonic sequence, not one per project. A
subscription filtered to one project receives ids with **gaps**, which is correct — the cursor's contract is
"everything after N that matches my filter", and gaps carry no information a client needs.

The alternative, a sequence per project, needs a counter per project, atomic allocation for each, and a
reconciliation story when a client subscribes across projects — all to remove gaps nobody reads.

**Only the store allocates `seq`** (DB20). Two allocators produce duplicates or regressions, and a cursor handed
a duplicate silently delivers the same event twice.

**Read first:** `internal/protocol/events.go` (S2) — the counter and its doc comment; `docs/aeon/S2-protocol/DEMO.md`
step 8, which says `seq` resets; the plan's Q7 and Q8.

## What to do

**1. `events.go`** — `AppendEvent`, `ReadEvents(scope, after, kinds, limit)`, `AppendMemory`, `ReadMemory`.
Events are **append-only**: no update, no delete.

`AppendEvent` returns the allocated `seq` — the rowid from `last_insert_rowid()` on the writer connection, which
is safe precisely because the writer pool is at one (Q7).

**2. `ReadEvents`** is the cursor's implementation: everything with `id > after` matching the filter, ordered by
`id`, bounded by `limit`. Gaps are expected and are not an error.

**3. Replace S2's counter** (Q8). Name the sequencing that does it without breaking a subscription mid-flight —
the daemon holds subscriptions in memory, so the switch happens at startup and an existing subscription's
`after` value is a store id from that point on. If a live migration is impossible, say so and require a restart.

**4. Delete S2's doc comment**, and **update `docs/aeon/S2-protocol/DEMO.md`** where it tells the reader `seq`
resets. Both are deliverables of this task, not follow-up work.

**5. Test durability explicitly**: write events, **close the store**, reopen it, append another, and assert the
new `seq` continues rather than restarting. That is the whole promise, and it is the one test S2 could not write.

**6. Test the filtered-gap case**: emit events across two projects, read filtered to one, and assert the
returned ids have gaps **and** that a cursor built from the last one returns exactly the next matching events.
