# T7 — `chat.go`: `question` and `chat_message`, the pair

> ## Notes — done 2026-10-15
>
> ### The forced failure, and the two attempts it took to force honestly
>
> D16 needs the SECOND write to fail with the first already inserted. My first attempt planted rows to make
> `chat_message.seq` collide — and it does not work: the store recomputes `MAX(seq)+1` on each retry, so
> occupying a range just moves the free slot. (That exploratory version is gone; the comment records why.)
>
> The honest forcing mechanism is a SQLite trigger that aborts every insert of a question-kind thread entry.
> It cannot be absorbed by the retry, which makes it a test of the TRANSACTION rather than of the retry —
> and it is exactly what a broken second write looks like from inside. With the trigger dropped, the same
> call must succeed, so the test cannot pass against an `Ask` that writes nothing.
>
> ### `IsAwaiting` is tested across all five states
>
> None · one unanswered · one answered · several with one unanswered · several all answered. A two-case test
> passes against an implementation returning `count > 0`, which is wrong in exactly the case that matters.
> Each case also asserts `IsAwaiting` and `PendingQuestion` AGREE — the two must never disagree, because
> nothing would say which is right.
>
> ### Answering twice is refused, and the refusal names the timestamp
>
> Checked in two places on purpose: the read before the transaction produces the MESSAGE (with the existing
> `answered_at` in it), and `WHERE answered_at IS NULL` in the UPDATE is the GUARANTEE. If the UPDATE loses
> the race, the question is re-read so the refusal names the timestamp that won.
>
> ### `seq` collision: retried, bounded, and tested with the collision forced
>
> Four attempts. Two goroutines append here — a runner and the server — so a collision is expected
> occasionally; four consecutive losses on a single-connection writer pool would mean something other than
> contention, and retrying forever would turn that into a hang. `TestASeqCollisionRetriesAndSucceeds`
> plants a row at the seq the store is about to compute.
>
> ### `AwaitingSQL` is published as a constant
>
> Because `aeon db query awaiting` and the app's Store tab both PRINT it. A second copy in the CLI would
> eventually print something the store does not run. `TestTheAwaitingSQLIsTheQueryTheStoreActuallyRuns`
> executes the constant.
>
> ### Nullability as fact, not convenience
>
> `tool_use_id` is NULL for a gate and set for a permission prompt, asserted on the COLUMN rather than on
> the struct: `''` and absent are different facts, and a fabricated id is one some resume path will
> eventually try to match. Same for `options` on a free-form question.

## Context

The second table v1 never had, and the one that makes chat possible. v1 could say *that* a loop was blocked —
`awaiting_user`, a flag and a reason — and had nowhere to hold the conversation that unblocks it.

**Two tables, because they fail differently** (DB7). `question` is the suspension mechanism: `tool_use_id`,
`options`, `answered_at`, read by the runtime to resume. `chat_message` is the human-facing thread: it holds
steering messages and notes that answer nothing, and it is what the app renders in order. They join on
`question_id`.

**The transactional pairing is the property that matters.** `Ask()` writes both rows or neither:

- a question with **no thread entry** is a loop waiting on something the user cannot see
- a thread entry with **no question** is a prompt nobody can answer

Both are silent. Neither errors. So the test **forces a failure mid-`Ask`** and asserts neither row exists.

**`tool_use_id` is nullable on purpose.** A permission prompt or a clarify question comes from a tool call and
has one; a phase gate is asked by the loop driver with no model turn behind it and does not. A non-null column
would force the driver to fabricate an id — and a fabricated id is one some resume path will eventually try to
match.

**Answering twice is a race, not an edit.** The first answer may already have resumed the step, so a second is
**refused**, not applied. An overwrite would leave the resumed step acting on a value the user believes they
replaced.

**Read first:** `docs/_archive/aeon-v1-horizontal/02-store/design.md`'s DDL for both tables and its "There is no `awaiting_user`
column" section; `scope.go` (T4); the plan's Q7 on `seq` allocation.

## What to do

**1. `chat.go`:**

```go
func (s *Store) Ask(sc Scope, q NewQuestion) (int64, error)          // one transaction
func (s *Store) Answer(id int64, text string) AnswerResult
func (s *Store) PendingQuestion(sc Scope) (*Question, bool)
func (s *Store) IsAwaiting(sc Scope) bool
func (s *Store) Thread(sc Scope, after int64) ([]ChatMessage, error)
func (s *Store) Note(sc Scope, m NewChatMessage) (int64, error)
```

**2. `Ask` in one transaction** — insert the `question`, then the `chat_message` of kind `question` with
`question_id` set.

**3. `Answer`** sets `answer` and `answered_at` and appends a `chat_message` of kind `answer`, also in one
transaction. **Refuse** when `answered_at` is already set, with a reason **naming the existing timestamp** (DB19
— a result, not an error).

**4. `PendingQuestion`** returns the single **oldest** unanswered question. Oldest, not newest: questions are
answered in the order asked, and a newest-first reader strands the first one indefinitely.

**5. `IsAwaiting`** is that existence query (DB6). **There is no column and no cached flag.**

**6. The store assigns `chat_message.seq`** (O3), monotonically per scope. Two goroutines append here — a runner
and the server — so state what happens under contention: the `UNIQUE` constraint catches it and the write
retries with a recomputed `seq`, bounded.

**7. Test `IsAwaiting` across every state**: no questions; one unanswered; one answered; several with exactly
one unanswered; several all answered. A two-case test passes against an implementation returning `count > 0`.
