# T11 — The CLI: `db`, `step`, `loop`

> ## Notes — done 2026-10-15
>
> ### Two ways to reach the store, and both are deliberate
>
> `loop`, `step` and `db query` go through the DAEMON — the same handshake a third party would perform.
> `db info` and `debug hammer` open the store DIRECTLY:
>
>   - **"where is the file" must be answerable with the daemon DOWN.** It is the first question anybody asks
>     when the daemon will not start, and routing it through the daemon makes the answer unavailable exactly
>     when it is needed. `TestDBInfoWorksWithTheDaemonDown` pins it.
>   - **`hammer` is the concurrency step**, and its point is a SECOND PROCESS writing while the daemon serves
>     reads. Through the daemon it would be the daemon writing to itself, which proves nothing about
>     `busy_timeout` or the write lock.
>
> ### `db upgrade` has no apply path, by design
>
> Migrations run on EVERY OPEN (DB8), so an apply command would be a second way to do what starting the
> daemon already does — and the second way is the one that gets run against the wrong file. `--dry-run`
> reports the state and says that opening applied them, because printing "none pending" without that would
> be true and misleading.
>
> ### Deviation: step ids are integers, and the demo said otherwise
>
> The demo wrote `aeon step show 4f2a1c`. Real ids are `AUTOINCREMENT` integers — which is also what makes
> them never reused, which is what makes `step verify 4` unambiguous. The demo was wrong and is corrected.
>
> ### `--save-step` cannot save a signature, and says so
>
> S3's streaming surface carries no thinking signature (`Delta` has `Kind` and `Text`), so a transcript saved
> this way holds an UNSIGNED thinking block. `ask` prints that next to the step id, `step verify` says "no
> thinking signature in this transcript" rather than printing nothing, and the demo's "1 thinking block
> (signed)" is corrected. The store's own tests write and read a signed block byte-identically; it is the
> bridge that cannot supply one.
>
> ### The failed call still saved its step
>
> Found while walking: a call against a provider that was not listening produced
> `step 1 · cost unknown (stream-aborted-early)`. That is M15 working — a failed ask that records nothing
> loses the spend, and those tokens were still bought. The step list then shows two cost states side by
> side, which is the clearest demonstration of DB11 in the whole slice.
>
> ### `splitPositional`
>
> Go's `flag` package stops at the first positional argument, and these verbs read better with the subject
> first (`step show 4`, `loop write SLUG NAME`). Up to n leading non-flag arguments are taken before the
> FlagSet sees the rest — which also means a refused document NAME is reported with its reason rather than
> as a flag parse error.

## Context

The commands that make the store visible, and every one of them exists for a step in the demo.

**`aeon db info` prints the path first**, because every later slice's debugging starts by finding the file. And
`--vectors` reports the statically linked version — the human-visible proof of DB18, and the thing that tells a
reader there is no extension to install.

**`aeon step verify` is the human-visible form of T6's fidelity test.** It reads a transcript and reports
whether it round-trips, with the `thinking` signature's length. Someone diagnosing a rejected replay at S7 runs
this first.

**`aeon db query awaiting` prints the query, not just the answer.** Anyone arriving from v1 will look for an
`awaiting_user` column and not find one; showing the derived query is how they learn why (DB6).

**`aeon loop list` is scoped by default** and takes `--all`. A daemon multiplexes every project on the machine,
so an unscoped default would show a person every repository's loops whenever they were in one — and they would
learn to ignore the list.

**Read first:** `store.go` (T10); `cmd/aeon/ask.go` from S3, which gains `--save-step`; S2's three-part error
rendering.

## What to do

**1. `db.go`** — `db info` (path, WAL state, size, applied migrations, tables), `db info --vectors`
(`vec_version()` and "statically linked"), `db query awaiting` (the SQL and its result), `db upgrade --dry-run`
(pending migrations).

**2. `step.go`** — `step show <id> [--json]` printing the canonical transcript; `step verify <id>` reporting
byte-identity and the signature length.

**3. `loop.go`** — `loop create --slug`, `loop list [--all]`, `loop write <slug> <name> --content`. The write
path surfaces T9's refusals **with their reasons**, so the demo's five refusals are legible.

**4. `ask.go`** gains `--save-step`, persisting what `ask` produced and printing the step id. That is the bridge
between S3 and this slice, and the reason the demo can restart the daemon and still find something.

**5. `debug hammer --writes N`** — sustained writes, for the demo's concurrency step. Not a benchmark; a load
generator a human can run in one terminal while reading in another.

**6. Errors render in three parts** (S2's shape), so a refused document path says what to do.

**7. Tests against a real in-process daemon on a temp store**, not a mock. A CLI tested against a mock of its
own store tests nothing about the store.
