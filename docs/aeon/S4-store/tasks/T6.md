# T6 — `step_message`: transcript fidelity

> ## Notes — done 2026-10-15
>
> ### The fidelity test asserts the bytes ON DISK, not a round trip
>
> `TestASignedThinkingBlockSurvivesWriteAndReadByteIdentically` checks the exact strings through
> `ReadTranscript` **and** reads the raw `content` column and parses it, because a comparison of two parsed
> structures passes through the same encoder twice and proves nothing about the column. The fixture
> signature ends in a newline on purpose: a trailing byte trimmed by a column or an encoder is the failure
> that would surface at S7 as a provider 400 about something else.
>
> `marshalBlocks` is the ONE encoder, used by `AppendMessages`, `ReplaceRange` and `VerifyTranscript` — so
> `verify` is not comparing its own output against the writer's.
>
> ### Validation happens twice, and the first attempt was wrong
>
> I wrote `AppendMessages` to run `model.ValidateTranscript` over each appended message. **The cascade test
> immediately refused a legitimate four-message transcript**: "the transcript begins with an assistant
> message", because message 2 was being validated on its own. S3's validator judges a WHOLE transcript, and
> an append is a fragment.
>
> So: each BLOCK is checked before the transaction (naming the block's index), and the resulting WHOLE
> transcript is validated INSIDE the transaction, rolling back if invalid. That is the stronger guarantee —
> an invalid transcript cannot be stored at all — and it is affordable because every intermediate state of
> a real step is a legitimate transcript, including a suspended one ending in an unanswered `tool_use`.
>
> ### A wrong assumption of mine, corrected by S3
>
> I asserted that a thinking block with no signature would be refused. It is not: S3 permits one
> deliberately, "because not every provider signs". The store does not get to be stricter than the model
> layer about what a provider may send. The test now uses a `tool_use` with no id, and the comment records
> why the obvious choice was wrong.
>
> ### An off-by-one in `ReplaceRange`, found by its own test
>
> Replacing two messages with one left `seq` as `[1 2 4 5]`, and in the neighbouring case collided with the
> row just inserted — surfacing as a UNIQUE violation during the tail restore, which reads as a constraint
> problem rather than as arithmetic. The shift is now derived rather than guessed: the first parked row held
> `toSeq + 1` and must hold `fromSeq + len(msgs)`.
>
> The tail is parked at a high offset before being brought down, because SQLite applies UPDATE row by row
> and a direct downward shift collides with rows it has not moved yet — correct behaviour from the
> constraint, and a bug here.
>
> ### `ContainsProviderShape` was built and then deleted
>
> I put the provider-shape scan on the store as a method. **S3's own boundary guard failed it** (D14: no
> provider field name outside `internal/model/adapters/`), because the needles `"choices"`, `"tool_calls"`
> and `"content_block"` are literals.
>
> The right fix was to move the needles into the test, not to add a file exemption — S3's comment records
> that "a check that grows a filename list gets weakened until it matches nothing". Its guard excludes
> `_test.go` files deliberately, for exactly this: a test that LOOKS FOR a provider shape is the opposite
> of a leak. The scan is now `scanForProviderShapes` in `transcript_test.go`, with a planted shape as the
> negative control.
>
> ### `ReadTranscript` returns a result, not `(messages, error)`
>
> A transcript can fail to be readable in three distinguishable ways — written by a NEWER Aeon, unparseable,
> or absent — and a recovery needs to tell them apart. S3's `MigrationResult` already draws those lines, so
> it is carried rather than flattened, and the row COUNT is reported even on a failure: "nine rows that
> will not parse" and "no rows" are different problems.
>
> The highest row version decides, so one row from the future refuses the whole transcript. Parsing the
> rest would hand a recovery a transcript with a hole in it.

## Context

One of the two tables v1 never had, and the one the spine rests on. A suspended step exits its process and
resumes cold (P2); a crashed one recovers the same way (§3a). Both read these rows and nothing else.

**This task's worst failure happens three slices away.** A signed `thinking` block that survives storage
*almost* intact — a trimmed trailing newline, a JSON round-trip that reorders keys, a text column that
normalises something — produces a replay Anthropic rejects, and the error surfaces in **S7** as a provider 400
about signatures with nothing pointing at the store. So the test asserts **exact strings**, and it is worth
being deliberate about the encoding rather than trusting a marshal/unmarshal cycle to be lossless.

**One message per row, not a blob.** A transcript grows by append, resume reads it whole, and compaction
rewrites a middle range. A blob makes every append a read-modify-write of the whole transcript, and
`UNIQUE (step_id, seq)` is what makes a concurrent append **detectably** wrong rather than silently lossy.

**No provider shape reaches this table.** Content is canonical `[]Block` JSON. A `choices` or `tool_calls` key
appearing here means something in S3 leaked, and a test looking for them turns that into a visible failure here
rather than a mystery later.

**Read first:** `../ARCHITECTURE.md` §3 for what suspension persists; `internal/model/format.go` (S3) for
`ValidateTranscript` and `MigrateTranscript`; `docs/_archive/aeon-v1-horizontal/02-store/tasks/T6.md`, which this ports.

## What to do

**1. Add to `steps.go`:**

```go
func (s *Store) AppendMessages(stepID int64, msgs []model.Message) error
func (s *Store) ReadTranscript(stepID int64) TranscriptResult
func (s *Store) ReplaceRange(stepID int64, fromSeq, toSeq int64, msgs []model.Message) error
```

`ReplaceRange` exists for compaction. It is here because it is the operation most likely to break the `seq`
invariant, and because compaction must never orphan a `tool_use` from its `tool_result` — a constraint the
caller enforces but that this function must not make impossible by renumbering unpredictably.

**2. `AppendMessages` assigns `seq`** itself, monotonically from the current maximum for that step (O3 — the
store assigns, never the caller). It writes `format_version` from S3's `FormatVersion`. **All rows for one call
go in one transaction**: a half-written transcript is unresumable.

**3. `ReadTranscript`** returns messages in `seq` order through `MigrateTranscript`, refusing a future
`format_version` **loudly** (O4). A newer Aeon wrote it, and a best-effort parse would silently drop blocks it
does not understand — plausibly including a signature.

**4. Store content as canonical JSON**, marshalling the `[]Block` for each message.

**5. Write the tests, in this order of importance:**

- **the signed `thinking` round trip**, asserting the `thinking` text and `signature` as **exact strings**, with
  a comment naming why (P21) and which slice the failure would otherwise surface in
- a transcript with all four block kinds round-trips and `ValidateTranscript` accepts it
- two inserts at the same `(step_id, seq)` — the second fails on the constraint
- `ReadTranscript` returns `seq` order even when rows were inserted out of order
- a row whose `format_version` exceeds current is refused loudly
- deleting a step cascades to its rows, asserted by **row count**
- no stored content contains `choices`, `tool_calls` or `content_block`
