# T5 — Phases — what a lane records

## Why this exists

S8's blueprints have **lanes**. S4's store has **`loop_phase`** rows with `TRACKED_PHASES` and `PHASE_STATUS`. Two names
for what looks like one thing.

If they were the same thing, one of them is redundant and would become a second source of truth about progress. **They are
not the same thing**: a lane is the declaration; a phase row is its state (L27).

## Scope

### A phase is what a lane records (L27)

**Answer Q2 first**: what exactly is in `TRACKED_PHASES`, and does an iterating lane appear in it?

The distinction that matters: **an iterating lane records per-item task state, not a single phase status.**

A single `build` phase status cannot say which of five tasks is in review. So the iterating lane's progress is the tasks'
statuses — S4's fourteen states, already there — and a `build: in-progress` row alongside them would be a third
description of the same thing, drifting from both.

### The three statuses that are not the same

S8's `loop show` already renders these distinctly (its O8); this is where they are **recorded**:

| Status | Means |
| --- | --- |
| `pending` | still to come |
| `not-needed` | its `when` was false |
| `skipped` | a mode-driven skip |

`PHASE_STATUS` already made the `not-needed`/`skipped` distinction, and S8's decide already produces the right `SkipAs`.
This task persists it, and the reason to keep them apart is unchanged: **a bypassed lane rendered as `pending` reads as
"still to come" for something that will never happen.**

### Bracketing

v1's protocol brackets each phase: `in-progress` before dispatch, then `done`/`skipped`/`failed` after. **That is now the
engine's job** — it was ritual in every one of the 26 agent bodies (S13 deleted it), so the engine must actually do it or
the behaviour was lost rather than moved.
