# T3 — Redo routing that carries its reason

## Why this exists

S8 built the routing: a `reject` goes to the enclosing ladder's `rework` target, bounded by `on_reject`. T2 supplied the
counters.

**What is missing is the information.** Re-running `implement` with no context is **the same call that just failed**, and
it spends a round reproducing the same output (L32). S8's `with:` is the mechanism; the rejection's reason is what belongs
in it.

## Scope

### The reason travels (L32, D7)

When a step rejects, the re-entered step's **input** carries:

- the rejecting step's id and the reason it gave
- **which attempt this is** — "retry 2 of 2" (O3, D7)

The attempt number matters because a handler on its last attempt should behave differently from one on its first — narrow
the change, ask a question, report what it could not do — and **it cannot know unless told.**

**Answer Q5**: how does a handler receive a step's input, and is there a place for these? If not, that place is this
task's.

### Routing keys on outcome **and** reason (Q6)

**Answer Q6 before implementing**: can a blueprint route differently by reason, or only by outcome?

**If routing cannot see the reason, T6's two redos are indistinguishable — and that is a finding to record**, not to work
around. `fail` and `unverified` both route as `reject`, and they call for different work: fix the finding, versus make the
check run.

The minimum this task needs is that the **reason reaches the handler's input**, even if the blueprint's routing keys only
on the outcome. Routing decides *where*; the reason decides *what to do there*.

### Not in scope

Exhaustion (T4). This task routes a reject that is inside its cap.

## Tests

| Test | Asserts |
| --- | --- |
| `TestRedoCarriesTheReason` | A **handler spy reads its own input** and finds the rejecting step's reason. Asserted from inside the handler, not on the routing call (D7, C5) |
| `TestRedoCarriesTheAttemptNumber` | "2 of 2" reaches the input, and differs on the first attempt (O3) |
| `TestRejectRoutesToRework` | To the lane's `rework` target, not to the top of the lane (D1) |
| `TestRoundIsConsumed` | The counter moves by exactly one per reject |
| `TestBareRetryIsNotPossible` | A redo with no reason in its input **fails a test**, so the omission cannot ship silently |
| `TestLaneLevelRejectUsesItsOwnGoto` | Outside a ladder there is no `rework`, so the step's `on_reject.goto` is used — S8's validation already required it |
| `TestQ6Recorded` | A test recording whether routing can see a reason, so T6 knows what it can rely on |

`TestBareRetryIsNotPossible` inverts the usual shape — it asserts that a **missing** thing fails. Without it, a redo that
forgets the reason still works, just worse, and nothing notices until someone reads a transcript and sees two identical
attempts.

## Definition of done

- [ ] The rejecting step's reason reaches the re-entered step's input
- [ ] The attempt number reaches it, and differs across attempts
- [ ] Q5 answered; Q6 answered and recorded
- [ ] A reject routes to `rework`, or to the step's own `goto` at lane level
- [ ] Exactly one round consumed per reject
- [ ] A redo missing its reason fails a test
- [ ] `make test`, `make lint` green
