# T4 — Exhaustion — `escalate`, `fail-item`, `block`

## Why this exists

S8's validation made `then:` **required** on any capped edge, because its absence *"is an infinite loop waiting to
happen"*. This task implements the three values it can take.

## Scope

### The three

| `then:` | Does |
| --- | --- |
| `escalate` | Raises to a human. The loop waits |
| `fail-item` | Fails this item and **continues to the next** — an iterating lane's other tasks are unaffected |
| `block` | Stops the loop |

`fail-item` is the one worth naming: in an iterating lane, one task that cannot converge should not stop the other four.
And a failed item's **dependents are `blocked`, not `failed`** (O5) — they never ran, and marking them failed would report
work as attempted that was not.

### `escalate` collapses to `block` unattended (L29, D4)

Escalating to a human nobody can reach is **a loop that stops without saying why.** Same collapse as G7's `ask` → deny,
for the same reason, and consistent so nobody has to remember two rules.

### The block's reason must distinguish two facts (O1, D4)

Both of these are true at once, and they call for **different responses**:

| Fact | Response |
| --- | --- |
| The cap was reached | Raise the cap, or accept the task cannot converge |
| Nobody could be asked | Run it attended |

A single message conflating them sends someone to change the wrong thing. So:

```
T2 retries 2/2 exhausted at 'verify'
   then: escalate — collapsed to block (loop is unattended)
```

Both clauses, always, when both apply.

### The loop ceiling also blocks (T2, D3)

Reaching `total_failed_gates` is a `block` rather than an escalation: **the loop as a whole is not converging**, which is
a different problem from one task struggling, and a human answering a question would not fix it.

## Tests

| Test | Asserts |
| --- | --- |
| `TestEscalateCollapsesToBlockUnattended` | The collapse happens, and the reason says so (L29, D4) |
| `TestBlockDistinguishesCapFromNobodyToAsk` | **Both clauses present** when both apply; and only the relevant one when only one does (O1) |
| `TestFailItemContinuesToTheNext` | An iterating lane's remaining items run |
| `TestSiblingsKeepTheirBudgets` | After a `fail-item`, the next task's counters are **untouched** — T2's split, observed through exhaustion |
| `TestDependentsOfAFailedItemAreBlocked` | `blocked`, **not `failed`** — they never ran (O5, C9) |
| `TestBlockStopsTheLoop` | No further advance |
| `TestEscalateAttendedWaits` | A question is created and the loop is `waiting` |
| `TestLoopCeilingBlocks` | Not an escalation (D3) |
| `TestAllThreeThenValuesAreReachable` | Each by a named test — S8 required `then:`, so all three must work |

`TestDependentsOfAFailedItemAreBlocked` is the one that would be missed. The obvious implementation marks everything
downstream `failed`, and a report saying five tasks failed when one did is a report nobody can act on.
