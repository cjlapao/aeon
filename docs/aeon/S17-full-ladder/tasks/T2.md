# T2 — Two-level counters and their caps

## Why this exists

**This is the one piece of arithmetic in the slice, and it is isolated (R5) because a per-loop-only implementation passes
every other test here.**

The question it answers bites: *is `review_rounds` per-task or per-loop?*

- **Per-loop only** → task three inherits tasks one and two's exhausted budget and **cannot be reviewed at all**. It
  presents as a loop escalating for no visible reason on a task nobody reviewed once.
- **Per-task only** → a twenty-task loop can spend forty review rounds and call it progress.

**v1 already answered: both, at different levels.** So this is inherited rather than invented (L28).

## Scope

| Level | Counters | Cap |
| --- | --- | --- |
| **Task** | `retries`, `security_rounds`, `review_rounds` | **2** each, per task, and `capExceeded` ⇒ escalate |
| **Loop** | `total_failed_gates`, `splits_done`, `qa_rounds` | loop-wide |

### The level is a property of the counter (I2)

Not of the call site. A counter whose level depends on who increments it **will be incremented at both**, and the bug
appears as a budget that drains twice as fast on some tasks and not others.

```go
type Counter struct {
    Name  string
    Level Level   // LevelTask | LevelLoop
    Cap   int     // 0 = no cap; the loop-level ceiling is separate
}
```

Look-up is by name, and the level comes with it. There is no `IncrementTask` / `IncrementLoop` pair for a caller to pick
between.

### The loop ceiling (D3)

`total_failed_gates` is the ceiling that stops a loop **whose tasks are each individually inside their caps.** Twenty
tasks each rejecting once is twenty rejections, none of them capped, and without a loop-level ceiling that is a loop that
runs all day producing send-backs.

**Answer Q11**: its value, and what happens at it. Reaching it is a `block`, not an escalation — the loop as a whole is
not converging, and that is a different problem from one task struggling.

### Store (Q1)

**Answer Q1 first**: do the counters have columns, or is a migration needed? If one is, it follows S4's discipline
exactly — numbered, one transaction, ledger-recorded, and the fresh-equals-migrated equivalence test must still hold.

### Not in scope

What happens **at** a cap is T4. This task counts and reports `capExceeded`; T4 decides between `escalate`, `fail-item`
and `block`.

## Tests

| Test | Asserts |
| --- | --- |
| `TestTaskThreeKeepsItsOwnBudget` | **Five tasks.** Tasks 1 and 2 each consume two `review_rounds`; task 3 still has **2 of 2**. **This test fails against a per-loop-only implementation and passes every other test in this slice** (D2, C2) |
| `TestLoopCeilingStopsTheLoop` | Twenty tasks, each rejecting once, none capped individually: the **loop** stops at `total_failed_gates` (D3) |
| `TestCounterLevelIsAPropertyOfTheCounter` | No API lets a caller choose a level; the level comes from the name (I2) |
| `TestTaskCountersAreIndependent` | Incrementing task 1's counter does not move task 2's, for all three task-level counters |
| `TestCapExceededIsReported` | At 2 of 2, `capExceeded` is true, and the counter does not go to 3 |
| `TestCountersSurviveSuspendAndRecovery` | S6's suspension and S7's recovery preserve counts — a step that regains its budget by crashing can loop forever |
| `TestSchemaFreshEqualsMigrated` | If Q1 needed a migration, S4's equivalence test still holds |
| `TestLoopCeilingIsABlockNotAnEscalation` | Reaching it blocks; the loop is not converging, which differs from one task struggling |

`TestCountersSurviveSuspendAndRecovery` is worth having explicitly. S5 stored the step deadline absolutely for the same
reason, and a counter that resets on recovery reintroduces exactly the unbounded loop the cap exists to prevent.
