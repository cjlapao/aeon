# T7 — The ladder's authorship — every lane running

## Why this exists

**Separate from the machinery** (R7), because authorship and arithmetic are different kinds of work and mixing them means
reviewing prose and counter logic in one diff.

S8 shipped `dev-loop.yaml` as **data that validates**. Its nine `unverifiable` diagnostics were code actions, and S16
retired those. Every lane can now run; this task makes them.

## Scope

### The ladder

```
clarify → discovery → legal? → plan → [PLAN GATE] → build (iterate: tasks) → qa? → done
                                                          │
                        issue → implement → verify → security? → push → pr → review → merge
```

**One approval gate** is the designed shape, and the protocol's own summary says so: *"investigates → plans → (one
approval gate) → builds task-by-task → verifies each task → commits, running unattended."*

Escalations open other questions, but they are **exceptions rather than steps**. A ladder with four routine gates is not
running unattended; it is a wizard.

### What each lane needs to be correct

| Lane | Must |
| --- | --- |
| `clarify`, `discovery`, `plan` | `produces:` their artefacts. S8 enforces it, so a step reporting `ok` without writing one becomes a `reject` |
| `legal`, `security`, `qa` | Be conditional on their flags; a false `when` records `not-needed` **with its condition** (T5) |
| `plan-gate` | A closed answer set — `[approve, revise, abort]`. `abort` is a **first-class outcome**, not a failure |
| `build` | `iterate: tasks`, with `rework: implement` and per-step `on_reject` counters |
| `verify` | Route all three of T6's outcomes |
| `review` | Gate on review **state** (T8) |
| `merge` | Be `irreversible`, so it asks (S16's L22) |

### `sets:` in every mode (Q7)

**Answer Q7**: is every `sets:` legal in every mode, POC included? S8's T5 validated this when the lanes were data; confirm
it still holds now that every lane runs and drives real transitions.

A `sets:` legal in the default table and illegal under the POC overlay fails at a task's third step, in a mode nobody
tested.

### `abort` is not a failure

A human answering `abort` at the plan gate has made a decision, and the loop's terminal status should say **aborted**, not
`failed`. v1's `loop_finish` took `done` or `aborted` for exactly this reason: a plan someone read and declined is a
working system, and recording it as a failure makes the metrics lie about the method.

### Not in scope

**No new lane, no new mechanism** (N1, D15). If a lane appears to need something S8–S16 did not build, **record it as a
finding and stop** — that is information about those slices, not work for this one.
