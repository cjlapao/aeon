# T6 — `verify`'s three outcomes

## Why this exists

**One task** (R6), because `unverified` touches the handler, the handoff, the routing and the record — spread across
tasks, the "never stored as `pass`" assertion has no home.

The protocol names the case exactly, and it is worth quoting because the wording is the specification:

> *Exit code **137** (or `signal: killed`, `Killed`, `out of memory`, `cannot allocate memory`, or a report that simply
> stops mid-package) is the **OOM killer**, NOT a lint finding. Never "fix" code in response to it. … lint is
> **unverified**, which is not the same as clean. **Do not report `verification=pass` on an unverified gate.***

## Scope

### Three outcomes (L33, D8)

| Outcome | Means | Routes as |
| --- | --- | --- |
| `pass` | the check ran and found nothing | `ok` |
| `fail` | the check ran and found something | `reject` |
| **`unverified`** | **the check did not run** | **`reject`, with a distinct reason** |

`unverified` is **not a fifth handoff outcome.** S13's T3 gave handlers four (L4's universal set) and this routes as
`reject` — the work cannot proceed on an unknown. What differs is the **reason**.

This is [P31](../../ARCHITECTURE.md#8-product-decisions)'s **fifth** instance, after cost, the `bash` receipt, blueprint
validation and connection liveness. Five separate designs refused to collapse an uncertain answer, and this is the one
where the collapse looks like a green check.

### The two redos differ (L33, D9)

| After | The redo should |
| --- | --- |
| `fail` | **fix the finding** |
| `unverified` | **make the check run** — raise memory, narrow scope, install the tool |

Those are different work, and collapsing them wastes a round. T3 carries the reason into the redo's input; this task
supplies two different reasons.

**If T3's Q6 found routing cannot see a reason**, the reason still reaches the handler's input — routing decides *where*,
the reason decides *what to do there*.

### `unverified` does not charge `retries` (O4)

**A tool that will not run is not the handler's failure.** Charging its retries exhausts the budget on an environment
problem before any real attempt is made.

**Answer Q8**: which counter it charges, if any. State it — and if the answer is "none", the loop ceiling
(`total_failed_gates`) is still what bounds it, so it cannot loop forever.

### The handler amendment

`verifier-engineer`'s body already carries the OOM **consequence** — S13's T4 kept *"…not a lint finding"* as domain
while deleting *"exit 137 means OOM"* as mechanism, and QAC-05 named its absence the worst of five possible losses.

This task adds the **outcome**: the handler must be able to *report* `unverified`, which its handoff schema did not allow.
Update the body, its handoff declaration, and its drop record.

### Not in scope

No change to `bash`. W5 already reports `oomKilled` as a fact; this task consumes it rather than re-deriving it.
