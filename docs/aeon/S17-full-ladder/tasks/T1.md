# T1 — The plan loader — `depends_on` validation and a stable topological sort

## Why this exists

**First, because everything downstream iterates over its output** (R4), and adding a sort later means retrofitting S8's
walk.

S8's `iterate` is a **monotonic forward walk** — `(lane, item, step)`, item-major. That was the right shape and it costs
nothing until items have an order they must respect. Tasks have `depends_on`, so either the walk skips blocked items and
revisits them — making the position non-monotonic, which the shape was chosen to avoid — or **the order is settled before
the walk begins** (L31).

## Scope

### Validation, at load

v1's `tasks_derive` refuses four things, and its reason is the one to keep: all four *"produce a task that can never
complete, and catching them here names the plan instead of surfacing a mystery at merge time."*

| Refused | Why |
| --- | --- |
| A `depends_on` naming a task that **does not exist** | Nothing will ever satisfy it |
| A **self-dependency** | Likewise, and it looks like a typo rather than a cycle |
| The **same taskid twice** | Two tasks, one identity; every status write is ambiguous |
| A **cycle** | No ordering exists |

Each refusal **names the offending task**, and the cycle refusal **names the cycle** — a message saying "there is a
cycle" leaves someone reading a twenty-task plan by hand.

### The sort must be stable (O2, I4)

Two tasks with no dependency between them **keep their plan order.**

An unstable sort makes a loop non-reproducible across runs from the same plan — and that breaks L6's whole reason for
pinning the blueprint. A pinned blueprint plus an unstable task order is still non-deterministic, which is the thing the
pin exists to prevent.

So: a deterministic algorithm over the plan's declared order, not a map-iteration-order traversal.

### Not in scope

**No change to `iterate`** (Q4). The sort goes **in front of** it, not inside it. `iterate` continues to walk a list in
order; this task decides what that list's order is.

That separation is what keeps S8's position monotonic without S8's code changing.

## Tests

| Test | Asserts |
| --- | --- |
| `TestFourBadDependencyClassesRefused` | All four — nonexistent, self, duplicate, cycle — refused at **load**, each naming the offending task (D5, C3) |
| `TestCycleIsNamed` | The refusal names the cycle's members, not just its existence |
| `TestSortIsStable` | Two independent tasks keep plan order. Run **repeatedly** — an unstable sort passes a single run (O2, E3) |
| `TestSortRespectsDependencies` | A dependent task follows the one it needs, in every arrangement of the input |
| `TestSortIsDeterministicAcrossRuns` | The same plan sorts identically a hundred times; no map iteration in the path |
| `TestIterateIsUnchanged` | S8's `advance.go` is not modified; the sort is upstream of it (Q4) |
| `TestValidationIsADomainRefusal` | Not an error — a bad plan is a domain outcome the loop reports, not an infrastructure failure (S4's DB19) |
| `TestEmptyPlanIsValid` | Zero tasks sorts to zero and does not fail. S8's `iterate` over nothing is already a legitimate no-op |

`TestSortIsStable` **run repeatedly** is the assertion that matters. Go's map iteration is randomised per run, so a sort
built on a map passes once and fails on the fourth CI run — which is the worst way to discover it.

## Definition of done

- [ ] Four bad-`depends_on` classes refused at load, each naming its task
- [ ] The cycle refusal names the cycle's members
- [ ] The sort is stable and deterministic, asserted across repeated runs
- [ ] `iterate` is unchanged; the sort is upstream
- [ ] A bad plan is a domain refusal, not an error
- [ ] An empty plan is valid
- [ ] `make test`, `make lint` green
