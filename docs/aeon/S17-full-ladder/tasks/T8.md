# T8 — The review-state merge gate and the deferred-findings backlog

## Why this exists

The last step of the lane, and the one before something irreversible.

The protocol's reasoning is server-agnosticism and it is worth quoting: *"Not every server can resolve conversation
threads (the granular reference server has **no** `resolve_thread` / pending-review workflow). So the loop gates on the
**review STATE**, which every server supports."*

**Gating on something a forge may not implement makes the gate unreachable there** — and a gate nobody can pass is a gate
people route around.

## Scope

### The merge gate (L34, D10)

Two conditions, both from something every forge reports:

1. **CI/checks green** via the status tool. **No checks configured = N/A**, not a failure — a repository without CI is a
   repository without CI, and treating that as a red gate blocks every such project.
2. **The latest review state is `APPROVED`** with no outstanding `REQUEST_CHANGES`.

If the forge **also** reports unresolved threads, honour that too. But **a missing thread API is not a blocker.**

### It records which state, and when (O6, D10)

The gate writes into the step's evidence: the review state it read, the reviewer, the timestamp, and the check results.

**A gate that passed on a state nobody can reconstruct is a gate nobody can audit** — and this is the last one before an
`irreversible` action. Six months later, "why was this merged" has to have an answer that is not "the loop said so".

### The deferred-findings backlog (O7, I6)

Non-blocking findings go to a **durable, append-only** file. Each entry names its PR, its date, and the finding.

**Appended, never rewritten.** A backlog that gets regenerated loses the history that makes it a backlog — and the whole
reason it exists is that a finding worth recording and not worth blocking on needs somewhere to live. Without it, every
finding becomes a blocker by default, and the review lane becomes the thing people route around.

`aeon/docs/BACKLOG.md` documents the entry shape. **Answer Q10**: where the file lives and what an entry looks like.

### Not in scope

No thread resolution, even where a forge supports it. Honouring reported threads is in scope; **resolving** them is not —
that is a write into someone else's conversation, and nothing in the method needs it.

## Tests

| Test | Asserts |
| --- | --- |
| `TestThreadlessForgeStillReachesTheGate` | A fake reporting no thread API passes the gate on state alone (L34, D10) |
| `TestGateRecordsWhichStateAndWhen` | The evidence carries state, reviewer, timestamp and check results (O6, C8) |

| `TestReportedThreadsAreHonoured` | Where a forge reports them, unresolved threads block; where it does not, they are not consulted |

| `TestBacklogEntryNamesPRAndDate` | Both present per entry |
| `TestGatePrecedesTheIrreversibleAction` | Asserted on ordering: `forge.merge` is unreachable until the gate passes |
| `TestThreadsAreNeverResolved` | No code path writes a thread resolution |

`TestGatePrecedesTheIrreversibleAction` asserted on **ordering** rather than on a boolean is the same shape as S11's
`AllowToken`: a check that happens to run before an action is a convention, and a check the action cannot be reached
without is a property.
