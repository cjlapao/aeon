# T8 · The "Daemon settings" panel on the real Settings screen

**Prefix:** CS · **Rules:** CS4, CS8 (sensitive confirmation), CS10, CS12, CS13 · P34 · **Depends on:** T5, T6
(needs T6's UI guard to exist so it can stop skipping). Parallel-safe with T7.

## Goal

A generic, **descriptor-driven** panel on `SettingsScreen.tsx` that lists every declared daemon setting from
`settings.list`, edits it through `settings.set`, resets it through `settings.unset`, and shows — never hides —
which layer is in force. It is the first thing in the app that writes a daemon-side setting from the Settings
route. **This is the real app's Settings, not a bench tab**: the bench-page registry
(`ui/src/features/test-bench/lib/benchRegistry.ts`) does not apply, and there is no per-key UI code — a new
declared key (T10's, later) appears here with **zero UI change**, which is the whole point of putting the
descriptor on the wire (CS10).

## Behaviour — the panel

1. **Load** `settings.list` with `useRpcQuery('settings.list', {}, controller, live)`. Loading shows the kit's
   existing loading idiom (read `ProjectsScreen`); an error shows `ErrorPanel` (`components/ErrorPanel.tsx`) with
   the daemon's message — never a blank panel.
2. **Empty registry** (`settings: []`) renders an `EmptyState`: "No daemon settings are declared yet." with a
   one-line body "Settings appear here when a feature declares one." (CS13 — the honest state, and the state the
   app is in at the end of this slice).
3. **Group by `area`** (alphabetical areas, keys alphabetical within — the daemon already sorts; the pure helper
   preserves the order, it does not re-sort).
4. **Control by `type`** (`controlKindFor`):
   - `bool` → a two-state switch (`true`/`false`);
   - `enum` → a select/`MultiToggle` over `enumValues`;
   - `int` → a numeric input honouring `min`/`max` (inline validation text from the same bounds; the daemon
     remains the authority — the UI never claims a value is valid, only that it looks malformed before sending);
   - `string` → a text input with `maxLength = maxLen ?? 4096`.
   The draft is **text** (canonical form). `parseDraft` converts nothing — it sends the text the control produced
   (`"true"`/`"false"`, the integer's base-10 digits, the member, the raw string). A numeric input that yields
   `"007"` or `"1e3"` is shown as malformed and **not sent** (canonical form is the contract, CS3).
5. **Row anatomy**: label (`key`), `description`, the current effective value in its control, a source badge
   (`Default` / `Saved` / `Environment`, using `Pill`), the default value ("Default: …"), "Last changed by
   `<updatedBy>` `<RelativeTime>`" when `updatedAt` is non-null (`components/RelativeTime.tsx`), and a
   **Reset to default** button, disabled when `source` is `default` **and** `stored` is null, and while `busy`.
6. **Environment lock** (`isLocked`): when `source === "environment"` the control is **read-only** and the row
   shows "Set by `<shadowedBy or the env var>` — unset that variable to change it here." If a row is stored
   (`stored !== null`) it also shows "Saved value `<stored>` is overridden." The panel never lets a person
   believe a write changed something it did not (CS4). *(A write is still possible through the CLI/socket and is
   stored; the UI simply does not offer a control that has no effect.)*
7. **Warnings** are rendered, not hidden: `envInvalid` → an `Alert` "`<var>` is set but is not valid for this
   setting and was ignored."; `storedInvalid` → an `Alert` "The saved value `<stored>` is no longer valid; the
   default is in force. Reset or save a new value."
8. **Write flow.** On change (switch toggled / enter or blur on text-number input / enum chosen): if
   `view.sensitive`, call `useConfirm` first with the setting's **description**, the current value and the new
   value, and a confirm button labelled with the action — **declining sends nothing and restores the control**.
   Otherwise (or after confirm) call `settings.set` through `useRpcAction().run(...)` with success toast
   "`<key>` saved" (or "unchanged" when `changed === false`) and the failure toast carrying the daemon's refusal
   message. On success, **replace that row's view with the response's `setting`** (the daemon's fresh view — do not
   optimistically assume the value) and leave other rows alone; on refusal, restore the control and show the
   daemon's three-part message inline under the control.
9. **Disabled when offline** (`canWrite` false: `live.state !== 'current'`): controls read-only with the kit's
   existing "reconnecting" affordance, reads still render the last data.
10. **Refetch** after reconnect is `useRpcQuery`'s own behaviour (`live.generation`). If T0/T4 ruled `setting.changed`
    **cheap**, subscribe and refetch the single affected key on that event (VERIFY the subscribe hook:
    `lib/useLiveSubscription.ts`); if **not**, add nothing and rely on the existing reconnect refetch — the
    multi-window staleness window is named in T9's findings, not papered over here.
11. **No `localStorage` for any daemon value** and no second copy of the descriptor: the panel's only source of
    truth is the last `settings.list`/`set`/`unset` response (T6 guard 3 greps for this).

| Test | Asserts | Fails when |
| --- | --- | --- |

| `groupByArea preserves daemon order` | input order kept within/between areas | UI re-sorts and disagrees with the CLI |

## Do NOT

- Do not hardcode any setting key, label or description in the UI — they come from the daemon.
- Do not store a daemon setting in `localStorage`/`sessionStorage`, and do not add a client-side cache beyond
  component state seeded from the last response.
- Do not add a bench page, a `routes.ts` entry, or touch `benchRegistry.ts`.
- Do not modify `appSettings.ts` or the three existing panels.
- Do not use `fetch`/HTTP — the panel speaks the socket through `bridge.ts`.
- Do not hand-edit `contract.ts`.
- Do not optimistically update a row before the daemon answers.
