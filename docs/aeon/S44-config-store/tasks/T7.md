# T7 · The CLI client: `aeon settings`

**Prefix:** CS · **Rules:** CS4, CS9, CS10 · P34 · **Depends on:** T5. Parallel-safe with T8.

## Goal

The CLI is the **secondary client** of the five socket methods (P34): `aeon settings list|get|set|unset|history`.
It follows `cmd/aeon/telemetry.go` and `graph.go` exactly — `dial(0)`, `c.Call(method, params, out)`, print what
the wire said — and implements **no** validation, precedence, registry or store access of its own. It exists so a
person on a headless box (or a script) has the same door the app has, never a different one. It is deliberately
**not** a way around T6's guards: the CLI reaches the socket, which is the human door.

## Verbs

```
aeon settings list    [--area NAME] [--json]     every declared setting: key, effective value, source, flags
aeon settings get     KEY [--json]               one setting in full: descriptor, effective value, stored value, source
aeon settings set     KEY VALUE [--yes] [--json] write; Sensitive keys need --yes (see below)
aeon settings unset   KEY [--yes] [--json]       return to the default (deletes the stored row)
aeon settings history [--key KEY] [--limit N] [--json]
aeon settings help
```

- **`VALUE` is the canonical text form** (`true`, `false`, `42`, a member, raw text). The CLI sends it verbatim as
  the `value` string. It does **no** coercion (`yes`→`true` would make the CLI a second spelling authority, CS3);
  an invalid value is the daemon's `ErrSettingInvalidValue`, printed as its three parts.
- **`--yes`** — the CLI's counterpart to the UI's confirmation (CS8). The CLI first calls `settings.get`; if the
  returned `sensitive` is true and `--yes` was not given, it prints what the key controls (the descriptor's
  `description`), the current value and the new value, says "re-run with --yes to apply", and **exits non-zero
  without calling `settings.set`**. A non-sensitive key never needs it. This is a client convenience over
  data the daemon already sent — the daemon does not trust it (the socket accepts the write regardless; CS9
  reasoning: the human door is the 0600 socket, not a CLI prompt).
- **`--json`** prints the raw result object (`{"setting": …}` / `{"settings": […]}` / `{"events": […]}`) exactly as
  received, one JSON document, so scripts depend on the wire shape and not on this printer.
- **Credentials as arguments:** `settings set` takes a **value** on the command line, which lands in `argv` and
  shell history. This is acceptable **only because C4/CS5 guarantee no declared key is a credential**. The usage
  text says so in one sentence. The CLI does **not** try to detect credential-shaped keys itself
  (`isCredentialName` is unexported and the CLI imports no `config`); a credential-named key can never be
  declared, so the daemon answers it with `ErrSettingUnknown` and the CLI prints that. The point of writing this
  down is that nobody "helpfully" adds a `--value-from-stdin` for secrets here.

## The printer — what it must never hide

| Wire fact | Terminal rendering |
| --- | --- |
| `source: "default"` | `value  3   (default)` |
| `source: "database"` | `value  4   (saved, by <updatedBy> at <updatedAt>)` |
| `source: "environment"` | `value  true   (environment — AEON_SETTING_… is set; a saved value, if any, is shadowed)` and, when `stored` is non-null, a second line `saved  false  (shadowed)` |
| `envInvalid` non-null | `warning: AEON_SETTING_… is set but not valid for this setting and was ignored` |
| `storedInvalid: true` | `warning: the saved value "<stored>" is no longer valid; the default is in force` |
| `sensitive: true` | a `[sensitive]` marker on `list`, and the descriptor's description printed on `get` |
| `changed: false` | `unchanged` (never `updated`) |
| an empty `settings` list | `no settings are declared yet` (the honest empty state, CS13) — exit 0 |

An unknown-key refusal prints the daemon's three parts verbatim, including the nearest-key suggestion. Exit codes
follow S23's six (`internal/exitcode`): usage/shape error, daemon-unreachable, and a refusal each keep the code
their neighbours use — **VERIFY by reading how `telemetry.go`'s errors map** and reuse those, never invent a code.

## Definition of done

- [ ] Five verbs + `help`, registered in `main.go`'s dispatch and usage.
- [ ] Pure socket client: no store, no config, no SQL imports; no validation of its own.
- [ ] `--yes` gate on sensitive keys, tested both ways.
- [ ] Every layer fact in the printer table is rendered; `--json` is verbatim.
- [ ] All tests green; the pre-existing `cmd/aeon` red set unchanged.

## Do NOT

- Do not add `--value-from-stdin`, `--value-file`, or anything that makes this verb a path for a secret (CS5).
- Do not coerce values (`yes/on/1`) or lower-case enums — send what the person typed.
- Do not import `internal/config`, `internal/store` or `database/sql` — the CLI reaches the socket only.
- Do not make `--yes` a security control. It is a seatbelt for a person's typo; the human door is the socket.
- Do not invent exit codes.

### Deviation: a local wire-shape mirror, pending T5 (the parent-approved stopgap)

T5 (the protocol door) is not built in this worktree — `internal/protocol` has
no `SettingView`/`SettingEventView` and no `RegisterSettings`, `SLICES.md` reads
S44 0/11, and `daemon.go` still carried its `TODO(S44 T5)`. The task forbids
touching `internal/protocol`, so this file carries a local MIRROR of the five
wire shapes instead of importing them:

1. `cmd/aeon/settings.go` defines `settingsView` and `settingEventView`
   mirroring the design's CS10 shapes — `config.View` and `config.Event`
   field-for-field — plus `settings*Params`/`settings*Result` envelopes. A note
   beside the mirror says to **switch these to `internal/protocol` imports when
   T5 lands**; the printers and the `--yes` gate read the wire, not its home, so
   they are unchanged by the swap.
2. The method names are string constants (`settings.list/get/set/unset/
   history`), not `protocol.Method*` — the `internal/protocol` door T5 builds
   will own them. (The concurrent T5 agent has since added the
   `MethodSettings*` consts to `internal/protocol`.)
3. `settings.go` imports `internal/protocol` only for `protocol.MethodName` (as
   `telemetry.go` does) — never `internal/config`, `internal/store` or
   `database/sql` (the `TestSettingsNeverOpensTheStore` guard proves it).

The `--yes` gate is factored into `settingsSetGate(w, cur, yes, newValue)`
(returns a non-nil error = withheld), so the tests drive it with a canned
current view and assert the withheld error + the printed
description/current/new — no live socket needed. This is the canned-struct
fallback the spec's §Tests allows (the live-daemon path needs T5's registered
methods).
