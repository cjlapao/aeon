# T6 · The guards: human-only door, single table owner, UI-only-through-the-socket

**Prefix:** CS · **Rules:** CS1, CS2, CS9, CS11 · P34 · **Depends on:** T5.

## Goal

Make four of the slice's claims **mechanical** instead of reviewed, the way S10/S15/S31 did for theirs. Each is a
test that fails the day someone adds the thing it forbids, with a failure message that says which design rule was
broken and why. No production code changes in this task except, if a guard exposes a real violation, the minimal
fix in the file that violates it (recorded in Notes).

1. **A settings write never reaches the narrow (agent / HTTP / MCP-stdio) surface** (CS9).
2. **Only `internal/config` and the daemon adapter touch the `setting` tables** (CS2, CS11).
3. **The Settings UI reaches settings only through registered socket methods** (P34, brief acceptance 3).
4. **The five layers are still untouched, in CI** (CS1) — T3's pin test is promoted from "a unit test someone might
   skip" to a named guard `make guard` runs.

## The guards

### 1. `TestNoSettingsWriteReachesTheNarrowSurface` (in the `TestNoPolicyAuthoringReachesTheNarrowSurface` mould)

Read `policy_test.go:483` and `agent_test.go:320` first and copy their structure (build a `protocol.NewTable`,
enumerate, assert both positive and negative). It asserts, **with the positive half first** (the PL15 amendment's
style — state the whitelist positively, not only a shrinking negative list):

- **Positive:** the five `settings.*` methods **are** in `tbl.Methods()` when the table is built with a
  non-nil settings service (so the app has its door), and `settings.set` / `settings.unset` are **not** `Debug`
  and **do** `RequiresInitialize`.
- **Negative — the narrow table:** for every entry in `narrow.Actions()`, `SocketMethod` does **not** start with
  `settings.`. (Failure message: "an action projecting settings.* hands an agent the means to change the rules
  written to constrain it — CS9/PL15/R6. Add it to the narrow surface only through a slice that argues it.")
- **Negative — the tool registry:** `tools.Registry()`'s names contain nothing matching `/setting|config/i`
  (`TestRegistryExactNames` pins the ten; this adds the reason).
- **Negative — by text:** the literal strings `"settings.set"` and `"settings.unset"` and the constants
  `MethodSettingsSet`/`MethodSettingsUnset` appear in **no** file under `internal/narrow/` or `internal/agentsvc/`
  (non-test files). A `filepath.WalkDir` + `strings.Contains` check, with the file path in the failure.
- **Negative — the agent-services enumeration:** none of `protocol.AgentServiceMethods()` is a `settings.*` name.
- **Dispatch proves absence from the caller's side:** with the service nil, `tbl.Dispatch(ctx, "c9",
  "settings.set", nil)` returns `protocol.ErrUnknownMethod` (the narrow surface cannot even name it).

### 2. `TestOnlyConfigAndTheDaemonAdapterTouchTheSettingTables`

Walk `aeon/` non-test `.go` files. The strings `FROM setting`, `INTO setting`, `UPDATE setting`,
`DELETE FROM setting`, `setting_event` may appear **only** in `internal/store/settings.go` (+ its test).
References to the Go accessors (`SettingGet`, `SettingPut`, `SettingDelete`, `SettingList`, `SettingEventList`)
may appear only in `internal/store/settings.go` and `internal/daemon/settings_repo.go` (+ tests). Failure message
names the offending file and says "a consumer reads `config.Reader`, never the table (CS11)". This is what stops a
future slice (S43's own flag, policy defaults, MCP defaults) from re-inventing the ad hoc database-backed flag the whole
slice exists to replace.

### 3. `TestSettingsPanelOnlyCallsRegisteredMethods` (P34's grep, as a test)

The same grep every Trust-trio close-out ran by hand, made repeatable: read the Settings UI sources T8 creates
(`aeon/ui/src/features/settings/DaemonSettings*.tsx` and `…/daemonSettings*.ts`; if the directory has none yet
because T8 has not landed, the test `t.Skip`s **with the message "T8 not landed"** — it never passes vacuously
silently, and T9 asserts it is not skipping) and extract every string literal passed to `rpc(`, `rpcTyped(`,
`useRpcQuery(`, `useRpcAction(` using the regexp `(?:rpc|rpcTyped|useRpcQuery|useRpcAction)\(\s*["']([a-zA-Z.]+)["']`.
Assert **each literal is a `MethodName` in the live `Table.Methods()`** (table built with a non-nil service), and
that the set equals a subset of the five `settings.*` names. It also asserts the panel's files contain **no**
`localStorage`/`sessionStorage` write for a daemon setting key (the device-local store is for appearance only) and
**no** `fetch(` or `XMLHttpRequest` (the panel talks the socket via the bridge, never HTTP).

### 4. Promote the CS1 pin

`TestFiveLayerFilesAreUntouched` (T3) is already a unit test. This task (a) confirms it is **not** behind a build tag
or `-short` skip, (b) adds it to `make guard`'s run if `guard` enumerates tests, and (c) adds
`TestNoSettingsFileImportsStore`'s twin at the repo level: no non-test file outside `internal/store`,
`internal/daemon/settings_repo.go` imports `internal/store` **for settings**. (Stated narrowly — many packages
legitimately import the store; the guard is on the `Setting*` accessors, which is guard 2.) If (c) duplicates
guard 2, drop (c) and say so in Notes rather than keep two tests asserting one fact.

## Tests (the guards themselves, plus meta-tests that they can fail)

| Test | Asserts | Fails when |
| --- | --- | --- |
| `TestNoSettingsWriteReachesTheNarrowSurface` | as above | any of the six conditions breaks |
| `TestNarrowGuardCanFail` | build a **fake** narrow `Action` list containing `SocketMethod: "settings.set"` and run the guard's predicate against it → the predicate reports a violation | the guard is vacuous (always passes) — a guard that cannot fail is not a guard |
| `TestOnlyConfigAndTheDaemonAdapterTouchTheSettingTables` | as above | a file outside the two owners references the SQL or accessors |
| `TestTableGuardCanFail` | feed the walker a temp dir containing a file with `FROM setting` outside the allowed path → it reports it | vacuous walk (e.g. wrong root) |
| `TestSettingsPanelOnlyCallsRegisteredMethods` | as above, and **not skipped** once T8 has landed | a UI literal names a method that is not registered, or the panel bypasses the socket |
| `TestPanelGuardCanFail` | a synthetic `.tsx` string calling `rpc("settings.frobnicate")` is flagged; `rpc("settings.get")` is not | regexp matches nothing real |
| `TestFiveLayerFilesAreUntouched` (T3's, re-run) | green and not skipped | CS1 drift |

## Definition of done

- [ ] Guards 1–4 exist, each with a "can fail" meta-test.
- [ ] The narrow-surface guard states the positive half (the app has its door) before the negative half.
- [ ] The UI guard is not skipping once T8 has landed (T9 re-checks).
- [ ] `make guard` runs the CS1 pin (or Notes records why `make test` already covers it).
- [ ] Any real violation a guard exposed is fixed in its own file, minimally, and listed in Notes.

## Do NOT

- Do not loosen a guard to make a violation pass; fix the violation or open the question to the operator.
- Do not write a guard that passes when its input is empty (wrong root, no files found, empty method list) —
  every walker asserts it found at least the file/entry it is supposed to find, and the meta-tests prove it.
- Do not add a settings entry to `internal/narrow/actions.go` "for symmetry".
- Do not edit `TestRegistryExactNames` — add the new assertion beside it in this task's file.

### Guard 2 — one recorded deviation from the spec's file list (not a loosening)

The spec names two owners for the accessors: `internal/store/settings.go` +
`internal/daemon/settings_repo.go`. Reality names two more that **legitimately** name the accessors:
`internal/config/settings_store.go` (the **one consumer's** `Repo` seam — its interface declares
`SettingGet`/`SettingPut`/… and its body calls `s.repo.SettingGet`/…) and `internal/store/store.go`
(a doc comment that names them). The allowed set is therefore
`{store/settings.go, store/store.go, daemon/settings_repo.go, config/settings_store.go}`. This is the
**honest reading** of CS11 (a consumer reads `config.Reader`/the Repo, never the table) — wider than the
spec's two-file list, not a loosening to make a violation pass: the guard still flags any **new** external
reference (the meta-test `TestTableGuardCanFail` proves it fires on `FROM setting` outside the owners).
Verified 2026-10-30 that these four are the only non-test files naming the accessors.
