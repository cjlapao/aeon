# T7 · The CLI client, `aeon init` integration and `doctor`

**Prefix:** SD · **Rules:** SD5, SD10 · P34 · **Depends on:** T6. Parallel-safe with T8.

## Goal

`aeon seed status|plan|apply|restore` as a **client** of the T6 methods, an offline fallback through the **same engine**
(the S45 PM4 pattern), `aeon init` offering the guard plan with an explicit confirmation, and a `doctor` line that says
what is out of date. The CLI re-validates nothing and prints what the wire said.

## Files

- `aeon/cmd/aeon/seed.go` — **new**: `cmdSeed`, verbs, usage; `selectDoor()` as in S45 T8 (dial; success ⇒ socket door;
  "no daemon" ⇒ direct door with the fixed stderr line `daemon not running — applied directly to the store`; **any other
  dial failure refuses, never falls back**).
- `aeon/cmd/aeon/seed_door.go` — **new**: `socketDoor` and `directDoor` (the latter builds `daemon.NewSeedEngine` over a
  directly opened store with actor `{cli, cli}`; **it applies `inert` sets freely and `guard` sets only via the explicit
  verb**, exactly the engine's own rules — no CLI-only bypass).
- `aeon/cmd/aeon/main.go` — dispatch + usage lines for `seed`.
- `aeon/cmd/aeon/init.go` (S23's init) — **VERIFY the file name** (`grep -n 'func cmdInit' aeon/cmd/aeon/*.go`): after the
  existing steps, run `seed apply` for **inert** sets (silent success line) and **print the guard plan** (`seed plan`
  for each guard set) followed by `apply these N records? [y/N]`; applying only on `y`. With `--yes` it applies; in a
  non-interactive session without `--yes` it **prints the plan and the exact command** and applies nothing. At the time
  this slice ships there is no guard set (S45 declares the first), so the guard branch is exercised by a fake set in tests
  and prints "no guard sets declared" in production.
- `aeon/cmd/aeon/doctor.go` — one line per set: `seed agents.firstparty: up to date (33/33)` / `N records behind` /
  `N removed, M diverged (aeon seed status)` / `N failed`. **Never prints record content.** Exit-code behaviour unchanged
  (a behind-but-working seed is a warning line, not a failure — VERIFY S23's doctor severity vocabulary and reuse it).

## Verbs

```
aeon seed status [--set ID] [--json]
aeon seed plan   --set ID [--key K ...] [--json]
aeon seed apply  --set ID [--key K ...] [--yes] [--json]     # a guard set requires --yes (see below)
aeon seed restore --set ID --key K [--yes] [--json]
```

`--yes` mirrors S44's `--yes`: a **seatbelt** for a typo, not a security control. For a `guard` set, `apply` without
`--yes` prints the plan and "re-run with --yes", exit non-zero, **no write**. Inert sets never need it. `--json` is the
wire result verbatim. No credential-bearing flag exists.

## Printer — what it must never hide

`status` shows set id, class, available vs applied version, and counts by state; **every** non-`applied` record is listed
with its state and reason (`removed — restore with …`, `diverged — local content differs from v3 applied; restore with …`,
`failed — <error>`, `retired`). A set with no ledger rows prints `not applied`. Empty registry prints `no seed sets
declared`. `plan` prints each decision with its op and reason; `apply` prints the engine's per-record result and a final
`applied N, skipped M (K diverged, J removed)`.

## Definition of done

- [ ] Four verbs dial the daemon; offline they use the same engine and say so; other dial errors refuse.
- [ ] `--yes` gates guard sets in the CLI; `init` offers the guard plan and never applies it unasked.
- [ ] `doctor` reports seed drift per set, content-free.
- [ ] Parity guard passes; output identical across doors.

## Do NOT

- Do not add a CLI-only way to apply a guard set; do not make `init` auto-confirm.
- Do not print record content in `status`/`doctor` (ids, versions, states only).
- Do not fall back on a dial error that is not "no daemon".
- Do not import `internal/store`/`internal/seed` outside `directDoor`.
