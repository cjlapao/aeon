# T1 — `peer.go`: a configured peer, off by default

## Why this exists

**A peer that arrives without a config edit is a peer nobody decided on** — and under RA4 it is also an
**egress nobody authorized**, which is the sharper half.

**MC3 said this about MCP servers. AP10 said it about plugins.** The reasoning does not change because the
subject is now on another machine: no `/.well-known` crawling, no mDNS, no registry lookup.

**And off by default, in the outbound direction** (RA9). N15 made HTTP off-by-default because *"a daemon
listening on a port by default is a daemon somebody exposed by accident."* **The same sentence works
outbound**: a daemon that reaches out by default is one somebody exfiltrated through by accident.

**Read first:** MC3 in [`../../S12-mcp-client/design.md`](../../S12-mcp-client/design.md), AP10 in
[`../../S15-agent-plugins/design.md`](../../S15-agent-plugins/design.md), N15 in
[`../../S19-narrow-surface/design.md`](../../S19-narrow-surface/design.md); the design's RA3, RA9.

## Scope

**1. A peer carries** an id, an address, a **pinned identity** and a reference to its key material.

**2. A peer without a pin is refused at configuration time**, not at dial time. The refusal says the system
CA set alone is not sufficient and why — because *"add a pin"* with no reason reads as bureaucracy.

**3. The key is read from the environment or a path** — never argv, never a config file, never a log
(C17). A pin is public and may sit in config; **a client key or shared secret may not.**

**4. Nothing is discovered.** Assert by grep: no well-known path, no mDNS, no SRV lookup, no registry URL.

**5. A fresh install reaches nothing.** Assert it — the empty state is *"nothing outbound is reachable"*,
stated, not an empty list.

**What the task file could not know, decided here:**

- **The grep test bans tokens, and bans them from comments too.** The sentence that says *"we do not crawl
  /.well-known"* is one refactor away from the code that crawls it, so `TestNothingIsDiscovered` reads
  `peer.go`'s own bytes and refuses `well-known`, `mdns/mDNS/MDNS`, `SRV/srv`, `registry/Registry`,
  `net/http`, `http.Get/http.Post`, `Dial(`, `dns.`, `Lookup` — even in prose. It also asserts the POSITIVE
  (`DisallowUnknownFields` still present) so an over-eager ban list cannot silently pass by deleting the
  strictness along with the tokens.
- **The address is schemeless, and BOTH schemes are refused.** `http://` is refused with the D1 sentence
  (no plaintext mode — not for localhost, not for a flag, not for development); `https://` is refused too,
  because a config that spells the scheme is one edit away from spelling a different one — TLS is the
  transport's decision (T3), not the config's. This is a small deviation with a reason: the task text only
  named the plaintext case; the schemeless shape is what makes it stable.
- **The key is a reference by construction, not by manners.** `Peer`/`Pin`/`KeyRef` hold no `[]byte`
  anywhere — a reflect walk of all three types asserts it — and the decoder is
  `DisallowUnknownFields`, so literal bytes under ANY field name (`literal`, `value`, even a top-level
  `argvKey`) are refused at the door by name. `%v`/`%#v` of anything config-shaped print the reference only
  (`key:env:NAME`); `String` and `GoString` both redact, and a test asserts the secret bytes never reach a
  format verb while a live env value is set. `LoadKey` is the use-time reader with the mcp client's
  injectable-getenv seam (`internal/mcp/client.go:117–120` precedent); it is deliberately **not** called by
  Validate or any decode path — reading a key to check the config's shape is how secrets reach stack traces.
- **The two missing-key sources refuse with different sentences** (env names the variable, path names the
  path, both restate C17 — *"never argv, never a config file"* — so the operator's fix is not "put it in
  the config"), and a `KeyRef` with both sources set is refused: one source, so a config review can see
  which one wins.
- **RA9 needs three doors, not one**: the task text leans on the pin; RA9 itself says *address, pinned
  identity AND a key*, so `Validate` refuses a peer missing any of the three, and the unpinned refusal
  carries the whole RA2 argument (`system CA set … proves TLS, not identity … "this is the peer we
  consented to"`) because "add a pin" with no reason reads as bureaucracy.
- **The empty state is a sentence, not an absence**: `Config{}.OutboundState()` returns the exact string
  *"nothing outbound is reachable — remote peers are off by default, and enabling one takes an explicit
  address, a pinned identity and a key (RA9)"*, asserted byte-equal, and the configured form names each
  peer `id at host:port` verbatim.

Nothing was discovered; the fresh install reaches nothing; the pin is refused before any dial exists.
