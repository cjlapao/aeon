# T2 — `trust.go`: pinning, and the rotation story

## Why this exists

**A valid certificate proves TLS to *some* host. It does not prove this is the peer you consented to.**

The system CA set answers *"is this a real certificate for this hostname"*. It does not answer *"is this
the agent we pinned"* — and the gap between those is every mis-issuance, every compromised CA, and every
hostname somebody else can obtain a certificate for.

**Pinning is S15's signed-card argument one layer up** (RA2): *"is this really from who it claims"* needs
an answer that is not trust.

### The risk that defeats pinning in practice

**Answer Q1 with the rotation story, because this is how pinning gets turned off.**

A **certificate** pin breaks on renewal. Certificates renew — routinely, automatically, every ninety days
in a lot of deployments. **The first renewal looks exactly like an attack**, somebody investigates, finds
nothing, and disables pinning to stop the noise.

**A public-key or SPKI pin survives renewal**, because the key is reused. That is the difference between
pinning that lasts and pinning that gets removed in month four.

**So: pick key or SPKI, and write down what happens when a peer legitimately rotates.** If there is no
answer to that, the pin is temporary no matter what the code says.

**Read first:** `peer.go` (T1); Go's `crypto/tls` `VerifyPeerCertificate` and `InsecureSkipVerify`'s
semantics — **you will need the former and must never set the latter**; the design's RA2 and Q1, Q2.

## Scope

**1. Verification refuses.** A certificate that is valid but unpinned is **refused**, and the refusal
prints both the pinned and the offered value so the difference is visible rather than asserted.

**2. Answer Q1**: certificate, public key, or SPKI hash — **with the rotation story written down**.

**3. Answer Q2**: a CA in the trust store, or leaf pins only. **Leaf pins are stricter and do not scale; a
private CA scales and widens.** For a handful of known peers, leaf pins are probably right — state the
choice and what it costs at ten peers.

**4. `InsecureSkipVerify` is never set.** Not behind a flag, not in a test helper. Assert by grep over the
whole package — **a test helper that sets it is the bypass T3's ordering rationale warns about.**

**5. Verification is additional to, not instead of, normal TLS validation.** Expiry, hostname and chain
still apply. A pin is a narrowing, not a replacement — otherwise an expired pinned certificate would be
accepted.

**6. Test certificates live in `testdata/`** and are generated by a committed script, so the suite does not
depend on a certificate that expires.

**Q1 — what is pinned: SPKI.** The decision and its reasoning are a doc-comment on `trust.go` itself, not
just here, because the code without the story gets "fixed" by someone who never heard it. Certificates
renew — every ninety days in a lot of deployments — and a certificate pin breaks on the first renewal,
which looks *exactly* like an attack; somebody investigates, finds nothing, and disables pinning to stop
the noise. That is how pinning dies in month four, and it is why the answer is the leaf's
`SubjectPublicKeyInfo` hash: the key is reused across renewals, so the pin does not fire on the boring
path. Both kinds stay configurable (`certificate` is the stricter promise-never-re-key option).
**The rotation story, written down as scope 2 demands:** renewal with the same key rides through an SPKI
pin unnoticed (asserted as a test, not just claimed — `TestRotatedKeyRefusedSayingPinMismatch` ends with
the renewal half); a real key rotation fires the pin and **the refusal is correct** until the operator
confirms out-of-band and re-reads it — there is no automatic re-pin, because a pin that re-pins on first
encounter is TOFU and TOFU's first encounter is the attacker's best day. The refusal prints **both hex
values** (scope 1), so the re-read is a diff against `testdata/certs/PINS.md`, not a 2 a.m. forensics
session.

**Q2 — CA in the store, or leaf pins only: leaf pins only.** Trusting a private CA scales to many peers but
widens the trust to that CA's whole issuance policy — the moment Aeon trusts a CA, every certificate it
mints for the hostname is "the peer". For a handful of known peers leaf pins are right. What it costs at
ten peers, stated rather than glossed: every coordinated key rotation is ten config edits, and the only
amortization that exists re-opens the CA door — the mitigation is the kind choice (SPKI + long-lived keys
pushes the edit rate near zero), never a store that trusts more.

**What the task file could not know, decided here:**

- **Verification is additional by construction, and both halves are tested over real handshakes.** The hook
  is `VerifyPeerCertificate`, mounted alongside full normal verification (chain, expiry, hostname all run
  against `RootCAs` first); `TestExpiredPinnedCertificateStillRefused` proves the narrowing property both
  ways — pin matches + expired ⇒ still refused, refusal says *expired*; pin matches + wrong hostname ⇒
  still refused. The token `InsecureSkipVerify` is banned by grep over **every `.go` in the package
  including tests** (scope 4), with the banned token assembled by concatenation so the hunting file does not
  contain what it hunts, and a floor assertion (≥3 files scanned) so the scan cannot pass by scanning
  nothing.
- **The tests mint certificates in memory; the committed `testdata/certs/**` exist for the demo, not the
  suite.** Only in-memory minting can produce an *expired* certificate to order, and it removes the expiry
  cliff the task explicitly worries about. `gencerts.go` (committed, `cd testdata/certs && go run
  gencerts.go`) writes the ~10-year demo PKI plus `PINS.md` — the pin table the T9 walk will quote — and a
  test sanity-checks the committed bytes load, carry every pin PINS.md states, and none expires inside a
  year. The rotation is on disk too: `peer-rotated.pem/.key` is the same CA re-issuing with a **new key**,
  the rotation story made bytes.
- `Offered` is exported so rotation tooling and the refusal compute the same value with the same function —
  "the refusal said one thing and the tool another" is designed out, and a test grades it against an
  independent `sha256.Sum256` so it cannot mark its own homework.

D2 (valid, right hostname, real CA — refused), D3 (rotation refused, *says* "pin no longer matches") and
the CA-set-alone gap (the identical handshake accepted without the hook, refused with it) are each their
own test, by name, in the record.
