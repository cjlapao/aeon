## Notes

**Built 2026-10-29.** Reused T6's `Fact`/`useFact`/`classify`/`FactCell`/`ProbeChip` verbatim — no second
copy.

Three real `mcp.status` states confirmed against `cmd/aeon/mcp_services.go`'s own file-header comment
(absent / present+valid / present+broken with `loadError`, no `servers` key). No fixture exercised the
broken state before this task, so `protogen` had never emitted `loadError` into `contract.ts` — added
`internal/protocol/conformance/routes/mcp-status-broken.json` (a real `Validate()` error string, "server
… is configured twice … (MC12)") and re-ran `go run ./tools/protogen`, same fix shape T6 used for
`tools.grants`' `reason`: widen the fixture, don't hand-type a field protogen can emit correctly.

**Deviation from this task's own chip vocabulary (§Chip vocabulary above, and design.md §4) — structured
`unreachable: {error}` / `timed out after {timeout}` chip text does not exist as two distinguishable
states in the real data.** T4's `ProbeResult{OK, Tools, Err, Ms}` (and `mcp.check`'s wire result,
`{ok, error?, ms, checkedAt, tools?}`) carries one free-text `error` string, never a classification of
*why* — a dial timeout and a connection refusal both just produce whatever `error.Error()` says. T6's
`ProbeChip` (built first, shared) already reconciled this the same way: one `failed` chip rendering
`probe.error ?? "failed"` verbatim, no timeout/unreachable split invented on top of a string the daemon
never structures that way. This page reuses that chip rather than forking a second, more elaborate one
that would have to synthesize a distinction the data doesn't carry.

**Deviation on refused rows:** T3's reality finding (already recorded in T3.md) holds — there is no
per-server `refused` field, so there is no "refused row, no Check button" case either. Every configured
server gets a Check button; a broken config is the whole-file state above, not a per-row one.

**Single-flight (TB8's UI half):** implemented as component-local `useState<Set<string>>` keyed by server
name, not a module-level/context store. The task's own text hedges this ("if that's ever possible") —
`McpPage` is mounted at most once at a time in this app (one bench tab, no second instance), so there is
no second instance to race with; a module-level store would guard a case that cannot occur here and was
skipped as unneeded weight. What the UI layer *does* need, and has: a second click while a check is
in-flight for that server must not even send a second `mcp.check` RPC (proven by
`TestMcpPageCheckButtonSingleFlightAcrossClicks`'s dial-count assertion, not a timing guess) — the
daemon's own `checkOrJoin` (T4) would have absorbed a redundant call anyway, but the UI shouldn't rely on
that to avoid firing one.

CLI twin per row: `aeon mcp list --agent <declaringAgent[0]>` when `declaredBy` is non-empty, else
`aeon mcp list` — flags cross-checked against `cmd/aeon/mcp.go`'s own `cmdMCPList` definition (same
convention T6 used).
