  **flip its verdict**. The check reads `tools.ToolNames()`; the verdict follows registry membership, not a list.
  (`search` at S22 is the same mechanism.)
- **English-word retired names** (`task`, `patch`) are refused only in tool positions — snake_case call syntax
  `name(` or backticked identifiers — because "apply a patch" is prose, not a tool reference.

## Why this exists

**This is the only automatable check on 2,902 lines of prose rewriting**, and it comes before any rewrite (R4) because
landing 25 unverified bodies means re-reviewing 25 bodies by hand.

## Scope

### `aeon handlers verify`

Checks every body for:

| Check | Rejects |
| --- | --- |
| **Forbidden tools** (A11, D1) | Any tool name not in the registry: `loop_get`, `memory_append`, `event_append`, `loop_readFile`, `loop_readTask`, `loop_writeFile`, `task`, `patch`, `lsp`, `codesearch` |
| **Skill loading** (D2) | Any reference to `dev-loop-protocol` or another skill. Nothing loads skills |
| **Ritual residue** (D3) | `FINAL REPORT`; a caller guard; an instruction to append to memory or events |
| **The `description`** (A20) | The same ritual and forbidden-tool checks. It is model-facing prose. **25 of 26 originals fail on the caller guard alone** |
| **Front matter** | Via T1's loader, including A19's `tools` translation |

**The tool set comes from the registry** (O1, I2), not a hardcoded nine. A hardcoded list is a second source of truth
about the toolset, and it would go stale the moment S22 adds `search` — at which point a body legitimately naming
`search` would fail.

### The negative control (D1, C2)

**`verify --file <an original>` must FAIL.**

This is what makes the guard trustworthy. Measured across the originals: **all 26** reference `loop_get`, **all 26**
reference `memory_append`, **all 26** reference `event_append`, and **all 26** load a 793-line skill. A check that
cannot fail on any of them is not measuring anything.

So the test suite runs `verify` against every one of the 26 originals and asserts **all 26 fail**, naming at least
three forbidden tools each. That is a live control, re-run on every build, rather than an assertion made once during
design.

### The drop-record format (A14, D6, O2)

One per handler, in `drops/`. Three sections, and the middle one is the reason the format exists (A12):

```markdown
# golang-engineer — drop record

original: opencode/agents/golang-engineer-loop.md  (84 lines)
rewrite:  bodies/golang-engineer.md                (31 lines)
delta:    53 lines removed, 0 added

## RITUAL (deleted — the engine does this)
- L8-L12   caller guard checking who dispatched   → the blueprint dispatches
- L14-L21  pwd + loop_get + loop_readFile + loop_readTask → context arrives resolved
- L44      "re-read prior failures"               → the transcript is the record
- L78      event_append return checkpoint         → the daemon emits events
- L82      FINAL REPORT line                      → the handoff is structured

## BECAME MECHANISM (deleted — a tool guarantees it now)
- L57      "exit 137 is an OOM kill, not a lint finding" → bash reports oomKilled (W5)
- L61      "never run git"                        → the allow-list has no git
- L63      "one task per turn"                    → the blueprint controls this

## DOMAIN (kept)
- L24-L40  Go idiom, error wrapping, table-test shape
- L67-L74  module hygiene, when a build tag is warranted

## REWORDED (O3)
- L24 shortened; meaning unchanged
```

Four requirements on that format:

- **Line references, not paraphrase** (O2). "Removed the ritual preamble" is unreviewable. A4's requirement was a human
  diff against the original, and a record that cannot be diffed did not satisfy it.
- **The line delta must add up.** An unexplained gap is an omission nobody reviewed.
- **`BECAME MECHANISM` is a required section**, even when empty. Its absence is how someone skips the category
  entirely — and it is the category that will be got wrong, because *"exit 137 is an OOM kill"* reads exactly like
  domain knowledge and is now W5's job.
- **`DEFERRED` is a required section** (A18), even when empty. **24 of 26 bodies reference MCP**, which Aeon defers
  (**S19's N17 — now reversed**: the client lands at S12, which precedes this slice, so this classification is an
  open amendment; see `ROADMAP.md` §7) — qa-engineer's *"UI cases — Playwright MCP first"* is
  the clearest case. That content is not ritual, not became-mechanism, and not keepable domain, because the tool does not
  exist. Recording it names what a future MCP client is for; dropping it silently means nobody remembers.
- **`REWORDED` exists so A17 is followable** (O3). Without it, every clarity improvement looks like invented content
  and the rule gets ignored rather than obeyed.
