## Why this exists

Twenty-five handlers exist and nothing chooses between them. This is the task that makes `agent: by-tech-tag` mean
something — and it comes after the rewrites (R7) because **wiring a resolver against two handlers proves nothing about a
table of ten tags.**

## Scope

### The resolver

```go
// Resolve maps a tech tag to a handler name. A closed registry.
func Resolve(tag string, st loop.LoopState) (string, error)
```

`by-tech-tag` is a **named resolver**, not an expression — the same closed-registry reasoning as S8's conditions and
predicates (L5). Adding one is a code change, deliberately: **a resolver expressible in config is a config file that
runs code.**

### The table (Q8, A5's `go→golang`, `react-ts→react-typescript` dispatch)

The full tag → handler mapping, committed and reviewable in one place. It is **authorship**, not an open design
question — but it must be written down before this task starts, because O5 makes a duplicate a load-time error and that
requires knowing the table.

### A duplicate tag is a load-time error (O5)

Two handlers claiming the same tag is an error at load, **naming both**.

Not "the first wins": which one that is depends on map iteration order, which is the same class of bug G2 fixed by making
policy an ordered array rather than a YAML mapping. A resolver that silently picks one produces a loop that dispatches
differently between runs, and nothing in the record says why.

### An unknown tag refuses, listing the **tags** (A13, D10, O4)

```
no handler for tech tag 'elixir'
available: go, python, javascript, rust, sql, react-ts, vue-ts,
           tauri-react, tauri-vue, websocket
```

**Available tags, not handler names** (O4). A user asked for `elixir`; they need to know which tags exist. Handler names
are an implementation detail they never supplied.

Surfaced as S8's `BlockedReason`, structured so S9 renders it and S17 can route on it.

### There is no fallback (A13, D11)

**Asserted by a test that no code path substitutes a default handler.**

A generic handler writing Elixir produces something plausible, the loop reports `ok`, and the badness surfaces three
steps later and is attributed to the model. A refusal costs a minute; a fallback costs an afternoon and a wrong
conclusion about the model's competence.

### Registry wiring

- `registry.go` grows from S8's **two** entries to **25**. One task, because it is a serialization point.
- `testdata/handlers.json` — S8's committed list — grows to 25 and is checked both ways: every registered handler is in
  the file, every file entry is registered.
- **`git-loop` is absent** (A3, T9).

### Blueprint validation becomes real (D13)

S11's T5 put resolver names in a committed reserve list and returned `unverifiable` with `Slice: "S13"`. That flips:

| Before | After |
| --- | --- |
| `agent: by-tech-tag` → `unverifiable`, arrives at S13 | **a real check** — the resolver exists |
| `agent: some-unknown-resolver` → `unverifiable` | **`invalid`** — the reserve list is now the complete set |

And an `agent:` naming one of the 25 is checked against the registry, which it already was — but now the registry has 25
entries rather than 2, so `dev-loop.yaml`'s `unverifiable` count should **drop**. S8's T12 committed that expected set
exactly so this change is deliberate: **update the fixture, and the diff is the evidence the slice did something.**

### Retry a historical missing-handler block explicitly

S9 once allowed `conversational-map` to start before `task-coordinator` existed. That loop is stored as `blocked` at
`triage`; S9 now refuses new starts until its handlers exist. After this task registers the missing handler, provide an
**explicit retry action** for an already stored loop. This is a narrow migration path, not a generic retry for all
blocked loops. The action must be reachable from the S13 app's loop detail, and the daemon must supply retry
eligibility and its refusal reason; the app must not infer eligibility by parsing a displayed error string.

- Recognise only a historical missing-handler block with a recorded handler name and no completed receipt for its
  current step. For legacy records, match the stored `unknown handler` cause narrowly on the daemon side; do not
  treat an arbitrary `blocked` status as safe to retry.
- Resolve the handler against the **now executable** registry first. If it is still unavailable, refuse with its name
  and leave the loop untouched. Preserve the original loop ID, workspace, provider route, pinned blueprint source,
  lane and item position. Do not start a new loop or silently advance the ladder.
- Commit a single durable transition back to runnable state before dispatch. A repeated or concurrent click must
  neither dispatch a second copy nor erase a completed step. Re-read the stored loop after restart and apply the
  same eligibility check. Emit the ordinary loop update so two app windows converge.
- Refuse unrelated blocks, a step with an in-flight execution or completed receipt, and a loop whose pinned source
  can no longer be read. Surface each refusal in the UI with no optimistic status change.

Keep the new protocol operation additive under the existing protocol-version rule. The S9 baseline `two-step` loop
and any other completed history stay unchanged. [The continuing S9 UI walkthrough](../../S9-app/UI-QA-DEMO.md)
records the historical loop URL used for the manual S13 check.
