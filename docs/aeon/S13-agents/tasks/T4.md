## Why this exists

**Four, not five** (R5). The shape of one rewrite determines the shape of twenty-five, and discovering the shape is
wrong on the twenty-second is expensive. This batch establishes it, and `golang-engineer` is the demo's §1 — the
highest-consequence rewrite, done while attention is freshest.

## Scope

For each of the four: rewrite the body, translate the front matter, write the drop record, and **run it once** (O7).

### The pattern, using `golang-engineer` as the worked example

Its original is **84 lines**, and roughly 60% is work the engine now does.

**Front matter** (A19, A20):

- `tools`: drop `task`, rename `todowrite` → `todo`, remove `codesearch`, `lsp`, `patch`. What remains for a Go
  implementer is `read`, `write`, `edit`, `bash`, `glob`, `grep`, `todo`, `question`. **Over-granting is the easy
  mistake** — ask what this handler actually needs, not what the original listed.
- `description`: rewrite. The original's ends *"append lessons via memory_append, and return a FINAL REPORT. It NEVER
  mutates loop state… NEVER runs git, and works one task per turn. If any agent other than dev-loops invokes it, it
  declines."* Every clause is ritual for machinery that no longer exists.
- `temperature`: **ports as-is** — `0.4` here. It is a model parameter, not prose.
- `mode`, `variant`: `mode` does not port (A1 removed the distinction). `variant`'s disposition follows T1's Q2 answer.

**Body**, in the three-plus-two categories:

| Category | What goes | Why |
| --- | --- | --- |
| **RITUAL** | The caller guard; `pwd` + `loop_get` + `loop_readFile` + `loop_readTask` context assembly; "re-read prior failures"; the `event_append` checkpoint; the `loop_writeFile` scratch note; the `FINAL REPORT` line; the `dev-loop-protocol` load | The engine does all of it, and six of those tools do not exist |
| **BECAME MECHANISM** | *"exit 137 is an OOM kill"* — **the decoding half only**; *"never run git"*; *"one task per turn"* | W5 reports `oomKilled` as a fact; the allow-list has no git; the blueprint controls the turn |
| **DOMAIN** | Go idiom, error-wrapping conventions, table-test shape, when a build tag is warranted, module hygiene | Judgement the model still needs |
| **DEFERRED** | Whatever it says about MCP | 24 of 26 bodies reference it; recording names what a future client is for (A18) |
| **REWORDED** | Anything shortened without changing meaning | So A17 stays followable (O3) |

**The middle category is the one to get right, and its hardest case is a line that splits.**

*"exit 137 is an OOM kill, not a lint finding"* is **two claims**:

| Half | Category |
| --- | --- |
| exit 137 / `SIGKILL` **means** an OOM kill | became mechanism — W5 reports `oomKilled` |
| an OOM-killed linter's **silence is not a pass**, and the fix is not in your code | **domain — kept** |

**Delete the decoding, keep the consequence.** The tool reports what happened; nothing reports what it means for the
work. `aeon-agents.md`'s QAC-05 requires that second half be present and names its absence the worst of five possible
losses — *"a model treating an OOM kill as a lint finding will edit correct code to satisfy a linter that never ran."*

Four more of QAC-05's at-risk details are in this handler and all survive: `-timeout 120s` on `go test` (Go-specific, so
domain — W3's mandatory timeout is a different guarantee), `gofmt -l` as the **final** verification step, the
memory-bounded `golangci-lint` ladder, and the ≥80% coverage mandate on new and changed code.

### Verify each by running it (O7)

Passing `aeon handlers verify` is necessary and not sufficient: **a body can satisfy every grep and still instruct the
model to do something impossible.** So each of the four runs once, against a real task in a throwaway repository, and
its output is checked.

`golang-engineer`'s run is the demo's §1 and its bar is concrete: **`go test ./...` passes and the binary runs.**
