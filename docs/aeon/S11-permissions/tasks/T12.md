# T12 — Wiring — policy on handlers, the allow-list, and retiring the warning

## Why this exists

Everything is built; this connects it. It is the **serialization point** for the registry and the last task before the
demo.

## Scope

### Policy attaches to handlers (G17)

A handler gains a `Policy`. S8's registry has two entries; S13 will bring 25 with the corpus's real blocks.

```go
type Handler struct {
    Name         string
    SystemPrompt string
    Tools        []string        // an allow-list (G10)
    Policy       policy.Policy   // ordered rules, per-agent (G2, G13)
}
```

**No shared default. Nothing hoisted** (G13, I8). The corpus proves why: `gh pr merge*` is `allow`, `ask` **and**
`deny` in different agents, so a well-meaning refactor extracting "the common denials" would change behaviour for
whichever agents disagreed.

Assert it: **no file contains a default or base policy**, and a handler with no policy block denies everything (G4) —
which is the safe reading and distinct from an unparseable one (T6's O5).

### `tools` stays an allow-list (G10)

The runtime grants exactly what is named. v1's 34 `filesystem_*: false` entries are **dead config** — a `false` entry
denies something never granted — and they do not port.

**And the registry still cannot grant a tool from a blueprint.** S8's T7 built that assertion; this task must not
weaken it while adding policy. A blueprint routes; it never grants (L8).

### All nine tools classified (D23)

S7's committed re-run class list marked six tools *not yet applicable*. They exist now:

| Tool | Class | Because |
| --- | --- | --- |
| `read`, `glob`, `grep`, `webfetch` | `safe` | Read-only |
| `write`, `todo` | `detectable` | Converges on re-run |
| `edit` | `detectable` | **Exact-match, so a re-run fails loudly** (W19) |
| `question` | `safe` | Suspends rather than acting |
| `bash` | **`unsafe`** | Arbitrary effects, none detectable |

**No pending entries left**, and `bash` is still the **only** `unsafe` one — asserted as a count plus a name, so a
second unsafe tool fails rather than passing a "bash is unsafe" check.

### `--allow-bash` retired (D22)

Since S5 the flag printed a stderr warning on **every** use, and its help said `bash` had no command policy. Both go.

**A warning that outlives its cause trains people to ignore warnings** — which is the real cost, because the next
genuine warning is then also ignored.

`bash` is still not granted by default: it is in a handler's `tools` allow-list or it is not available. The flag
remains for a single `aeon step` without a handler, minus the apology.
