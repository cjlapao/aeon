# T13 — Walk the demo, amend the QA suites

## Why this exists

A slice is not done when its tests pass. It is done when someone who did not build it can follow `DEMO.md` and watch
the thing work (§14).

## Scope

### Walk every section

On a throwaway repository with a bare `origin` nobody cares about. Fix whatever does not match — the demo or the code,
whichever is wrong.

**Three sections carry the slice.**

**§1 — the deciding rule is on screen.** A prompt reading only *"approve `git push origin feature/x`?"* is a **FAIL**.
The user must be able to tell whether **the rule is wrong or the command is**, because those call for opposite actions,
and the prompt is the only place that distinction can be made. Confirm the rule, its verdict, and the agent whose
policy produced it are all visible without expanding anything.

**§2 — the denied command is proven never to have spawned.** Not "the push was refused" — use the
`touch … && git push` form and confirm the file **does not exist**. Any denied segment denies the whole (G8). Then
confirm the **receipt table is empty**: a receipt means *"this may have started"*, and one for a refused command turns
a clean denial into a step recovery must fail as unknown.

**§4 — the two cases at the end.** `gh pr merge` **denied** against a bare `gh` rule, which a plausible matcher gets
wrong and which is the one silent over-permit in the slice. And `bash -c "git push"` **allowed**, which is **correct
behaviour**.

That second one is the wording test. **If whoever walks the demo leaves thinking the matcher is a sandbox, §4 has
failed and the fix is the prose.** The limit is acceptable because the corpus's denials target accidents rather than
adversaries, and because the tool allow-list is the actual boundary — both of which must land with the reader.

Also confirm **§3's attendedness** from both ends: opening the app during an unattended loop changes nothing, and
closing it during an attended `ask` leaves the loop waiting.
