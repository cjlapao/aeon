**The shape the skeleton did not have, and why.** `Verdict.Token(command string) (AllowToken, bool)` — the
skeleton showed a bare `Token()`. `Verdict` deliberately carries **no** `Command` field (`evaluate.go` copies

an unproven forgery is an unenforced rule. The package reports `[no statements]` under coverage because it is a
pure external-proof package; its subject code is counted in `internal/policy`.

**No exported-for-tests mint seam, anywhere.** Every token in the suite mints through the real
`policy.Evaluate` (`policyseam_test.go`), because a seam that lets a test mint is a seam that lets production
mint too.

# T5 — The `AllowToken`, and the verdict-receipt-spawn ordering

## Why this exists

G12 said the evaluator is consulted before any spawn **structurally** — *"not 'checks then spawns' as source
ordering, but a spawn that is unreachable unless the verdict was `allow`."*

Source ordering is a convention, and a refactor can reorder it without anything failing. This task makes it a **type**
(G16, R7): a `spawn` you cannot reach without having asked.

And it fixes the second ordering, which S7 forces: **the verdict comes before the receipt** (G15).

## Scope

### The token (G16, D12)

```go
// AllowToken proves a verdict was obtained and was allow.
// Its fields are unexported and its only constructor is Evaluate.
type AllowToken struct {
    rule  string
    agent string
    cmd   string
}

// Allowed returns a token only when the decision permits the command.
func (d Decision) Allowed() (AllowToken, bool)
```

Unexported fields mean **no other package can construct one**, even by composite literal — the zero value exists but
carries no command, and `spawn` rejects a token whose `cmd` does not match the command it was given.

That last check matters: without it, a token obtained for `go test` could be passed to a spawn of `git push`. The
token proves a decision was made **about this command**, not that some decision was made.

```go
// spawn is unexported and takes a token. Nothing runs without one.
func spawn(tok AllowToken, cmd string, b Bounds) (Result, error)
```

### The ordering (G15, D13)

```
   Evaluate ──▶ allow ──▶ BeginReceipt ──▶ spawn ──▶ CompleteReceipt
       │
       ├── ask   ──▶ T6 resolves it
       └── deny  ──▶ tool error. NO receipt. NO spawn.
```

**A denied command gets no receipt.** A receipt means *"this may have started"* (S7's K31), so writing one for a
refused command would make recovery report an **unknown outcome** for a command that provably never ran — converting a
clean denial into a step nobody can resolve without inspecting a repository by hand.

This is why the two orderings are one task: they are the same property viewed twice. Nothing runs without a verdict,
and nothing is **recorded** before one.

### A denial is a tool error, not a step failure (W6)

`{ok: false, error: "denied by rule 'git push*' (github-steward)"}` goes back to the model, which can adapt. That is
the point of giving a model tools — a denial is information, not breakage.

## Definition of done

- [ ] `AllowToken`'s fields are unexported; its only constructor is `Decision.Allowed`
- [ ] A separate test package attempting to forge one **fails to build**
- [ ] A token is bound to its command; a mismatched or zero token is rejected
- [ ] `spawn` is unexported and unreachable without a token
- [ ] A denied command produces no spawn **and no receipt**, asserted by effect and by an empty table
- [ ] An unresolved `ask` produces no receipt
- [ ] The allowed path writes the receipt before spawning
- [ ] A denial is a tool error; the step continues
