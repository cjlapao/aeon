Written by `golang-engineer-loop`; checked by the record pass (loop T20) against the committed code. Code:
`aeon/internal/tools/glob.go`, `grep.go` and their tests. The §4a record for this task was **deferred to the
record pass by the dispatch** (the T8–T16 precedent in this loop) and is written here.

**Caps: which were pinned and which were chosen.** The spec pinned `GlobMaxResults 500`, `GrepMaxMatches 200`
and the NUL sniff at 512 bytes — honoured verbatim. Chosen, each with a provenance comment in the limits style:
`GlobMaxBytes`/`GrepMaxBytes` at **64 KiB** (deliberately agreeing with `BashStdoutCap`, so the layers agree at
the boundary rather than one silently permitting more) and `GrepMaxLineBytes` at **512**. The constants are
**tool-local**, following `files.go`'s `maxWriteBytes`/`maxListEntries` precedent, *not* in `limits.go` — whose
roster is the `Limits()` surface read by `read`/`bash`, and the spec's file list was honoured exactly.

**Exact counts, not stop-early.** The truncation sentences report `showing N of M` from a `cappedBuffer` that
**keeps counting after the cap**, rather than the "at least" form the spec also permitted. Exact totals are house
style, and a truncation line that understates what it dropped is the kind of confident wrong answer P31 exists to
prevent.

**Three decisions the spec left open, recorded because they are behavioural.** (1) `grep`'s `path` must name a
**directory** — a file is refused, as `list` refuses one; reading a single named file is `read`'s job and the
tools must not overlap into each other's guarantees. (2) Both tools are **pure reads** (class `safe`) and every
path goes through the one resolver, so **a path that appears in a result is information, never a read** — that
is the whole of "no escape through results", and the structural test fails by design if a future edit adds an
opener *before* the resolver call textually, or reaches for `filepath.Join` instead of `path.Join`/
`walkerRelative`. (3) Two verbatim strings are pinned by tests because they are load-bearing for the reader:
`"showing N of M paths (truncated at N; narrow the pattern)"` and grep's analogue, and the description sentence
**"This tool's glob syntax is its own; policy command patterns use a different, single-asterisk syntax."** —
the second one exists because a model that has just used `glob` will otherwise write `**/*.go` into a
`command_access` pattern and be silently over- or under-matched.

**For the reader who is about to grant them.** `DefaultGrant` is unchanged, so `glob` and `grep` **exist and no
step can call them** until an author names them in a grant — the registration audit (loop T19) pinned that
"registered is not granted" for these two alongside `bash` and `webfetch`. `daemon/recover.go`'s
`recoveryClasses()` derives from `Registry()` automatically, so the additions broke no pin.

# T9 — `glob` and `grep`

## Why this exists

The two read-only search tools, sharing a task (R8) because they share path enforcement, output bounding, and one
failure mode that is specific to them.

Both are `safe` on re-run (S7's W16) — read-only, so recovery re-runs them without thought.

## Scope

### `glob`

Matches paths against a pattern, rooted at the project root. Returns relative paths.

### `grep`

Searches file contents. Returns matches with paths and line numbers.

### The failure mode specific to these two (D18)

`write` and `edit` are refused when *given* an escaping path. These tools **produce** paths — and a search rooted
inside the project can still **return** a path that resolves outside it, through a symlink it walked into.

So enforcement is on both sides: the search root goes through T7's `Resolve`, **and every returned path is verified to
resolve inside the root before it is reported.** A tool that refuses `../../etc/passwd` as input but happily reports
`escape/passwd` in its results has leaked the same information by the other door.

### Bounded output

Both cap their results, and **report the truncation** — S5's W13 discipline applied to search rather than to a shell.

A silent cap lies about what is there, which is the same reasoning v1's QAU-05 gave for diffs: *"a diff that quietly
omits changes lies about what the step did."* A `grep` reporting 100 of 4,000 matches without saying so leads a model
to conclude a pattern is rare.

Report the count found alongside the count returned, so the model knows the shape of what it did not see.

### Both

- Rooted through T7's `Resolve`; **no path handling of their own** (W18)
- Honour `exec.signal` (W10) — a `grep` over a large tree is exactly the operation a step cancellation needs to stop
- Skip what should be skipped: `.git`, and anything the project's ignore rules exclude. **Say that it was skipped**,
  rather than silently omitting it — an unexplained absence reads as "no matches"
- Failures are tool errors (W6)

## Tests

| Test | Asserts |
| --- | --- |
| `TestBothArePathEnforced` | An absolute or `..` search root is refused in both tools, through `Resolve` |
| `TestNoEscapeThroughResults` | With a symlink inside the root pointing outside it: neither tool **reports** a path resolving outside. **The other door, and the one an input-only check leaves open** (D18) |
| `TestResultsAreBoundedAndTruncationReported` | Both cap, and both report found-versus-returned counts |
| `TestTruncationIsNotSilent` | A search exceeding the cap says so in the result the model receives |
| `TestSkipsAreReported` | `.git` and ignored paths are skipped **and named as skipped**, so an absence is never mistaken for no matches |
| `TestBothHonourSignal` | A cancelled context stops a search over a large tree promptly (W10) |
| `TestGlobPatternSemantics` | The glob syntax is documented and tested; it is **not** the policy matcher's syntax, and conflating them would be a subtle surprise |
| `TestGrepReportsPathsRelativeToRoot` | No absolute path ever reaches the model (W2) |
| `TestNoOwnPathHandling` | Neither file resolves paths outside `Resolve` (W18) |
| `TestEmptyResultsAreDistinctFromErrors` | Zero matches is a successful result, not an error |

`TestNoEscapeThroughResults` is the one that would be missed. The instinct is to enforce paths on input, and these two
tools' outputs are paths.

`TestGlobPatternSemantics` matters because this slice contains **two** pattern matchers — the policy matcher (T2,
where `*` is the only wildcard and everything else is literal) and this one. They are different by design, and
documenting that is cheaper than someone discovering it.
