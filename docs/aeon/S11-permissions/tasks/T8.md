# T8 — `write` and `edit`

## Why this exists

Two tools that share a task (R8) because they share their path handling and their failure modes.

And `edit` carries a cross-slice obligation that nothing else would catch.

## Scope

### `write`

Writes content to a path, resolved through T7. Creates parent directories within the root. Reports bytes written.

Its re-run class is `detectable` (S7's W16) because **the same path with the same content converges** — running it
twice leaves the file as it would have been once.

### `edit` — exact-match, and why it must stay that way (W19, D19, I6)

Replaces an **exact** string with another. If the original string is not present, **it fails loudly**, naming the
string it could not find.

**Not fuzzy. Not nearest-match. Not a no-op.**

This is not a convenience preference. **S7 classified `edit` as `detectable` on re-run precisely because a re-run
finds the original string absent and fails loudly rather than patching twice.** A fuzzy implementation would make that
classification silently wrong — and then crash recovery would re-run an `edit`, match something *near* the original,
and corrupt a file while believing itself safe.

So the test carries a comment recording that dependency (D19). Someone will later be tempted to make `edit` more
forgiving, and the comment is what tells them what else breaks.

**Also refuse an ambiguous match.** If the original string appears more than once, fail and say how many times —
replacing the first occurrence silently is a different kind of wrong answer, and one the model cannot detect.

### Both

- Path-enforced through T7's `Resolve` — **no path handling of their own** (W18)
- Honour `exec.signal` (W10), so S5's `Aborted` and `Timeout` exits are not a lie
- A failure is a **tool error** the model can adapt to, not a step failure (W6)
- No permission check: file tools are governed by the path boundary, `bash` by the policy evaluator

## Tests

| Test | Asserts |
| --- | --- |
| `TestEditFailsLoudlyOnStaleString` | A string not present: an **error result** naming the string. Not a no-op, not a silent success (D19) |
| `TestEditIsNotFuzzy` | A string differing by whitespace, by case, and by one character each **fail**. The near-miss cases are the ones a fuzzy implementation would accept |
| `TestEditRefusesAmbiguousMatch` | A string appearing three times: refused, and the count reported |
| `TestEditRerunClassDependency` | A test whose **comment** records that S7's `detectable` classification depends on exact-match, asserting the failure behaviour that classification assumes (I6) |
| `TestEditReplacesExactlyOnce` | The single-occurrence case, byte-exact, with surrounding content untouched |
| `TestWriteIsPathEnforced` | Absolute, `..` and symlink-escaping paths all refused, through `Resolve` (T7) |
| `TestWriteConverges` | Writing the same content twice leaves the same file — the property behind `detectable` |
| `TestWriteCreatesParentsInsideRoot` | And refuses to create any outside it |
| `TestBothHonourSignal` | A cancelled context stops each mid-operation (W10) |
| `TestNoOwnPathHandling` | Neither file calls `filepath.Abs`, `filepath.Clean` or `os.Open` on tool input (W18) |
| `TestFailuresAreToolErrors` | The step continues in every failure case (W6) |

## Definition of done

- [ ] `edit` exact-match: fails on a stale string, on every near-miss, and on an ambiguous match
- [ ] A test comment records S7's dependency on exact-match
- [ ] Neither tool does its own path handling
- [ ] Both honour `exec.signal`
- [ ] Failures are tool errors, not step failures
