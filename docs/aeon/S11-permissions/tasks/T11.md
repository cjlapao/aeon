**The property, and how it is actually proven.** `todo` is a within-step device (W8): the list lives in the
**toolset instance**, every result re-renders the whole list, and **no row of any table is ever written**. The
proof is a **row count**, not a review — `todo_test.go` runs a scripted client against a real store
(`internal/store` + `internal/database`) and asserts the task table is untouched — which is the only kind of
evidence that survives someone later adding a convenient persistence call. This mattered more after S8 than
before it: there is now a **real task ladder** in the store, and putting model-authored checklists into it would
make a loop's actual progress ambiguous, which is worse than useless because the ladder is what a human reads to
know where things stand.

**Two bounds the spec did not set, and the class of failure they close.** `maxTodoItems = 200` (tool-local,
glob/grep precedent, provenance comment saying it was chosen) and, from the security review, the **SEC-T17-01**
set: a pre-unmarshal `len` gate at 256 KiB, `id` ≤ 256 B and `content` ≤ 4 KiB with **named** refusals, and the
JSON schema mirroring `maxItems` with the mirror itself pinned by a test. The reason is not tidiness: the whole
list renders into **every** result and the transcript **is** the record, so an unbounded model-authored list
inflates the record through the model's own door — the SEC-011 / `grepOne`-OOM class, bound at the boundary.
**SEC-T17-02** landed in the same sitting: each item renders as `Quote(id)` with content single-lined and
backslash-first, and a forge-into-extra-lines test proves the renderer emits exactly items+1 lines, so a list
item cannot fabricate a line of the transcript.

**Pointer semantics where an omission must never destroy the record.** `set` with **omitted** `items` is refused
while an explicit `"items": []` **clears** — the two intentions are different and one nil cannot express both.
A list **with** items is refused, blank `id`/`content` are refused naming the value, and an unknown `action` is
refused naming the value.

**Deviation on labelling, recorded so it does not get "fixed".** `todo` adds **no** trust labelling: its
content is model-authored, arriving in-band inside the assistant turn, with no third-party text to label — so
there was nothing to label and **no fourth wording was written**. The canonical untrusted renderer stays in
`untrusted.go` untouched. The separate fourth-wording cleanup for `webfetch` remains in the **SEC-T16-04**
backlog, which the record pass keeps visible rather than letting it go quiet.

**Harness note for the next person in this package.** The store proof lives in package `tools` as an internal
test importing `internal/runtime` + `internal/store` + `internal/database`. That is legal and does **not** cycle
(`runtime` does not import `tools` — documented at `loop.go:93`). The scripted client and the tool-caller
adapter are small local mirrors because the real ones are unexported elsewhere.

# T11 — `todo`

## Why this exists

W8 made `todo` a **within-step device**: in memory for the step, visible in the transcript, gone afterwards.

**That mattered less before S8.** Now there is a **real task ladder** in the store — `task` rows, `loop_phase` rows,
a status machine — and putting model-authored checklists into it would make a loop's actual progress **ambiguous**.
The ladder is what a human reads to know where things stand, so ambiguity there is worse than useless.

So the confusion this decision prevents is now live rather than hypothetical, which is why W20 restates it as an
invariant with a test that queries the store.

## Scope

```go
// A todo list lives for the duration of one step.
type Todo struct {
    items []Item   // in memory. Never persisted as loop state.
}
```

Operations: add, complete, list. The model manages its own checklist inside a step.

### Never the store (W20, D21, I7)

No `task` row. No `loop_phase` row. No write to any table.

Asserted by **querying the store** after a step that used the tool (C10) — not by inspecting the tool's return value,
which would pass against code that returned a list and also wrote one.

### Always the transcript (O8)

The list and its updates appear in the step's transcript, as tool results.

**A within-step device that leaves no trace is one nobody can review after the fact.** The step's record is where
someone reconstructs what the model was doing, and a checklist that vanished is a gap in that record. So: ephemeral as
*state*, permanent as *record* — which are different things, and the transcript is where the distinction lands.

### Re-run class

`detectable` (S7's W16): re-applying converges, because the list is state the daemon holds for the step and a repeated
add of the same item is idempotent.

### Not the task ladder

`todo` has no relationship to S8's `iterate: tasks` or to the status machine. A test asserts a step's `todo` items do
not appear in `aeon loop show`, because that is where someone would first notice the confusion.

## Tests

| Test | Asserts |
| --- | --- |
| `TestTodoNeverReachesTheStore` | After a step using `todo`: `select count(*) from task` is unchanged, `loop_phase` is unchanged, and no table gained a row. **Queried from the store** (D21, C10) |
| `TestTodoAppearsInTheTranscript` | The list and each update are in the step's `step_message` rows (O8) |
| `TestTodoDoesNotAppearInLoopShow` | `aeon loop show --json` has no trace of the items — the place someone would notice the ladder being polluted |
| `TestTodoIsGoneAfterTheStep` | A second step in the same loop starts with an empty list |
| `TestTodoSurvivesSuspendAndResume` | Within **one** step, a suspend and resume (S6) preserves the list — it is step-scoped, and a step that suspends is still the same step |
| `TestRepeatedAddIsIdempotent` | The property behind `detectable` |
| `TestTodoIsBoundedAndTruncationReported` | A model adding a thousand items is capped, and told |

`TestTodoSurvivesSuspendAndResume` is the interesting one. "In memory for the step" and "a step can exit its process
and resume cold" (P2) are in tension: the list must be part of what a step carries across a suspension, which means it
is persisted *somewhere* — in the step's own record, not as loop state. Getting that distinction right is the whole
task.

## Definition of done

- [ ] Add, complete, list; step-scoped
- [ ] No row in any store table, asserted by querying the store
- [ ] The list and its updates are in the transcript
- [ ] Nothing appears in `aeon loop show`
- [ ] Gone by the next step; **preserved across a suspend and resume within one step**
- [ ] Repeated add is idempotent
- [ ] Bounded, with truncation reported
- [ ] `make test`, `make lint` green
