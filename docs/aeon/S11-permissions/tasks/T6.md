### T10 — the spec contradicted itself, and the pinned rule won

**Recorded because a contradiction between two specs is exactly what a Notes block is for.** The loop task file
(`.projects/loops/aeon-s11-permissions/tasks/T10.md`) pinned the one-question-selection rule in its step 2 and
then gave a fallback *example* in step 4 that contradicted it — the example had a `tool_access` deny for `bash`
denying `Decide{Tool: "bash", Command: "ls"}`, which the pinned rule cannot produce: once a bash block carries a
command, the request is a **`command_access`** request, and the engine's type filter makes a `tool_access` rule
inert against it. **The verifier and the code reviewer adjudicated in favour of the pinned rule** (the rule is
the requirement; an example is an illustration), and the shipped code follows the rule:
`internal/daemon/policy_gate.go`'s `gateQuestion` —

```go
if preq.Tool == "bash" && req.Command != "" {
    preq.Type = policy.CommandAccess
    preq.Command = req.Command
}
```

— is the **one** expression of it, shared by `Decide` and by the spawn-key read (T13 extracted it precisely so
the two could not drift). `TestPolicyGateFallsBackToTheToolQuestion` pins the empty-command arm.
`permissionAskBody` renders rule + agent + command and closes with the verdict sentence **verbatim**; the
command reaching the question is the runtime's own parse of the block, never the gate's echo (SEC-051 — in round
1 the echo write was dead code, and the surviving channel is the explicit `command` argument).

**What filling the Command arm activated, and the regression it exposed (T12's find, said plainly).** Wiring
`PolicyGateRequest.Command` switched on T11's committed selection rule, so a command-carrying bash block became
governed by **command** rules rather than **tool** rules. Two S10-era recovery tests
(`TestRecoveredStepIsJudgedByItsFrozenSetNotTodaysStore`, `TestZeroPolicyStepRecoveryStaysFrozenNotPreS10`) had
seeded `tool_access`-only sets for a touch-marker block and broke **deterministically** — *not* race-dependent,
which corrects an earlier `-race` attribution in this loop's records. The fix moved their seeds to the S11 world
without weakening a single assertion (frozen deny, live drift, disagreement naming, hash pin — all unchanged, now
driven by `all-agents` `command_access` rules), and made the DEF-042 overnight-mutation plant a **command**
allow, because a tool allow had quietly become toothless for the pending call.

### T11 — three states, and a bool that is not one

`loop.attended` is read **by name**, never collapsed into `Loop`'s struct — the honest three-state value
(`1` attended · `0` unattended · `NULL` never-declared) has no home as a bool, and the comment in the store says
so. `OperatorPresentFor` is the one adapter and its collapse is fail-closed in **every** direction: declared
attended ⇒ true; declared unattended ⇒ false; **never declared ⇒ false** ("nobody said" is not "somebody is
here", D2/P31); **any read failure ⇒ false**, spoken through the logger — a step that cannot check whether
anyone is watching must not suspend on the assumption that someone is. The CLI flag is `--attended` and
**defaults true** (a human typing the verb at a terminal *is* attended); `--attended=false` is the deliberate
statement that nobody is. The wire field is optional and its **absence** is never-declared, not attended: the
daemon never infers or defaults. `CreateLoop` persists it on both creation paths, and a stored value outside
`0/1/NULL` is refused **by name**, never guessed into a declared state.

**Measured on the walk (loop T20):** the ad-hoc `aeon step` verb files its step under the `step` loop, which
never declares attendedness — `select slug, attended from loop` shows `step` with `attended` **NULL** — and an
`ask` there denies immediately with **no question row**. That is this design working, and it is why the demo
walks the answer path on a `loop start` loop instead.

### T12 — suspension is exiting, and the siblings are closed honestly

`st.pendingPermission` is the channel out of `runTool` (the signature stays `(block, error)`), consumed
immediately by `RunLoop` **and** by `RecoverStep` Case C, and `suspendWith` is the **single** suspend
constructor — `TestOnlyTheSharedLoopProducesSuspended` pins one assignment site so a third path cannot appear.
An ask suspends exactly like the `question` tool (P2: no process), and every tool_use **after** the blocked one,
plus the `question` blocks, closes **at suspension** via `closeUnrunTool`: an `IsError` result naming the
blocked id and saying *"not made and not approved — re-issue it after the answer if still wanted"*. Leaving them
silent is legal only while that assistant turn stays final, and the answer appends a new turn, so a silent
sibling would read as a lost tool result forever. **Case C chose honest closure over re-running the remaining
`CallPlan`s**, because dispatching behind a verdict nobody has given is what G12 forbids and a denied ask would
have left pre-committed work nobody approved.

**Answered, not approved.** `ResumeStep` puts the human's answer in as the blocked call's **tool result** —
which is what `hasPendingQuestion`'s comment says and what the walk measured. The options are `[approve deny]`,
pinned by a `DeepEqual` on both the loop side and the recovery side. **Nothing in this path converts an approval
into an allow** — the gate decides only from the frozen set (T21's `PoliciesFrozen` is what keeps a mid-step
`allow` from widening it), so the model re-issues and the `ask` asks again. See finding **F-21** in
`docs/aeon/DEMO.md` §S11: the slice DEMO predicted the command running, and the walked record says what happens
instead. The unattended arm denies **at once** with the verdict sentence verbatim and creates **no question
row** (the adapter creates rows only for suspended results, so the table is empty by construction) — but note
finding **F-10**: the sentence says *asked*, not *"resolved to deny because nobody was there"*, which the slice
DEMO §3 predicted. `--unattended` does not exist; the flag is `--attended=false` (F-7).

# T6 — Resolving `ask` — attendedness, and what the question carries

## Why this exists

The evaluator returns `ask`; the **caller** resolves it (G6). This is that caller, and it has two problems the
superseded design could not have had.

## Scope

### What "unattended" means now (G14, D17)

G7 resolves `ask` to **deny** when nobody can answer, and that used to be a property of a CLI invocation. The daemon
now owns loop execution (P29) and a runner advances loops whether or not anyone is watching.

**Inferring attendedness from whether a client is subscribed is wrong.** A client disconnecting mid-loop would flip
the policy and reconnecting would flip it back — **the same command allowed or denied depending on whether someone
happened to have a window open.** A guard whose verdict depends on that is not reproducible, and reproducibility is
the one property a guard cannot trade away.

So attendedness is **declared at loop start and pinned**, alongside the blueprint (L6's reasoning generalising):

```
aeon loop start --unattended --blueprint <bp> "<prompt>"
```

Default is **attended**, because a person running a command is present by definition. `--unattended` is the deliberate
act, and its help says what it does: an `ask` becomes a `deny`.

A single `aeon step` is attended if a terminal is attached and unattended otherwise — but that inference is made
**once, at start**, and pinned. Same rule: decided once, never re-evaluated.

### Attended — suspend, and say what is being decided (G18, D15)

The `ask` becomes a `question` row, and S6's mechanism carries it. Its payload:

```
prompt:  Run this command?
command: git push origin feature/x
rule:    git push*        (ask)
agent:   github-steward
answers: [approve, deny]
```

**The rule and the agent are not decoration.** v1's QAU-01 put it exactly: *"A prompt that says only 'approve `git
push origin main`?' is a FAIL — the user needs to know they are overriding `git push*`, which is what tells them
whether the rule is wrong or the command is."* Those two situations call for opposite actions, and the prompt is the
only place to tell them apart.

**This does not violate S9's U14.** U14 forbids distinguishing the **mechanism** — a human should not have to know
whether a step question, a gate, or a permission ask is the thing asking. It does not license withholding **what is
being decided**. Same affordance, richer payload.

**Confirm Q3**: a permission ask **is** tied to a `tool_use_id` (the `bash` call), unlike a gate which has none. Both
shapes must exist in the `question` table.

### Unattended — deny at once, with no question (G7, D16)

Not a question nobody answers — a **denial, decided immediately**, naming the rule:

```
bash: denied by rule 'git push*' (github-steward) — ask resolved to deny (loop is unattended)
```

**No `question` row is created.** A question in an unattended loop is a row that will never be answered, and it would
make the loop look like it is waiting for someone when it is not.

### A second identical ask is a new question (O6)

Approving `git push` once does **not** approve it forever. Each `ask` is its own question, answered once (S6).

Caching the answer is the obvious optimisation and it is wrong: the second `git push` may be to a different remote, at
a different point in the step, after the first one already did what the human intended. State this in the code and
assert it.

### An unparseable policy (O5)

A handler whose policy will not parse **cannot run `bash` at all** — a loud refusal naming the file, not a silent
fallback to deny-everything.

G4 says an empty policy denies everything, and an unparseable one must not be **silently equivalent** to it: one is a
deliberate choice someone made, the other is a broken file someone needs to fix. Rendering them the same way loses the
only information that distinguishes them.
