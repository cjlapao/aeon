# T3 — Git plumbing — worktree mode, staging, and the completeness assertion

## Notes — built tests-first 2026-10-25

**The spec's literal "`git status --porcelain` EMPTY" is the nothing-to-commit state, not the pre-commit
state** — after `add -A` a about-to-be-committed tree is full of STAGED porcelain lines, and an assertion
that demanded literal emptiness would make every commit self-refuse (the first red here proved it). The
implemented assertion keeps the spec's exact plain command and asserts the property EMPTY expresses: no
untracked lines and no unstaged column (Y not blank) after staging — the hand-pick shape of the recorded
incident. Nothing-to-commit is then exactly the empty listing (TestNothingToCommitIsClean pins both
halves).

**A refusal must name what it refused**: plain porcelain collapses an untracked DIRECTORY to one line, so
the first version's refusal said "?? deep/" and could not name `left-behind.txt` (second red). The
assertion runs the spec's plain command; when it trips, a second `-uall` listing names the individual
files. Naming is best-effort; the EMPTY check itself is the plain command, unchanged.

**Two more grep-test lessons, both self-inflicted and both caught by the tests themselves**: banned
literals written plainly in the test file indict it (concatenation, T1's lesson re-learned), and the Q3
grep was initially over-broad — banning the artefacts-directory NAME repo-wide collides with legitimate
historical references in store/handler comments. L24 retired the EXCLUSION, not the word: the honest
checks are that `internal/git` contains no `:!` pathspec magic and no `add -A --` command shape, plus
the store-prefix assertion (XDG_STATE_HOME dir provably outside the repo). The only things Aeon writes
INTO a repository are `produces:` artefacts, which belong in the commit — Q3 answered: nothing must be
excluded.

**O8 is the test that fails the obvious implementation**: the fake git reports push success while
`ls-remote` shows the ref sitting still, and Push fails with push-unverified naming BOTH shas it
compared. Exit-code trust would have shipped a PR-against-a-phantom-ref pipeline.

**Discriminated results (DB19), five kinds proven**: missing ref is (false, nil) absence; unmerged paths
are conflict; an unreachable remote is transport; a lying push is push-unverified; create-attempted-in-
worktree-mode is refused (D6). The worktree promises are asserted on the COMMAND LOG — what was never
attempted — including no force flags on the local-only first push.

**Q2 answered here**: `paseo.json` at the root selects `existing-worktree` (mode selection wires at T4);
the mode checks existence locally AND remotely, creates nothing, deletes nothing, and when the branch is
local-only pushes it plain `-u` and verifies (O8) before a PR could target a ref nobody can fetch.

Counts dated 2026-10-25: internal/git **9** (5 plumbing + 4 worktree), all against real git where the
claim is about git semantics (squash-ancestry, stray files, nothing-to-commit) and the recording fake
where the claim is about the command log.

## Why this exists

Two of the three constraints a naive implementation breaks live here, and both come from **recorded incidents**.

It precedes the git actions (T4) because these are the rules those actions must obey — building the actions first means
retrofitting them.

## Scope

### The completeness assertion (L24, D3)

Stage everything, then assert the tree is clean:

```
git add -A
git status --porcelain        →  must be EMPTY
```

**Never hand-pick.** The recorded incident is hand-picked files left behind and then **dropped by the squash merge** —
work that appeared committed, passed review, and vanished. Code has no excuse for hand-picking, so this is an assertion
rather than advice.

**And it has no exclusion** (L24). v1 staged `git add -A -- ':!.projects/loops'` because the loop's artefacts lived
untracked inside the repository. Aeon's store lives at `$XDG_STATE_HOME/aeon/state.db`, **outside the working tree**,
and the only things Aeon writes into a repository are `produces:` artefacts — which belong in the commit.

**Answer Q3 before implementing**: does Aeon write anything into a working repository that must not be committed? **L24
assumes not.** Verify it — an exclusion carried forward out of habit would hide exactly the class of leftover the
assertion exists to catch.

### `existing-worktree` mode (D6)

**Answer Q2**: is `paseo.json` present at the root, and what exactly does the mode change?

In that mode the feature branch is a **pre-existing worktree branch**:

- **Never created.** A `createBranch` that always creates breaks every worktree loop.
- **Never deleted.** A cleanup that deletes it **destroys a workspace Paseo owns** — a recorded incident.
- **Usually local-only**, so it must be pushed before the first task PR, or the PR has no base to target.

### No force-push, no deletion (N8, N9, I5)

**Not as an action, not as a fallback, not behind a flag.**

Force-push is the one git operation whose damage is unbounded and unrecoverable from the loop's side: it destroys
history on a remote that other people may have pulled. There is no failure this slice can encounter whose correct
recovery is a force-push, so the capability is simply absent.

Branch and tag deletion is absent for the same reason plus the recorded Paseo incident.

Asserted by grep over the whole package, not by convention.

### Verify the push landed (O8)

`git push` reporting success is not proof. **Re-read the remote ref** and confirm it points where expected.

A push that appears to succeed and did not is indistinguishable from success by exit code alone — and everything
downstream assumes the commit is fetchable, so the failure surfaces as a PR against a ref nobody can find.

### The rest

Branch existence checks (`show-ref --verify` local, `rev-parse --verify origin/…` remote), `merge-base --is-ancestor`,
and reading the current branch. Thin wrappers, each returning a discriminated result rather than an exit code (S4's DB19).
