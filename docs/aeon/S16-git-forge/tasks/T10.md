# T10 — The registry, and retiring S8's refusal

## Why this exists

The serialization point. Every action exists; this makes them reachable, retires the refusal S8 left behind, and flips
`dev-loop.yaml`'s nine `unverifiable` diagnostics to real checks.

## Scope

### Eight actions plus `audit`, and no `render` (L25, D13)

```
git.createBranch    local          check-then-act
git.commitAndPush   outward        check-then-act
git.mergeBranch     local          check-then-act
forge.openIssue     outward        check-then-act
forge.openPR        outward        check-then-act
forge.postReview    outward        receipt-first
forge.merge         irreversible   check-then-act
forge.closeIssue    outward        check-then-act
audit               local          naturally idempotent
```

**`render` is absent.** v1 had one, writing `loop.md`, `events.jsonl` and `memory.md`. S4 always said *"the mirror is
disposable; the store is the source of truth"*, and S9's app plus `aeon loop show` cover everyone who would have read it.
S4's stale deferral of it to "a separate module (S11)" is already corrected (I8) — **do not re-edit that**.

Each entry carries an args schema, its **effect class** (T2), its **idempotency strategy**, and returns **evidence** —
issue number, PR number, SHA — which lands in state and the transcript.

### The registry is closed, and that is asserted (D14, O2)

Not merely true: **a test proving no blueprint field, handler field, or config value can introduce an action.**

S8's I5 did exactly this for tools, and the same shape applies. It matters more here, because T2's effect classes are
sufficient *only because* the set they govern is known — an open registry would make them decoration.

### S8's refusal is retired (D16)

S8's `execute` returned `blocked` with `Kind: "unimplemented-action"` and `Slice: "S16"`. That branch goes, and **a test
asserts no code path still returns it** — a refusal left behind for one action would be found by a user, not a test.

The `BlockedReason` kind itself stays: S17 may need it for something else, and removing a kind from a structured type is
a protocol change.

### Validation flips (D15)

S11's T5 made an unknown `action:` `unverifiable` with `Slice: "S16"`. That becomes a **real check**: the registry
exists, so an unknown action is now **`invalid`**.

And `dev-loop.yaml`:

| Before | After |
| --- | --- |
| 9 `unverifiable` — all code actions | **0** |
| `--strict` fails | **`--strict` passes, for the first time** |

**S8's T12 committed the expected diagnostic set exactly so this change is deliberate and visible.** Update the fixture,
and **the diff is the evidence the slice did something** — the same pattern S13's T10 used when resolver validation
became real.

### `aeon action list` and `aeon action check`

`list` prints the table above, with class and strategy. `check` prints one action's class and the verdict it produces —
the demo's §3 uses it to compare both governance routes side by side.

## Tests

| Test | Asserts |
| --- | --- |
| `TestEightActionsNoRender` | Eight plus `audit`; **`render` absent**; each with a class, a strategy and an args schema (D13, L25) |
| `TestRegistryIsClosedAsserted` | No blueprint field, handler field or config value can add an action — asserted reflectively, like S8's tool check (D14, O2, E2) |
| `TestNoRefusalPathRemains` | A grep plus a test: nothing returns `unimplemented-action` for a registered action (D16) |
| `TestUnknownActionIsNowInvalid` | Not `unverifiable` — the registry exists (D15) |
| `TestDevLoopValidatesStrict` | Zero `unverifiable`, zero `invalid`, and `--strict` **passes** (D15) |
| `TestExpectedDiagnosticFixtureUpdated` | The committed set changed, and the diff is asserted — the evidence (D15, C10) |
| `TestEveryActionReturnsEvidence` | Each returns its numbers or SHAs, and they reach state and the transcript (Q7) |
| `TestStrategiesAreEnumerated` | Eight check-then-act, one receipt-first, one naturally idempotent — **the exception is asserted by count**, so a second receipt-first action fails |
| `TestActionListAndCheck` | Both CLI surfaces |

`TestStrategiesAreEnumerated` asserting the receipt-first count is **exactly one** is the guard against the mistake the
superseded design warned of: *"a plan that applies one strategy uniformly will get it wrong in exactly one place."* A
second receipt-first action means somebody generalised the exception.
