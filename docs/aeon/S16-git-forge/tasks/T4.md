# T4 — The three git actions

## Notes — built tests-first 2026-10-25

**The tests caught the branch-inheritance bug class during development, exactly as designed**: the first
green-ish runs committed on `main` (a `branch X` never checks out), and the action happily pushed a ref
that did not match HEAD — O8's verification is what made the wrongness VISIBLE (push-unverified naming
both shas) rather than silent. The fix is structural, not cosmetic: `CommitAndPush` refuses unless the
task branch it belongs to is the branch that is CHECKED OUT (refusal names both), and `CreateBranch`
arrives on a task branch it creates or reuses — while the FEATURE branch is never checked out by this
action, because yanking a shared workspace onto it is the sibling of the deletion incident. L3's split
gets its second half here: constructing names in code is one door; refusing to work where the identity
does not stand is the other.

**`TestCompletenessAssertionApplies` was reframed after the first version tested the wrong thing.** Its
first shape demanded that a hand-picked stray FAIL the action — but the action stages `add -A` first, so
the correct, demanded outcome is the opposite: the leftover is CAPTURED and rides into the commit
(proven against real git with `git show --name-only`). The assertion's real job is the BACKSTOP: if
staging was ever bypassed or raced, loose work at assertion time fails the commit BEFORE it can happen —
proven with a fake whose tree shows `?? race-left-behind.go` after staging, with the command log asserted
never to reach `commit`. Both shapes are in the one test now; the reframing is the Notes-worthy finding.

**`nothing to commit` answers SUCCESS with `NothingToCommit: true`** (D2) — and on that path the action
first checks the remote: a clean tree with the remote current skips the push entirely (check-then-act
for an already-current ref, verified by the second run of the twice-is-a-no-op test showing
`Pushed: false` and HEAD unmoved on git itself).

**Twice-is-a-no-op is three separate subtests with independent logs**, never one loop (D1/O6/C2):
createBranch asserts no `branch` command in the second run's segment; commitAndPush asserts HEAD
unchanged on real git; mergeBranch asserts no `merge`/`checkout` touched an already-ancestor branch.

**`TestCommitIsIdempotentOnlyWithAHeadCheck` demonstrates the mechanism before pinning the guard**: a
forced `git commit --allow-empty -m "same message"` provably creates a NEW SHA (same message ≠ same
commit), then the action's own second run is shown unable to do it — the check is tree and head, never
message.

**Reflection, not convention, for L3**: each of the three actions takes `BranchNames` exactly once, and
bare strings are capped at dir+message — a branch name has nowhere to be typed. `NewBranchNames`
validates the identity slugs (the "feat/ure"/"a b/c" spelling attempts are refused at the door).

## Why this exists

`git.createBranch`, `git.commitAndPush`, `git.mergeBranch` — all three **check-then-act**, each with a specific check
that the superseded design names exactly.

## Scope

| Action | Class | The check |
| --- | --- | --- |
| `git.createBranch` | `local` | `show-ref --verify --quiet refs/heads/{branch}` local, `rev-parse --verify --quiet origin/{branch}` remote. Absent → create; present → **reuse** |
| `git.commitAndPush` | **`outward`** | `git status --porcelain` **empty ⇒ nothing to commit, which is success**. Pushing an already-current ref is a git no-op |
| `git.mergeBranch` | `local` | `merge-base --is-ancestor {feature} {base}` exits 0 ⇒ already merged |

### `nothing to commit` is a success (D2)

An empty `git status` means the work is already in. **A naive implementation treats it as an error** and fails a step
that has nothing left to do — which then routes as a `reject`, sends the handler back to redo work already done, and
burns a redo round.

This is the single most likely place for an idempotency bug to present as a loop that cannot finish.

### A commit is idempotent by content **only if you check the head first**

Worth stating because it is counter-intuitive: a second commit carrying the same message is **not** the same thing as no
commit. It is a new SHA, a new entry in history, and a diff against the previous one that is empty.

So the check is on the tree's cleanliness (T3's assertion) and the branch head, not on the message.

### Identifiers come from code (L3, I3)

Branch names are constructed by code from the loop and task identity — never taken from a handoff field or tool input.
That is the split that removes the identifier bug class, **including the recorded branch-inheritance bug** where a model
re-derived a branch name and got it subtly wrong.

Asserted: no action signature accepts a branch name from model output.

### Governance

`git.commitAndPush` is **`outward`** and therefore asks (T2). `createBranch` and `mergeBranch` are `local` and do not.

That split is worth noticing: creating a local branch affects nobody, and pushing affects everybody who fetches.
