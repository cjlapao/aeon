## Why this exists

**`forge.postReview` is the only one of the eight needing receipts**, and that is worth stating because **a plan applying
one strategy uniformly gets it wrong in exactly one place.**

And `forge.closeIssue` exists because of a GitHub behaviour that surprises everyone once.

## Scope

### `forge.postReview` — receipt-first (D7)

**A review has no natural business key.** Same body, same verdict, two reviews, and nothing distinguishes them. Every
other action has one — an issue's title-plus-label, a PR's `head` ref, a branch's name, a commit's tree — which is why
they are check-then-act and this one cannot be.

So:

1. Write an **intent** keyed `(pr, step, attempt)`.
2. Post.
3. Record the returned review id.

On resume, **an intent with no id means go and look**: list reviews and reconcile **by id, never by body text** (D7).

Two reviews with identical bodies are two reviews. Matching on text would either miss one or merge two, and both are
wrong in a way nobody can see afterwards.

**Answer Q6 first**: does S7's receipt table generalise to an action intent, or does this need its own? **Two tables
holding intents would be two recovery paths**, and S7's recovery already knows how to read one.

### Bounded reconciliation (O3)

Listing every review on a PR with hundreds is a slow path at exactly the wrong moment — during recovery, when something
has already gone wrong.

So reconcile **within the attempt's window**, and if the intent cannot be resolved, **fail naming it** rather than
posting again. An unresolvable intent is the honest unknown, and S7 established that failing beats guessing when an
effect may or may not have happened.

### `forge.closeIssue` — and why it has to exist (D4)

**`Closes #n` does not fire.** GitHub's keyword auto-closes only on a merge into the repository's **default** branch.
Task PRs target the **feature** branch, so the keyword never fires — a PR body containing `Closes #14` is a comforting
no-op.

So `forge.closeIssue` is the only thing that closes a task issue when its work lands, and it **must read the issue
back** to confirm.

**A silently-failed close leaves the issue open with nothing downstream noticing** — the loop believes the task is done
and the tracker disagrees, indefinitely, until somebody wonders why a finished feature has eight open issues.

Check-then-act: read the issue; `state == "closed"` ⇒ done.
