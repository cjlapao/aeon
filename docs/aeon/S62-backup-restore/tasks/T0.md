### 2. The three technical bets — answered with measurements

**Bet 1 — online backup API. WORKS, and is the mechanism (OD1 decided: BACKUP API).**
mattn v1.14.52 ships `(*SQLiteConn).Backup(dest string, srcConn *SQLiteConn, src string) (*SQLiteBackup, error)`
with `Step(p int) (bool, error)`, `Remaining()`, `PageCount()`, `Finish()` (`backup.go`).
**Trap measured: the `*SQLiteConn` from `(*sql.Conn).Raw` is valid only INSIDE the callback** — using it
after `Raw` returns segfaults. The whole `init → Step(-1) → Finish` must nest inside BOTH connections'
`Raw` callbacks (the driver's own backup test uses exactly this shape). T2's `SnapshotTo` follows it.

Numbers, 76.6 MiB fixture (200 pair rows + 16,384 × 4 KiB bulk + vec0(8-dim, 32) + FTS5(32)):
- reader-connection backup `Step(-1)`: **271 ms** idle (18,724 pages); destination becomes **one file**
  (`snap.db`, no sidecar) after `PRAGMA journal_mode=DELETE` on the dest conn and close.
- copy verified read-only (`?mode=ro&_foreign_keys=1`): `integrity_check` = ok; row counts identical
  (pair 200 / bulk 16384 / vec 32 / fts 32); `vec_version()` = **v0.1.6 on the copy** — vec0 shadow tables
  arrive **verbatim**; FTS5 `MATCH 'zebra quantum'` = 32 hits — the FTS5 index is intact.
- **VACUUM INTO** on the same store: 309 ms, 76,677,120 bytes (API: 76,693,504) — equivalent speed, but it
  runs on the **writer** connection (blocks writes for its duration, no cancel). The API runs on a reader,
  is ctx-cancellable, and is what T2's "zero writer-pool use" requires. **OD1: online backup API.**

**Bet 2 — concurrency (T0 §1.4).** One writer hammering paired `BEGIN IMMEDIATE` inserts while a
reader-connection backup runs on the 76.6 MiB fixture:
- backup: 18,726 pages in **335 ms** (+23 % over idle); read snapshot held for that duration (~0.3 s).
- WAL: **flat** (19,256,912 → 19,256,912 bytes) — no WAL growth, checkpointing not blocked.
- writer latency over 3,639 writes during the backup: **p50 41 µs, p95 92 µs, max 7.7 ms** — zero
  busy-timeout stalls. The writer never waited on the backup.

**Bet 3 — daemon-down proofs (T0 §1.5).** Two separate processes against one WAL database
(scratch `probe.go` under `aeon/.tmp/scratch-s62/`):
- process A holds an open read transaction (even idle between statements — a WAL read snapshot is held
  until COMMIT/ROLLBACK).
- process B: `PRAGMA locking_mode=EXCLUSIVE` then `BEGIN EXCLUSIVE` → **fails after the full
  `_busy_timeout` (1.51 s at 1500 ms) with `database is locked`** (SQLITE_BUSY family).
- same attempt with no holder → **succeeds**.
So T7's `LockExclusive` (EXCLUSIVE, pre-swap window only) is a real gate, and `Probe`'s "daemon down ⇒
proceed" must be the socket check, not the lock.

**OD7 (compression) — revised on measurement: no compression.** The backup API copies pages 1:1; the
artifact is 76.7 MiB for a 76.6 MiB source (the store is BLOB-heavy — bulk payloads, archive content in
`loop_archive_file.content` — and incompressible in practice). VACUUM INTO gives the same size. A codec
buys nothing measurable and adds a decompression step to every restore/verify; T4 ships the single
uncompressed file.
