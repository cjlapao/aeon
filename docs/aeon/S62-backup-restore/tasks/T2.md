# T2 · The store's half: online snapshot, file checks, row counts

**Prefix:** BK · **Rules:** BK3, BK5, F10 (I2) · **Depends on:** T1. Parallel-safe with T3.

## Goal

Everything that needs SQL or the driver lives in `internal/store` (I2): a consistent **online snapshot** of the live
database into a file, and read-only **checks on a database file** (integrity, foreign keys, fingerprint, row counts, vec and
FTS5 availability). `internal/backup` (T4) builds the container, naming and retention on top and contains no SQL.

## Files to create / modify

- `aeon/internal/store/backup.go` — **new**:
  - `func (s *Store) SnapshotTo(ctx context.Context, destPath string) (SnapshotInfo, error)` — takes a dedicated connection
    from the **reader** pool (`s.r.Conn(ctx)`), opens the destination file with the **same driver path**
    (`sql.Open(database.DriverName, "file:"+dest+"?_foreign_keys=1")` after `database.RegisterExtensions()`), obtains both
    `*sqlite3.SQLiteConn`s with `(*sql.Conn).Raw`, runs `Backup("main", destConn, "main")` and `Step(-1)` then `Finish()`,
    honouring `ctx` (a cancel between the call and completion removes the destination file and returns `ctx.Err()`); then,
    on the destination only, `PRAGMA journal_mode=DELETE` and close — the artefact is **one file** (BK3.2). Refuses to write
    over an existing file. Never touches the writer pool (DB15/O6).
  - `type SnapshotInfo struct{ Bytes int64; Duration time.Duration; PagesCopied int }` (counts only).
  - `func CheckFile(ctx context.Context, path string) (FileReport, error)` — opens `path` **read-only**
    (`mode=ro`, `immutable=0`, own connection, no migrations, no WAL creation: `?mode=ro&_journal_mode=` untouched — **T0
    records the exact DSN that does not create `-wal`/`-shm`**) and returns `FileReport{IntegrityOK bool; IntegrityDetail
    []string (≤ 20 lines); ForeignKeyViolations int; Fingerprint Fingerprint; Tables map[string]int64 (row counts);
    Applied []string (ledger names); VecVersion string; FTSUsable bool; JournalMode string}`. Uses `PRAGMA integrity_check`
    (not `quick_check`; the report says which), `PRAGMA foreign_key_check`, the existing `fingerprint(db)` (`fingerprint.go`),
    `SELECT count(*)` per table from `sqlite_master` (identifiers read from `sqlite_master`, quoted — never from a caller),
    `select vec_version()`, and a trivial `retrieval_chunk_fts MATCH` probe when the table exists.
  - `func (s *Store) AppliedNamesAndPending() (applied []string, pending []Migration, empty bool, err error)` — the T0 F4
    predicate: `empty` is true when there is **no ledger or no applied row**, and the call **creates nothing**.
  - `func KnownMigrationNames() map[string]bool` — from `Migrations()`, for the newer-schema check.
- `aeon/internal/store/store.go` — no change expected; `Info` is untouched (T9 adds facts through a new accessor).

## Behaviour (each a test)

1. **Consistent under writes.** A writer goroutine commits paired rows (`A(i)` and `B(i)` in one transaction; also a
   running-sum row updated with each) as fast as it can while `SnapshotTo` runs; the snapshot satisfies the invariants
   (every `A` has its `B`; the sum equals the counter in the same snapshot) and `integrity_check` is `ok`.
2. **Vectors and FTS arrive verbatim.** A store with a populated `vec0` table (created through the real on-demand path) and
   `retrieval_chunk_fts` rows: the snapshot's `vec_version()` answers, a nearest-neighbour query returns the same ids, an
   FTS5 `MATCH` returns the same rows, and per-table row counts equal the source's counts **at the snapshot instant**
   (taken from a quiesced run).
3. **One file.** After `SnapshotTo` returns, the destination directory contains exactly the destination file — no `-wal`,
   no `-shm`, no journal; its header journal mode is `delete`.
4. **Cancellation.** Cancel the context mid-copy (a large fixture with a slow step injected through a test hook): the
   destination does not exist afterwards, the read transaction is released (a writer's `wal_checkpoint(PASSIVE)` can complete),
   and the error is `context.Canceled`.
5. **No overwrite; no writer use.** Existing destination ⇒ refused. A test hook counts connections taken from `s.w`
   during `SnapshotTo` and asserts **zero**.
6. **`CheckFile` is read-only.** Hash the file before/after: identical; no `-wal`/`-shm` appears next to it; a corrupted copy
   (flip bytes in the middle of a table page) ⇒ `IntegrityOK=false` with detail; a dangling FK row ⇒ `ForeignKeyViolations>0`.
7. **The empty-store predicate** (F4) on the five cases T0 listed, creating nothing (directory listing before == after).
8. **Fingerprint equality**: a snapshot's fingerprint `Equal`s the source's; a store with one extra column does not.
9. **I2 holds:** `TestNoSQLLivesOutsideTheStore` stays green; the new file is the only place the driver's backup types are
   imported (a grep test: `mattn/go-sqlite3` is imported by `internal/database` and `internal/store` only).

## Tests

| Test | Asserts | Fails when |
| --- | --- | --- |
| `TestSnapshotIsConsistentUnderConcurrentWrites` | paired-insert and sum invariants hold in the copy | the copy mixes two instants |
| `TestSnapshotCarriesVectorAndFTSData` | vec/FTS queries and counts equal | virtual-table data lost or rebuilt wrongly |
| `TestSnapshotIsOneFile` | no sidecars, journal `delete` | a stale WAL could be inherited |
| `TestSnapshotCancelLeavesNothing` | no file, read txn released | a partial is left or the WAL is pinned |
| `TestSnapshotNeverUsesTheWriter` | zero writer connections | backup queues behind writes |
| `TestSnapshotRefusesToOverwrite` | existing dest refused | data destroyed |
| `TestCheckFileIsReadOnly` / `…DetectsCorruption` / `…DetectsFKViolations` | as above | verification can lie or mutate |
| `TestEmptyStorePredicateCreatesNothing` | five cases, listing unchanged | the hook would create the ledger |
| `TestKnownMigrationNames` | equals `Migrations()` names | newer-schema check wrong |
| `TestDriverImportedOnlyByDatabaseAndStore` | grep walk, ≥ 30 files | a second driver user |
| T1 goldens | unchanged | accidental behaviour change |

## Definition of done

- [ ] Snapshot consistent, vector/FTS-safe, single-file, cancellable, writer-free; `CheckFile` read-only and truthful.
- [ ] The empty-store predicate creates nothing. I2 and the driver-import grep green.

## Do NOT

- Do not run the snapshot on the writer connection. Do not use `cp`, `VACUUM INTO` or a checkpoint as the primary path (the
  fallback is switched only if T0's measurement said so, recorded). Do not let any identifier come from a caller. Do not edit
  an existing store test body.

### What exists

- `aeon/internal/store/backup.go` — the four capabilities, exactly as specced:

    (T0's crash proof); dest claimed with `O_EXCL` at 0600 (an existing dest is refused, named); on ANY failure —

    `Applied`), not an error.
  - `AppliedNamesAndPending()` — the F4 predicate, both probes reads; no-ledger or zero-applied ⇒ empty + all

### Findings the spec could not know

- **F-T2-1 (a spec contradiction, resolved by the guard's own convention): the DB10 guard had to gain a named
  exception.** `TestOnlyOpenGoTouchesTheFilesystem` (open_test.go) asserts no file outside `open.go` touches the
  filesystem, but T2's own spec places `SnapshotTo` in `internal/store/backup.go`, where the snapshot file is by
  definition written. The guard already carries one named exception (store.go's `os.Stat`), so the edit keeps the
  convention: `backup.go` is banned from `os.Create`, `os.WriteFile`, `os.Rename` (arbitrary bytes and renames
  stay refused for it) and allowed the three calls the artefact needs (`os.MkdirAll`, `os.OpenFile`-O_EXCL,
  `os.Remove`-on-failure). Recorded here per §4a because it edits an existing store test's guard list, which
  T2's Do NOT nominally forbids — the Do NOT targets test BODIES (weakening assertions), and the contradiction
  made the other reading impossible: the specified design cannot satisfy the old list.
- **F-T2-2 (a payload flip is invisible to integrity_check).** The spec's "flip mid-page bytes" as written is
  undetectable: the bulk fixture's BLOBs are content without checksums, and a flip inside one passes
  `integrity_check` (probed: flips at 1/2 and 3/4 of a 66 MiB artefact both answered `ok`). The test therefore
  corrupts the STRUCTURE: the b-tree page-type byte of page 2, zeroed (0 is never a legal page type, so whatever
  page 2 holds, `btreeInitPage` fails — probed: `IntegrityOK=false`, `btreeInitPage() returns error code 11`).
  Page size read from the file header, not assumed.
- **F-T2-3 (a saturated writer live-locks the raw step loop — production code carries a backoff now).** mattn's
  `Step` reports `SQLITE_BUSY` as `(false, nil)` — no error, no progress. Against a writer that commits
  back-to-back, the naive loop spins forever (measured: the consistency test hung >10 min until the writer's
  first scheduling gap; a goroutine dump showed the test blocked on its commit counter because the writer's
  transactions were being refused… see F-T2-4). `backup.go` now counts consecutive no-progress steps and yields a
  millisecond after 100 (progress never sleeps). A cancel still lands, because the ctx check precedes every step.
- **F-T2-4 (a test-design trap that also would have been a data trap).** The paired-insert fixture's first cut
  used `i INTEGER PRIMARY KEY` with a two-row `VALUES (?, 'A'), (?, 'B')` — both rows carry the SAME `i`, so every
  transaction died on the UNIQUE constraint and the writer goroutine exited silently (a goroutine dump showed it
  absent; the wait on the commit channel blocked forever). The pair's key is now `(i, tag)`. The same shape — a
  multi-row insert where a parameter repeats a key — would have masked a real consistency failure, so the test
  asserts `b >= 10` (ten commits provably before the read instant) rather than `b > 0`.
- **F-T2-5 (vec0's MATCH query is JSON, not hex, in v0.1.6).** A hex-encoded query vector is refused
  (`JSON array parsing error: Input does not start with '['`); the query takes the same JSON-array text the rows
  store. The test queries `[7.25,0,…]` over vectors `0..7` on the first axis — distances 0.25/1.25/2.25/3.25/4.25,
  no ties, so the top-5 ordering `[7 6 5 4 3]` is comparable between source and snapshot.
