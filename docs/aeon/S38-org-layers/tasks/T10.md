## Steps

1. **Catalog entries:** `task_list {component?, status?, manual?, assignee?, goal?, parent?, limit?}` (safe); `task_show {id}` (safe); `task_create {id?, title (req), tech?, engineer?, depends_on?[], parent?, manual?, type?, body_note?}` (detectable); `task_update {id, title?, tech?, depends_on?}` (detectable); `task_set_status {id, status, evidence?}` (detectable); `task_bump_counter {id, counter enum retries|security_rounds|review_rounds}` (detectable).
2. **Scoped implementations** (all through `Identify`):
   - `task_create` inside a loop → a **loop task**: `CreateTask(Scope{loop, component_root}, NewTask{…})`; `assignee` = the `engineer` arg or the agent's handler name; `manual` is **false** and not an argument **unless** the loop is a *plain chat*, in which case `manual: true` is honoured. **Measured 2026-10-27 (S39 T0 drafting): every loop pins a blueprint today — there is no blueprint-less loop** (`loop_blueprint` is required by every reader), so "no pinned blueprint" cannot detect a plain chat. Implement the rule as one helper `isPlainChat(ident Identity) bool` in `daemon/records.go`; **until S39 defines the chat loop it returns `false`** (so `manual` input is always refused), with a comment saying so. S39 T6 adds the dedicated **`chat`** agent and **`chat`** blueprint (decided 2026-10-27, `../downstream-impact.md` §6) and changes the helper to test that the loop's pinned blueprint id is `chat`. Test the helper with a stub, not a real chat.
   - `depends_on` may name only tasks that already exist in this loop; a duplicate id, a self-dependency, or an unknown dependency is refused with the **text of `plan`'s `Refusal.Sentence()`** — call `plan.Validate`-style helper (VERIFY: `internal/plan/derive.go`) or build a `plan.Refusal{Kind: "depends-on-missing", …}` and render with `.Sentence()`; never re-type the sentence.
   - `task_set_status` goes through `SetTaskStatus` (loop tasks) which runs `ValidateTransition`; an agent may only touch **tasks its own loop owns**; any other id → `Failure{"task %q is not owned by this loop"}`. For a manual task the agent's loop must be a **worker** on it (`task_loop`).
   - `task_update` on a loop task refuses unless the task's loop is the caller's (the read-only rule is for **people** on the socket, T7/T15, not for the owning agent).
3. **Pins:** add the six names (sorted) everywhere T9 step 8 lists; dated comment `// 2026-10-27 (S38 T10): + task family …; Count <old> -> <new> DELIBERATE.`; `rerun_classes.json`.
4. **Handler data (declarations, never grants beyond the allow-list):**
   - `project-planner.md`: `tools: [read, write, edit, glob, grep, todo, task_create, task_list, task_show, attach]`
   - `brief-author.md`: `tools: [read, write, edit, glob, grep, bash, todo, question, goal_show, brief_create, attach]`
   - `proposal-author.md`: `tools: [<existing>, goal_create, goal_list, epic_list, attach]`
   - Add a short paragraph to each body (end of "Working method") telling the agent **what to call and when**, e.g. for the planner: *"After writing `plan.md` and each `tasks/{taskid}.md`, call `task_create` once per task (in dependency order), then `attach` each task's detail file to it. The loop's engine owns task status — you never call `task_set_status`."* Keep the reviewed-body rule: do not paste retrieved content into `Body`.
5. **`brainstormer.md`** (new): front matter `name: brainstormer`, `description: Talks an idea through with the person and, when asked, turns it into a goal with a proposal and a brief.`, `temperature: 0.4`, `tools: [read, list, glob, grep, write, edit, todo, question, goal_create, goal_update, goal_list, epic_list, component_list, attach]`, a `handoff:` block copied from `intent-clarifier.md`. Body: converse first, **never create the goal until the person asks**, then write `proposal.md` and `brief.md` with `write`, call `goal_create {title, type, components[], document: "proposal.md"}`, then `attach {subject:{kind:goal,id}, document:"brief.md"}`; afterwards keep talking and use `goal_update` when asked. Add `"brainstormer"` to `registeredBodies` (registry.go).
6. **Policy rows are operator data, not code.** Do not seed `allow` rows. Document in Notes the one-line `aeon policy add` command an operator runs to allow `task_create` for the default chat agent (use `aeon policy add --help` to get the exact flags — VERIFY).
7. Update any handler test that pins these tool lists.
