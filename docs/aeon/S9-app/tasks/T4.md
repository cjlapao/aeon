# T4 — The three-state renderers

**Notes (2026-10-18):** Installed and inspected `@cjlapao/ui-kit@0.2.3`. Its `StepStatus` still lacks `not-needed` and `skipped`, and its `ConnectionState` still describes flow diagrams, so the S9 ladder and liveness states must be composed locally. Added `Uncertain` and shared validation, recovery, and liveness notices with explicit text for every uncertain state. `costLine` refuses a known or partial cost that omits its numeric amount; `totalCost` keeps a floor over a measured amount when another part is uncertain, and reports unknown when no cost was measured. Rendered tests cover the literal `$0.00` failure, floor wording, S16's unverifiable diagnostic, the named recovery receipt, and liveness states. Six focused UI tests and the full `make ci` gate passed. Product screens in T6–T10 consume these renderers.

## Why this exists

**This is the slice's thesis, and it is a twenty-line component with a test behind it.**

Four independent designs in Aeon refuse to collapse an uncertain answer into a certain one:

| What | States |
| --- | --- |
| Cost (S3) | `known` · `partial`, a floor · `unknown`, with a reason |
| The `bash` receipt (S7) | ran · did not run · **outcome unknown** |
| Blueprint validation (S8) | valid · invalid · **could not check**, naming the slice |
| Liveness (T3) | current · stale · disconnected |

That is [P31](../../ARCHITECTURE.md#8-product-decisions). Each of those cost real design effort, and **a UI is where
it gets thrown away by accident** — because `unknown` renders as `—`, and `—` becomes `$0.00`, and nothing errors, so
nobody notices.

This task exists before the screens (R5) so that no screen ever formats one of these inline. A screen that formats a
cost itself is a screen that will flatten it.

## Scope

### The renderers

```tsx
// The shared shape for a value that may be uncertain.
type Uncertain<T> =
  | { state: "known";   value: T }
  | { state: "partial"; atLeast: T }
  | { state: "unknown"; reason: string };

// One component. Every three-state value in the app goes through it.
export function Uncertain<T>({ v, render }: { v: Uncertain<T>; render: (t: T) => string }): JSX.Element;
```

| State | Renders |
| --- | --- |
| `known` | the value |
| `partial` | **"at least $0.0180"** — worded as a floor, not styled as one. A grey `$0.0180` is indistinguishable from a known cost to anyone not told about the convention |
| `unknown` | **the reason**, e.g. *"unknown — the provider returned no usage"*. Never `—`, never blank, never a zero |

### Cost formatting (U6, D1, D2)

`lib/cost.ts` maps S3's `Cost` onto `Uncertain<number>` and formats it.

**The total is where this is most often lost** (D2): a total summing a `partial` component is **itself a floor**. A
confident total over an uncertain part is the same error one level up, and it is the more damaging one, because a
total is what someone quotes.

```
step A  $0.0312
step B  at least $0.0180
step C  unknown — no usage returned
─────────────────────────────────
total   at least $0.0492
```

Not `$0.0492`. And step C contributes nothing to the floor while making the floor a floor — which is exactly what
`partial` means.

### The other three

- **Validation** — `valid` / `invalid` / `unverifiable`, the last naming the missing registry **and its slice**. It
  must be styled as neither an error nor a pass; those are the two lies S8 built three states to avoid.
- **Recovery** — a step failed by S7 renders **the tool name and the receipt state**, because *"it started and we
  cannot say what happened"* is a different fact from *"it failed"*, and only one of them tells someone to go look at
  their repository.
- **Liveness** — T3's states render through here too, so the fourth uncertain value is not a special case.

### The guard (U17, I6)

A test enumerating every three-state value in the app and asserting each renders through these components. That is
what stops a **fifth** one being flattened by someone who never read P31 — and there will be a fifth.

## Tests

| Test | Asserts |
| --- | --- |
| `TestUnknownCostNeverRendersAsZero` | Rendered output for an `unknown` cost contains its reason and **does not contain the literal string `$0.00`** — asserted on rendered output, not props (D1, C2) |
| `TestUnknownNeverRendersAsDashOrBlank` | The same, for `—`, an empty string, and whitespace |
| `TestPartialReadsAsAFloor` | The word "at least" is present. **Styling alone fails this test** — a grey number is not a floor |
| `TestTotalOverPartialIsAFloor` | A total summing a `partial` is itself `partial` (D2) |
| `TestUnknownContributesNothingButKeepsTheFloor` | A total over known + unknown is `partial`, not `known` |
| `TestValidationThreeStatesAreDistinct` | `unverifiable` renders unlike both others, and names its slice (D15) |
| `TestRecoveryFailureNamesToolAndState` | The tool name and receipt state both appear (D14) |
| `TestEveryThreeStateValueUsesTheRenderers` | An enumeration of the four, each asserted to route through `Uncertain` — the guard against a fifth (I6, A9) |

`TestPartialReadsAsAFloor` failing on styling alone is deliberate. The obvious implementation greys the number and
believes it has communicated something.

## Definition of done

- [ ] One `Uncertain` component; all four values route through it
- [ ] `partial` reads as a floor in **words**
- [ ] `unknown` renders its reason; never a zero, a dash, or a blank
- [ ] A total over a `partial` or `unknown` component is itself a floor
- [ ] Validation's `unverifiable` is styled as neither error nor pass, and names its slice
- [ ] A recovery failure names the tool and the receipt state
- [ ] The enumeration guard exists
- [ ] Assertions are on rendered output, not props
