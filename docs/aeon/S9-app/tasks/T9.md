# T9 — The thread — messages, step summaries, and questions inline

> **Complete · 2026-10-18.** `ui/src/product/Thread.tsx` orders retained per-loop events by daemon `seq` and places the active `QuestionCard` at its matching event. S4 allocates `seq` from a unique event rowid, so no same-sequence tie-break exists. The thread uses `question.asked` for step prompts and `loop.waiting` for gates, suppressing the duplicate step waiting row; both prompts remain visible after an answer. The same card handles step questions and gates; writes are blocked while stale or pending, and a refused answer does not create an optimistic row. Gate prompt and options come from `loop.show` when its waiting event was pruned; step question body/options come from `step.show`. Existing `question.answered` and gate `loop.advanced` events carry additive answer fields, so confirmed answers render as durable `You` rows at their daemon sequence positions. The local acceptance banner appears only until that event arrives. Tests cover both event payloads, sequence order, historical prompt, pruned gate event, inline placement, rejected and accepted answers, double submit suppression and stale writes. A real 1024px Tauri replay walk showed both questions, both sequenced answers, and a completed loop with both artifacts. That walk exposed and led to fixes for resumed-loop state and the durable gate snapshot. T11 still owns the two-window refusal walk and full demo.

## Why this exists

The chat is **how a person interacts with the system**, not a conversation with a model, and it is **per loop**
(U18). One ordered stream holding chat messages, step summaries and questions is what makes *"what happened, and what
does it want"* a single read.

It shares `Loop.tsx` with T7's ladder — the ladder above, the thread below — but the components are disjoint, which is
why they are separate tasks.

## Scope

### One ordered stream (U18, O4)

```
  step   survey       ok        SURVEY.md      $0.0312
  ask    Which package should I start with?
         [ internal/store ] [ internal/runtime ] [ internal/loop ]
  you    internal/store
  step   survey       ok        (resumed)
  ask    Approve the survey and continue?
         [ approve ] [ revise ] [ abort ]
```

**Ordered by the daemon's `seq`, never by client-side timestamp** (O4). Two events in the same millisecond, or a clock
skew between two reads, reorders a thread — and a reordered thread makes a question look like it was answered before
it was asked, which is worse than being out of order by a second.

**Confirm the same-`seq` tie-break** (Q10) and state it. If `seq` is the `event` rowid (S4) it is unique and there is
no tie, in which case say that rather than writing a tie-break nothing exercises.

### Both kinds of question, indistinguishable (U14, D8)

The two `ask` rows above are **different mechanisms**: the first is a step question that resumes a step via
`ResumeStep` (S6); the second is a gate that advances the loop via `AdvanceLoop` (S8).

**They render identically**, differing only in text and options. That is L11 delivered: a human answering something
should not have to know what is asking. The app sends `answer` with the question id; the daemon dispatches on `kind`.

Asserted by **comparing rendered output** (C6), not props — a test on props passes while a `kind` badge sits on screen.

### Options come from the question (O7)

Never a hardcoded set. A gate's `answers` are declared in the blueprint (S8), so a hardcoded `[approve, reject]`
would silently drop `revise` — and the author who wrote `revise` would have no way to choose it.

### Inline, never modal (U4)

A modal detaches the decision from the context needed to make it, which is exactly what a person needs in order to
decide well. The question sits in the thread, in position, with the step that raised it above it.

### No optimistic rendering (U9, U19, D9)

The answer appears **when the daemon says it landed**. Not before.

`answer` refuses a second answer, and an optimistic render would show an accepted answer that was rejected — leaving
someone believing the step resumed on their input when it did not. Concretely: on submit, the option set stays live and
disabled-pending; on confirmation it becomes the `you` row; on refusal it returns to live with the reason.

### Out-of-set answers (S8's O6)

The daemon refuses an answer outside the declared set. The app should not be able to send one — the options are the
only affordance — but if a refusal arrives, render it rather than swallowing it.

### Staleness (T3)

While stale, the thread stops accepting answers and says why. Sending an answer into a connection that cannot be
confirmed is how someone answers twice.
