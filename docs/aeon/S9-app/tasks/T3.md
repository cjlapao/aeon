# T3 — Liveness — staleness, silence, and reconnect-and-re-read

> **Notes · 2026-10-18.** Implemented in `ui/src/lib/live.ts` and the product shell. The Rust shell's existing `ping` probes confirm an idle socket after 20 seconds of silence and retire it after two unanswered 10-second probes; the web layer treats the shell's close event as the liveness signal and never polls application data. `LiveController` reports `connecting`, `current`, `stale` with age/cause/path, and `disconnected` with reason/path. Reconnect reruns registered snapshot readers before publishing `current`. `ui/test/live.test.ts` covers drop, five minutes of silence, reread, and manual reconnect; `ui/test/product.test.tsx` caught and guards a React StrictMode listener-registration race. The negotiated `protocolVersion` comes from S2's handshake; a newer version is bannered read-only. The v1 `ConnectionPill` was not copied because it reads v1's HTTP connection context; the product shell composes the same status from the new bridge and shared `LivenessNotice`. An isolated 1024px Tauri replay window was observed going stale after a real daemon `SIGKILL` and current again after restart. T11 still owns the complete desktop demo and five-minute idle-gate walk.

## Why this exists

**A UI showing a loop `running` when the socket died forty seconds ago is lying, and it is the most believable lie
in the product.** Nothing looks wrong. The spinner spins.

This task comes before every screen because staleness is not a badge added at the end: **every rendered value is
either confirmed or not**, and retrofitting that distinction is a change to every component.

## Scope

### The three states (U13)

| State | When |
| --- | --- |
| `current` | connected, and the connection is confirmable |
| `stale` | the socket dropped, or is reconnecting — showing **how long since last confirmed**, **what it is waiting on**, and **the socket path** (O1) |
| `disconnected` | given up, with the path and the reason |

S1's T5 already established three connection states and the rule that the disconnected state shows the path it
tried. This extends that rather than replacing it, and `ConnectionPill` ports from v1.

**"Stale" without a cause sends people to the wrong problem** (O1). Reconnecting and given-up are different
situations, and the path is the first thing anyone debugging this needs.

### Silence is not staleness (D6)

**This is the distinction the task turns on.**

A loop waiting at a gate emits nothing for hours and is **perfectly current**. Staleness is the connection being
*unconfirmable* — not the absence of events.

Getting it backwards produces a UI that cries wolf until people stop reading the warning, at which point the
genuine warning is worthless too. So `current` must survive five minutes of silence on a live socket, and that is
its own test rather than an assertion inside another one.

**Answer Q8 before implementing**: what mechanism confirms the connection? A heartbeat, a periodic cheap request, or
a socket-level signal. State it and its threshold. Note that a periodic request is a **liveness probe**, not
polling for data — I4 forbids polling as a way to *read state*, not a way to confirm a socket. Say which you built
and why, because the distinction is easy to lose.

### Reconnect re-reads (D7)

On reconnect the app **re-reads** the state it is displaying. It does not resume from its last event `seq` alone.

`seq` is the `event` table's rowid (S4), and a **filtered** subscription legitimately sees gaps — so a gap tells the
app nothing about whether it missed something. A gap it cannot bound is a gap it must not paper over.

**Confirm Q3 first**: is `seq` monotonic across filtered subscriptions? The answer decides whether a gap is even
detectable, and D7's test depends on it.

### Version mismatch (O6)

If the daemon's protocol version is newer than the app's, the app **says so plainly and keeps working read-only
where it can** — it does not refuse to start.

A version mismatch after a partial upgrade is an ordinary state, and an app that will not open is a worse answer
than one that says "some things may be missing." **Confirm Q4**: if S2 exposes no version to compare, say so and
raise it — do not invent a handshake (N9).

### No polling for data (I4, D12)

Screens update from the event channel. No interval timer drives a data read, asserted by grep.

## Tests

| Test | Asserts |
| --- | --- |
| `TestDropGoesStaleWithAge` | A fake bridge that stops responding: state becomes `stale`, the age **counts up**, and the cause and socket path are present (D5, O1) |
| `TestSilenceStaysCurrent` | A **live** fake bridge emitting nothing for well past the threshold: state stays `current`, no warning, no age. **Its own test** (D6, C4) |
| `TestReconnectReReads` | Drop, restore: a **re-read request is issued**, asserted on the fake bridge's call log — not merely that the UI recovered (D7, C5) |
| `TestSeqGapDoesNotSilentlyPersist` | After a reconnect, displayed state matches the daemon's, including a change made while disconnected |
| `TestGivenUpIsDistinctFromReconnecting` | Two different renderings, both carrying the path |
| `TestNewerProtocolVersionKeepsWorking` | The app opens, states the mismatch, and read paths still function (O6) |
| `TestNoIntervalDrivesADataRead` | A grep over the web layer: no `setInterval` reaching an `rpc` data call. A liveness probe is exempt and must be **named** as such (I4) |
