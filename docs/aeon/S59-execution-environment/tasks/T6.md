# T6 · The daemon doors, the seed set and the guards

**Prefix:** EV · **Shape:** P4, P8 · **Rules:** EV2, EV16, EV17, EV18, EV19, EV10 (the spawn-site guard) · P34 · **Depends on:** T2, T3, T5; **S43-extra T3** (the seed engine) for the seed set. **Gates T7, T8, T11.**

## Goal

The daemon is first class: every environment and secret-reference operation is a **socket method**, the writes are a
**human door** with guards that are shown to fail, the system environment is **seeded** as an inert set with the
first-binding rule, and the "no process inherits the daemon's environment" rule becomes a test that cannot pass
vacuously. No client is built on these methods before this task has landed.

## Deviations (four, each deliberate)

1. **The injection deny rule (`internal/execenv/validate.go`, 579 lines).** `refuseName` refused a credential-shaped
   name absolutely, so `Build` refused an `inject_as` of `GITHUB_TOKEN` — while the refusal's own remedy is *"use a
   secret reference"*. That is a contradiction that closed the sanctioned path, so the shape checks were factored
   into `refuseVarNameShape` and a new `refuseInjectionName` governs an injected name: credential words and vendor
   prefixes (**allowed** — injecting `GITHUB_TOKEN` from a reference is the whole point of EV7), while loader names
   (`LD_PRELOAD`, `NODE_OPTIONS`), Exact handles (`SSH_AUTH_SOCK`, `KUBECONFIG`, `DOCKER_HOST`…), SetOnly names
   (`PATH`) and the daemon's own namespace (`AEON_`) stay **refused**. `internal/execenv/validate_test.go` now pins
   both directions: `…a mechanism name in an inject_as is refused by Build too` and
   `TestAnInjectedCredentialKeepsItsName` (GITHUB_TOKEN, GH_TOKEN, AWS_SECRET_ACCESS_KEY, NETLIFY_TOKEN,
   OPENAI_API_KEY, STRIPE_SECRET_KEY all inject, with `Source` prefixed `secret:`). T4's rule text is unchanged;
   this amends how it applies to the one place it contradicted itself.
2. **`store.MarkProvisionFailed` now accepts `tearing_down`** (`internal/store/provisions.go`, 412 lines). Its own
   doc comment has always described `provisioning → ready → tearing_down → removed | failed`; the from-map omitted
   `tearing_down`, so a removal whose driver failed left the row stuck in `tearing_down` with no `last_error` — a
   ledger that cannot record the failure it failed to complete. The door now also reports what the ledger actually
   says (`the ledger now reads <state>`, or that it could NOT record the failure).
3. **`tools/protogen` reads the package, not one file** (348 lines). The generator took
   `internal/protocol/method.go` alone; that file is **1,954 lines** — already past the repository's 1000-line line —
   so appending twenty constants to it would be a change that pushes a broken file further broken (SIZE1), and each
   plane's constants live beside its handlers anyway. `methodNames` now walks the package (a file path still works,
   for the teeth test). **What that surfaced: the app's contract was missing 68 methods** — `dod`, `learnings`,
   `merge`, `mergerule`, `queue`, `roadmap`, `triage`, `verify` had handlers and fixtures and were absent from
   `RpcMethods`. `ui/src/proto/contract.ts` went **225 → 293** methods, 6,417 lines, with **zero lost** (verified by
   diffing the sorted name sets), and `TestPackageScanSeesTheExecutionEnvironmentPlane` floors the count at the
   measured **293**. The generator's teeth were proven the hard way: the first run refused with
   `methods without request/result fixtures: environment.teardown, secretref.create`, which is why those two
   methods carry a success fixture as well as a refusal one. `contract.ts` was never edited by hand.
4. **EV1 at a spawn site this slice did not own.** `internal/skills/install.go`'s `gitCloneShallow` had a **nil**
