# T10 · Services and the preview refusal

**Prefix:** EV · **Rules:** EV4 (`services`, `preview`), EV12, EV14 · **Depends on:** T9.

## Goal

An environment may declare **per-loop service dependencies** — a database, a queue — started before the loop's first
command, health-checked, reachable by derived names, torn down with the loop. **Preview deployments** are *specified
only*: the spec member exists, is refused when set, and the follow-up's shape is recorded.

## Files

- `aeon/internal/execenv/container/services.go` — for each `services[]` entry: a per-loop user network
  (`aeon-<slug>-net`, created once, ledger owner `network`), a service container (`aeon-<slug>-<name>-<provisionId>`,
  same labels, ledger owner `service:<name>`, same hardening, **no** published host port), joined to the network;
  `Ensure` runs **after** the network and **before** the app container; the app container joins the same network.
- `aeon/internal/execenv/container/health.go` — `WaitHealthy(ctx, svc)`: with `health.cmd`, the runtime `exec`s that
  command inside the **service** container (the image's own tooling) and a zero exit is healthy; with `health.tcp`, the
  daemon runs one short **probe container** on the loop network that connects to `<name>:<port>` (so the check never
  needs a published host port). Both are bounded by `timeoutSeconds` (default 30, max 300) and retried on an interval; an
  unhealthy service ⇒ `service-unhealthy` refusal naming the service and the last probe error; the loop's provision is
  marked `failed` and torn down.
- `aeon/internal/execenv/container/servicenv.go` — the derived names the app container receives:
  `AEON_SERVICE_<NAME>_HOST` (the service container's network alias = its declared `name`) and `AEON_SERVICE_<NAME>_PORT`
  — **names the daemon derives** from the declared `name`/`port`, never typed values; plus the service's own `env`
  literals and its `secrets` (injected into the **service** container by the same `--env NAME` mechanism; the app gets a
  secret only if its own `env.secrets` lists the reference). A service name must match `^[a-z][a-z0-9-]{0,31}$` and
  must not collide with another service after upper-casing.
- `aeon/internal/execenv/validate.go` (T3) — already refuses `services` on non-container backends; this task adds the
  per-service checks (image required, port 1–65535, `health` shape, duplicate names, env deny rules apply to a
  service's `env` too).
- `aeon/internal/store/provisions.go` — `owner` values `loop`, `network`, `service:<name>` (T2 column) with the unique
  live index already covering them.
- **Preview (spec only):** `spec.preview` is reserved; non-null is refused with "preview deployments are specified, not
  built (S59 EV14)". The follow-up's brief is recorded in this task's **Notes**: a build step, a URL/TTL record, an
  inbound-egress allowance, an owner and a teardown — **no code**.

## Behaviour (each a test against the fake runtime)

1. Provision order: network → services (each healthy) → app container; teardown in reverse; each step a ledger row.
2. An unhealthy service ⇒ `service-unhealthy`, nothing left behind (reconcile finds no orphan).
3. The app container's environment has `AEON_SERVICE_DB_HOST/PORT`, the service's secrets are **not** in the app
   unless listed, and no argv contains a secret value.
4. No service publishes a host port; services are unreachable from outside the loop network.
5. A second loop on the same environment gets its **own** network and service containers (no sharing across loops).
6. A `blocked` loop keeps its services until the TTL (T9), then all go.

## Commands

P10, `./internal/execenv/... -run 'Service|Preview|Health' -count=1 -race -v`; the opt-in real-runtime test from T9 gains
one service case (`AEON_TEST_CONTAINER=1`).

## Definition of done

- [ ] Services provisioned, health-checked and torn down with the loop; derived names only; no host ports;
  preview refused with its follow-up brief recorded.

## Do NOT

- Do not publish a service port to the host. Do not accept a typed value for a derived variable. Do not share a
  network between loops. Do not build preview deployments.

Wired: `newStepExecResolver` hands the provisioner the two doors it cannot open itself (`p.ServiceArgs = r.serviceArgs`, `p.Probe = daemonProbe`) — with either unwired the driver REFUSES a service that declares secrets or a health check rather than starting it blind; the daemon's two teardown sites (`onEnvironmentTerminal`, `SweepIdleProvisions`) now walk `orderForTeardown`, which is the driver's rank (app → services → network) because a network with endpoints attached cannot be removed and the store returns rows in CREATION order.

**Three product bugs the tests caught, none theoretical:**
1. The app container's ledger row was written with `Owner = LoopRef.Owner`, i.e. the STEP's identity. The store's owner vocabulary is `loop | network | service:<name>` — the real store would have refused every container provision. The fakes had never validated it, so T9's green said nothing about it.
2. `WaitHealthy` was handed the row as it looked BEFORE `MarkProvisionReady`, so it saw `provisioning` with an empty handle and returned "healthy" without ever running a probe — the health check silently did nothing. It now gets the ready row, and `TestUnhealthyServiceFailsProvisioningCleanly` is the assertion that keeps it honest.
3. The rollback on a failed dependency tore down the row SNAPSHOT taken at creation (no handle yet), so `teardownRow` had nothing to name and removed nothing while reporting success — measured as the loop's network left running behind a failed provision. It now re-reads each row from the ledger before removing.

**Deviations.** (1) The ledger needed a third owner and SQLite would not widen the CHECK: `20261103203000_provision_owner_network.sql` rebuilds `environment_provision` (copy → count guard → drop → rename → re-create the two indexes), the Go twin in `provisions.go` admits `network`, and `ProvisionOwnerNetwork` is exported for the driver. (2) The tcp probe runs `--entrypoint /bin/bash <service image> -c ": >/dev/tcp/<name>/<port>"` — the loop's own network makes a published host port unnecessary, and the service's image is used so no second image has to be pulled; an image without bash cannot be tcp-checked, which is what `health.cmd` is for. (3) The health probe's policy token is minted by the DAEMON for its own agent (`aeon-daemon`), because a probe is the daemon's action and the step has no way to name it; the command being minted is built by the driver from a validated name and an int, never by a spec author. (4) The driver does NOT re-implement T3's per-service validation (image, name charset, duplicates, health shape) — `execenv.Validate` owns it; the driver checks only the port it dials and the name it spells into a variable and an alias, and says so. (5) `CreateSpec.ServiceName` selects the service shape inside the driver rather than exposing a second create method, so no caller can hand a service container a mount. (6) A `failed` row whose resource still exists is removed by reconcile (T9 left it skipped), because "nothing left behind" is the promise a failed provision makes.
