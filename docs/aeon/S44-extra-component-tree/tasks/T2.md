# T2 · Migration A: the component tree

**Prefix:** CT · **Rules:** CT1, CT2, CT5 (A), CT6, CT7 · **Depends on:** T1. **Merges with T3 and T4.**

## Goal

One timestamped migration that turns the `project`→`component` pair into one `component` tree: `parent_id`,
`archived_at`, nullable inherited settings on children, depth triggers; every `keep` project becomes a root component
with the **same id**; children of `component` survive the rebuild; telemetry rows for kept projects move into
`component_telemetry`. Nothing is lost and every guard is physical.

  (the parser uses it). Never edit `schema.go` or a shipped migration.
- `aeon/internal/store/ct_migration_a_test.go` — **new**.

## The SQL, in order (read the **current** `component` DDL first — S44 may have added a column; copy every column)

1. **Map.** `CREATE TABLE zz_ct_project_map (project_id TEXT PRIMARY KEY, component_id TEXT NOT NULL, disposition TEXT
   NOT NULL CHECK (disposition IN ('collapse','drop','keep')))`, filled with three `INSERT … SELECT` statements over
   `project` and `component` implementing CT5 A1 exactly. The "referenced anywhere" predicate is one `EXISTS` per
   source T0 listed (epic, goal, automation_event.project_id, event_trigger.project_id, event_trigger match JSON via
   `json_each`, project_telemetry with any non-zero counter). A guard row asserts every project got exactly one
   disposition: `CREATE TABLE zz_ct_map_guard (n INTEGER, total INTEGER, CHECK (n = total))` inserted from counts.
2. **`component_new`**: every current column **except** `project_id`, plus `parent_id TEXT REFERENCES component_new
   (id)` — **VERIFY** in T0 how SQLite rewrites a self-FK on `ALTER TABLE … RENAME` (it rewrites references to the
   renamed table; write the FK as `REFERENCES component(id)` if the rename rewrites only *other* tables' references —
   prove with a test either way), `archived_at TEXT`. Inheritable columns: drop `NOT NULL`, keep the default, CHECK
   becomes `x IS NULL OR x IN (…)` / `x IS NULL OR x BETWEEN 1 AND 16`.
3. **Copy components**: `INSERT INTO component_new (…) SELECT … , CASE WHEN m.disposition='keep' THEN m.component_id
   END, NULL FROM component c JOIN zz_ct_project_map m ON m.project_id = c.project_id` — values of the inheritable
   columns copied **verbatim** (no NULLing).
4. **Insert kept projects as roots**: one row per `keep` project: same id; `name`; `short_description`; `description`;
   `icon = COALESCE(icon_emoji, icon_image, '')`; `slug` = a SQL slugify of the name (lower, non-alnum → `-`, trim
   dashes; T0's collision census says whether a suffix is needed — if any collision exists, append `-group`, then a
   counter; record the rule); repository columns NULL; inheritable columns at their defaults; timestamps preserved.
5. **Park children** of `component` (T0's verified list; default: `component_root`, `component_telemetry`,
   `goal_component`, `task`): `CREATE TABLE zz_ct_park_<t> AS SELECT * FROM <t>` with a copy guard each; `DELETE FROM`
   the child first where the FK is NO ACTION (so the parent drop does not fail), then `DROP TABLE component`,
   `ALTER TABLE component_new RENAME TO component`, restore each child with an **explicit column list**, drop the
   parks. Indexes: recreate those that rode out (AGENTS.md §3, 0019 lesson): `idx_component_remote_key`,
   `idx_component_repo_key`, new `idx_component_parent (parent_id)`; **drop** `idx_component_project`.
   *If T0 finds parking `task` too costly or too risky* (it is wide and indexed), the alternative is to rebuild `task`
   in the same migration with its FK unchanged — decide in T0, record which.
6. **Telemetry**: `INSERT INTO component_telemetry SELECT <project_telemetry columns with project_id as component_id>
   FROM project_telemetry WHERE project_id IN (SELECT project_id FROM zz_ct_project_map WHERE disposition='keep')`.
7. **Depth triggers** (after the data): `component_tree_parent_insert` (BEFORE INSERT) and
   `component_tree_parent_update` (BEFORE UPDATE OF parent_id), each `RAISE(ABORT, 'component tree: …')` for: parent
   missing, parent is a child, parent archived, self-parent, node has children. Plus
   `component_tree_root_settings` (BEFORE INSERT / BEFORE UPDATE) refusing NULL inheritable values on a root.
8. **Final guard**: `CREATE TABLE zz_ct_fk_guard (n INTEGER CHECK (n = 0)); INSERT INTO zz_ct_fk_guard SELECT count(*)
   FROM pragma_foreign_key_check(); DROP TABLE zz_ct_fk_guard;` and the depth check
   `… SELECT count(*) FROM component c JOIN component p ON p.id=c.parent_id WHERE p.parent_id IS NOT NULL` = 0.

`project` and `zz_ct_project_map` **stay** after A (B needs the map; `epic`/`goal` still reference `project`).

## Notes

**Built 2026-10-30 — merge-unit intermediate; T4 (the store rewrite) is required for the runtime to be green. T2–T4 are one unit.**

`aeon/internal/store/migrations/20261030200000_component_tree.sql` — one file, one transaction, over the store's `_foreign_keys=1` connection (verified: `PRAGMA foreign_keys=OFF` is a no-op inside a txn, so it is never relied on).

**Deviation (recorded per §4a):** the self-FK is written as `parent_id TEXT REFERENCES component_new(id)` (the NEW table name), not `REFERENCES component(id)`. Verified on the bundled driver (mattn v1.14.52, SQLite 3.53.4): a self-FK written as `REFERENCES component(id)` while `component` exists is **lost** when `component` is dropped and not restored by the rename; `REFERENCES component_new(id)` survives the rename and becomes `REFERENCES component(id)`. The post-migration DDL shows `parent_id TEXT REFERENCES "component"(id)` — confirmed.

Does: builds the CT5 map (`zz_ct_project_map`, collapse/keep/drop, one row per project, with a `zz_ct_map_guard` asserting every project got exactly one disposition); rebuilds `component` as `component_new` (self-FK + `archived_at`, inheritable columns nullable with `x IS NULL OR …` CHECKs); copies every component verbatim (`parent_id` = the project's new id for a `keep`, NULL for a `collapse`); inserts each kept project as a root under its own id; **parks and restores** `component_root`/`component_telemetry`/`goal_component`/`task` around the drop+rename (the 0035 hazard); moves each kept project's rollup into `component_telemetry`; installs the depth triggers (`component_tree_parent_*`, `component_tree_root_settings_*`) AFTER the data; installs the fk/depth guards. `project` and the map survive (B needs them).

Validation (env preamble AGENTS §6, `XDG_STATE_HOME=$(mktemp -d)`):
- migration applies on a fresh store: `pragma_foreign_key_check() = 0`; `component` has `parent_id`+`archived_at`, no `project_id`; `project` survives; `zz_ct_project_map` survives; 4 depth triggers; `parent_id` DDL is `REFERENCES "component"(id)` (self-FK survived).
- depth triggers fire: child-under-root inserts; grandchild aborts `a child of a child is three levels`; self-parent aborts `a node cannot have a parent`; root-with-NULL-setting aborts `a root cannot inherit its settings`.

**ORDER AMENDMENT 2026-11-02 (found on a live store, same-day fix):** the park/restore lists ran in an order the store's own data shape could not survive. The re-insert restored `chat_message` BEFORE `question`, but `chat_message.question_id` references `question(id)` — the parent must exist at re-insert time whatever the delete action says — so the first live store that had ever asked a chat question died at `INSERT INTO chat_message SELECT * FROM zz_ct_park_chat_message` with `FOREIGN KEY constraint failed` (reproduced on this machine's store: 10 chat_message rows, all with `question_id` set; the ledger row is `20261030200000_component_tree` = `failed`). A second, latent defect sat in the clear: `DELETE FROM question` ran before `DELETE FROM agent_task`, and `agent_task.question_id` is `ON DELETE NO ACTION` — a store with a completed async agent task that raised a question would die on the clear, not the restore (this store's `agent_task` was empty, so only the first defect fired). Both were invisible to every drill because the census fixture and the S55 drill seed no `question`/`chat_message`/`agent_task` rows at all — on an empty store the order is a no-op.

The file is amended IN PLACE (the 20261101193000 precedent for a shipped-but-unapplied migration): the clear now runs `agent_task` before `question`, and the restore runs `question` before `chat_message`. This is ordering, not shape — the final schema is byte-identical to what T2 shipped, and no database can hold this migration as `applied` with a different data shape (it only applies on a store without chat questions, where the order provably changes nothing), so the §3 immutability rule's undetectable-divergence hazard does not arise; a new migration number could not fix the order inside a transaction that never applied. Regression drill: `internal/store/ct_park_order_test.go` (`TestCTUpgradeParkOrderSurvivesChatQuestions`, the S55 T12 shape parked at this vintage with the one data shape the shipped order could not carry) — RED on the shipped order with the live store's exact error, GREEN on the amended one, 2026-11-02.
