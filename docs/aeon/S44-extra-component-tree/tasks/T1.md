# T1 · Characterization goldens and the census fixture

**Prefix:** CT · **Shape:** P2 (Phase A only) · **Rules:** CT5, CT6, CT7 · **Depends on:** T0.

## Goal

Pin today's behaviour **on the untouched code** so every later task proves what it changed and what it did not:
the wire results of every touched method, the CLI output of every touched verb, telemetry rollups, trigger matching,
records tools — and a **census fixture**: a pre-migration store containing every shape the migrations must map.

## Files to create

- `aeon/internal/store/testdata/ct_census/` — a Go builder (`ct_census_test.go` helper `buildCensusStore(t)`) that
  creates, through **today's** store API (never raw SQL where an API exists, so the fixture is realistic):
  - explicit project with 0, 1 and 3 components;
  - implicit project with 1 component (the common case); implicit with 2 components (reached by today's
    `UpdateComponent` move); implicit with 0 components that is referenced by a goal; implicit with 0 components that
    nothing references;
  - epics and goals on each kind of project; `goal_component` rows; manual and loop tasks with `component_id`;
  - event triggers whose match uses `project` and `component` keys; automation events with project ids;
  - telemetry on every tier (record turns through the real record functions);
  - children with non-default `queue_advance`, `sizing_mode`, `max_parallel_agents`, `branch_prefix`.
  It also writes `expected.json`: for every row, the id and table it must have after T2+T3 (the CT5 mapping written
  out by hand, **not** computed by the migration code it checks).
- `aeon/internal/store/ct_golden_test.go` — store-level goldens: `ListComponents`, `ReadComponent`,
  `ComponentForRoot`, `ComponentQueueSettings`, `ComponentMaxParallelAgents`, `ListTaskRows` with a project filter,
  `ListGoals`, `ListEpics`, `ComponentTelemetry`, trigger matching over the census events — serialized to
  `testdata/ct_golden/store/*.json`.
- `aeon/internal/daemon/ct_golden_test.go` — wire goldens: `component.list/create/update`, `component.show` (catalog),
  `goal.show`, `task.list` with `project`, `telemetry.component`, `automation.trigger.list` — over a daemon on the
  census store.
- `aeon/cmd/aeon/ct_golden_test.go` — CLI goldens for `aeon goal list --project`, `aeon task list --project`,
  `aeon telemetry component`, `aeon project list/show` (the last two pin what is being **removed**, so T8's
  replacement output can be compared field by field).
- `aeon/internal/daemon/ct_records_golden_test.go` — records tools `component_list/show`, `project_list/show`,
  `epic_list`, `goal_list`, `loop_list` results.

## Rules for the goldens

- Deterministic: fixed clock (`s.Now` seam), fixed ids where the API allows, sorted output.
- Each golden file names the **later task** expected to change it and how (a header comment in the test, not in the
  JSON): e.g. "T5: `projectId` removed, `parentId`/`kind`/`childCount`/`effective` added; every other field
  byte-identical".
- Removed surfaces (`project.*`) are pinned so their information is proven to survive in the new reads.
