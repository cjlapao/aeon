# T11 · The CLI as a client of the daemon

**Prefix:** BP · **Rules:** BP12, BP13 · standing rule 1 · P34 · S45 PM4 · **Depends on:** T6, T7, T8. Parallel-safe with T10, T12.

## Goal

`aeon blueprint` becomes a **client of the socket methods** (parity is a test), gains the management verbs, retires `path` (a filesystem path no longer means anything), and offers `edit` and `export` for people who live in an editor. Offline it falls back to the same
code. `blueprint validate` keeps working with no daemon.

## Verbs (final set from T0's parity table; expected)

```
aeon blueprint list     [--origin system|user] [--q TEXT] [--json]          # now includes custom blueprints (the one intentional change)
aeon blueprint show     NAME [--json]                                       # content + report + references
aeon blueprint fields   [--json]                                            # unchanged
aeon blueprint validate [NAME | --file F] [--mode M] [--strict] [--json]    # unchanged semantics; by-name reads the database
aeon blueprint save     NAME --file F [--create-only] [--note N]            # reads the file client-side, sends content
aeon blueprint edit     NAME [--note N]                                     # export to a temp file → $EDITOR → save; invalid ⇒ temp file kept, path printed
aeon blueprint duplicate FROM NAME [--note N]
aeon blueprint delete   NAME [--yes]
aeon blueprint revert   NAME --rev N [--yes] [--note N]
aeon blueprint history  NAME [--limit N]
aeon blueprint diff     NAME [--a REV|current|shipped] [--b REV|current|shipped]
aeon blueprint usage    NAME [--json]
aeon blueprint lint     [NAME | --file F] [--json]
aeon blueprint export   [NAME ...] [--out DIR]                              # a DISPOSABLE mirror — never read back
aeon blueprint path NAME                                                     # retired: refuses naming export/edit
```

`delete` and `revert` need `--yes` (a seatbelt for typos, not a security control). `--yes` is **not** required for `save`/`duplicate` (they validate and are revertible).

## Files

- `aeon/cmd/aeon/blueprint.go` — extend `cmdBlueprint` dispatch; `list` reads through the door; `path` becomes a refusal: *"blueprints live in the database — use `aeon blueprint export` for a file copy or `aeon blueprint edit NAME` to change one"* (exit code per S23's usage-error convention; documented intentional change).
- `aeon/cmd/aeon/blueprint_client.go` — **new**: `blueprintDoor` with `socketDoor` (default) and `directDoor` (offline; the **same** `internal/daemon` write service/read adapters built over a directly opened store; actor `{cli,cli}`, `actor_kind='cli'`); `selectDoor()` as S45 T8 (dial; "no daemon" ⇒ direct + the fixed stderr line `daemon not running — applied directly to the store`; any other dial failure refuses). `validate --file` and `lint --file` need no store at all and work offline via `Analyze` with `embeddedSource` agents (printing the T3 offline-tools note).
- `aeon/cmd/aeon/blueprint_edit.go` — **new**: `edit` writes the content to `os.CreateTemp` (0600) under `$TMPDIR`, runs `$VISUAL`/`$EDITOR` (refuses if neither is set, naming both), reads the file back, and calls `blueprint.save`; invalid ⇒ prints the report, **keeps** the temp file and its path; unchanged ⇒ "no changes", temp file removed; never passes content on a command line (C17-style hygiene).
- `aeon/cmd/aeon/blueprint_parity_test.go` — the parity guard.

## The CLI re-validates nothing

Flag parsing refuses only what cannot be a value (a missing `--file`, an unreadable file, a non-numeric `--rev`). Every other refusal is the daemon's sentence/report printed **verbatim**; `diff` prints the daemon's unified diff verbatim; no client-side YAML editing (`duplicate` is a daemon call).

## Definition of done

- [x] All verbs dial the daemon; offline via the same code and says so; other dial errors refuse; `validate`/`lint --file` need no store.
- [x] Parity guard both directions; `path` retired with the named pointer; `edit`/`export` safe; daemon sentences/diffs verbatim.

## Do NOT

- Do not re-validate, re-serialize YAML, or diff client-side; do not read the export mirror back; do not pass content on a command line.
- Do not fall back on a non-"no daemon" error; do not keep a local copy of write logic; do not import `internal/store` outside `directDoor`.

**Observation for the record, not fixed here:** through a live daemon, a shipped row arrives on revision
**2** (an op-`update` write from the boot seed after the migration's own seed), while a store the offline
door seeds itself lands on revision **1** with the same content hash. Byte-parity therefore runs over a
row BOTH roads wrote (`parity-door`, saved from one file, then deleted with `--yes` on both) plus the
state-free answers (`list`, `fields`, `validate` of a shipped name); comparing `show two-step` would be
comparing T4/T5's arrival net across two databases. If the double-write is unintended it belongs to T5's
applier, not to this door.
