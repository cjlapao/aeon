## The migration drills (two migrations)

1. **Fresh apply** — the four tables, indexes and triggers; a fresh start seeds one system row per shipped blueprint with revision `seed`; the `proposal` rebuild accepts `blueprint_save` and refuses an unknown kind.
2. **Upgrade from a files-era state dir** — craft a store dir containing: every shipped blueprint **pristine**, one **older pristine** (`dev-loop` at the recorded legacy hash), one **edited** `dev-loop`-equivalent, two **custom** blueprints, one **invalid** file, a symlink and a stray non-yaml file → first start: adoption classes and counts exactly as T4 specifies; the edited blueprint's bytes equal the file's; the older pristine is updated in place by the seed; the invalid one is `refused` with diagnostics and `doctor` names it; the symlink/stray are reported skipped; **file bytes/mtimes/inodes unchanged**.
3. **Proposal-table rebuild drill** — every pre-existing proposal row/index preserved (count + checksum of id/status/payload before and after).
4. **Idempotent re-open/re-start/re-apply** — no second adoption, no second seed write, one ledger row per hash.
5. **Append-only** — `UPDATE`/`DELETE` on `blueprint_revision` fail. **Forward-only** — no rollback; recorded.
6. **Behavioural drill** — start a loop from an adopted blueprint, edit the blueprint, resume the loop: the loop uses its **pinned** content; a **new** loop uses the new content.
