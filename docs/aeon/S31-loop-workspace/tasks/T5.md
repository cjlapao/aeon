# T5 · Agent identity and the write_file line counts (D1, D8)

**Prefix:** LW · **Contract:** [`../brief.md`](../brief.md) §6 T5 · **Code map:** [`../CODEMAP.md`](../CODEMAP.md) §1, §8, §15 · **Depends:** T1 (same sink code path — do this with/after T1)

## What to do

- `agent` on every step event: the step's `Agent` (handler name), `"default"` when empty — **one helper**, not repeated at each call site.
- `write_file` computes `linesAdded`/`linesRemoved` against the previous content (a line-diff count, not a full diff) onto its result **metadata** — the sink copies them onto `step.tool.end` (`{stepId, tool, toolUseId, path, linesAdded, linesRemoved}`). **Does not change the tool's model-facing content** (N5 — the nine tools' behaviour is frozen; `Result.Content` stays byte-identical, metadata rides new fields per CODEMAP §8's seam).

## Notes

**Built 2026-10-24 (solo pass).**

- **The agent half was already T1's**; this pass added only the brief's remaining clause —
  `"default"` when empty — inside the ONE helper `stepEventPayload`, which every sink and every
  direct-emitted step event now funnels through. No call site normalizes anything.
- **`Result` grew fields, not behaviour (N5).** `tools.Result` gained `Path`, `LinesAdded`,
  `LinesRemoved` beside `Content`/`IsError`/`Summary`; `write`'s model-facing `Content` is the
  byte-identical sentence its pinned tests already guard (`wrote a.txt (5 bytes)` — unchanged,
  green). `runtime.ToolOutcome` mirrors the three fields and `daemon`'s `toolCaller` is the
  ONE conversion point; the sink copies verbatim onto `step.tool.end` and never re-derives.
- **Counts are multiset arithmetic, not a diff** — `countLineDiff` answers how many lines the
  write cost, not which moved. `a,b,c → a,x,c` is +1 −1 regardless of position; identical
  content is +0 −0 even reordered; emptying a file is −N with a trailing-newline convention
  (a trailing newline ends the last line, it is not a line). Table-tested.
- **Baseline is what was on disk at write time.** Delete-then-create is +N −0 (the delete's
  cost belongs to the delete); a second write onto a first write's output counts against the
  FIRST write's result, not the seed. A failed or refused write announces NOTHING (no path,
  no counts) — an announcement would claim a change that did not happen.
- **The prev-content read is best-effort by design**: a read failure for any reason counts the
  write as new (+N −0). Metadata must never fail a write that would otherwise succeed; the
  file is the record, the counts are the announcement. (Noted as a deliberate three-state
  lean: a permission-denied read of an existing file reads as new — under-reporting removals,
  never over-claiming them.)
- **`step.tool.end` now carries its `toolUseId`** (brief §5 asked): the real-execution emit
  gained the block's own id, so start/end/transcript-result pair without guessing.
- **Fixture:** `conformance/events/step-tool-end-write.json` (a new event FILE, not an edit —
  the pre-existing `step-tool.json` stays S5's read-shaped record; fixtures are history).
- **Not asserted as a threshold anywhere:** the counts are ints with no cap (a 1 MiB write is
  ≤ ~500k lines; the tool's own cap bounds the absurd case).

## Validation

New file → `+N −0`; overwrite → correct counts; delete-then-create counts; payload fixture for the enriched `step.tool.end` (conformance/events/); the write tool's own model-facing-output tests keep passing unchanged.
