## F-22 — `write_file` replay freezes on S8-era fixtures (Medium)

**What was found** (`internal/tools/toolset.go`'s own comment, confirmed while scoping this task): the
`write_file` alias is **deliberately** grant-side-only. `aliasWriteFile`'s own documentation: *"HIDDEN: not
in `ToolNames()`, not in any grant list or help text"* — the model is only ever told about `write`, never
`write_file`. A recorded fixture from before S11's rename, where the model's own turn literally emits a
`write_file` tool-use, is not a bug the dispatcher should accept — it is a fixture describing a model call
that could not happen against the current toolset at all, because the current toolset never advertises that
name.

**Resolution — this is a fixture-migration task, not a toolset-behavior change.** Making the call side also
accept `write_file` would reopen exactly the "two names reading as one tool" ambiguity `T19`'s own rulings
(SEC-051, SEC-059) closed — this task does not propose it, and whoever picks up this task should not either
without a real reason beyond "it would make old fixtures pass."

**Scope:**
1. Grep the whole test tree for any recorded SSE/fixture file where a model turn's `tool_use` block names
   `write_file` literally (not `aliasWriteFile`'s one documented production reference — this is about test
   data).
2. For each one found, replace the tool name with `write` (the same fix T9's own walk used for
   `s31-walk-write.sse`, applied repository-wide instead of to one fixture).
3. Add a lint/test — the same "assert it rather than hope it stays true" discipline this project uses
   everywhere — that fails CI if a new fixture is ever committed with a `write_file` tool-use block, so this
   does not quietly reappear fixture by fixture.

**Validation:** `grep -rl '"write_file"' --include="*.sse" --include="*fixture*"` (or the project's actual
fixture glob) returns zero hits for a model-emitted tool-use name after migration; the new lint test fails
against a deliberately reintroduced one and passes against the clean tree.

## F-26 — identical writes are indistinguishable from unreadable previous content (Low)

**What was found**: `linesAdded`/`linesRemoved` on `step.tool.end` are `omitempty` (D8, built in T5). An
identical rewrite (zero lines actually changed) and "previous content could not be read, so no count was
computed" both currently produce a payload with `path` and no count keys — byte-identical on the wire,
despite being two different facts (one is a real zero, the other is P31's third state, "could not tell").

**Resolution — a new field, additive, matching D8's own protocol-addition shape exactly.**

**Scope:**
1. Add `countsAvailable: bool` to `step.tool.end`'s payload for `write_file`/`write` calls — `true` whenever
   `linesAdded`/`linesRemoved` were actually computed (including the real-zero case), `false` when the
   previous content could not be read and no count was attempted. **Never omit the field itself** — a
   missing `countsAvailable` key would just recreate the exact ambiguity this task exists to close.
2. Wire the computing function (T5's own line-diff counter in `internal/tools/write.go` or wherever it
   landed) to report this explicitly rather than inferring it from whether the two count fields are present.
3. Update the conformance fixture for `step.tool.end` (T9's own fixture set) to include the new field;
   `make protogen`.
4. **Surface it in the UI** (T10's inspector Step tab, where line counts are shown) — a real zero renders
   as "no changes" or similar; an unavailable count renders as "unknown," never silently blank the way the
   wire payload used to force it to.

**Validation:** a fixture with an identical rewrite asserts `countsAvailable: true, linesAdded: 0,
linesRemoved: 0`; a fixture with unreadable previous content asserts `countsAvailable: false` and no count
keys; the UI test (extending T10's own suite) renders the two states distinctly, not as the same blank.
