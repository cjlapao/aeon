# T1 · Loop steps stream live (D1, D2)

**Prefix:** LW · **Contract:** [`../brief.md`](../brief.md) §6 T1 · **Code map:** [`../CODEMAP.md`](../CODEMAP.md) §1, §3, §4, §7, §15, cross-cutting (a)(g)

## Context

A step run by a loop publishes nothing: `daemon/blueprint.go:123` → `RunStepForLoop` → `handleStep(ctx, nil, raw)` with no `SubscriptionID` → `runtime.DiscardSink{}` (`protocol/step.go:311`). `stepSink` omits `StepID`; `Daemon.publish` passes projectRoot `""`. A subscriber filtered by `Filter{ProjectRoot}` therefore cannot select a loop step's stream — the loop chat screen cannot be live.

## What to do

- `RunStepForLoop` builds a real sink (not `DiscardSink`) publishing through `OnEvent` with the step's `projectRoot` and full identity (`stepId`, `loopId`, `lane`, `step`, `agent`). The step id is only known after `CreateRunningStep` — the `onCreated` callback (`step.go:376–380`) is the seam: capture the id before the first event is emitted.
- Fix `stepSink` to set `StepID` for the ad-hoc path too (`step.go:646–663`).
- `Daemon.publish` / `Table.OnEvent` gain a project-root argument (or a payload interface exposing one) so the root is not `""`; keep old call sites honest — pass `""` only where there genuinely is no project. Remember CODEMAP (g): an empty-root event matches EVERY subscriber, so real roots must be appended for step events and the foreign-root test is load-bearing.
- Emit `loop.step.dispatched` (`loopId, lane, step, stepId, agent, route, reasoningEffort`) from the loop's `Model` callback in `daemon/blueprint.go` once the step id exists — before the step's first event (D2).

## Validation

Daemon-level test (fake `scriptedModel`, `daemon/step_test.go:32–76` pattern): run a two-step blueprint; a subscriber with `Filter{ProjectRoot: root, Kinds: ["step.*","loop.*"]}` receives, **in order**: `loop.started`, `loop.step.dispatched` (stepId=N), `step.started` (stepId=N, loopId, agent), tool start/end, `step.done`, `loop.advanced`… A second subscriber with a different `ProjectRoot` receives **none** of them. Cursor replay (`After`) returns the same sequence. Conformance fixture for the enriched payload. **Measure and record here** (Q1): events/sec and `seq` allocations for a long `model.delta` reply — the number decides whether deltas need coalescing; do not coalesce speculatively.

## Notes

Built; full `go test ./...` green at commit.

**Q1 measured (not guessed)** — `TestLongModelDeltaStreamLoadIsMeasured` streams 10,000 `model.delta` events end to end through a real daemon with a filtered live subscriber: **733 ms, ~13,646 events/sec, 10,006 durable `seq` allocations (one row each), monotonic seq asserted**. Realistic streamed replies (hundreds of deltas/sec) sit two orders of magnitude below that ceiling, so the brief §10 default stands: **no delta coalescing** in this slice. The load-bearing assertion is the per-event seq allocation, not the rate — a future coalescer is what would change that number.

**Decisions.** `OnEvent` keeps ONE signature: step payloads carry their root unexported and expose `protocol.ProjectRooted`; anything not implementing it publishes daemon-wide ("" is honest absence for lifecycle/`ask.*`; the leak this fixes — CODEMAP (g) — is that a step event with "" matched every project-filtered subscriber). The sink is built AFTER the step row exists (the id cannot precede `CreateRunningStep`, K22), from ONE helper `stepEventPayload` — the whole reason `stepSink` could forget `StepID` for three slices was that sinks each built their own envelope. `loopStepSink` publishes whether or not anyone is subscribed (the durable log is what a late subscriber or reconnect replays); the subscription stays the GATE for ad-hoc steps, not the route. `LoopStepIdentity` is server-supplied via context like the `onCreated` seam — a client-settable identity is a client-chosen one (PL1 argument). `loop.step.dispatched` is ordered inside `onCreated`, after `MarkStepStarted` and before the runtime starts: the ordering is structural, not a race a reader must trust.

**Deviations.** (a) No dedicated conformance fixture for the enriched step payload: step-family kinds are not `Kinds()` entries (they ride `runtime.EventKinds()`), so none is required; the shape is pinned by the daemon tests, and the conformance directory is T9's to close. (b) The answer-resume sink (`continueAnsweredStep`) gained `stepId`/`agent`/root but not `loopId`/`lane`/`step` — no `LoopStepIdentity` is in scope on that path; loop-step continuation is T2's wiring. (c) `loop.step.dispatched` omits `reasoningEffort` until loop steps carry one — absent reads as "none named", never as the route's value (P31).

**Not verified.** Nothing Tauri-side (N1: no UI in this slice); ordering is proven against the scripted model, not a real provider.
