# T2 · Stop and continue on loop steps (D6)

## Notes (lead, at completion)

**What was built.** `Decide`/`AdvanceLoop` interpret a new `stopped` model-result
kind: the loop PARKS (`waiting`, `LastReason:"stopped"`, `StepStates` `waiting`,
`loop.waiting {reason:"stopped", stepId}`) — the `blocked` fall-through that
awaited an unknown kind is what `advance_stopped_test.go` first pinned red
(`status = "blocked", want waiting`). `CompleteSuspendedStep` gained the
matching re-park branch for a second stop of a CONTINUED step. The Model
callback maps a stopped step through `pause_reason=="user"` (never through
the runtime's kind — a stopped step reports `suspended` with no question, and
a loop "waiting on a question that does not exist" is the plausible wrong
answer D6 exists to prevent); the recovery reader maps `suspended`+`user` to
`stopped` before its no-question contradiction check.

**The store primitive.** `ContinueStepWithMessages` (checkpoint.go) flips
`suspended→running` and replaces the transcript in ONE transaction —
exactly-once across a crash: retry refused by the flip's own `status=
'suspended'` guard, crash-before-model leaves the running row already
carrying the message. `continue_step_test.go` pins all three histories.
`QuestionStore` gained `ContinueWithMessages`; the message-less path keeps
`MarkRunning` (there is nothing to deliver exactly once there).

**Deviations, stated.** (1) `step.continued`'s event payload lost `route` and
`reasoningEffort` (they moved to the response/`step.show`, per brief §5's
`stepId, loopId?` table); nothing consumed them. (2) `step.paused` was
RENAMED to `step.stopped` — one event per stop, no consumer existed for the
old name (checked: step.go only + generated contract). (3) `loopId` is
resolved through a new `LookupLoopID(slug, projectRoot)` seam — slug is
unique only WITH its root (the store's rule), so the seam asks for both;
absent seam/unknown loop means `loopId` is absent from the payload, never
guessed.

**Two findings that changed production code, both from hammering the new
daemon tests (9 of 20 package runs panicked before the fix):**
(a) **peek vs clear**: `stepCancels.wasStopped` reports-and-CLEARS (single
read by the owning run). The event sink must consult stop-ness on EVERY
terminal event, so consuming there stole the fact from `handleStep` — a
stopped step then completed as `cancelled` and BLOCKED its loop. New seam
`StepIsStopped` is the non-consuming peek; only the run reads
`StepWasStopped`. (b) **the runner must not advance a settled loop**:
`OnStepContinued` called `loopRunner.Start` for every completing hand-back,
even when `CompleteSuspendedStep` had ALREADY run the loop to `done`
(it saves `done` and emits `loop.finished` itself). That redundant post-`done`
pass wrote and published AFTER any observer had seen the loop finish —
goroutines outliving every watcher, which is exactly what the test's deferred
store close exposed. `Start` is now gated on the row reading `running`.
Also pinned by this: a stopped step publishes NO `step.done` at all (sink
suppression via the peek seam — the runtime's failed/ok terminal event for a
cancelled run is a lie either way; `step.stopped` is the terminal truth).

**Test-honesty note.** `waitLoopSettled` answers `status != running &&
!Active` — for a loop that was ALREADY waiting (mid-stop/continue sequences)
it answers immediately and means "settled", not "finished". Tests that wait
for an async hand-back must watch `loop.finished` on the WIRE first; the
deferred store close is unforgiving of goroutines that read the store after
their last observable act.

**Race:** `go test -race ./internal/daemon ./internal/loop` clean (and 12/12
plain package runs after the two fixes). Full `make ci`/`make test-race` at
slice end per plan.

**Amended 2026-10-30 — the same race on the `continueAnsweredStep` path, drained, not lifetime-tied.** The
race (b) above pinned on `OnStepContinued` had a second instance on the answer/continue resume path:
`continueAnsweredStep` was spawned as a bare `go t.continueAnsweredStep(...)` from **two** sites —
`answer.go:125` (the resume after an answer) and `step_stop.go:242` (the continue-after-stop) — and
neither drained it. A continuation goroutine that outlived the store's close wrote the DB after teardown,
so `database/sql` panicked on a nil `*sql.DB` (the location moved between runs — a race, not a fixed line).
The fix makes the spawn **trackable** and the shutdown **wait** on it, exactly as (b) gated `Start` on the
row: `continueAnsweredStepAsync` (`protocol/continuation.go`, new) does `Add(1)` / `defer Done()` around the
same `continueAnsweredStep` body and both spawn sites call it instead of the bare `go`; a
`continuationWG sync.WaitGroup` on `Table` (`method.go`) counts the live continuations; `Daemon.Shutdown`
(`daemon/terminal.go`) calls `Table.WaitContinuations()` **first** — before `termCancel`/`CloseAll` — so no
continuation writes the store while it is closing. The two blueprint fixtures
(`blueprint_stop_test.go` `gatedFixture`, `blueprint_stream_test.go` `newStreamFixture`) drain in a
`t.Cleanup` registered after `d := New(...)`, so the drain runs before the recovery store's own close
cleanup (LIFO). **Deviation, stated:** the drain is a *shutdown* contract, not a lifetime tie — a
continuation may still run and complete the resume after the request returns (that is the resume; P2's "a
suspended step has no process" is preserved); only the *store close* is ordered after the last
continuation. **Validation (2026-10-30, `go test -tags sqlite_fts5 -count=1 -v -run '…' ./internal/daemon/...`):**
the answer-dispatch tests that used to panic now pass — `TestApprovingStartsTheRun` (0.38s),
`TestDenyingReturnsToTheModelAndStartsNothing` (0.19s), `TestRunStartIsDeniedAtOnceOnAnUnattendedLoop`
(0.37s, both `declared-false`/`never-declared`) and `TestASteerQueuedMidCallSkipsTheTurnsToolsAndTheLoopCarriesOn`
(0.19s) — `ok 1.290s`, 0 panics, 0 `nil *sql.DB`; the full package run has 0 panics and only the two
pre-existing base-owned reds (`TestBrainstormReplayCreatesGoalAndAttachments`,
`TestT6WalkBrainstormRestsAndTalks`, both `loop.Run`/walk paths the change does not touch).

## Context

`step.stop`/`step.continue` reach only the ad-hoc path — `step_stop.go:35–44` says so itself ("What this does NOT do"). `step.continue` takes no message. Stopping a loop step must park the loop (`loop.waiting`, reason `stopped`) — never `failed`, never `blocked`.

## What to do

- Thread `TrackStep` into the loop path so `step.stop` reaches a loop step's context (stepCancels is keyed by stepID; the loop ctx comes from `d.loopRunner.Start(context.Background(), …)` — blueprint.go:184).
- The loop `Runner`'s model result gains a `stopped` kind; `AdvanceLoop` parks the loop as `waiting` with reason `stopped` (`loop.waiting {reason:"stopped", stepId}`), not failed/blocked (advance.go:166 is the `suspended` interpreter — extend the kind vocabulary honestly, don't overload).
- `step.continue` on a loop step resumes it and, on completion, hands the result back to `AdvanceLoop` exactly as a first run would (the `OnStepContinued` hook, blueprint.go:137–158, is the existing seam).
- `step.continue` gains `message?`: appended as a user text block before the resumed call, checkpointed before it.
- Remove the "What this does NOT do" paragraph and replace it with what is now true.
- Events: `step.stopped` / `step.continued` carry `stepId` (+ `loopId?`).

## Validation

Tests: stop a loop step mid-turn (fake model that blocks until cancelled) → loop `waiting/stopped`, step `pause_reason` set, no `step.done(failed)`; continue with a message → transcript contains it once, loop advances to the next lane; stop between tools (the `ctx.Err()` check inside the tool loop); stop of an unknown or finished step → existing named result. `make test-race` clean for `internal/daemon`, `internal/loop`.
