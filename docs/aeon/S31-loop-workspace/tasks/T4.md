# T4 · Steer injection in the runtime (D3, D5) — the core of the slice

**Prefix:** LW · **Contract:** [`../brief.md`](../brief.md) §6 T4 · **Code map:** [`../CODEMAP.md`](../CODEMAP.md) §5, §2, §14 · **Depends:** T3 (store), T2 (daemon/blueprint stable)

## Context

`step.steer` queues a message (and/or `route`/`reasoningEffort`) for a running step; it is injected at the next **turn boundary** (LW1 — the in-flight model call always finishes), **including when the turn ended in tool calls** — those calls are then not run, each answered with a synthetic "not run: the person steered" `tool_result` (LW2), the `question` tool alike (LW3 — the step does NOT suspend), and the model decides what to do next. Overrides apply from the next model call, stick for the rest of the step, persist on the step's saved request (LW6 — `LoadResume` replays with them; `compile.go`'s tools-vs-reasoning rule `reasoningFor` runs again on the new pair), and are announced by events.

## What to do

In `internal/runtime/loop.go RunLoop`, with a new optional `LoopDeps.Steers` dependency (`Pending(ctx) []Steer`, nil = feature off — I2: every pre-existing runtime test passes unchanged):

1. **Before every model call** (top of the loop, after the bounds checks, loop.go:166–195): drain pending steers; apply any `route`/`reasoningEffort` to `st.Request` (re-running the compile rule, LW6); append text — if the last message is a `user` message (tool results) append text blocks to it, else append a new `user` message. Persist with `CheckpointWithSteers`; emit `step.steer.delivered` and, when changed, `step.route.changed`.
2. **After the assistant turn is saved and before any tool runs** (just after the `len(turn.toolUses) == 0` check, loop.go:229): drain again; if pending, do **not** run the turn's tools — build one `user` message with a synthetic `tool_result` for **every** `tool_use` in the turn (`isError: true`, text *"not run: the person steered before this tool ran — read their message below and decide whether to call it again"*), then the steer text blocks **after** the results in the same message (LW2); persist with `CheckpointWithSteers`; emit `step.tool.skipped` per tool and `step.steer.delivered`; `continue` the loop.
3. Iteration bounds and deadlines apply unchanged — a steer buys nothing (Q4).

Daemon wiring: `Steers` wired to the store for **both** ad-hoc and loop paths; `step.steer` handler validates (LW4 — refused unless the step is `running`, each refusal naming the state and the method to use; LW10 — text ≤ 32 KiB, ≤ 16 pending per step) and emits `step.steer.queued`. `step.steers` lists; `step.steer.cancel` cancels (pending only). Recovery (S7): a resumed step drains `pending` on its first iteration like any other.

## Notes

**Built 2026-10-24 (solo pass).** What the task file could not know:

- **Drain #2 sits BEFORE the `len(turn.toolUses) == 0` finish check, not after it.** The
  task's line ("just after the check") would finish a tool-free turn even when a steer is
  pending — and the task's own validation ("steer during a text-only turn → the loop
  continues, no finish") requires the steer to intercept the finish. So: drain #1 after the
  bounds block (pre-first-call drain = recovery included); drain #2 before the finish check,
  covering both the tool-bearing and the would-finish cases.
- **One canonical fold, not two.** `runtime.AppendUserText` is exported and shared with
  `step.continue`'s injection (protocol's private `appendUserText` deleted at T2's
  handoff-review); the not-run closure `steeredResults` builds the same fold plus per-call
  results. `steeredNotRun`'s sentence is grep-locked by a code comment — keep it byte-exact.
- **Recovery.** `daemon/recover.go`'s RunOpts now carries `Steers`; the pre-resume tool-replay
  phase reads no queue (the tool results it replays are history, not turns), and the loop it
  hands over drains pending at its first boundary. Crash semantics live in the store's
  same-transaction guarantee (T3's tests), not in the runtime.
- **LW10 at the door, count of `pending` only.** Sixteen DELIVERED rows is a busy step, not a
  jammed queue; only unread rows assemble into one prompt. Accepted TOCTOU: two concurrent
  steers can both count 15 and land 16+1 — the cap is a guardrail against an accident, not a
  hostile boundary, and the store deliberately has no cap (its header argues why).
- **The cancel-after-drain race, and what the wire says.** The store commits the transcript
  and reports the row not-delivered (the withdrawal wins the row). The daemon's
  `CheckpointWithSteers` adapter returns nil for that shortfall — a step must not die from a
  race the person authored — while `step.steer.delivered` was already published at the drain.
  Recorded reading: the EVENT says the model read the text (true — the transcript committed);
  the ROW says whether the flip happened (authoritative, readable via `step.steers`/
  `step.steer.cancelled`). The two facts are different, and each has exactly one home.
- **Anthropic adapter, one user turn.** The brief pins "`tool_result` blocks then `text` in
  ONE user turn"; the shipped mapping flushed results into their own message before the text.
  Results now LEAD the turn they answer (`content = append(pendingResults, content...)`) for
  USER messages only — a run of results still flushes to its own user turn before an
  assistant message, and the pre-existing merge test (two separate result messages → one)
  stays green.
- **`step.route.changed` announces `Route.ID`** (the name the person used), not the model
  string; the change test compares IDs, so two routes with one model still announce.
- **`RunOpts.Steers` admitted to the I2 allow-list deliberately**: a source that can only READ
  the queue cannot deliver — delivery remains Checkpoint's exclusive act (its own error message
  prescribes this admission).
- **`step.steers` answers a BARE array** — the skeleton's conformance fixture is the contract;
  an earlier draft's wrapper struct was dropped. Empty reads as `[]`, never `null`.
- **Store gained `ReadSteer`** (surface table updated): the cancel params name only a steerId,
  and `step.steer.cancelled` is a STEP event — the owning step comes from the row, not the caller.
- **Route disappearance at drain time**: a steer naming a route deleted after queueing is
  delivered WITHOUT the override (the instruction still matters); the row keeps showing the
  unresolvable name — three states, none invented.
- **Crash-point tests**: simulated at the runtime boundary (the recording `Checkpoint` fake
  asserts the FIRST save containing the steer's text is the save naming its ids — text and
  delivery arrive in one write; the store's transaction test is T3's half of exactly-once).
- **Race**: `go test -race` clean for runtime, daemon, protocol, store (slice-wide
  `make test-race` re-runs at T9).

## Validation

Table-driven, fake model + fake tools: steer during a text-only turn → appears at the start of the next request exactly once; steer while the turn ends in two `tool_use`s → neither tool runs (fake records zero calls), next request carries two `isError` `tool_result`s then the text, in that order; turn with a `question` tool + pending steer → no suspension, question answered as not-run; route-only steer → next `ModelRequest.Route` changed, transcript unchanged, `step.route.changed` emitted; effort change on a route that refuses tools-with-reasoning → the compile rule's lowering applies; two steers in one turn → both delivered in order in one message; cancelled steer → never delivered. **Crash points:** kill after drain but before checkpoint → on resume still `pending`, delivered once; kill after checkpoint → `delivered`, present once, not re-delivered. **Provider shape:** resulting canonical messages are accepted by BOTH adapters' recorded request fixtures (Anthropic: `tool_result` blocks then `text` in one user turn; OpenAI-shaped: `tool` messages then a `user` message) — add recorded fixtures, never a live call. `make test-race` clean for `internal/runtime`.
