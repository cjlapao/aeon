# T1 — `schema.go`: `graph_node`, `graph_edge`

## Why this exists

Every later task in this slice needs somewhere to write rows. This task is where D1 and CG1 are enforced:
**no `sqlite-vec` reference anywhere in this task.** It would be easy to copy S22's or S28's migration
shape out of habit — both of those legitimately need a vector column, this slice does not, and a column
added "in case" is scope this slice explicitly declined (brief §6 N1).

**Read first:** S4's migration discipline (`internal/store/migrate.go`'s header comment — the framework's
`migrations.MigrationService` is the one and only runner; this task registers one more worker, it does not
build a second ledger). The current highest migration number in `schema.go` at the time this task starts is
whatever is live then — do not hardcode a number in this task file; find it.

## Scope

**1. `graph_node`**: `id`, `project_root`, `file_path`, `start_line`, `end_line`, `kind` (function, type,
file, …), `symbol` (qualified name), `language`. Indexed on `(project_root, symbol)` for exact-match lookup
and on `(project_root, file_path)` for per-file rebuild (T4 needs this index to make the scaling proof
possible at all).

**2. `graph_edge`**: `id`, `project_root`, `from_node_id`, `to_node_id`, `kind` (one of the six relations —
`design.md`'s table), `resolution` (`extracted` or `inferred`, D4). Foreign keys to `graph_node.id`.

**3. No vector column, no `sqlite-vec` import, anywhere in this migration.** Assert it as a test: the
migration's SQL text contains no `vec0` or `sqlite-vec`-specific syntax.

**4. Both tables are additive.** No existing table is altered; nothing here touches S22's or S28's schema.
