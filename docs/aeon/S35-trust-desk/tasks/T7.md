## Notes

**Built 2026-10-29.**

**`payload` is hand-typed, never read off `contract.ts`** — the same gap S34 T6 found for `mcp.status.probes`:
protogen infers a shape purely from the fixtures' own example JSON, and `proposal.create`/`proposal.list`'s
`payload` field merged my two fixtures' two different shapes (`mcp_server_add`'s and `policy_add`'s) into
one wrong struct — a problem no finite fixture set fixes, since every OTHER kind would still be wrong.
`lib/proposals.ts` hand-types `ProposalRow`/`McpServerAddPayload`/`McpServerRemovePayload` and every caller
casts at the point of use, documented inline exactly as T6's own precedent did. Two of `proposal.list`'s
generated PARAMS also came back narrower than reality (`Record<string, never>` — the one fixture's params
happened to be `{}`, so protogen inferred "no fields ever," not "status is optional") — `listProposals`
uses the untyped `rpc<T>()` escape hatch, `PolicyPage.tsx`'s pre-existing pattern for the same reason.

**The Tools-strip toggle's real semantics, decided here (the task's own text left this open):** GrantView
carries no underlying policy id, so there is no target row to `policy_remove`. The toggle always proposes
`policy_add` — the OPPOSITE action from the tool's current effective state (`available` → propose deny,
anything else → propose allow) — never `policy_remove`, which would need information this page's read
does not carry.

**`AgentTransitionControls` (enable/disable/revoke) are plain writes, confirmed live-immediately by test** —
no "proposed" language anywhere, refetching the Identity strip's own `Fact` after a successful call, exactly
TD5's distinction. Revoke's reason field is a client-side mirror of the CLI's own demand (required before
the button enables) — the real guard stays the daemon's CHECK (S35 T4), this is UX only.

**`McpPage`'s pending-add rows render through a separate `PendingAddRow` component, never the same
`ServerRowView`** — a server that exists only as a proposal has no transport/declaredBy data shaped like a
real `ServerConfig` row in every field (no `declaredBy` at all, since nothing in the live config declares
it yet), and forcing one component to handle both shapes would mean optional-everything. The no-Check rule
(MC11/TD8 extended to time) falls out structurally: `PendingAddRow` simply has no Check button to omit.

**The toast text's exact string is tested via `vi.spyOn(notifications, "push")`, not a DOM query** —
`notifications.push` only reaches a visible toast when a `<ToastProvider>` ancestor registered its API
(`router.tsx`'s `ProductApp`); a bench page rendered in isolation (every existing bench test's own
convention) has no such ancestor, so `toastApi` stays `null` and the push silently no-ops its DOM half.
Spying on the exported `notifications.push` call itself tests the real, exact string the production code
path sends, without needing to mount the whole app just for one page's test.

**`TestNoPageEverCallsProposalDecideMethods` landed inside `test/policy.test.tsx`'s own pre-existing
repo-grep test** (`"names no authoring method anywhere under src/"`), not a new file — that test already
walks every `src/**/*.{ts,tsx}` file for forbidden method-name substrings, built by string concatenation to
avoid self-matching; added `"proposal."+"commit"`/`"proposal."+"reject"` to its existing `forbidden` array
rather than duplicating the walk logic, mirroring T6's own backend amendment (a sibling check sharing
infrastructure, not a parallel implementation).

**Two pre-existing policy.test.tsx assertions needed updating, caught by the first full-suite run**:
`THE_FOUR_READS` (renamed `THE_ALLOWED_READS`) pinned PolicyPage's exact method set to four — widened to
five now that `ProposedPolicyPanel` also reads `proposal.list`. Comments referencing "the four reads" in
prose were updated alongside.
