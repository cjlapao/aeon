# T5 · The human door: `aeon proposal commit / reject / list`

**Prefix:** TD · **Rules:** TD4 (commit is the existing effect path plus a flip) · **Depends on:** T1–T4 —
this task composes them and adds no new effect path of its own.

## Goal

`cmd/aeon/proposal.go` (new), a CLI-only verb family: `aeon proposal list [--status proposed]`, `aeon
proposal commit <id>`, `aeon proposal reject <id> [--reason "..."]`. **This is the only place a proposal's
effect is ever applied** — nothing added by T1–T4 has a second commit path.

## Files to create / modify

- `cmd/aeon/proposal.go` — **new file**, same shape as `cmd/aeon/policy.go`'s header (the "why this verb is
  the only door" comment block, adapted): `cmdProposal(w, args)` dispatching `list`/`commit`/`reject`.
  - `cmdProposalList`: `st.ListProposals(status)` (T1), render newest-first with `command: aeon proposal
    commit <id>` per row exactly as the socket's `proposal.list` does (TD6 — same rendering, two doors,
    checked by a test that diffs the two, not by eyeballing).
  - `cmdProposalReject`: `st.DecideProposal(id, "rejected", by, reason, at)` (T1) — no reason required
    (TD5: rejecting loosens nothing). Double-reject hits the guarded error from T1.
  - `cmdProposalCommit`:
    1. Read the row (`st.ListProposals` filtered, or a new `st.GetProposal(id)` if T1 didn't already
       expose one — **check T1's actual exports before adding a new store function here**;
       `VERIFY: grep -n '^func.*Proposal' internal/store/proposal.go`).
    2. **Re-validate**: call T2's registry entry for the row's `kind` on the row's stored `payload` —
       **the same function `proposal.create` already ran**, not a second implementation (criterion 4).
    3. **Apply through the existing effect path**:
       - `policy_add`/`policy_remove`/`seed_corpus` → the T2-extracted corpus-insert function(s) from
         `cmd/aeon/policy.go`.
       - `mcp_server_add`/`mcp_server_remove` → build the new `Config` (current + the change) and call
         T4's `SaveConfig`.
    4. **Idempotent flip**: `st.DecideProposal(id, "committed", by, "", at)`. If the process crashed between
       step 3 and step 4 on a prior attempt, re-running `commit` on the same id must detect the effect is
       already present (for `policy_add`: the corpus row already exists with matching content; for
       `mcp_server_add`: the server is already in `mcp.json`) and complete only the flip, not reapply the
       effect a second time (which for a corpus insert could mean a duplicate rule, and for a config write
       is merely redundant but must not error). **Design this detection explicitly — do not assume
       idempotency from "the functions happen to be safe to call twice" without checking each one.**
    5. If step 3 fails (the effect could not be applied — e.g. disk full on the config write, or the
       corpus insert hit a constraint the create-time validation didn't catch), set `applied_error` on the
       row via a new `st.SetProposalAppliedError(id, msg string) error` (T1 didn't list this — add it here,
       in this task, since it's commit-specific) and leave `status = 'proposed'` for retry. **Do not flip
       to `committed` on a failed effect.**

## Tests

| Test | Asserts | Fails when |
| --- | --- | --- |
| `TestCommitAppliesThroughExistingPath` | committing a `policy_add` proposal produces the exact same corpus row `aeon policy add` would have produced for the same payload | a second, divergent apply path was written |
| `TestCommitRevalidatesNotJustTrusts` | a proposal that was valid at create time but would now fail validation (e.g. a server name that collided with one added by a *different*, later-committed proposal) is refused at commit, not blindly applied | re-validation step skipped |
| `TestCommitIdempotentAfterCrashBetweenEffectAndFlip` | simulate: apply the effect manually, do NOT flip, then run `commit` again → completes the flip, does not duplicate the effect | idempotency detection missing or wrong per-kind |
| `TestCommitSetsAppliedErrorOnFailure` | a forced effect failure (e.g. a read-only config directory in the test) leaves the row `proposed` with `applied_error` set, never silently `committed` | the failure path flips the status anyway |
| `TestDoubleCommitFails` | committing an already-`committed` row hits T1's guarded error | guard bypassed |
| `TestRejectNeedsNoReason` | reject with no `--reason` succeeds | TD5 violated in the other direction |
| `TestCliListMatchesSocketList` | `aeon proposal list`'s rendered rows equal `proposal.list`'s socket response for the same store, field for field | the two doors drifted (TD6) |

## Definition of done

- [x] `commit` re-validates through T2's exact registry entry, then applies through T2/T4's exact existing
      functions — no third implementation of any effect anywhere.
- [x] Idempotent recovery is a passing test for `policy_add` (the kind with a real effect to duplicate and
      a real constraint to trip); the four other kinds' idempotency shapes are measured and handled, per
      Notes, without a dedicated test for each.
- [x] A failed effect leaves the row `proposed` with `applied_error` set; a successful one flips to
      `committed` and never both.
- [x] CLI `list` and socket `proposal.list` render identically for the same store.

## Do NOT

- Do not write a new corpus-insert or config-write function for commit "to keep it self-contained" — call
  the exact functions T2/T4 already extracted.
- Do not flip a row to `committed` before confirming the effect actually applied.
- Do not require a reason for commit or reject (brief/design: `decide_reason` exists for the human's own
  record, not as a gate).

## Notes

**Built 2026-10-29.**

**T1's real exports (the task's own VERIFY)**: `CreateProposal`/`ListProposals`/`DiscardProposal`/
`DecideProposal` only — no single-row `GetProposal`, no `SetProposalAppliedError`. Added both to
`internal/store/proposal.go` here, exactly as the task's own text anticipated ("T1 didn't list this — add
it here, in this task, since it's commit-specific").

**Idempotency is heterogeneous across the five kinds, measured rather than assumed** — the task's own
warning ("do not assume idempotency from 'the functions happen to be safe to call twice'") turned out
precisely right, and in BOTH directions:
- `policy_add`'s effect (`boundary.Add`) is **not** safe to call twice — `policy.id` is the table's
  `PRIMARY KEY`, so a reapply hits a real SQL constraint violation, surfaced as a store-failure `*Reject`.
- `mcp_server_add`'s effect, reapplied, would trip `Config.Validate`'s own MC12 "configured twice" refusal
  on the exact server it already added — a different mechanism, same shape of false refusal.
- Both `*_remove` kinds have the OPPOSITE problem: re-validating through T2's exact registry entry (the
  membership check) **genuinely fails on a crash-retry**, because by the time the retry runs, the thing
  it's checking for already isn't there. Re-validation and idempotent retry are in real tension here, not
  merely apparent — resolved by ordering `effectAlreadyApplied` BEFORE re-validation and skipping both
  re-validate and apply when it answers true, so a crash-retry on a `*_remove` proposal never asks the
  question that would wrongly refuse it.
- `seed_corpus` needed no detection at all — `resolveSeedTargets`'s own validation never depends on
  current store state (only the embedded corpus and the requested agent names), and `runPolicySeedCorpus`'s
  own per-rule skip-if-exists discipline (D4) makes reapplying it naturally convergent regardless of how
  much of a prior attempt landed.

**Validate-then-apply collapsed to one call for three of the five kinds, deliberately — not a shortcut.**
`boundary.Add` (policy_add) and `mcp.SaveConfig` (both mcp kinds) already re-run T2's exact validator
internally as their own first step (`Add` calls `policy.ValidateForAdd`; `SaveConfig` calls
`Config.Validate()`). Calling `validateProposalPayload` explicitly before them is still done, uniformly
across all five kinds — the task's own instruction ("the same function `proposal.create` already ran, not
a second implementation") reads more naturally as "always call it explicitly," so that is what every path
does, even where the apply function would have caught the same refusal on its own. `policy_remove`
(`boundary.Remove`) and the `seed_corpus` resolve-step are the two cases where the explicit call is not
redundant — `Remove` itself validates nothing.

**`seed_corpus`'s apply reuses `runPolicySeedCorpus` itself, fed `io.Discard`** — not a re-implementation,
the literal function `aeon policy seed-corpus` calls, with its progress printing going nowhere. This is the
most direct reading of "apply through the existing effect path" available for this kind.

**A real PL15 collision, found immediately on the first full-suite run, not anticipated by this task's own
text**: `TestNoPolicyAuthoringReachesTheNarrowSurface` (`cmd/aeon/policy_test.go`) whitelists boundary
`Add`/`Remove` callers BY FILE NAME, and the whitelist named only `cmd/aeon/policy.go`. `cmd/aeon/proposal.go`
calling `boundary.Add`/`Remove` for `policy_add`/`policy_remove` commits tripped it immediately. This is
exactly the amendment T6 (next, explicitly scheduled last among backend tasks for this reason) is specced
to make at the `internal/protocol/` level — but this particular test is a CLI-side, whole-repo file
whitelist, a different mechanism than T6's own described scope. Added the one minimal entry
(`"cmd/aeon/proposal.go": true`) needed to keep the suite green now, documented inline as not a weakening
(the map already names two files for the same door) and explicitly deferring the FULL amendment to T6.

**The CLI actor is `store.Actor{Kind: "user", ID: "cli"}`** — there is no peer uid to read on the CLI side
(no socket connection); `DecideProposal`'s own schema-level CHECK (`decided_by_kind = 'user'`) is the real
backstop regardless of what string `ID` carries, so a literal `"cli"` names the fact plainly rather than
