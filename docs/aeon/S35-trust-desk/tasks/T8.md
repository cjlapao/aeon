## The real plumbing — bench pages render flat today; grouping needs the same pattern the primary rail already uses

Verified this session: `ui/src/app/PageLayout.tsx`'s `panelItems` maps `section === 'bench'` to a **flat**
list — `BENCH_PAGES.map((page) => ({slug: \`bench:${page.id}\`, type: 'link', ...}))` (around
`PageLayout.tsx:95-97`, `VERIFY` the exact lines as they will have shifted). The primary rail already does
grouping for its own items (`RAIL_ITEMS`, `PageLayout.tsx:35-45`): `{ slug: 'workspace', type: 'group',
label: 'Workspace' }` followed by its link items, with an optional `hasDivider: true`. **This task changes
the bench branch of `panelItems` to the same shape** — it is not a `BENCH_PAGES`-only change; the mapping
function in `PageLayout.tsx` itself needs to know where the groups start.

## Notes

**Built 2026-10-29.** Option (a) from the task's own open choice: `group?: "trust"` added directly to the
four `BENCH_PAGES` entries (`policy`/`agents`/`mcp`/`proposals`) — `BENCH_PAGES` IS `as const`-typed but a
heterogeneous array of object literals under `as const` is fine (each element keeps its own precise type;
nothing fights it), confirmed by a clean `tsc` run.

**A real finding beyond what the task's own text anticipated**: giving `panelItems` a `type: 'group'` item
positioned before its four links was NOT sufficient to render it. Read the kit's own `SideMenu` source
(`node_modules/@cjlapao/ui-kit/dist/index.js`) after the group silently failed to appear in a test: it
computes a `groupsWithVisibleLinks` set from each LINK item's own `groupName` field and only renders a
group item when `groupsWithVisibleLinks.has(group.slug)` — positional adjacency in the array is not what
the kit reads. `RAIL_ITEMS`' own `links('workspace')` helper doesn't carry this field either because
`AppRoute.menu.group` already IS that signal for the primary rail's own different code path — the bench
branch has no equivalent, so every Trust link in `panelItems` now explicitly carries `groupName:
'bench-group:trust'`, matching the group item's own `slug`. Recorded here since nothing in `design.md`/this
task's own text named this requirement, and a future group added to any other `section` branch will need
the same field or will reproduce exactly this silent-no-render bug.

**The group-rendering assertion uses `screen.getByText("Trust")` for the "exactly once" half** — React
Testing Library's `getBy*` queries throw unless precisely one match exists, which is a cleaner "exactly
one" proof than hand-rolling a `querySelectorAll` count (the first draft of this test used one and it
under-matched the kit's real DOM structure; the built-in query needed no guessing about which elements
carry the text).

**`TestBenchMenuOtherEightTabsStillFlat`** is asserted structurally rather than as a literal count: since
`screen.getByText("Trust")` already proves exactly one group label exists anywhere in the document, no
other tab can have picked one up — checking each of the eight's `previousElementSibling` isn't `"Trust"`
closes the loop without a second, parallel counting mechanism that could drift from the first.

Tests: `TestBenchMenuHasOneTrustGroupAboveFourRows` and `TestBenchMenuOtherEightTabsStillFlat` both landed
inside `product.test.tsx`'s existing secondary-menu test (not new standalone functions — the task's own
