## Goal

A `map[string]func(payload json.RawMessage) error` (or the real payload type each validator wants — do not
force everything through `json.RawMessage` if a validator's natural input is already a Go struct) with
exactly four entries, one per `proposal.kind`, each calling **existing** validation code:

| Kind | Validator | Source |
| --- | --- | --- |
| `policy_add` | the function from Q1 | `cmd/aeon/policy.go` |
| `policy_remove` | the function from Q1 (remove's own) | `cmd/aeon/policy.go` |
| `seed_corpus` | whole-corpus validation, one row (commit is all-or-nothing per TD3) | `cmd/aeon/policy.go`'s seed-corpus path |
| `mcp_server_add` | build the *would-be* `Config` (current file's `Config` + the candidate server) and call `Config.Validate()` verbatim | `internal/mcp/config.go:194` (confirmed this session) |

**Zero new validation logic** — if writing this task produces a single new `if` that decides whether a
payload is *valid* (as opposed to well-formed JSON), that logic belongs in the function being reused, not
here. TD3's whole point is that a bug fixed in the validator fixes both doors at once.

## Seam note — this registry is called from two places, by two different callers

`proposal.create` (T3, a socket method in `internal/protocol`) and `aeon proposal commit` (T5, a CLI verb
in `cmd/aeon`) both need to run the **same** validator on the **same** payload. Since validation logic must
live in `cmd/aeon` (it calls `cmd/aeon/policy.go`'s functions and `internal/mcp`'s `Config.Validate`, and
`internal/protocol` must not import either `internal/mcp` — S34 T3's finding — or reach into `cmd/aeon`),
`proposal.create`'s handler reaches this registry through a **function seam in `daemon.Options`**, the
exact pattern `S34-trust-bench/design.md`'s amended §5 and `S36-mcp-dispatch/design.md` MD1 both establish:
one new field, e.g. `ValidateProposal func(ctx context.Context, kind, payload string) error`, implemented
in `cmd/aeon`, wired in `serve.go` beside `wireAgentServices`/T3-of-S34's `wireMCPServices`. **Name this
precisely in this task's Notes** — T3 (this slice's T3, `proposal.create`) depends on the exact field name
chosen here.

**Q1 — the real answer, different from the task's own guess.** The task's text pointed at
`cmd/aeon/policy.go`'s `cmdPolicyAdd`/`cmdPolicyRemove`/`cmdPolicySeedCorpus` (confirmed those line numbers
were still accurate: 542/777/844). But the actual refusal logic for `policy_add` is **not** in `cmd/aeon`
at all — `cmdPolicyAdd` only parses flags and builds a `policy.Policy`; every real check (closed-set
re-parse, identifier policy, PL1 authorship, the per-type spec validator) runs inside
`(*policy.Store).Add` (`internal/policy/store.go:376`), interleaved with the write. Extracted the
validation-only prefix into `policy.ValidateForAdd(p Policy) (Policy, *Reject)` — pure, no `ctx`/`now`,
same file (`store.go`) so `checkAuthorship`'s pinned per-file call count
(`TestTheAuthorshipRuleAppearsInExactlyOnePlace`) stays at 1 def + 1 call, just moved within the file.
`Add` now calls it and does the write with the returned canonical `Policy`. Ran `internal/policy`'s full
suite immediately after — green, zero assertion changes — before touching the registry, matching the
task's own "mechanical first, separate commit" instruction even though the location differed from its
guess.

`seed_corpus`'s per-agent resolve-before-write step (D4's "every requested agent must be in the corpus
before any write") was the same situation: inline in `runPolicySeedCorpus`, using a function-local
`seedTarget` type. Hoisted `seedTarget` to file scope and extracted `resolveSeedTargets(corpus, agents)
([]seedTarget, error)` — same logic, copied verbatim, `runPolicySeedCorpus` now calls it.

`policy_remove` and both `mcp_server_*` kinds had **no existing reusable validation to extract** —
`(*policy.Store).Remove` is a bare `s.repo.PolicyRemove(ctx, id)` with no checks at all (removing an
unknown id is a benign no-op there, not a refusal), and there was no MCP writer of any kind before this
task (brief §2's own measured finding). Wrote fresh, minimal membership checks for both — not "new
validation logic" in TD3's forbidden sense (no new *decision rule* over a payload's correctness), just
existence tests the proposal flow needs that the direct CLI verbs never needed (a direct `remove` of a
missing id is harmless; a *proposal* to remove one wastes a human's future commit on a no-op, worth
catching at create time).

**`mcp_server_add`'s "build the would-be Config" helper** landed in `internal/mcp/config.go` as
`Config.WithServer(tier, agent string, srv ServerConfig) (Config, error)`, per the task's own fallback
instruction (config-shaped work belongs there). It is a pure copy-and-append — `c` itself is never
mutated (fresh slices via `append(append([]ServerConfig{}, …), srv)`, a fresh map via `maps.Copy` into a
new one) — returning a candidate the caller runs `Validate()` on. Both `mcp_server_add`'s proposal
validator (here) and whatever T4/T5's commit path builds will call this same builder, satisfying TD4
("the same code the direct CLI verb calls") even though there is no direct CLI verb to call — there never
was one; `WithServer` + `Validate` together **are** the one authoring path, which proposal.create and
commit both run through.
