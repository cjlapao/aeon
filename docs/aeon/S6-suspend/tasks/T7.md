# T7 — `protocol/answer.go`: the method, events, persistence order

**File(s):** `aeon/internal/protocol/answer.go`, `aeon/internal/protocol/step.go`, `aeon/internal/protocol/method.go`, `aeon/internal/protocol/answer_test.go`
**Engineer:** golang-engineer-loop · **Tech:** go · **Depends on:** T6 · **Est. changed lines:** ~290

## Context

The caller side of suspension, and **the order of two writes decides whether a crash is recoverable.**

```
persist transcript + manifest
persist the question        ← via S4's Ask, one transaction with its thread entry
set status = 'suspended'
```

If the process dies **between** the first two, a transcript with no question is recoverable: the step re-runs its
last turn, which is wasteful and correct. The reverse — a question with no transcript — is **not** recoverable:
there is a prompt with nothing behind it, and answering it resumes a step that has no history.

So the order is a requirement (D14), and the test forces a failure between them.

**The process must actually exit** (D3). Not a goroutine parked on a channel, not a timer, not a context with a
long deadline. Asserted by observation — no process, no parked goroutine — because a suspension that holds
anything is the design P2 rejects, and the symptom is a machine with twelve waiting loops holding twelve
processes, none surviving a reboot.

**Answering reuses S4's guarantee.** `store.Answer` already refuses a second answer, naming the existing
timestamp, in one transaction (S4 T7). Do not reimplement it — the first answer may already have resumed the
step, and an overwrite would leave it acting on a value the user believes they replaced.

**Read first:** `internal/protocol/step.go` (S5 T10) for the persistence pattern; `internal/store/chat.go`
(S4 T7) for `Ask` and `Answer`; `resume.go` (T3).

## What to do

**1. Extend `step.go`** to handle `{Kind: suspended}`: persist transcript and manifest, call `store.Ask`, set
`status='suspended'`, emit `question.asked`, and **return** — the handler's work is done and the process is free
to exit.

**2. `answer.go`** — the `answer` method. Params: `stepId` (or `questionId`), `answer`. It calls `store.Answer`,
reads back the step, the manifest, the transcript and the answered question, and calls `ResumeStep`.

**Resuming is not done inside the request.** Return promptly and let the resume proceed, emitting `step.*` events
— because a model turn inside an HTTP-or-socket request makes the client's timeout the step's deadline, and a
client disconnecting mid-request would strand it.

**3. Refusals** reuse S4's: answering twice → refused with the existing timestamp; no pending question → refused.
Both as named errors with all three parts, allocated in S2's registry.

**4. Emit `question.asked` and `question.answered`** so S9's app has them without a protocol change.

**5. Tests.** The write-order test forces a failure between the transcript and the question, then asserts the
state is recoverable — a transcript present, no question, and the step re-runnable. The no-process test observes
after the handler returns.

## Notes (lead, at completion)

**Amended 2026-10-30 — the answer resume path now drains its continuation, not just spawns it.**
`answer.go`'s resume path used to spawn the resumed step with a bare
`go t.continueAnsweredStep(...)` (:125). That goroutine could outlive the store's close and write the DB
after teardown, so `database/sql` panicked on a nil `*sql.DB` (a race — the location moved between runs).
The fix replaces the spawn with `t.continueAnsweredStepAsync(...)` (`protocol/continuation.go`, new):
`Add(1)` / `defer Done()` around the same body, tracked by a `continuationWG sync.WaitGroup` on `Table`
(`method.go`); `Daemon.Shutdown` (`daemon/terminal.go`) calls `Table.WaitContinuations()` **before**
`termCancel`/`CloseAll`, so no continuation writes the store after it closes. The resume itself is
unchanged — it still runs and completes after the answer request returns (that is the resume; a suspended
step has no process, P2) — only the *store close* is now ordered after the last continuation. The second
spawn site (`step_stop.go:242`) got the same change; the full account and validation are in **S31 T2's
Notes** (`../S31-loop-workspace/tasks/T2.md`). Validation here
(`go test -tags sqlite_fts5 -count=1 -v -run '…' ./internal/daemon/...`, 2026-10-30): the answer-dispatch
tests that used to panic pass — `TestApprovingStartsTheRun`,
`TestDenyingReturnsToTheModelAndStartsNothing`, `TestRunStartIsDeniedAtOnceOnAnUnattendedLoop`
(+`declared-false`/`never-declared`) — with 0 panics and 0 `nil *sql.DB`.
