# T5 — Compaction: the summary, the replacement, the cost

**File(s):** `aeon/internal/runtime/compact.go`, `aeon/internal/runtime/loop.go`, `aeon/internal/runtime/compact_summary_test.go`
**Engineer:** golang-engineer-loop · **Tech:** go · **Depends on:** T4 · **Est. changed lines:** ~270

## Context

Separate from T4 because it fails differently: T4 is about **what may be replaced**, this is about **what
replaces it and what it costs**.

**The summary's cost is added to the step's total, and recorded separately** (D13, O2). A compaction call goes
through the same `model.Client` and costs real money; not counting it is a hole in exactly the accounting S3, S4
and S5 have each preserved. And recording it separately matters because a user asking "why did this step cost
that" needs to see the compaction as a **line**, not as a discrepancy between the total and the visible calls.

**A summary that exceeds its own bound is an inadmissible compaction** (O6), not a truncated summary. A truncated
summary is a transcript that **lies about what it replaced** — the model reads it as a complete account of
sixteen messages when it is a fragment of one.

**No admissible range means `blocked`** (K28, D12), with a reason. A truncation to fit fails later, at the
provider, with an error about signatures or a rejected turn. `blocked` fails here, legibly, where the reason can
name the cause.

**Read first:** `compact.go` as T4 left it; `internal/runtime/loop.go` for the trigger point;
`internal/model/cost.go` (S3 T4) for how cost is composed.

## What to do

**1. `Compact(ctx, st, deps) CompactResult`:**

- `SelectRange` (T4). Refusal → return it; the loop turns it into `blocked`.
- Ask the model — through the **injected** `Client` — to summarise the selected range.
- If the summary exceeds its stated bound, treat the compaction as **inadmissible** (O6) and return a refusal.
- Replace the range with **one `user`-role message** carrying the summary.
- Return the new transcript, the summary's `Usage`, and its `Cost`.

**2. Wire the trigger into the loop.** Before each iteration, if `EstimateTokens` exceeds the budget, compact.
On a refusal, return `blocked` with the reason.

**3. Cost attribution.** Add the summary's cost to the step's total **and** record its usage separately on the
step, so the CLI and the app can show it as a line.

**4. Emit `step.compacted`** carrying the replaced range, the estimate before and after, and the summary's cost.
That event is how the demo shows compaction at all — the thing it prevents is a failure nobody sees.

**5. Tests.** The cost test compares a compacted step's total against the sum of its model calls including the
summary — a compaction whose cost vanished would otherwise look correct.
