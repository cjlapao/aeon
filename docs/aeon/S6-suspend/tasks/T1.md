# T1 — `tools/question.go`: the ninth tool, never executed

**File(s):** `aeon/internal/tools/question.go`, `aeon/internal/tools/question_test.go`
**Engineer:** golang-engineer-loop · **Tech:** go · **Depends on:** — · **Est. changed lines:** ~190

## Context

First, because suspension detection needs a tool to detect. And unusual among the nine: **its execute function
is unreachable and panics** (W15).

The runtime recognises `question` by name and suspends (K18), so nothing ever calls it. Writing the execute as a
panic naming K18 means that if it is ever reached, the error says why that is a runtime bug — rather than
fabricating an answer nobody gave, which is the failure mode a silent no-op would produce.

**Its description is the deliverable, and it is load-bearing in a way no other tool's is.** For `read` or `bash`,
a vague description costs a wasted call. For `question`, the description is the **only** instruction a model
receives about when interrupting a human is appropriate — and a model that asks about everything is as useless as
one that asks about nothing. The calibration lives in prose.

**It is not in the default grant list.** `aeon step` grants `read`; `question` is granted when a handler declares
it. That keeps S5's allow-list discipline intact.

**Read first:** `docs/_archive/aeon-v1-horizontal/05-tools/tasks/T10.md` — the superseded slice's version of this tool;
`internal/tools/toolset.go` (S5 T7) for the grant vocabulary; `docs/_archive/aeon-v1-horizontal/04-permissions/design.md` G5–G7 for
what a `permission` kind will mean at S11.

## What to do

**1. `question.go`** — the `ToolSpec`:

- `name: "question"`
- parameters: `text` (required, string), `options` (optional, array of strings), `kind` (optional, one of
  `clarify | gate | permission | free`, defaulting to `free`)
- `execute`: **panics**, with a message stating that `question` is recognised by name and suspended by the
  runtime (K18), and that reaching this line is a bug

`options` present means a structured choice; absent means free-form. Both are needed — a gate wants options, a
clarify conversation does not.

**2. Write the description deliberately.** It must tell the model:

- ask when a decision is **the user's to make** — a trade-off, a preference, an irreversible action, or an
  ambiguity where two readings lead to materially different work
- do **not** ask what the code, the task or a tool can answer
- do **not** ask permission to do what the task already asked for
- **asking suspends the step**, possibly for hours; the answer arrives as this tool's result

That last point matters most: a model that does not know asking is expensive will ask casually.

**3. Add it to the grant vocabulary, not the default grant list.** A handler declaring `question` gets it; the
default step does not.

**4. Write the tests.** The description-content test asserts the four points above, so a later rewrite that drops
the cost warning fails rather than quietly changing the calibration.
