# T7 — Cost — unmetered routes, and attribution by provider

## Notes (2026-10-26, at implementation)

**Q5, answered from the code first.** The compute path was already honest:
`ComputeCost` checks no-prices FIRST (`no-price-for-route`), then no-usage
(`provider-omitted-usage`), and `partial` keeps a floor — S3 got M9 right at
the layer the spec suspected. The zero-coercion the question warned about was
real, but it lived **one layer up, in the renderers**: `formatUSD(0)` returned
the literal `"0.00"`, which the `ask` known-line printed as **`$0.00`** — the
exact forbidden claim — and every sub-cent figure rendered through `%.5f`
came out `"$0.00430"`, `"+$0.00062"`, digits that begin with the look of free.
Two pre-existing tests had even *pinned* those strings; they evolved with the
fix, their point (the figures ARE visible on the line) unchanged. A rendering
rule that makes a real 0.43-cent charge read as free to a skimming eye is the
same D9 failure wearing a different hat.

**One computation, two renderers (D16, P34).** `store.LoopCostRows` READS
(cost from the columns — never inferred, D12 — and the provenance of the
step's LAST assistant turn: billing follows the turn that ANSWERED, M26);
`model.AttributeCosts` computes (group by route+provider+model — O4's
two-routes-one-model case is pinned; the total folds through `Add`, which
keeps floors, so P32/D5's "at least" needs no second sum anywhere);
`daemon.viewLoop` decorates `LoopView.CostAttribution` — same data `loop.show`
already returns, so S31's panel gets the per-route table rather than a lone
total; `cmd/aeon`'s `writeCostLedger` FORMATS and never adds. `MoneyString`
is the one money renderer: `≥$0.01` prints `%.5f` (every pre-existing figure
assertion keeps its exact bytes), sub-cent prints scientific so nothing can
begin `$0.00`, and a reported-and-priced-to-nothing usage spells itself out
instead of showing `$0.00`.

**Deviations, named.** `files_expected` listed four files; the ledger needs
its read side in `internal/store/steps.go` (`LoopCostRows`, plus the surface
table entry and the documented model-name set — `CostRow`, and `AttributeCosts`
as a comment-named reference in the `StoreTranscript` tradition), and each of
the nine gates lives where its code lives: eight in `internal/model/cost_test.go`,
the completion gate in `internal/runtime/cost_ledger_test.go`, the view gate in
`internal/daemon/cost_attribution_test.go`, the table gate in
`cmd/aeon/loop_run_test.go`. The renderer unification touched
`store_verbs.go`, `ask.go` and `answer.go` — leaving three money renderers and
making the fourth obey D9 would have been the task done wrong.

**What was not verified.** No provider was contacted (I7): the ledger is
exercised from store rows through the daemon view to the CLI printer, and the
app's footprint panel consumes the same `costAttribution` JSON that
`TestLoopViewCarriesPerRouteAttribution` pins — the panel's pixels are S31/T10
work, and the zero-coercion sweep covers the Go renderers that exist today,
not a UI one written later.

## Why this exists

Two things S3's cost path could not do, both of which become ordinary the moment a loop can switch providers.

## Scope

### An unmetered route is `unknown` with a reason (M30, D9)

**Not `$0.00`. Not a fourth state.**

A local model's cost is genuinely unknown to Aeon — electricity and hardware are real, and Aeon has no idea what either
costs you. `$0.00` would be a **claim**, and a false one.

`unknown` already means exactly this, so M30 reuses M10's three states rather than extending them. What is new is the
**reason**:

```
cost: unknown — route 'local' is unmetered (no price declared)
```

**Confirm Q5 first**: what does S3's cost path do today when usage is entirely absent? **If it produces zero rather than
`unknown`, that is a bug M9 already forbade** — *"coercing absent to zero reports a $0 cost as though it were known"* —
and fixing it is part of this task.

### Attribution by provider (M26, D5)

T1's provenance makes this possible. Before it, a transcript spanning providers could report a total and nothing more.

```
  anthropic  claude-…      $0.0412   known
  openai     gpt-…         $0.0180   known
  local      qwen2.5-…     unknown — route unmetered
                   total   at least $0.0592
```

**Grouped by route, not only by provider** (O4). Two routes can share a provider and model with different prices, and the
ledger is the one place that difference matters.

### The total over an `unknown` is a floor (D5)

`at least $0.0592`, not `$0.0592`.

This is S9's rule — *a total over a `partial` part is itself a floor* — arriving at the case where a loop **legitimately**
mixes a metered model with an unmetered one, which is exactly what a laptop-plus-cloud setup looks like.

A confident total over an uncertain component is the same error one level up, and a total is what someone quotes.

### The attribution reaches the daemon surface, not only `cmd/aeon/loop.go` (D16, I10, P34 — added 2026-10-26)

**The per-route breakdown this task builds for the CLI's table must also be on `LoopView`** (built in
`internal/daemon/blueprint.go`, the type `loop.show`/`loop.list` already return) — otherwise S31's
`LOOP FOOTPRINT` panel can show a single total but never the per-route table this task exists to produce,
and the app silently stays one step behind the CLI for the exact fact this task is about. Same floor
semantics, same "at least $X" wording, same route grouping — one computation, two renderers (the CLI table
and S31's footprint panel), never two implementations of the sum.

### Not in scope

Any new cost state. M10's three are complete, and M30 is a reason rather than a state.
