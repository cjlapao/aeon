## Notes (2026-10-26, at implementation)

**A refusal needs a declaration to stand on.** The spec's table row says the route "lacks the capability,
*honestly*" — and honesty here is a **declaration**: `WireCapabilities == nil` (never said anything, every
pre-S18 route) is NOT the operator saying "no", and refusing on it would strand every route that runs tools
perfectly well. Only `[]` — declared-none, the distinction T2's storage fight preserved — refuses. Same
division as T3's `FirstContradiction` judging only declared capabilities: the operator's stated answer
governs, the absence of one is nobody's verdict (I5, read from both directions).

**Placement: the first statement of `RunStep`.** The spec said "in the runtime, before `RunStep` reaches a
provider"; the strongest form of that is before the sink is wrapped, before the first event, before the
opening checkpoint — a refused step emits nothing, persists nothing, sends nothing. It is a return path
*outside* the loop, so T9's "returns exactly once" stands. Every step path converges on `RunStep` (the
daemon's `StepRunner.Run`, blueprint loops, recovery), so one call site guards them all — and the T3
contradiction gate stays exactly where it is, upstream of this one: different failure, different door,
different sentence, no overlap.

**The structured refusal.** `*runtime.CapabilityRefusal{Capability, RouteID}` — `errors.As` discriminates it
from any transport failure (DB19); the `Error()` text is the spec's sentence verbatim including
"(no model call was made)", and it is the ONE formatter — surfaces print `Reason`, they do not rebuild it.

**`Required` reads the STEP, not the route:** tools iff `len(req.Tools) > 0` (grant-filtered already),
thinking iff `req.ReasoningEffort != ""` (assembly may have lowered it; `reasoningFor` decided on the step,
so the need is the step's). The route's own default effort is the route owner's configuration — a step that
inherited it is not "requesting" thinking. Empty toolset + empty effort = needs nothing.

**Deviations.** (1) `files_expected` missed the one wiring line — `Check` is called at the top of
`runstep.go` (the test greps for exactly `Check(req.Route, req)` there, so the gate cannot silently drift
out of the runtime). (2) The first missing capability in `Required`'s order is the one named — a sentence
naming both would invite "fix" for the capability the operator never meant to offer. (3) The two
`// absent-direction` tests (`TestUndeclaredRouteIsNotRefused`, `TestDeclaredSufficientRouteRuns`) are not
in the spec's table; they are the gate's other half — a check that over-refuses is the same bug as one that
under-refuses, and the nil-vs-[] trap is exactly where it would hide (it bit the test's own helper during
development: `append([]string(nil))` is nil, not declared-none, and the DomainError test caught it).

**Measured.** All eight spec tests plus the two direction tests pass (`go test ./internal/runtime/`);
loop/daemon/protocol regression-green — every existing fixture routes through undeclared (nil) routes, which
proves the backward-compatibility claim on the existing corpus rather than asserting it. No test reaches a
provider (I7); `TestClientSpyIsAtZero` and `TestCheckRunsBeforeContextResolution` assert on spies, not on
the refusal's own words (D8/C6).

# T4 — The pre-call capability check

## Why this exists

A step whose handler grants `bash` needs a model that can call tools. **Discovering otherwise at the first tool call wastes
every step before it** (M29).

This is the same instinct as S8's L9 — validation loud and early enough to be actionable — applied one layer down.

## Scope

```go
// Required returns the capabilities a compiled step needs.
func Required(req StepRequest) []model.Capability

// Check refuses before any model call.
func Check(route model.Route, req StepRequest) error
```

A step needs `tools` if its toolset is non-empty. It needs `thinking` if its handler requests it. Nothing else in the
current set is step-dependent — but the function's shape is what matters, because a future capability that is will have a
place.

### In the runtime, not the adapter (I3, E-checks)

**An adapter refusing a request it cannot serve is too late.** By then the step has been compiled and its context
resolved — which for a step with a large declared context is real work, and for one that resolved context through retrieval
(S22) will be more.

So the check sits in the runtime, before `RunStep` reaches a provider.

### The refusal names both sides

```
refused: step requires capability 'tools'; route 'local-notools' does not have it
         (no model call was made)
```

**"No model call was made" is part of the message**, because the first question anyone asks a refusal about a paid API is
whether they were charged.

And it is a **domain refusal**, not an error (S4's DB19) — the caller must be able to tell it from a network failure.

### Distinct from T3's contradiction

Two different failures, two different messages:

| Situation | Message |
| --- | --- |
| The route **lacks** the capability, honestly | *step requires 'tools'; route does not have it* (this task) |
| The route **claims** it and a probe disagreed | *route declares 'tools' but the probe contradicted it* (T3) |

Conflating them would tell someone to change their route when the route was right and the server was wrong, or the reverse.

## Tests

| Test | Asserts |
| --- | --- |
| `TestMissingCapabilityRefusesBeforeTheCall` | A step needing `tools` against a route without them is refused (D8) |
| `TestClientSpyIsAtZero` | **Nothing was sent.** Asserted on the model client spy, not on the returned error (D8, C6) |
| `TestCheckIsInTheRuntimeNotTheAdapter` | A grep: no adapter performs this check. It happens before compilation reaches a provider |
| `TestRequiredDerivesFromTheToolset` | A non-empty toolset requires `tools`; an empty one does not |
| `TestRefusalNamesBothSides` | The capability and the route, plus "no model call was made" |
| `TestRefusalIsADomainError` | Distinguishable from a transport failure (S4's DB19) |
| `TestDistinctFromContradiction` | The two messages differ, asserted as unequal — they call for opposite fixes |
| `TestCheckRunsBeforeContextResolution` | Asserted on ordering: a step with a large declared context is refused without resolving it |

`TestCheckRunsBeforeContextResolution` is the one that earns its keep later. Today context resolution is cheap; after S22
it involves a vector query, and a check that runs after it wastes that too.

## Definition of done

- [ ] `Required` derives capabilities from the compiled step
- [ ] `Check` refuses before any model call, with the spy at zero
- [ ] The check lives in the runtime; no adapter performs it
- [ ] The refusal names the capability, the route, and that nothing was sent
- [ ] It is a domain refusal, distinguishable from a transport failure
- [ ] Its message differs from T3's contradiction
- [ ] It runs before context resolution
- [ ] `make test`, `make lint` green
