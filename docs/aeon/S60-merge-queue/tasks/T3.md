# T3 · `internal/mergequeue`: the pure state machine, `ValidateEnqueue`, the store adapter

**Prefix:** MQ · **Rules:** MQ3, MQ5, MQ9, MQ13, MQ14 · P3 · **Depends on:** T0 (core); step 5 needs T2. Parallel-safe with T2.

## Goal

The decisions of the queue live in one pure, exhaustively tested package; the daemon, the CLI and the tools never re-derive them.

## Files

- `internal/mergequeue/state.go` — `Status` consts (the closed nine), `ReasonKind` consts (closed), `Mode`, `ConflictPolicy`, `LandMethod` — each with `Valid()` exhaustive switches mirrored by a
  test against the migration's `CHECK` text (parsed from the embedded SQL — a drift fails).
- `internal/mergequeue/transitions.go` — `Legal(from, to) bool` and `Describe(from) []Move` (the legal moves with a one-sentence meaning — the source of `mergequeue.vocabulary`, T8).
- `internal/mergequeue/decide.go` — `Next(Item, Facts) Decision` (pure): `Facts{SlotHolder, HeadOfBase, Config, LoopStates (landing/resolve), Behind *int, BehindState, GrantMerge bool, RuleOK *bool, HeadSHAMatches bool, CatchUps}`; `Decision{To Status, Reason, StartLoop {blueprint,...}?, Sentence string}`.
  Implements the MQ5 table row for row; unknown/`unavailable` facts **never** advance (three states, P31); `mode=off` ⇒ `Hold("mode is off")`.
- `internal/mergequeue/validate.go` — `ValidateEnqueue(EnqueueRequest, RepoFacts) error` with the MQ14/MQ15 refusal sentences: branch missing, base unknown, duplicate open item, repository without a primary root, branch equals base, branch name fails the identity regex.
- `internal/mergequeue/describe.go` — `Describe(item)` one-sentence status text from ids/enums (the "next-step sentence" for `mergequeue.show`); `Statement(config change)` for authority-widening settings (`auto`).
- `internal/mergequeue/adapter.go` — **step 5, needs T2**: `Service` over a narrow store interface (`mergequeueStore`: the T2 functions) implementing `Enqueue`, `Dequeue`, `Reorder`, `Retry`, `Settings`, `Transition` with `ValidateEnqueue` and `Legal` in front of every write; actor passed in, never read from params.

## Behaviour (each a test)

1. Every `(from, to)` pair is checked: legal pairs are exactly MQ5's; `Legal` over the full 9×9 matrix equals a **hand-written** table in the test (not derived from the code).
2. `Next` for each state × facts combination in a table-driven test with a name per row; at minimum: slot taken ⇒ stay `queued`; head with slot free and `mode=manual` ⇒ `catching_up`; behind>0 at `ready` ⇒ `queued` (while `CatchUps < max`) else `failed(stale-exhausted)`; red gate ⇒ `failed(gate-failed)`; `mode=auto` ∧ no grant ⇒ `failed(denied)` **only when the `forge.land` step actually denied** (the pure core never invents a denial); mismatched SHAs ⇒ `failed(head-moved)`.
3. `unavailable` staleness never produces a transition and the `Decision.Sentence` says why.
4. `ValidateEnqueue` create/commit parity: the same function serves the socket, the blueprint action and the proposal commit (T9) — the test calls it from all three entry points' adapters.

**Things the task file could not know, measured this session:**

- **`Describe` was already spoken for**: the spec gives `Describe(from) []Move` to
  transitions.go and `Describe(item)` to describe.go — one package, one name. The
  item-sentence keeps `Describe` (it is the outward one, T8 renders it); the moves list
  is **`Moves(from)`**. `Moves` and `Legal` are cross-checked pair-by-pair in the matrix
  test, so the rename costs no coverage.
- **`Item.EndReason`** was added to the pure `Item` (the store's `ReasonKind` maps onto
  it) — a `failed` hold and a `Describe` must say WHICH failure; the spec's `Item` shape
  could not, and inventing the reason in prose was the wrong fix.
- **`Facts` grew the fields the spec's own tests demand** beyond its list:
  `GateResult *bool` (the red-gate row), `Conflict *ConflictFacts{Count}` (conflict
  carries a COUNT — paths have no field to travel in, the structural half of SEC-033),
  `Landed`/`Ancestor *bool`/`Refused`/`LandDenial`/`Aborted`/`LandRequested`/
  `IntegrationSHA`. Three-state fields are pointers; the zero-facts test proves none of
  them defaults to a confident move.
- **`failed(denied)` stays honest**: `Next` reaches it only through `Facts.LandDenial`
  (the step's own word). `mode=auto ∧ no grant` HOLDS with a sentence saying the step's
  denial will end it — a row that exists precisely because the naive implementation
  would invent the denial here (named test: "auto without the grant HOLDS — the core
  invents no denial").
- **`Service.Retry` refuses `not-retryable` on a non-failed item** before the store:
  MQ5's `ready → queued` edge belongs to the DRIVER's base-move bounce (facts-carrying
  `Transition`), not to a person's retry verb — same edge, different doors, so the
  person-facing door owns the extra guard (deviation, recorded).
- The service NEVER retries a lost race: `stale-state` travels back verbatim, and the
  fake store counts calls to prove exactly one (the spec's own guard, canaried).
- Enqueue idempotency lives in the SERVICE (open-row reuse answers before the
  validator); `ValidateEnqueue`'s `duplicate-open` refusal stays as the last line for
  any caller that skipped reuse — the MQ14 "one validator" parity holds (T8/T6/T9
  record which door reuses).
- The migration-lock test reads `store.Migrations()`'s `.SQL` (whitespace-normalised —
  the same trick T2's store-side lock uses), so the five vocabularies are pinned against
  the EMBEDDED DDL from the outside, without the core importing the store (`state.go`
  stays import-free; the test file is the only store importer).
