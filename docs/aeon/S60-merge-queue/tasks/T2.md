## Behaviour

1. `EnqueueMergeItem`: refuses an unknown `component_root`, an empty branch/base, and a duplicate **open** branch (`merge_queue_one_open` ⇒ refusal naming the existing item id); assigns
   `position = max(position among open items of (root, base)) + 1000` (gaps allow reorder without a rewrite of every row); writes the `queued` transition event (`from NULL`).
2. `TransitionMergeItem` is the **only** status writer. A lost race (`status ≠ from`) returns `MergeRefusal{Kind:"stale-state", Current: <status>}` — never an overwrite.
   Entering a slot state while another item holds the slot returns `MergeRefusal{Kind:"slot-taken", Holder: <id>}` (the partial index is the backstop; the store checks first so the refusal has a sentence).
3. `ReorderMergeItems` moves one `queued` item before another or to the end; refuses non-`queued` items; one transaction; one `kind='reorder'` event with the ids.
4. Events: actor from the caller (never SQL); `detail` produced by one function `eventDetail(facts)` from ids, counts, enums, SHAs and conflict **paths** (≤ 100, ≤ 512 bytes each,
   control chars refused) — a test greps that no other column can carry text.
5. `merge_queue_event` rows survive any item change; no code path deletes either table's rows (grep test: no `DELETE FROM merge_queue`).
