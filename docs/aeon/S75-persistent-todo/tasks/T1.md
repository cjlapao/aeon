# T1 · Store: the persisted list

**Rules:** TD1, TD4, TD11, TD12. **Depends on:** nothing.

## Goal

The store holds a loop's todo list, its revision and its closed state, with accessors the daemon and the tool seam call. Nothing reads or writes it yet.

## Steps

1. Read the latest migration in `internal/store/schema.go` and its naming (`migrationNNNN`, the registry list near line 88). Add one additive migration creating `loop_todo` and `loop_todo_list` per TD1, with `ON DELETE CASCADE` from the loop (look at how `question` references `loop (component_root, slug)`), CHECK constraints on status (`pending|in_progress|done`) and `closed_by` (`all-done|cleared|person`), and an index on `(component_root, loop_slug)`.
2. `internal/store/todo.go`: `TodoList(root, loop) (TodoListRow, []TodoItemRow, error)` for the active list or the latest closed one; `TodoReplace(root, loop, step, expectRevision, items) (TodoListRow, error)` in ONE transaction: refuse a stale revision naming both numbers, open a new list when there is no active one, write the items in order, close the list when every item is done or the list is empty (`closed_by` accordingly); `TodoClose(root, loop, by) (TodoListRow, error)`. Item bounds are the tool's; the store refuses only structurally invalid rows.
3. Keep the file under 1000 lines. Table tests over a real store: replace, replace stale, all-done closes, empty set closes, reopen after close starts revision 1 of a new list, cascade on loop delete, close of a list that is already closed is a no-op that says so.

## Definition of done

- Migration applies on a fresh store and on one at the previous version (the repo's upgrade test passes).
- `go test -tags sqlite_fts5 ./internal/store` passes for the new tests; measured line counts in Notes.

## Do not

- Do not store anything the tool did not validate; the store is not a second validator.
- Do not add a protocol method or touch the tool here.
