# T5 · The nudge and the completion guard

**Rules:** TD9, TD10, TD11. **Depends on:** T2.

## Steps

1. A setting `todo.nudge_after` (integer, default 8, 0 = off) through the settings registry (see how `continuous.*` or `budget` settings are declared and read fresh per step); the daemon hands the runtime a `TodoPolicy` in `LoopDeps` with `ActiveOpen(ctx) (open []string, ok bool)` and `NudgeAfter()`. The runtime imports neither the store nor the tools package.
2. In `internal/runtime/loop.go`, beside the mailbox drain: count model calls since the last `todo` tool call or the step start; at the threshold with open items append one user turn with the fixed reminder sentence (one constant, shared with T4) via `AppendUserTurn`, reset the count, emit `todo.nudged`. A turn the nudge adds is a runtime turn, never the person's: check how the mailbox turn marks its provenance and do the same.
3. The completion guard, where a handoff is accepted as `ok`/`done` (find the path that builds `Handoff` and calls `complete`): if the policy reports open items and this step has been sent back fewer than two times, append the completion-worded reminder and loop again; the third time complete as the model asked and record `closed_with_open_todo: N` in the step record and in the `step.done` reason. `failed`/`blocked` and lanes of type `converse` are not guarded.
4. Each guard bounce counts toward the step's iteration budget (no free loops).
5. Tests with a scripted model: nudge fires once at the threshold and again one window later; no nudge when the list is closed, empty or the setting is 0; guard bounces twice then completes with the recorded fact; `converse` exempt; `failed` not guarded; the reminder turn is not recorded as the person's message.

## Definition of done

- The scripted tests above pass; `go test -tags sqlite_fts5 ./internal/runtime` passes.
- The reminder strings exist once, in one file, greppable.

## Do not

- Do not block a `failed` or `blocked` step.
- Do not nudge on a closed list.

## Notes

**Done 2026-11-07, with two deviations.** Nudge and guard are in `internal/runtime/loop.go` behind `LoopDeps.Todo` (`TodoPolicy`: `ActiveOpen`, `NudgeAfter`, `GuardApplies`), the daemon adapter `stepTodoPolicy` reads setting `todo.nudgeAfter` (declared in `config/settings_decl_todo.go`, default 8, 0 = off) fresh per call. Deviations: (1) the nudge is a STEP event `step.todo.nudged` (reasons `stale`, `completion`, `closed-with-open`) rather than a protocol kind `todo.nudged`, so it rides the step stream beside `step.compacted`; the `closed_with_open_todo` fact is that event, not a column on the step record. (2) Exemption: a step is guarded only when it has a lane that is not `converse` (a conversation turn has no lane; the chat blueprint's lane is `converse`); resumed and recovered steps carry no lane on hand and stay unguarded, the nudge still applies. Tests: `todo_guard_test.go` (nudge fires once per window and only with open items, a todo call restarts the window, setting off, guard bounces twice then completes with the fact, exempt and honest-stop cases). The CLI watch printer renders the new event. Pinned by name: `RunOpts` field list, the settings registry count (23 to 24).

**Addition 2026-11-07, revised the same day.** The step's model-call bound was a compiled constant (12) and a conversation blocked within seconds. A loop is meant to run until it is done, so the bound is now OPTIONAL and unlimited by default, set in three layers, most specific first: the AGENT's own bound (its metadata blob, key `maxIterations`) wins; then the blueprint STEP's `max_iterations`; then the daemon setting `step.maxIterations` (`config/settings_decl_steps.go`, default 0). In every layer absent means "not set here" and 0 means "no bound"; a caller that names a bound itself (`aeon step --max-iterations`) outranks all three. `daemon/step_limits.go` resolves them in `StepRunner.Compile`; the runtime reads a manifest bound of 0 as "no bound" and keeps its compiled 12 only for a daemon with no settings store. The wall-clock deadline (30 minutes per step) is a separate bound and still applies. `blueprint.Step.MaxIterations` is validated (model steps only, not negative). The same fix replaced a `config.Reader` interface holding a nil `*config.Store` (a non-nil interface that panics) with the concrete pointer, in both the bound and the nudge policy. Not built: a field for the agent's bound in the agents page form (it is edited as JSON in the metadata field today) and in the blueprint editor.
