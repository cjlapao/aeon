# T7 · Gate scope, failure blast radius, cap draining

**Prefix:** PA · **Rules:** PA6, PA7, PA15 · **Depends on:** T5.

## Goal

Three claims that need proving under real concurrency, not just by code inspection — each is "the existing
mechanism already does the right thing once contexts/positions are genuinely independent," and each gets
its own test to make that a measured fact rather than an assumption.

## Files to modify

Mostly test files — the brief's own framing is that PA6/PA7 need **no new engine code**, only proof that
T4/T5's widening didn't accidentally couple siblings together. PA15 is the one with a real (small) change.

- `internal/loop/advance_parallel_test.go` (from T5) — extend with PA6/PA7's tests below.
- Wherever the fan-out reads `component.max_parallel_agents` (T5's `AdvanceLoopParallel`) — confirm (or
  fix, if T5 cached it) that the read happens **fresh on every new-unit-launch decision**, never once per
  loop run. `VERIFY` T5's actual implementation before assuming this needs a code change here — if T5
  already reads it fresh each time, this task is tests only.

## Tests

| Test | Asserts | Fails when |
| --- | --- | --- |
| `TestGateInOneUnitSuspendsOnlyThatUnit` | a blueprint with one parallel unit hitting a gate and a sibling with no gate: the gated unit's position goes `waiting`, the sibling's keeps running and later completes normally | PA6 — suspension leaked across units |
| `TestLoopReachesWaitingOnlyWhenAllActiveArePaused` | with two units, one waiting and one still running, the loop's own status is **not** yet `waiting` — only once the second also pauses/completes does the loop-level status reflect it | the loop-level status was derived from the first unit alone |
| `TestFailedTaskNeverCancelsIndependentSibling` | re-run under the real fan-out (not a mock): a task with no `depends_on` edge to a failing task keeps running, uninterrupted, to its own completion | PA7 — a shared cancellation path exists somewhere T5 didn't catch |
| `TestFailedTaskBlocksOnlyItsTransitiveDependents` (re-run of `escalate.go`'s existing test, under concurrency) | the existing dependents-blocked assertion still holds when the failure happens while unrelated siblings are mid-flight | concurrency changed `escalate.go`'s own behavior somehow |
| `TestCapReadFreshPerLaunch` | lowering `max_parallel_agents` mid-run (while N > the new cap are active) launches zero new units until enough finish to be back under the new cap, and never kills anything already running | the cap was cached at run start instead of read per launch decision |
| `TestRaisingCapMidRunAlsoTakesEffect` (the symmetric case, not explicitly in the brief but worth confirming since "read fresh" cuts both ways) | raising the cap mid-run allows a new unit to launch sooner than it would have under the old cap | the fresh-read only works in one direction |

## Definition of done

- [ ] PA6/PA7's claims each have a dedicated, passing test under real concurrency (not mocked contexts).
- [ ] The cap is confirmed read fresh per launch decision, both directions (lower and raise).
- [ ] `escalate.go`'s pre-existing failure test still passes unmodified under concurrency.

## Do NOT

- Do not write a new suspension or cancellation mechanism — if one of these tests fails, the fix belongs
  in T5 (the fan-out itself), not a new mechanism layered on top.
- Do not cache `max_parallel_agents` anywhere in the loop's in-memory state across its run.
