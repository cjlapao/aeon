# T2 · Blueprint schema and the validator pass

**Prefix:** PA · **Rules:** PA4, PA11 · **Depends on:** nothing — parallel-safe with T1/T3.

## Goal

`blueprint.Lane` gains the two opt-in fields (PA4's two shapes); the validator gains the author-time
`produces`-disjointness check for Shape A (sibling lanes sharing a `parallel_group`). Nothing here touches
the runtime — this is schema and static validation only.

## Files to modify

- `internal/blueprint/types.go` — on `Lane` (confirmed this session at `types.go:51-59`):
  ```go
  type Lane struct {
      // ... existing fields unchanged ...
      Parallel      bool   `yaml:"parallel,omitempty" json:"parallel,omitempty"`
      ParallelGroup string `yaml:"parallel_group,omitempty" json:"parallelGroup,omitempty"`
  }
  ```
  `Parallel` is only meaningful on a lane that also sets `Iterate` — `VERIFY` whether the existing
  validator already has a place to refuse `Parallel: true` on a non-iterating lane (it should: a static
  lane either carries a `ParallelGroup` to join a sibling set, or neither field, never `Parallel` alone).
- `internal/blueprint/validate.go` — a new pass, called from `Validate` (confirmed this session at
  `validate.go:84`): group lanes by non-empty `ParallelGroup`; for each group with ≥ 2 members, union each
  member's `Step.Produces` (direct steps) — an iterating lane's `ParallelGroup` membership is **refused as
  a diagnostic**, not silently ignored (Shape A and Shape B are mutually exclusive per lane, PA4); raise
  `invalid` naming both lane ids and the overlapping path(s) on any intersection. A `ParallelGroup` with
  exactly one member is **also** a diagnostic (a group of one is either a typo or dead configuration,
  worth catching at author time rather than silently behaving like no group at all).
- `internal/blueprint/blueprints/` — no change to shipped blueprints in this task (none currently use
  either field); fixtures live under `testdata/` instead (next bullet).
- `internal/blueprint/testdata/` — two new fixture blueprints: one with two lanes correctly sharing a
  `parallel_group` with disjoint `produces` (validates clean), one with overlapping `produces` in the same
  group (must raise `invalid`), one with `Parallel: true` on a non-iterating lane (must raise `invalid`),
  one with a one-member `parallel_group` (must raise `invalid`).
- `internal/blueprint/validate_test.go` — the tests below.

## Definition of done

- [ ] `Lane.Parallel`/`Lane.ParallelGroup` exist, documented, mutually exclusive with each other's shape.
- [ ] The disjointness check raises `invalid` (not `unverifiable`) with both lane ids and the path named.
- [ ] A one-member group and `Parallel` on a non-iterating lane are both refused.
- [ ] Every shipped blueprint still validates clean.

## Do NOT

- Do not raise `unverifiable` for the disjointness check — it needs no model call, it is a pure data
  comparison, and `invalid` is the correct severity per this project's three-state diagnostic vocabulary.
- Do not let a lane set both `Parallel` and `ParallelGroup` — refuse that combination too, naming it.
